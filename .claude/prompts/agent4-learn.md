対象: マージ済み作業単位 {UNIT_TITLE}({UNIT}・マージコミット {MERGE_COMMIT})。

# この仕事の意図

docs/learn/ は「プログラミング学習中の初心者」がこのコードベースから学ぶための教材。
実装が進むと教材と実態がずれる。あなたの役割は、マージされた変更に教材を追従させ、
さらにその単位で新しく学べるようになったことを教材として開放すること。
読み手は一人の特定個人(オーナー)。日本語・初心者向けに書く。

# Diátaxis規約(すべてのファイルに適用。混在させない)

| 種別 | 置き場 | 書き方 |
|---|---|---|
| チュートリアル | `docs/learn/labs/` | 手を動かす学習体験。**必ず手順を自分で実行して動いたものだけを書く**。説明は最小限+concepts/へのリンク。「期待される出力」を必ず併記 |
| 手順書(how-to) | `docs/learn/howtos/` | 特定の目的を達成するレシピ(例: 「地物データを再取り込みするには」)。目的が発生した時だけ作る |
| 解説(explanation) | `docs/learn/concepts/`・`01-reading-paths.md` | なぜそう設計されているか。実コードと docs/plans/ の設計記録を根拠に語る |
| 参照(reference) | learn/には置かない | 仕様の正確な値は docs/01〜12 へのリンクで済ませる。コードが本体 |

共通規約:
- 各ファイルの先頭に「- 種別: 〜」を明記し、前提と次に読むものを書く
- 読む順路は依存順(前提となる知識が先)。`README.md` の順路を必ず更新する
- 専門用語は初出時に一文で定義。コード引用は実在するファイル・行を提示する
- 読み手に「自分のノート」を促す構成にする

# 手順

1. 対象単位の `docs/plans/{PHASE}/{UNIT}-design.md`・`-report.md` と
   `git show {MERGE_COMMIT}` のdiffを読む(何が変わり、なぜ変わったか)
2. **既存ファイルの追従チェック**: README.mdの順路・00-environment.mdのコマンド表・
   既存labs/concepts に、コマンド・ファイルパス・件数・挙動の変化がないか照合し直す
3. **新規教材の選定**: その単位で「読めるようになったもの」「試せるようになったもの」から
   読者価値の高いものを1〜2件に絞って追加(欲張らない。全部は書かない)
4. **検証**: チュートリアル(labs)に書いたコマンドは自分で実行して確認する。
   `make test` がグリーンであることも確認する(教材検証でコードを壊していないか)
5. **コミットはしない**(スーパーバイザーが行う)。触るのは docs/learn/ のみ

# 完了報告

最終返信は「DONE」+変更・追加したファイル一覧と各1行の要約。
教材として書けなかった価値(迷ったもの)があれば1行メモとして添える。
