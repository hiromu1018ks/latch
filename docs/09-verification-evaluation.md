## 1. 目的と位置づけ

MVPは5仮説(01第4節)の検証装置である。本書はその計測の設計図として、(1)成功指標の測定定義の集約、(2)5仮説の検証マッピング(第2.3節)、(3)Offline/Online評価、(4)A/B Test計画、を確定する。測定の土台は04のObservability 3群(パイプライン / Jev / 提案と行動)であり、マッチングの質・コストの指標はこのメトリクスから導出可能な形で定義する。使われ方群のDAU・再来訪はセッション開始イベントによる計測とし、この計測範囲の追加は04 v0.2で実施済みである(POST /v1/sessions、05 v0.3)。

## 2. 測定設計

### 2.1 North Star — Mutual Latch Rate

01第23節の確定定義を再掲し、集計実装の規定を加える。

```text
Mutual Latch Rate = 分子 ÷ 分母
分母 = 当該期間に通知を送信したLATCH候補数(1候補1カウント、
       グループ候補も1候補、クローズ済みを除かない)
分子 = そのうち必要人数全員がYESした候補数
```

集計はproposed遷移を分母カウント、matched遷移を分子カウントとし、latch_status_events(05 v0.3。遷移を書くトランザクションと同時に挿入される)から日次で集計する。期間は日次・週次の2種を常設する。

修正の趣旨(FR-29): 無回答を分母に残す計算は、無回答を「実行しなかった/キャンセルした」と同等に扱うことになり、D-09の「無回答は欠測として扱い、補完しない」の決定と矛盾した。よって実行率・キャンセル率の分母を回答済みに限定し、無回答の規模そのものは無回答率として並列に計測する(欠測の増大はデータ資産の劣化として監視する)。実行率とキャンセル率の分子は重ならない(actual_attended=trueとcancelled_after=trueは排他)。

保留→expired率(FR-47)の意義: D-08の保留は「破棄せず順次提示する」が設計意図であり、保留の多くがexpiredで閉じているなら仮説4の検証装置(通知頻度の抑制)が実質の破棄に置き換わっている。提示順の公平性の監視も兼ねる。通知オフ率(FR-26)はD-02の警報線(第6節)の測定定義である。

使われ方・マッチングの質・安全網は提案と行動の群、コストはJevの群(04第7節)から導出する。意図的な集計イベントを追加する場合も、個別Intentの文言を含めない(08第2.4節)。

### 2.3 5仮説の検証マッピング(FR-24、プロダクトオーナー決定)

01第4節の5仮説それぞれに、主指標と支持判定基準を事前に固定する(運用後の恣意的な基準選択を防ぐ)。判定基準の値も事前に固定し、その妥当性の再検討はベータ終了後の総括で行う。

| 仮説(01第4節) | 主指標 | 支持判定基準 | 補助 |
|---|---|---|---|
| 1. Intentだけ登録して待つ体験を便利と感じる | 体験アンケート(オンボーディング直後・4週後): 便利さの5段階設問+自由記述。行動面: Intent再作成率 | 4週後の5段階平均が4.0以上、かつPhase 2以降の週次Intent再作成率が40%以上 | 自由記述の定性分析(「待つ」体験の肯定言及の有無) |
| 2. 完全一致ではなくても、意味的に成立する提案を受け入れる | proposed時点の語彙一致/意味近接セグメント別YES率 | 意味近接セグメントのYES率が10%以上、かつ語彙一致セグメントのYES率の50%以上 | セグメント別の回答期限切れ率 |
| 3. 双方YESの予測を一定精度で実現できる | Offline評価(Precision・Mutual Acceptance Precision)+実測Mutual Latch Rate | Offline: 閾値0.80でのPrecisionが0.60以上(ゴールドセット)。実測: MLRがD-02のベースラインで前期比−5pt以内を維持 | Calibration Error・Brier Score |
| 4. 通知頻度を抑えれば反応率が高い | A/B(D-08の通知頻度上限): 通知あたり反応率(制限群 vs 拡大群) | 制限群(日6件・同時3件)の反応率が拡大群に対して有意に高い(第5節の共通規定の判定) | 通報率・通知オフ率の停止ルール |
| 5. 「検索しない・募集しない」行動様式が継続利用につながる | 30日継続率+4週後アンケートの継続意向設問 | 30日継続率が30%以上、かつ継続意向(5段階)が4点以上の回答者が過半 | 7日継続率・Intent再作成率 |

アンケートの実施方法: 定量設問(5段階)はオンボーディング直後(初回Intent保存後)と4週後の2回、アプリ内で配信する(1回あたり3設問以内)。定性設問(自由記述)は4週後の1問とし、任意回答とする。回答は押しつけにならない単発の配信にとどめ、アンケート自体が体験を壊さないようにする。回答データは個別Intentの文言と紐付けない(08第2.4節)。

仮説2のセグメントフラグの定義: Layer 5の提案化時にペア単位で判定し、calibration_records.predictionへ`segment`キー("lexical" / "semantic")として記録する(predictionキー一覧への追加は05の次回改版へ反映する旨を第7節に記録)。判定規則は次のとおり — **両Intentのcategory_secondary(一方がnullの場合は当該Intentのsoft_constraintsの文言)の間で表層のトークン一致があれば`lexical`(語彙一致)、なければ`semantic`(意味近接)**とする(方向性を持たない対称判定)。なお、両セグメントともLayer 2のANN検索で候補化される点は同一であり、本フラグは候補化の経路ではなく、提案ペアの表現の間に語彙レベルで見える一致があるかを分類するものである。グループ提案では集約スコアのminとなるペアのフラグを適用する。判定基準の根拠: 10%は無視できない反応率の下限であり、語彙一致の50%は「語彙が一致しなくても受け入れが半分程度に保たれる」ことを示す線である(値は事前固定)。

仮説1・5の判定基準の根拠: 5段階4.0は「便利と感じる」の上端寄りであり、中間帯の拾いが機能していることの最低ライン。再作成率40%・30日継続率30%は、招待制クローズドベータで体験が継続使用に転化していることの目安線であり、いずれも値は事前固定で運用後の選別を防ぐ。仮説3のPrecision 0.60は、提案10件中6件が成立し得るペアであることを要求する水準で、Calibration改善(第4.4節)前の合格線として固定する。

## 4. Offline評価

**評価対象と日本語評価の必須(v0.5)。** Jev精度の評価は、第一候補のTypeSafe Jev(System Oneモデル)の応答に対して行う — would_a_accept_b・would_b_accept_aのnoul確率と、5軸scoreを0〜1へ正規化した値・confidenceが評価対象である(07 v0.5第4節)。ECE・Brier Score(第4.2節)は較正済み確率を直接評価する指標であり、System Oneモデルの前提と整合する。フォールバックLLM(Anthropic Claude API・Sonnet 5)も同一のゴールドセットで評価し、両経路の指標はjev_resultのproviderキー(05 v0.5)で分離して記録・比較する。**日本語評価はG2(M2終了)の必須条件とする** — TypeSafe Jevの言語サポートには「英語が主訓練言語・CJK(日本語を含む)は同等ではない(handled but not equally well)」との公式留保があり、非英語のワークロードでは自分のコンテンツで試すよう公式に指示されている。LATCHのstateと質問群は日本語であるため、ゴールドセット(日本語・評価ペア500件以上、第4.1節)による実測が唯一の採用判断材料である。合格基準の値(Precision・ECE等の水準)はG2の実施前にオーナーが確定し(第2.3節と同じ事前固定の原則)、合格しない場合はフォールバックLLMを第一候補へ繰り上げる判断をオーナーに持ち帰る(07 v0.5第4節・12 v0.2のG2条件)。

### 4.1 ゴールドセットの作成方針

規模はシードIntent 200〜300件、評価ペア500件以上(成立し得る/し得ないのバランスを概ね2:3)とする。シードは02 D-22の前提(単一エリア・飲食中心)を反映し、場所・時間帯・人数・予算・soft条件の組み合わせテンプレートから典型表現のバリエーションを作る。ペアの正解ラベルは2名が独立して「成立し得るか」を判定し、不一致は3人目の裁定による。ゴールドセットの文言はテスト資産として10と共有する(生産データではないため、ログ制限の対象外)。運用開始後は、同意を得た形で匿名化した実データの一部を追加していく。

### 4.2 指標の算出方法(01第24節)

- **Precision** = 提案(閾値超過)したペアのうち、ゴールドラベルが成立し得るペアの割合
- **Recall** = ゴールドで成立し得るペアのうち、提案したペアの割合
- **Calibration Error** = 予測MutualScoreを10分割のビンに分け、各ビンの平均予測値と実YES率の差の加重平均(ECE)
- **Brier Score** = (予測MutualScore − 実際のYES)² の平均。実YESはゴールドラベルまたは運用後は実際の回答
- **Mutual Acceptance Precision** = min方向の予測(MutualScore)が双方YESを正しく上位に置けた率。ランク指標として、実際に双方YESとなったペアのスコア分布とそうでない分布の分離度で測る

### 4.3 構造化精度の検証手順(07 D-17との接続)

02第4節#1・#2の入力セット(30件以上)と期待値表を本書が整備し、10と共有資産とする。手順は「入力セットをParserへ流す → 出力と期待値をフィールド単位で照合 → 完全一致率を集計 → 07 D-17の基準(category 85% / time.start 90% / location 90% / participants 80% / budget 90%)と判定」。期待値は丸め規則(07第2節)適用後の値で比較する。この検証はリリース前のゲートとし、Parserやプロンプトを変更するたびに再実行する。

**alcohol_involvedの精度ゲート(FR-20)。** ゲートにalcohol_involvedを追加する。期待値表に飲酒判定専用の入力セット(30件以上)を含め、alcohol_involved=trueの正例に加え、「ワイン会」「日本酒好きの集まり」「バーでの誕生日会」のような飲酒を明示しない境界表現、および「コーヒーを飲む」等のアルコールを指さない用法の負例を含める(10と共有資産)。合格基準は次のとおりとする。

- **alcohol_involved recall 100%(見逃し0件)** — 見逃しは飲酒Intentの作成時検証(422)とLayer 1年齢条件の双方を素通りさせ、未成年への飲酒機会提供(08 D-10の法的リスク)に直結するため、最も強い基準を置く
- **alcohol_involved precision下限90%** — 過剰検出は飲酒不要のIntentの作成抑制(体験損失)にとどまり、検出漏れより損失が小さいため、recall側より緩い

基準の再実行タイミングは既存の構造化精度ゲート(Parser変更時の毎回)と同一である。動作面(18〜19歳テストユーザーによる作成拒否)は10の追加試験が担う。

### 4.4 C係数の再計算手順(FR-49)

Calibrationデータの蓄積に基づくC係数の調整は次の手順で行う。

1. **判定周期**: 四半期ごと(または警報運用でCalibration Errorの悪化を検知した場合)に、calibration_recordsの蓄積(匿名化後を含む)に対しECE・Brierを計算し、Jev予測の系統的な過大/過小を確認する
2. **Cの再計算**: 提案時点の予測(MutualScore)と実際のYES/NOの比(実測YES率 ÷ 平均予測値、直近四半期分)から導く。丸めは小数点2位とし、値域(0, 1]にクランプする
3. **変更のゲート**: Cの変更はOffline評価(第4節)の通過を必須とし、本番適用はA/B対象とする(閾値A/Bと同時実施はしない。交互作用が大きいため)
4. **Cで補正できない方向の明示**: Cの値域は(0, 1]であるため、Jevが系統的に過小(低く出すぎ、実測YES率が予測を上回り続ける)の場合はCでは補正できない。この場合の打ち手は、通知閾値の引き下げ(A/B、D-01)またはJevプロンプトの改善(07の改版、構造化精度ゲートとOffline評価を経て適用)に限られる。打ち手の限界を事前に明示しておくことで、精度劣化時の対応が閾値とD-08上限に偏らない

## 5. Online評価(A/B Test計画)

対象は01第24節の7項目(通知閾値、Candidate数、Jev判定軸、表示情報量、通知文、回答期限、グループ人数)に、03 D-08が調整を約束した通知頻度上限(日次上限・同時進行上限)を加えた8項目とする(01第24節への追加を要する)。**表示情報量には公開設定2値(hidden_until_match / summary_only)による提案画面の情報量の差を含める(v0.4、02 v0.3 D-03)** — hidden_until_match(初期値)の提案は条件サマリを表示しないため、summary_onlyを処置群とする表示情報量のA/Bとして実施できる。通知頻度は仮説4の直接の検証装置であり、通知閾値との交互作用が大きいため、D-01の閾値試験とは同時に実施しない。計画の共通規定を次に示す。

- **設計**: 1テスト1変数・2群(対照/処置)。割付はユーザーIDのハッシュで層化(Active Intent数の層)。最小期間2週間(短寿命Intentの周期を2回以上カバー)
- **ペア適用規則(FR-25、プロダクトオーナー決定: ユーザー単位割付を維持)**: 処置(閾値・頻度等)はペア・集合単位で効果を持つため、ペアへの適用値は次のとおり決める — 参加ユーザーの群が同一ならその群の値を、混在するなら**対照群の値**を適用する。時間交互切替(time-switch)にはしない。対照値を混在ペアへ適用するのは、処置群ユーザーの検出機会が対照群の品質基準に制限される方向のみに偏らせ、測定差の過大評価(処置効果の水増し)を防ぐためである(保守側に倒す)
- **最小検出効果の概算**: 提案数1,000件/群・MLR 10%前提で、4週間の2群比較で有意に検出できる最小差は約3ポイント(相対約30%)である(標準誤差の概算値)。実勢の提案数がこれに届かない期間(コールド期・Phase 1)は検出力不足が既知であり、判定不能を前提とした持続規定をD-01に置く
- **判定不能時の持続規定**: 期間終了時点で判定不能(検出力不足)の場合は、処置変更を行わず**対照値(閾値0.80等)を全群に適用して**運用を続け、提案数が確保できた後の追加A/Bで再判定する(既存基準の継続がデフォルト)
- **判定**: プライマリ指標はMutual Latch Rate。セカンダリはYES率・キャンセル率・通知あたり反応率。サンプルサイズは事前計算せず、期間固定の連続監視とし、途中の判断は有害シグナル(通報率・通知オフ率の急増)の停止ルールに限る
- **倫理的配慮**: 表示情報量のテストはD-11・D-20・02 v0.3 D-03の最小化の枠を下回る変更をしない(v0.4: 公開設定2値のいずれも、raw_text・NG条件・表示名・プロフィールを成立まで表示しない最小化の枠の内側であり、summary_onlyは条件サマリのみ、hidden_until_matchはそれより厳しい。すなわち2値の比較は最小化の枠内でのA/Bである)。回答期限は03 D-05の下限(通知+15分)を割らない。Jev判定軸の変更はOffline評価(第4節)を通過させてから本番に載せる。グループ人数はMVP上限4を超えない

## 6. 未決事項の決定

### D-01 通知閾値0.80の妥当性検証手順

- 決定内容: 次の2段階の手順で確定する
  - **事前(Offline)**: ゴールドセットで0.70 / 0.80 / 0.90の3閾値によるPrecision・Recallを計算し、A/B前の見当をつける
  - **本番(A/B)**: 対照群0.80、処置群0.70の2群とし、4週間実施する。判定基準は、処置群のMutual Latch Rateが対照群から有意に低下しなければ(提示数増加と引き替えに品質低下がないなら)低い閾値での提示拡大を許容し、低下するなら0.80を維持する。0.90側はOffline結果がRecallを大きく損なうと示した場合のみ検討する。**判定不能(検出力不足)の場合は0.80を維持する**(持続規定、第5節)。ペアへの閾値適用は第5節のペア適用規則(混在ペアは対照値0.80)に従う
- 根拠: 閾値を下げれば提示数は増え、分母が増える分Mutual Latch Rateは構造的に下がる方向へ働く。したがって判定は「低下が統計的に無視できるほど小さいか」でなく「提示機会の増加と品質の低下の交換が許容できるか」であり、同等性の実務判定として2群比較+事前のOffline見当で固定する。持続規定を置くのは、検出力不足のままベータが終わった場合に「未決のまま放置」を避け、既存基準の継続をデフォルトにするためである。群間干渉(SUTVA違反)はペア適用規則で対照値側に倒して封じる
- 01への影響: 第24節のA/B対象に本手順を明記。値の確定は試験完了後、01第10節の初期値を更新

### D-02 Mutual Latch Rate合格ラインの決定手順

- 決定内容: 相対基準で運用する。初期のIntent密度構築期間(11第1節のPhase 1)を除いた、密度構築完了後4週間(11 Phase 2)のMutual Latch Rate週次値の中央値をベースラインとして記録し、以降は「前期比マイナス5ポイント以内」を維持条件(合格ライン)とする。あわせて絶対的な警報線として、YES率10%未満または通知オフ率の急増(週比2倍。測定定義は第2.2節)を検知した場合は閾値・D-08上限の見直しを起動する。v0.3追記(FR-26)は次の2点である
  - **ベースライン計測期間中の本番変更凍結**: Phase 2の4週間中は、提案生成の構造に影響する本番変更(Parserプロンプト・Jev温度・K上限・閾値・Index追加・06のK_j配分変更等)を凍結する。緊急修正(Safety・可用性の復旧、D-23等)は可とし、変更内容と日時を記録したうえで、計測の起算を変更完了時点から繰り直す(継続4週間を保証)
  - **A/B採用後の再ベースライン**: 採用したパラメータ(閾値・通知頻度等)への本番切替後、警報運用(前期比−5pt)に復帰する前に、採用パラメータで4週間を再計測し、週次中央値を新ベースラインへ置き換える。軽微な変更(通知文言等)では、変更時点のシフト量を記録して補正するか、再ベースラインを選ぶ。意図的変更による構造シフト(閾値を下げればMLRは機構的に下がる)を前期比に混入させないためである
- 根拠: 01が自ら記すとおり、比較基準を持たない事前の目標値は機能しない。外部サービスとの直接比較も定義が異なり不能である。よって「初期データで線を引き、相対で守る」手順のみが意味を持ち、5ptはCalibration改善(C係数の調整、第4.4節)の通常の変動幅より広く、構造劣化を検知できる幅度として設定した。測定を密度構築完了後の期間に限定するのは、Intentプールが薄い期間はMutual Latch Rateがほぼゼロに貼り付き、ベースラインを不当に低くするためである(01 D-22のコールドスタート)。変更凍結を置くのは、計測途中で提案生成の構造が変わると前期比の比較対象が無効化されるためであり、再ベースラインの手順を置くのは、A/B後の常時誤警報・見逃しを防ぐためである
- 01への影響: 第23節に合格ラインの決定手順を追記

### D-09 「実際に参加したか」の収集方法

- 決定内容: 成立LATCHがcompletedに遷移する時点(対象時刻の経過、05第6節)で、プッシュ+アプリ内通知(お知らせ。UI語彙は03 v0.4第10節)により1問の自己申告を求める。設問は「実際に会いましたか?」(はい/いいえ)、回答期限3日、スキップ可能とする。回答は はい→actual_attended=true、いいえ→cancelled_after=true の対応でcalibration_records(07第6節)へ反映する。無回答は欠測として扱い、補完しない(実行率・キャンセル率の分母から除外し、無回答率として並列計測する。第2.2節)。通知はcancelled LATCHには送らない(08 v0.3第2.5節、FR-19)
- 根拠: 位置情報による確認はD-11とプライバシー原則(01第21節)と衝突し、チャットでの確認は網羅性がない。completed遷移は全成立LATCHで確実に走るイベントであり、この確定タイミングでの1タップ自己申告が、CalibrationのGround Truth(原則6)を最小の摩擦で集める方法である。参加の対価を設けないのは、インセンティブによる回答歪みを避けるためだ
- 01への影響: 第14節に収集方法を追記。実行率・キャンセル率・無回答率(第2.2節)の供給源となる
