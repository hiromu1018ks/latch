## 1. 目的と位置づけ

プライバシーは個別機能の前に置く前提である(01第21節)。本書が守るべき性質は3つに集約できる。(1)成立前のIntentは相手に見えない、(2)送信・表示・記録・OS通知(プッシュ本文・通知履歴・ウィジェット・読み上げ)のそれぞれで、扱う情報を目的の最小限へ絞る、(3)ユーザーが削除を求めたとき、預けた意思はシステムから消える。安全要件は02 D-12で確定したとおり、ブロック・通報・アクセス制御・レート制限の4系統に限る。

## 2. プライバシー原則の実装

### 2.1 Intentの非公開性

Intentは原則非公開とし、マッチング処理のみで利用する。実装はAPIレベルの強制である(05: Intentの参照・更新・削除は所有者のみ、認可はサーバ側判定)。ユーザーに見せるLATCHはproposed以降のみで、candidateの閲覧経路を持たない(03第2節)。

### 2.2 成立前後の情報開示

成立前の提案画面に表示するのは、visibility=summary_only(候補にだけ概要を表示)の場合は条件サマリ(人数・時間帯・地域名・カテゴリ・ペア予算)のみで、相手の表示名・プロフィール・Intent全文は出さない。visibility=hidden_until_match(条件一致までは非公開)の場合は、条件サマリも表示せず、提案先が受け取るのは「条件が合う候補があります」の通知と一致度・回答期限(+グループなら必要人数)のみとする(02 v0.3 D-03再決定・05 v0.4のproposal生成分岐)。プロトタイプのプライバシーノート「相手の名前やプロフィールは、全員が承認するまで表示しません。」は、どちらの値でも共通の前提としてUIに固定した文言である(03 v0.4第10節)。必要人数のYES(承認)が揃った時点で、条件サマリ(未解放の場合)・表示名・最小限のプロフィール・チャット・集合情報を解放する(03第6節)。不成立時に相手へ開示するのは「この提案は成立しませんでした」の一文のみで、回答種別も理由も開示しない(03 D-20)。nearby_also(お知らせ設定、03 v0.4第3節)による閾値未満候補の存在通知には、条件サマリ・相手情報を一切含めない。

### 2.3 表示の最小化

内部の判定条件と、相手への表示を分離する。proposal(05のlatches.proposal)には表示用のサマリのみを格納し、soft constraints・NG条件の文言は含めない。生成は06 Layer 5が行う(フィールド一覧と生成元は05 v0.3のproposal構造)。

```text
内部: 会社関係者以外で、天文館で、20時以降、3人程度なら飲みたい。
表示: 今夜20:00以降 / 天文館 / 3人前後 / 軽い食事・飲み
```

### 2.4 ログ・計測・Analyticsからの排除

ログ・計測・Analyticsの出力に、Intent原文(raw_text)、正確な位置(座標)、NG条件を含めない(01第21節)。実装は次の3規定とする。

- **構造化ログは許可リスト方式。** 出力できるフィールドを列挙型で固定し(raw: intent_id / status / version / error_code等)、許可リスト外のフィールドは Serializer の段階で落とす。raw_text・geo座標・constraints系フィールドは不許可
- **Analyticsは集計値のみ。** 計測するのはCandidate数・Jev実行回数・スコア分布・YES率等(01第20節の3群)で、個別Intentの文言に紐づくイベントは送らない
- **例外・エラーはIDのみ。** 例外スタックとエラーメッセージにIntent本文を混入させない。Parser・Jevの失敗ログはintent_idとエラーコードで表現する

### 2.5 削除・退会時の削除範囲と保持期間

ユーザーによるIntent削除・退会時には、次を削除する(01第21節)。

- 該当Intent行(raw_text・structured_data・embeddingを含む。pgvectorの値は同カラムなので同時に消える)
- 当該Intentを含むすべてのmatch_candidates・group_candidates(**処理済みを含む**、FR-22)。処理済み候補のjev_resultには、LLMが双方のsoft/NG条件を言い換えた自由文(reason、07 v0.3第4節)が格納されており、raw_textに準ずる機微性を持つ。削除ユーザーのIntent行が消えても相手側レコードに条件由来の自由文が残る状態は、01第21節(「センシティブな条件は内部判定にのみ使用する」)の趣旨に反する。evaluated・skipped・closedを問わず削除する。既に生成されたlatches・calibration_recordsの扱いは後述のとおり分離する
- 当該Intentを含む回答待ちのlatches(cancelledで閉じる)
- **matched済みLATCHの参加Intentが削除された場合も、当該LATCHをcancelledで閉じる(FR-19)。** 残った参加者は来ない相手との「成立済み」チャットを保持し続け、当日のドタキャン事故になり、D-09の自己申告が実態と乖離するためである。遷移と表示は次のとおりとする — LATCHはcancelledへ遷移、チャットは読み取り専用化(新規送信不可。閲覧は可能、D-23と同じ線)、残った参加者への表示は「この提案は成立しませんでした」の一文のみ(03 D-20の二値化と同一。削除したのが誰か、理由は開示しない)。実施自己申告(D-09)の通知はcancelled LATCHには送らない。退会(全Intent処理)と単発のIntent削除でこの扱いは一致する。**解散時に残る参加Intentは、expires_at経過済みならexpired、経過前ならactiveへ復帰し再提案可能とする** — 参加Intentが「成立済み」のまま凍結し、以後の提案対象から外れ続ける状態を防ぐためである(05第6節の遷移表・06 v0.3第6節と同一の規定。復帰Intentは次の時間Bucket再評価で再評価される)。05第6節の遷移表・06第9節の削除Event処理・09 D-09への反映事項は第6節に記録した
- 当該ユーザーのmessages・notifications
- calibration_records該当行の匿名化(ID系の除去と粒度低下。処理方式はD-13)
- 退会時は上記全てに加え、関与したlatches内の表示名を「退会したユーザー」へ置換する(相手側の履歴は残すが、個人との紐付きを切る)

**match_candidates・group_candidatesの保持期間(FR-22)。** 削除要求がない場合も、両テーブルのレコードは**評価確定から30日で定期削除する**。jev_resultのreasonは30日を超えて存続しない(07 v0.3第4節と同一の期限)。根拠は次のとおりである — 再提案制御(D-07)の抑制期間は最大24時間、no回答による拒否判定に参照するのはlatches.responsesであり、候補レコード自体の長期保持に実用上の根拠がない。Intentの寿命は数日(03 D-19)であり、09の品質調査に必要な値は回答確定時にcalibration_recordsへ移っている。保持期間を設けない場合、削除されたユーザーの条件由来の自由文が相手側レコードに恒久残存する経路となる

latches・responses・messagesはユーザーの履歴として維持する(削除範囲は上記のとおり。退会時の表示名置換・ID除去は適用する)。Calibration用データの扱い(匿名化保持)はD-13で確定する。

### 2.6 OS通知経路の表示規制(FR-21、プロダクトオーナー決定)

プッシュ通知は、ロック画面・通知履歴・ウィジェット・読み上げ等のOS経路を通じて、端末の持ち主以外(家族・同僚・端末を一時借りた第三者)にも表示され得る。LATCHは成立前の意思を扱う(01第21節)ため、表示制御の対象にOS通知経路を明示的に含める。08の既存の表示制御(2.2〜2.3節)は「相手へ」の露出を対象としており、本節が第三者露出を閉じる。

- **プッシュ通知の本文は汎用文「LATCH候補があります。詳細はアプリでご確認ください」のみとし、条件サマリ(人数・時間帯・地域名・カテゴリ・予算)を含めない。** 飲酒カテゴリ(drinking)の提案も様式は同一とする(カテゴリの推察自体を防ぐ)
- 条件サマリの表示は、summary_onlyの提案に限り、アプリ内通知(お知らせ。topbarのベルpopover+未読ドット)+提案画面で行う(03 v0.4第4節と同一の規定。hidden_until_matchの提案では条件サマリを表示しない、02 v0.3 D-03・05 v0.4)
- この規制はプッシュ許可の有無と独立に適用する。プッシュ許可したユーザーほど露出する構造的なねじれ(許可拒否ユーザーは自動的に安全)を解消する
- D-11・D-20と同格に、成立前の情報最小化の一部として扱う。検証は10の追加試験(通知ドライラン記録のプッシュ本文が汎用文であること、および条件サマリがプッシュへ出力されないこと)を依頼する

## 3. LLM送信のプライバシー

外部LLMへの送信は07のとおり、構造化データからの正規化テキストに限り、raw_textが送信経路に入らない。LLM Gateway(04)は送信先・データ種別・時刻を記録する。この記録は内容を含まない(どのIntentの何種別をいつ送ったか)もので、ユーザーからの問い合わせ時に開示できる状態を保つ。送信の告知・同意・契約条件は第4節D-14で確定する。

## 4. 未決事項の決定

### D-10 年齢制限の内容と年齢の取得方法

- 決定内容: 年齢制限は必要と判断し、次のとおり設ける
  - **利用登録は18歳以上**とする(自己申告の生年月日をusers.birth_dateへ保持。05へ反映済み。登録は05 v0.3のPOST /v1/usersが行い、18歳未満は422 UNDER_AGE)
  - **飲酒を含むIntent(category_primary=drinking、または文言から飲酒が読める場合)は20歳未満のユーザーが作成できない**。作成時に年齢を検証する。飲酒判定の規則は「Parserが alcohol_involved フラグ(飲む・飲み・酒・呑む・バー・ビール・サワー等の飲酒を示す語の検出)を出力し、category=drinking は常に true、『食事のついでに軽く飲む』のようなmeal内の言及も true とする」もので、規則の実装は07(プロンプト規則7)へ反映済み(07 v0.2以降)。保存時にcategory_primary=drinkingならサーバ側でtrueを確定する(05 v0.3)。作成時検証とLayer 1条件はこのフラグを使う
  - **alcohol_involved=trueのIntentは、20歳以上のユーザー同士の間でしか候補にならない**(Layer 1のHard条件。06第2節へ反映済み)
  - 02の留保を受け、第25節Safetyへ「20歳未満のユーザーは飲酒を含むIntentを作成できない」を変更管理で追加する
- 根拠: 未成年の飲酒機会への関与は法的リスクであり、02 D-12で除外した他の安全機能(ミュート等)と性質が異なる。LATCHは現実の飲食へつなげるサービスであるため、飲酒Intentの年齢線は検証装置として必須である。生年月日は自己申告とし、IdPからは取得しない(IdPが生年月日の提供を標準化していないため)
- 01への影響: 第22節に年齢制限の内容、第12節・Layer 1(06第2節)にdrinkingの年齢条件、第17節にusers.birth_date(05反映済み)、第25節への追加項目

### D-11 相手へ表示する位置情報の丸め粒度

- 決定内容: 相手への位置表示は地域名(市区町村・駅・ランドマーク単位)のみとし、座標・距離の数値は一切表示しない。内部のgeo_centerから表示への変換は、中心点を約1kmのグリッドへ丸め、その代表点の地名(例: 鹿児島市天文館)を用いる。変換結果の地域名のみをproposalへ格納する
- 根拠: 「正確な位置情報を相手に公開しない」(01第22節・第25節)と、候補の条件確認に必要な「どこ周辺か」の情報の両立をとる。1kmグリッドは飲食の目的地文脈を保持しつつ、自宅・滞在位置の特定に使える精度を落とす線である
- 01への影響: 第21節・第22節に丸め粒度を追記。proposalの生成は06 Layer 5、スキーマは05。ジオコーディング(正転・逆転)の手段はセルフホストの地物データ(位置参照情報+OSM)による内部変換で、04 v0.2で確定済みである(位置情報の外部送信経路を持たない。01レビューF-18の依存棚卸しに対応)

### D-13 削除・退会時のCalibrationデータの扱い

- 決定内容: 匿名化して保持する。削除するのはuser_id・intent_id・latch_id・地域名より細かい位置・文言で、保持するのはスコア・回答種別(yes/no/defer)・成立・参加・キャンセル・時刻(07第6節の構造からID系を除いた統計値)。退会時の同意文に「匿名化した統計データとして保持する」ことを明示する。v0.3追記(FR-23)として、匿名化の実体を次のとおり強化する
  - **匿名化は月次バッチで実行し、退会時の即時個別変換は行わない。** 退会・削除時点でID系(user_id・latch_id・intent_ids)をNULL化する(第一段。calibration_recordsのCHECK「anonymized_at NOT NULLならID系NULL」(05)と矛盾しない。anonymized_atはバッチ実行時に立てる)。ベータ規模(単一エリア500人、11 D-22)の小母集団では「土曜20時・天文館で4人焼肉」のような特徴的なレコードが本人固有であり、即時の個別匿名化は高識別性の仮名データを恒久残存させる。バッチは集計単位の件数を前提に変換でき、D-02のベースライン計測(4週間)の母集団規模でも識別力を下げられる
  - **バッチ実行時の変換内容**: (1)時刻系(actual_responses内の回答時刻・created_at等)を日単位へ丸める、(2)proposal_snapshotの粒度を低下させる — 時間帯は昼/夕/夜のビン、地域名は市区町村単位、category_secondary・対象日時は除去し、人数はビン化(2〜3人・4人)する、(3)actual_responsesは回答種別と丸め済み日付のみ保持する
  - **同意文面との整合**: 強化後の実体(時刻は日単位、地域は市区町村、二次カテゴリなし、ID完全除去)は同意文面「匿名化した統計データとして保持する」と一致し、文面の変更は不要である。むしろ現行の「即時匿名化+高識別性保持」より文面との乖離が縮まる
- 根拠: 01第14節はこのデータをLATCHの独自データ資産と位置づける。削除すればCalibrationの蓄積が失われ、残存ユーザーの提案精度を劣化させる。ただしIDの完全除去と数値・分類値のみの保持は、母集団が大きい場合にのみ再識別の経路を閉じる根拠になる。クローズドベータのような小規模母集団では、時刻(秒精度)・対象日時・地域・人数・二次カテゴリの組合せが当事者の記憶や他の記録と突合されれば容易に特定できる。よって丸め・粒度低下・生成遅延の3点で識別力を下げ、個人情報保護法の匿名加工情報の要件(特定個人による復元不可能性)に近づける
- 01への影響: 第21節に匿名化保持の規定を追記

### D-14 告知・同意・契約条件(告知・同意・契約面)

- 決定内容: 次のとおり確定する
  - **告知・同意**: オンボーディングで「Intentの内容は、マッチング判定のために外部のAIサービスへ送信されること(送信先の名称を含む)、送信範囲は判定に必要な最小限であること、学習には利用されないこと」を明示し、同意を取得する。同意はマッチング機能の利用条件であり、設定画面から常に再確認できる。送信記録(第3節)は問い合わせ時に開示する
  - **契約条件**: プロバイダ契約に (1)入出力の学習利用禁止、(2)保持期間の最小化(Zero Data Retention相当)、(3)サブプロセッサの開示、(4)データ所在地の明示、(5)漏洩時の通知義務 を含める
  - **選定基準(契約面)**: 上記5条件を契約上確定できること。確定できないプロバイダは、技術基準(04 D-14)を満たしていても採用しない
- 根拠: 潜在意思の第三者提供に当たるため、同意は利用開始の前置きとして明示的に取る必要がある。契約条件は04 D-14技術基準の第1・第2基準(学習利用禁止・データ取り扱い)を法務面から裏付ける同じ線である
- 01への影響: 第21節に告知・同意・契約条件を追記

### D-23 LATCH成立後のブロック適用

- 決定内容: ブロックは成立後も即時に適用する。効果は3つである
  - 今後の候補生成から除外(Layer 1、06)
  - 進行中の提案(proposed / partial_accept)はcancelledで閉じる
  - 成立済み(matched)のLATCHは、チャットを読み取り専用化して新規送信を不可にする。completedへの遷移は通常どおり。解放済みの情報の回収は行わない
  - ブロックされた側の画面には「このチャットは利用できません」のみ表示し、ブロックされた事実を直接通知しない(03 D-20の二値化と同じ精神)
- 根拠: ブロックの目的は今後の接触機会の排除であり、マッチングとコミュニケーションの両経路を断つ必要がある。一度表示された情報の回収は技術的に不可能で、この限界は受け入れたうえで、次の接触を確実に防ぐことを優先する。messages書き込み可否の条件は05(messagesの409 CHAT_READONLY)へ反映済みである。matched済みLATCHの参加Intent削除時の扱い(本書第2.5節、FR-19)も本決定と同じ線でチャットを読み取り専用化する
- 01への影響: 第22節・第8節に成立後のブロック適用を追記

## 5. 安全要件の実装(02 D-12確定分)

### 5.1 ブロック

blocksテーブル(05)に単方向で記録し、Layer 1が (A,B)(B,A) の双方向を確認して候補から除外する(06第2節)。参照は毎回DBを見ずRedisキャッシュ(04)から行い、ブロック設定の反映はキャッシュ更新を経由する。成立後の適用はD-23のとおり。解除は05 v0.3のDELETE /v1/users/{id}/blockで行い、遡及効果は持たない(候補除外・読み取り専用化を取り消さない)。

### 5.2 通報

POST /v1/reports(05)で受け付け、運用者の手動対応に回す。フローは「受付・記録 → 運用者によるレビュー → 必要に応じた対処(警告・アカウント停止・ブロック支援)」で、MVPでは自動検知・自動停止を行わない(02 D-12)。通報理由は選択式(不適切な内容 / 不快な対応 / なりすまし疑い / その他)とし、通報自体は提案画面・チャット画面から常に可能である。

### 5.3 アクセス制御

すべてのAPIは認証済みユーザーのみ利用可能とする(04 D-21のJWT。認証不要はPOST /v1/auth/tokenとPOST /v1/auth/refreshのみ、05 v0.3)。Intentの参照・更新・削除・回答操作は所有者本人または提案の参加者のみに許可し(05)、公開設定による開示範囲の制御(proposal生成分岐。v0.4でLayer 1の公開範囲判定は廃止、02 v0.3 D-03再決定)とブロックの判定はクライアント入力によらずサーバ側で強制する(01第22節・06 v0.4 Layer 5)。セッションの失効(ブロック・退会の即時反映)はRedisの失効リストで行う(04。操作面は05 v0.3のPOST /v1/auth/logout)。

### 5.4 レート制限(上限値の確定)

02で実装を決定した「ユーザーあたりのIntent作成数・更新頻度の上限」を次の値に確定する。

| 制限 | 上限 | 超過時 |
|---|---|---|
| Active Intent数 | 5件 / ユーザー | 422(ACTIVE_INTENT_LIMIT、既存Intentの停止・期限切れを促す) |
| Intent作成 | 20件 / 日 / ユーザー | 429(RATE_LIMITED) |
| Intent更新 | 6回 / 時間 / Intent | 429(RATE_LIMITED) |
| API全体 | 60リクエスト / 分 / ユーザー | 429(RATE_LIMITED) |

根拠は、正常な利用実態(Active数件、修正は数回)を損なわない下限と、反復更新によるMatch Eventの大量発生(01レビューF-32)でJevコスト上限(04 D-16)を食い潰す攻撃経路を源流で塞ぐ上限の間に置いた。Intent更新の上限は06のdebounce(10秒、作成即時・更新のみ窓統合、06 v0.3第9節)と直交して働く。ステータスコードは05 v0.3のエラーcode列挙と整合する(Active上限のみ422、その他は429)。カウンタはRedis(04)で持ち、API Layerで強制する。この上限は源流の抑制であり、通過後のJev消費の抑制は06 v0.3第5節のJev予算(1Intent日次40回・1ユーザー日次120回)と頻度制限(30分)が担う(二層の保護)。
