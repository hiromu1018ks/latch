## 1. 本書の目的と位置づけ

本書は01の次に作る最初の合意文書で、(1)MVPスコープの最終境界、(2)第25節受け入れ条件と検証方法の対応付け、の2つを確定させる。後続文書(03 UX仕様書以降)はすべて本書の境界を前提に設計する。検証方法は、内部設計に依存しないブラックボックス検証として書ける範囲に限る。設計依存の検証は06以降の設計文書と10テスト環境・非機能検証計画書が担う。

## 2. MVPスコープの確定

01第7節を出発点とし、第3節の決定と08 D-10の判断を反映した最終境界を次に示す。

**実装する**

- アカウント / プロフィール(認証は外部Idプロバイダ、第3節D-21)
- 自然言語Intent入力と構造化 — 判定に必要なデータをシステムが持たないNG条件を含む(D-04)
- 下書き保存(v0.3) — Intentをstatus=draftでサーバー保存し、後から再開して「預ける」(active化)する経路。プロトタイプの「下書き保存」ボタン(トースト「下書きを保存しました」)と確認モーダルの体験に対応する。draftはマッチング処理の対象外である(05 v0.4・03 v0.4)
- Active Intent管理
- Hard Constraint Filter / Vector Search / Cheap Judge / Jev判定
- 1対1 LATCH、および最大4人の簡易グループLATCH
- YES / NO回答と双方承認
- 通知 / LATCH成立後チャット / 期限管理
- ブロック / 通報
- 年齢制限(利用登録は18歳以上、飲酒を含むIntentは20歳未満作成不可・20歳以上同士のみ候補化。08 D-10の判断で本書v0.1後に追加。第4節#27)
- 基本Analytics
- ユーザーあたりのIntent作成数・更新頻度の上限(Jevコスト保護の一部。受け入れ条件には含めない)

**実装しない**

- 01第7節の既存除外リスト(決済、店舗予約、自動購入、外部店舗在庫連携、複雑なRecommendation Feed、広告、完全自動交渉、第6節の将来領域)
- 友人関係の管理(相互承認)とvisibilityのfriends_only — v0.2でD-03としてMVPに含めたが、v0.3で将来版へ移した(D-03の再決定を参照)
- visibilityのfriend_of_friend(2ホップ判定。将来バージョン)
- 所属情報(会社・組織)の収集、およびそれによるコード判定(D-04)
- ミュート、スパム検知、不適切コンテンツ検知、なりすまし対策(通報による手動対応で代替)
- 自前でのパスワード認証(保存・リセット)(D-21)

**境界の運用** — 上記のどちらにも読める機能提案が出た場合は、第25節の受け入れ条件を満たす最小構成を実装側とし、残りを「実装しない」へ置く。判定が割れる場合はプロダクトオーナーの裁可による。

## 3. 未決事項の決定

### D-03 友人関係データ・管理機能の包含(v0.3で再決定)

- 決定内容(v0.3、プロダクトオーナー決定による再決定): visibilityは**「条件一致までは非公開(hidden_until_match)/ 候補にだけ概要を表示(summary_only)」の2値**とする。friends_onlyと友人関係(friendships)のMVP実装は取りやめ、将来版へ移す
  - hidden_until_match: 提案(proposed)・回答中も自分の条件サマリは相手に表示しない。提案先が受け取るのは「条件が合う候補があります」の通知と一致度・回答期限(+グループなら必要人数)のみとし、成立(matched)した時点で初めて条件サマリ・表示名・プロフィールを解放する。プロトタイプの確認モーダル文言「成立までは非公開」と同一の内容である
  - summary_only: 提案先に条件サマリ(人数・時間帯・地域名・カテゴリ・ペア予算)のみを表示する。raw_text・NG条件・名前・プロフィールはどちらの値でも成立まで非表示である(08 v0.4第2.2節と同一)
  - 初期値はhidden_until_matchとする(プロトタイプの既定選択)。提案画面の情報量の差は09のA/B対象(表示情報量)で検証する
  - この2値は公開相手の範囲(誰に見せるか)ではなく、**提案時点で開示する情報の範囲(いつ・どの程度見せるか)**を決める。判定位置はLayer 1の公開範囲チェックから、Layer 5のproposal生成の分岐へ変わる(06 v0.4)
- 変更履歴: v0.2では「友人関係データはMVPに含める。相互承認のみの最小構成とし、visibilityはpublic/friends_onlyの2値に縮小する」で解消した(根拠: 公開範囲というHard Constraintの検証がpublic一種類しかできずLayer 1の要件検証として弱い)。v0.3で反転した。旧根拠で挙げた検証の多様性は、公開設定2値によるproposal内容の差異の検証(第4節#22 v0.3改訂版)で代替する。friendshipsのEntity・API定義は05 v0.4に将来版として残置する
- 01への影響: 第9節のvisibility列挙・第17節・第19節・第22節を更新(済み。01 v0.4)。Layer 1とLayer 5の実装層の割当変更は06 v0.4へ反映済み

### D-04 判定データを持たないNG条件の扱い

- 決定内容(スコープ判断のみ): 所属情報を収集する機能はMVPに含めない。判定に必要なデータをシステムが持たないNG条件は、保存前の条件リストで「確実に除外できる条件ではない」旨を利用者に提示したうえで、Soft Constraintとして扱う(注意表示のUI位置は03 v0.4第3節)
- 根拠: 所属情報の収集は登録体験の摩擦を増やし、仮説1(置いて待つ体験)と衝突する。機微性も高く、外部LLM送信(D-14)と絡む新たなリスクを生む。一方で入力を拒否すれば自然言語で置く体験(01第9節)が損なわれる。Soft Constraintへの降格は原則2(絶対条件をAIに任せない)に反しない。もはや絶対条件として扱わないからであり、誤提案のリスクは成立前の情報解放の最小化(01第21節)で緩和する
- 実装層の割当: どの層で判定しJevの判断材料にどう入れるかは、06マッチングパイプライン設計書で確定する(降格フラグの格納構造は05 v0.3のstructured_dataスキーマ)。本書はスコープ判断のみを解消する
- 01への影響: 第5節・第9節にNG条件の分類規則(判定データを欠くものはSoft Constraint)を追記

### D-12 安全要件のMVP受け入れ条件への包含

- 決定内容: ミュート、スパム検知、Intent大量投稿制限、不適切コンテンツ検知、なりすまし対策を、MVP受け入れ条件(第25節Safety)に含めない。第25節Safetyは本書v0.1時点で4項目(ブロック、通報、Intent全文非公開、正確な位置情報非公開)と確定した。その後、08 D-10の判断により**年齢制限のみ性質が異なる**(飲酒Intentへの法的リスク)として、「20歳未満のユーザーは飲酒を含むIntentを作成できない」が02が定めた変更管理(本書の改版と01の該当節の更新)によって第25節へ追加され、**Safety受け入れ条件は5項目となった**。01第25節の現状と一致する。ただしIntent作成数・更新頻度の上限は実装する(コスト保護の一部であり、受け入れ条件外)
- 根拠: MVPは検証装置であり、コールドスタート期に悪用対策へ開発量を割く余裕がない。ブロックと通報で事故対応の最小線は確保できる。年齢制限のみ飲酒Intentへの法的リスク(D-10)として性質が異なるため、内容を08で決定したうえで、必要と判断されたため変更管理で追加した(v0.2はこの追加を本書の本文へ反映する改版である)
- 01への影響: 第22節と第25節の不一致を解消し、Safety 5項目として一致(第25節の現状と同じ)

### D-21 認証方式の方向性

- 決定内容(方向性): 外部Idプロバイダによるソーシャルログインを主手段とする。自前のパスワード認証は持たない。プロバイダ種・トークン・セッション管理の確定値は04で定める(04 v0.2のD-21で確定済み: Google + Apple、IdPトークン検証+独自JWT。契約面は05 v0.3の認証・ユーザー系API)
- 根拠: 登録の摩擦は仮説1の検証の直前関門であり、最小化する。パスワード管理の自前実装はMVPの範囲を超える。なりすまし対策をMVPに含めない(D-12)ため、Idプロバイダ側の本人性に依存する構成とする
- 01への影響: 第22節に認証の方向性を追記(確定値は04)。第7節「アカウント」の内容確定

### D-22 初期リリース地域・Intent密度の方向性

- 決定内容(方向性): 初期リリースは単一都市内の限定エリア(駅周辺程度の半径)への集中投入とし、クローズドベータでIntent密度を担保する。対象地域・必要密度の数値・招待規模は11リリース計画書で確定する(11で確定済み: 単一エリア・駅周辺3km相当)。10の試験はこの前提を反映する
- 根拠: 01第12節のファネルはスケール後のイメージで、密度がなければMatching〜Analyticsの全受け入れ項目が検証不能になる。MVPの検証に必要なのはユーザー総数ではなく密度である
- 01への影響: 第26節D-22の方向性を記録(確定値は11)。地理的範囲の確定は11
