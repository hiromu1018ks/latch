# LATCH 最終総括レビュー — レビューアーB(実装可能性 Engineering)

- 対象: 00〜11 全文書(重点: 04〜07、10)
- 観点: 実装着手可能性 / データフロー接続 / API実務完全性 / 非機能・試験の実行可能性 / レースコンディション・障害時挙動
- 件数: 全21件(Critical 2 / Major 12 / Minor 7)

全体評価: 層構造・K上限・状態遷移・競合制御の方針は実装に落とせる水準にあり、文書間の決定の連携(04→05→06→07)は概ね閉じている。ただし (1) パイプラインのトリガー構造(EmbeddingとEventの順序)、(2) 認証・アカウント登録系のAPI契約、の2点が未定義のままであり、Layer 2とAPI Layerの実装は現状着手できない。以下は文面から確認できる確度の高い欠落・矛盾のみを列挙する。

---

## F-B-01 Critical — Embedding(非同期)の完了と Match Event 処理の順序関係が未定義で、Layer 2 が実装できない

- 対象文書: 06 第1節・第9節・D-15 / 07 第1節・第3節 / 04 第2節・第7節 / 10 第4.1節
- 問題:
  - 07 第1節は Embedding を「Intentの作成・更新後(イベント駆動)、非同期」と確定。一方 04 第7節は Intent保存経路から同期LLM呼び出しを排除しており、保存時点で embedding は存在しない。
  - 06 第1節のパイプライン図は「Match Event 1件 → Layer 1 → Layer 2(embedding をクエリに使用)→ … → Layer 5」と1段構造で、Embedding 完了待ちの位置がない。06 第9節の処理手順(debounce / idempotency / version検査)にも Embedding の扱いがない。
  - 起点Intentのembeddingが未完了のまま Event が Worker に届いたとき、(a) Embedding を同期的に行ってからマッチングを続行するのか、(b) Embedding 完了を第2段トリガーとする別イベントで再処理するのか、が決まらない。07 が「非同期」と確定しているため (a) は採れず、(b) のイベント設計(payload・idempotency key・version 検査との関係)がどの文書にもない。
  - 06 D-15 は embedding=NULL を「失敗」状態として規定するが、「未処理(成功も失敗もしていない)」状態のIntentを Layer 1〜2 がどう扱うかの規定がない。
  - 波及: 10 第4.1節「Candidate Retrieval p95 1秒 = Layer 1〜2処理時間」の測定境界(Embedding を含むか)、および「初期LATCH判定 p95 10秒」の予算配分が確定しない。
- 影響: Matching Worker と Layer 2 の実装、初期LATCH判定の性能試験の設計が着手できない。パイプラインの根幹のトリガー構造が未定義。
- 推奨対応: 06 に「Embedding 完了を第2段トリガーとする」等の方式を確定し、第2段イベントの idempotency key・version 検査・10秒目標内での予算配分(Embedding / Layer 1〜2 / Jev)を追記する。併せて 07 第1節の表に Embedding の timeout を明記(F-B-09と連動)。

## F-B-02 Critical — 認証・ユーザー登録系の API 契約が 05 に存在せず、API Layer が着手できない

- 対象文書: 05 第5節 / 04 D-21 / 03 第2節
- 問題:
  - 04 D-21 は「アプリがIdPトークンをAPIへ提示し、APIはJWKSで検証して独自JWTを発行。紐付くUserがない場合は新規登録」と確定するが、05 第5節のAPI一覧にトークン発行・リフレッシュのエンドポイント(POST /v1/auth/token 等)が存在しない。リフレッシュトークン30日・回転式の契約面(要求/応答/失効)も未定義。
  - users.birth_date は NOT NULL・登録時に18歳以上検証(08 D-10)だが、IdP初回ログイン時のユーザー作成と birth_date・display_name・profile を登録する API(POST /v1/users、PATCH /v1/users/me 等)が一覧にない。GET /v1/users/me もない。
  - Redis 失効リストによる即時失効(04 D-21)の操作(ログアウト/失効発行)のエンドポイントもない。
  - 05 のAPI一覧は「確定」として読まれる契約書であり、実装チームがエンドポイントを追加することは文書変更を要する行為になる。
- 影響: 04 D-21 の実装を開始するための契約が存在しない。アプリ側の認証実装も同時に止まる。01 第25節の全受け入れ条件がこの下にぶら下がる。
- 推奨対応: 05 に `POST /v1/auth/token`(IdPトークン検証+JWT発行+新規登録フロー)、`POST /v1/auth/refresh`、`POST /v1/auth/logout`、`GET /v1/users/me`、`POST /v1/users`(birth_date・18歳検証を含む初回登録)を追加し、要求/応答/エラー契約を定義する。

## F-B-03 Major — Parser出力→Intent保存の結合点が未定義(ジオコーディングの実行箇所・失敗応答・structured_data保存スキーマ・D-04フラグ構造)

- 対象文書: 05 第2節・第5節 / 04 第3節 / 07 第2節 / 06 第2節
- 問題:
  - POST /v1/intents は `structured_intent`(parse結果を修正したもの)を受けるが、parse出力の `location.name` は地名文字列であり、05 の intents.geo_center は geography 型 NOT NULL。04 第3節の「Parser通過後・Intent保存前の正転ジオコーディング」をどの処理(API保存処理内?)で行い、request の location をどう受けるか(name のままか、確認画面で座標化済みか)が契約として未定義。
  - ジオコーディング失敗(地物DBに該当地物がない)時の応答(422? 503? エラーコード名)が未定義。05 の422条件列挙(必須欠落・20歳未満飲酒)に含まれず、ユーザーへの修正促し(03 第3節)と接続できない。
  - structured_data の保存スキーマ(キー名・構造)がどこにもない。07 出力(category.primary / time / soft_constraints / negative_constraints / ng_unverifiable)を 05 の structured_data に格納する際の正式なJSON構造、および D-04降格条件を soft 側へ「フラグ付きで」格納する構造(06 Layer 3 がフラグで機械的に除外するため必要)のフィールド名・値域が未定義。
  - 細部不一致: 07 のParser出力JSONスキーマ(「この形式のみ認める」)に visibility がないのに、05 第5節の parse 応答例には `"visibility": "public"` が含まれる。07 D-17 の精度検証(フィールド完全一致率)の期待値表がどちらのスキーマに従うかも決まらない。
- 影響: Intent保存API・確認画面・Layer 3 のフラグ参照・09 の期待値表が相互にずれる。実装者が各自で構造を決め、検証資産と不整合が生じる。
- 推奨対応: 05 に structured_data の正式JSONスキーマ(D-04フラグのフィールド名を含む)を定義し、POST の location 受け方とジオコーディング失敗時の応答コードを規定する。07 の出力スキーマと 05 応答例の visibility をどちらかに揃える。

## F-B-04 Major — match_candidates の同一バージョン内上書き更新で、D-07 の「スコア変化」判定の比較元が消える

- 対象文書: 05 第2節(match_candidates)/ 06 第10節 / 03 D-07
- 問題:
  - 05 は「同一バージョン内の再評価(時間イベント等)は既存レコードを更新する」と規定。06 第10節は「現行の評価と直近の過去評価の latch_score を比較して変化を判定する」と規定するが、更新型では上書き前の latch_score がレコード上に残らず、「直近の過去評価」が取得できない。
  - 比較のタイミング(更新トランザクション内で前値を読んで比較するのか)・比較結果の保持(変化フラグをどこに置くのか)・比較対象(同一バージョン内の前回値か、直近の別バージョン組の値か)のいずれも未規定。グループ由来のペア評価の場合の比較単位も未定義。
- 影響: 再提案制御(03 D-07 条件(b))が実装できず、実装者が独自解釈で埋めることになる。staging の再提案検証(10 第3節経由)の期待値も定められない。
- 推奨対応: 06 第10節に比較手順を具体化する(例: 更新トランザクション内で前値を読み、変化しない場合は再提案を抑制する旨の記録列を追加)。必要なら 05 に前回値保持列を追記する。

## F-B-05 Major — D-08 の保留キューの保持構造・提示時の期限再計算・75分ルールの適用が未定義

- 対象文書: 06 第10節 / 03 D-08・D-05 / 05 第2節(latches)
- 問題:
  - 通知上限超過の候補を保留するキューの保持構造がどの文書にもない。latches(status=candidate)で表現するのか、match_candidates のまま扱うのか不明。保留候補の proposal・score・response_deadline の保持場所が決まらないと「保留中に候補側の対象時刻が来たものは expired として閉じる」(03 D-08)も実装できない。
  - 保留キューから後で提示する際の response_deadline は「その時点の通知時刻」で再計算すべきだが、保存時の計算値を流用するのか再計算するのかの規定がなく、流用すると通知時刻+15分の下限を割れる。
  - 「対象開始時刻まで75分を切った時点で生成された提案は通知自体を行わない」(03 D-05)について、その候補を保留キューへ入れるのか破棄するのか未定義。
  - 再評価トリガー「既存提案のクローズまたは0時リセット」の検知手段(クローズイベントの観測方法)も F-B-11 と連動して未規定。
- 影響: Layer 5 の通知生成・保留管理が実装できない。D-08 は仮説4の検証装置そのものであり、放置すると A/B 試験(09 第5節)の前提が崩れる。
- 推奨対応: 06 に保留の表現(推奨: latches.status=candidate を使用し expires_at で期限切れ処理)と、提示時の response_deadline 再計算・75分ルールでの破棄規定を追記する。

## F-B-06 Major — 再評価時の Jev 再実行抑制の規定がなく、D-16 の上限想定と衝突し得る

- 対象文書: 06 第9節・D-15 / 04 D-16 / 11 D-22
- 問題:
  - 時間Bucket(30分)での再評価は「Candidate Retrieval から再実行」とされ、Intent更新による再評価も同様。しかし「同一ペアについて jev_result が既に存在する場合に Jev を再実行するか」の規定が 06 に存在しない。D-15 の skipped 回収(同一バージョン組レコードの更新)も同様。
  - 再実行抑制なしで素直に実装すると、Active Intent が到来Bucketごとに繰り返し評価され、Jev実行回数が K_j=8 × イベント数 で積み上がる。04 D-16 の根拠は「1イベントあたり平均1〜2回、正常時1万回/日以内」だが、11 D-22 の密度確定値(同一Bucket×同一カテゴリ15件)では Cheap Judge 通過候補が K_j に届く可能性が高く、夜間ピークの時間Bucket評価が数千回/日規模になり得る。D-16 の「正常運用が上限に触れない」前提がこの抑制規定なしでは保てない。
- 影響: 実装者が抑制を入れないと D-16 上限が日常的に発動し、縮退運転(提案見送り)が常態化する。入れる場合も、抑制条件(Jev済みペアのスキップ、Layer 1 再検証のみ)の文書根拠がないため検証(10 第4.5節)の期待値が定められない。
- 推奨対応: 06 第9節に再評価時の Jev スキップ規定(jev_result 保持・評価世代同一なら Hard Filter のみ再検証、等)を追記し、04 D-16 の根拠計算と 11 D-22 の密度値から日次実行数の概算を再確認する。

## F-B-07 Major — LATCH期限切れ遷移の実行者が未定義で、回答APIの期限チェックとの競合制御も未規定

- 対象文書: 05 第5節・第6節 / 06 第6節 / 03 D-05
- 問題:
  - 05 第6節は「proposed・partial_accept→expired: response_deadline/expires_atの経過」をトリガー表に置くが、Intent expired と異なり LATCH expired の実行者(時間バッチ?)・頻度・Clock参照がどの文書にもない(Intent 側は「時間バッチ。idx_intents_expiresの対象と一致」とあるが LATCH 側の実装手段は未規定)。
  - 回答APIの409(回答期限切れ)と、遅延した期限切れバッチの競合が規定されていない。status がまだ proposed の行に期限直後の回答が届いた場合、status のみの条件付き UPDATE では yes が通ってしまう。06 第6節の競合制御は「status遷移」に言及するのみで、`response_deadline < now()` を UPDATE 条件に含めること・時刻源(アプリ内 Clock と DB 時刻のどちらか)が未規定。
  - 10 第1節の「時刻の参照はすべてClockインターフェース経由」の強制が、この期限判定・バッチ・DBトリガにまで適用されるかの明示がない(F-B-17 と連動)。
- 影響: 期限直後の回答が通る「期限後成立」バグの温床。02 #16(期限切れ処理)の検証が Clock 操作でも再現できない。
- 推奨対応: 06 第6節に、回答処理の UPDATE 条件へ response_deadline / latches.expires_at との比較を含めることを規定し、LATCH 期限切れ処理の実行者(バッチ名・周期・切替条件)を 05 または 06 に追記する。

## F-B-08 Major — match_events の冪等キーに UNIQUE 制約の規定がなく、削除済み Intent 参照 Event の破棄/隔離の区別もない

- 対象文書: 05 第2節(match_events)/ 06 第9節 / 10 第4.7節
- 問題:
  - 06 第9節は idempotency key=(event_type, source_intent_id, version) を規定するが、05 の match_events 定義に対応する UNIQUE 制約が存在しない(users.auth_subject や match_candidates には UNIQUE を明記する文書様式なので、書かれていない=未規定と読める)。Pub/Sub は at-least-once 配信であり、並行 Worker が同一 Event を同時取得した場合の DB レベルの重複排除根拠がない。
  - version 検査「payloadのversion < 現行version なら破棄」に、参照先 Intent が存在しない場合(DELETE 後の正当な遅延 Event)の取り扱いがない。破棄なのか quarantined なのかの基準がなく、10 第4.7節の「不正なIntent参照を含む毒ペイロードは隔離」との区別規定がない(正常な削除後 Event を隔離すると滞留・alert が誤発報する)。
- 影響: 重複処理による二重候補生成・Jev 二重実行(コスト直結)。Queue 障害試験(10 第4.7節)の合格判定が曖昧になる。
- 推奨対応: 05 match_events に UNIQUE(event_type, source_intent_id, payload version)相当の制約を追記し、06 第9節に「参照先不在は破棄、payload 不正は隔離」の区別規定を追記する。

## F-B-09 Major — Jev・Embedding の timeout 値と circuit breaker のしきい値が未定値で、縮退運転の実装・試験合格判定ができない

- 対象文書: 07 第1節・第4節 / 06 D-15 / 04 D-14・D-16 / 10 第4.1節・第4.5節
- 問題:
  - Parser のみ timeout 10秒が確定(07 D-17)。Jev と Embedding の timeout 値がどの文書にもない。04 D-14 基準4は「timeout・retryを含む安定性」と基準のみ。初期LATCH判定 p95 10秒の層別予算配分(Parser/Embedding/Layer1〜2/Jev/通知)も未定義で、10 第4.1節が「Jev レイテンシ注入 p50 2秒/p95 5秒」を試験条件に据えているが、timeout が 5 秒以上なのか否かすら文書から読めない。
  - 06 D-15 の circuit breaker は「LLM Gatewayのエラー率・レイテンシしきい値で開放、一定時間後に半開」と状態機械のみで、しきい値・測定窓・半開の期間が未定値。10 第4.5節は「circuit breaker が開放し、一定時間後に半開」を合格確認項目にするが、開放条件の値が確定しないまま合格/不合格を判定できない。
- 影響: 縮退運転(D-15)の実装と 10 の縮退試験が両方とも確定値を欠く。p95 10秒の性能試験も、予算配分の根拠なく実施される。
- 推奨対応: 07 に Jev・Embedding の timeout・再試行回数を確定し(10秒目標内の配分を明記)、06 D-15 に circuit breaker の初期値(エラー率%・窓時間・半開期間)を定める。

## F-B-10 Major — 他文書で決定済みの操作が 05 のAPI一覧に未反映(セッション開始・D-09自己申告・ブロック解除・友人拒否)

## F-B-11 Major — LATCH 状態遷移イベントの記録構造がなく、Mutual Latch Rate 集計と保留キュー再評価のトリガーが実装できない

- 対象文書: 09 第2.1節 / 05 第2節 / 06 第10節
- 問題:
  - 09 第2.1節は「proposed遷移を分母、matched遷移を分子として、latchesのstatus遷移イベント(05)から日次で集計する」と規定するが、05 に latches の状態遷移履歴(イベント)の保持構造が存在しない。notifications からの間接導出では通知失敗・保留との対応が取れず、North Star の集計根拠が定まらない。
  - 06 第10節の保留キュー再評価トリガー「既存提案のクローズ検知」も同一の遷移観測に依存する。
- 影響: North Star 指標(01 第23節、02 #26)の算出根拠が実装不能。A/B 判定(D-01)と D-02 ベースラインの前提が崩れる。
- 推奨対応: 05 に latch_status_events(または遷移ログの保持方針)を定義するか、09 に「notifications + latches 最終状態からの再構築集計」等の代替手段を明記する。

## F-B-12 Major — proposal・通知文の表示データ構造が未定義で、03 の通知文言(「焼肉」等)を生成するデータソースが存在しない

- 対象文書: 05 第2節(latches.proposal)/ 08 第2.3節 / 03 第4節・第5節 / 06 第6節
