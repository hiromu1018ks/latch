## 1. 結論 — Phase 0の2週間は約$56・Phase 1の継続は月約$262(LLM込み)

- **シナリオ1(Phase 0・2週間使って環境を削除): 約$56**。うちGCPインフラ約$49+LLM約$6.5。月額換算すると約$120相当の環境を2週間だけ立てる形
- **シナリオ2(Phase 1・500人で1ヶ月継続): 約$262/月**。うちGCPインフラ約$122+LLM約$140
- 金額を押し上げているのは**常時稼働が前提の3点(Cloud SQL・Memorystore・Cloud Runの常時2インスタンス)で、GCPインフラの約8割を占める**。逆にPub/Sub・FCM・Loggingは規模に対して無料枠に収まり、実質ゼロ
- 試算の信頼性の限界が3つある。(1)東京リージョンの単価が価格ページの選択式UIのため直接確認できず、既定表示基準(us-central1)の単価で計算している。(2)Cloud Monitoringの課金単位に表記上の曖昧さがあり、読み方次第で月$0.6と月$650の差が出る。(3)LLMのフォールバック切替が1ヶ月続くと約$1,000まで膨らむ。この3点は第8節・第9節に整理した
- 新規GCPアカウントであれば$300の無料トライアル(Firebaseページに「If eligible」と記載・適用条件は要確認)でPhase 0の2週間分はまるごと賄える可能性がある

## 2. 試算の方法と前提 — 単価は一次ページ取得・東京値は未確認

**単価の取得方法。** GCPの価格ページ(cloud.google.com)はリージョンや課金モードを選ぶ式の動的ページで、通常のページ取得では本文が取れないものがあった。そのため本文取得が可能なツールを使い、2026-10-06時点のページ本文から単価を読み取った。出典と確認日は各項目に付している。

**リージョン。** docs(04・11)にはリージョンの確定値がなく、本試算では日本向けサービスを想定した**東京(asia-northeast1)を仮置き**する。ただし取得できた単価表の多くはページの既定表示基準(主に米国Iowa=us-central1)であり、東京の値は選択式UIのためにテキスト取得できなかった。東京は米国主要リージョンより割高になるという第三者試算(usage.aiで「1.2〜1.5倍」の言及)があるため、**実際の請求は本試算より高くなる可能性が高い**。上振れケースは第8節の感度分析に示す。

**月間時間。** GCPの価格例に合わせ、1ヶ月=730時間=2,628,000秒、2週間=336時間=1,209,600秒で計算する。

**構成の前提。** 「最小適正サイズ」の意味は、04 §6〜§7の本番確定値(API常時2インスタンス・マネージドPostgreSQL+PITR・Cloud Monitoring+OTLP)を守る範囲での最小である。04 §6のマルチAZ配置は、Phase 0の2週間の検証環境では単一ゾーンに緩めた(緩めた場合の差は第8節に示す)。LLM費用は第7節、FCMは無料(第4節)として分けて扱う。

**為替。** 円換算はしていない。請求通貨の設定はアカウント側の前提になるためである(第9節)。

## 4. 項目別見積 — 最小構成の月額と計算式

### 4.1 Cloud Run(API・Worker)

課金モードは**リクエストベース(requests-based billing)**を選ぶ。リクエストが来ている時間(active)と、最小インスタンスとして温まっている時間(idle)で単価が異なる。

- 単価(2026-10-06・<https://cloud.google.com/run/pricing>・既定表示基準): CPU active $0.000024/vCPU秒・CPU idle(最小インスタンス)$0.0000025/vCPU秒・メモリ active/idleとも $0.0000025/GiB秒・リクエスト $0.40/100万件
- 無料枠(月次・請求アカウント単位で全サービス合算): CPU 180,000 vCPU秒・メモリ 360,000 GiB秒・リクエスト200万件。「無料枠はTier 1単価ベースの金額割引として適用」とページに明記がある
- 構成仮定: APIは1vCPU/512MiB(0.5GiB)・最小2インスタンス。Workerは1vCPU/1GiB・最小0。アクセス量は「1人1日50リクエスト・平均処理100ms」を仮定(仮定であることを明示し、Phase 0実績が出たら差し替える)

**API(最小2インスタンス)の月額。**

| 項目 | 計算式 | 月額 |
|---|---|---|
| アイドルCPU | 2インスタンス × 1vCPU × 2,628,000秒 × $0.0000025 = 5,256,000 vCPU秒 × $0.0000025 | $13.14 |
| アイドルメモリ | 2 × 0.5GiB × 2,628,000秒 × $0.0000025 = 2,628,000 GiB秒 × $0.0000025 | $6.57 |
| active(Phase 1想定・500人×50req/日×30日=75万req×0.1秒=75,000 vCPU秒) | CPU 75,000 × $0.000024 = $1.80・メモリ 75,000 × 0.5GiB × $0.0000025 = $0.094・リクエスト 750,000/1,000,000 × $0.40 = $0.30 | $2.19 |
| 小計 | 13.14 + 6.57 + 2.19 | $21.90 |
| 無料枠控除(上限・合算前提) | 180,000 × $0.0000025 + 360,000 × $0.0000025 + 2,000,000/1,000,000 × $0.40 = 0.45 + 0.90 + 0.80 | −$2.15 |
| **API月額(控除後)** | 21.90 − 2.15 | **≈$19.75** |

注記: アイドル課金が金額を支配する。最小インスタンスを0に下げればAPI月額はほぼゼロになるが、04 §6の「常時2インスタンス」に反するため本試算では守った。**常時2インスタンスの代償が約$14/月(アイドル分)であり、これを削るかは可用性要件の判断**である。

**Worker(最小0)の月額。** Event処理を「1イベント1秒」で積算する。

- Phase 0(20〜50人・Event数千): 5,000イベント×1秒=5,000 vCPU秒 → CPU $0.12+メモリ $0.0125+push呼び出し $0.002 = $0.13 → **無料枠内で$0**
- Phase 1(04 §6・D-16の根拠どおり通常時1万イベント/日の上限想定): 10,000×30日=300,000イベント×1秒=300,000 vCPU秒 → CPU 300,000×$0.000024=$7.20・メモリ 300,000×1GiB×$0.0000025=$0.75・リクエスト $0.12 = $8.07。APIと無料枠を共用するため控除後**$2〜3**
- 感度: Workerを最小1にした場合、アイドル分 1×1vCPU×2,628,000×$0.0000025=$6.57(CPU)+1×1GiB×2,628,000×$0.0000025=$6.57(メモリ)=**+$13.14/月**(初期LATCH判定p95 10秒のためのコールドスタート対策として現実的な選択肢)

### 4.2 Cloud SQL for PostgreSQL(PostGIS+pgvector対応確認済み)

- 単価(2026-10-06・<https://cloud.google.com/sql/pricing>・**既定表示基準。東京値は未確認**): Enterprise edition 1vCPU $0.0413/時・メモリ $0.0070/GiB時。共有コア db-g1-small $0.035/時。SSDストレージ $0.000232877/GiB時(≈$0.170/GiB月)。バックアップ $0.000109589/GiB時(≈$0.08/GiB月)。HA(リージョン冗長)はこれらの2倍の単価系
- 拡張対応: PostGISは全メジャーバージョン対応・PG16/17で3.5.2(<https://cloud.google.com/sql/docs/postgres/extensions>・2026-10-06取得)。pgvectorは対応・リリースノートで0.7.4→0.8.0への更新を確認(<https://docs.cloud.google.com/sql/docs/postgres/release-notes>)。**05のvector(768)とPostGISの両方がCloud SQLで動くことは裏取り済み**
- 主案(Enterprise・db-custom-1-3840=1vCPU/3.75GiB・単一ゾーン・SSD 20GiB・バックアップ20GiB想定):

| 項目 | 計算式 | 月額 |
|---|---|---|
| インスタンス | (1 × $0.0413 + 3.75 × $0.0070)/時 = $0.067550/時 × 730時 | $49.31 |
| SSDストレージ 20GiB | $0.000232877 × 20 × 730 = $3.40 | $3.40 |
| バックアップ 20GiB(PITR込みの想定) | $0.000109589 × 20 × 730 = $1.60 | $1.60 |
| **小計** | 49.31 + 3.40 + 1.60 | **$54.31** |

- 2週間分: $0.067550 × 336時 = $22.70(インスタンス)・ストレージ $0.000232877×20×336=$1.56・バックアップ $0.000109589×20×336=$0.74 → **$25.01**
- 節約案: 共有コア db-g1-small なら $0.035 × 730 = $25.55/月(2週間$11.76+ストレージ分)。ただし**共有コア(db-f1-micro/db-g1-small)はGCPが「開発/テスト専用・SLA対象外」と位置づけている**。「本番同環境での最終確認」(11 §1)というPhase 0の趣旨に合うかはオーナー判断を要する
- 注記: バックアップについて「インスタンスストレージの2倍まで無料」という旧規定が現行ページで確認できなかったため、**全量課金で保守側に計上した**(第9節#4)
- HA化(04 §6のマルチAZに厳密に従う場合): 上記がほぼ2倍 → 月$108.62(差分**+$54.31**)

- 単価(2026-10-06・<https://cloud.google.com/memorystore/docs/redis/pricing>・既定表示はIowa。東京値は未確認): Basic tier・M1(1〜4GiB帯)$0.049/GiB時。最小容量は1GiB(M1帯の下端)

### 4.4 Pub/Sub

- 単価(2026-10-06・<https://cloud.google.com/pubsub/pricing>): 最初の10GiB/月が無料(請求アカウント単位)・その後$40/TiB(全リージョン)。**リクエストごとに最低1KBの課金**(小さいメッセージはバッチ送信が得)・保持(storage)$0.27/GiB月
- 量の積算: 1イベント≈2KB。Phase 0: 数千イベント×2KB≈20MB未満。Phase 1: 1万イベント/日×30日×2KB=600MB。ともに10GiBに遠く及ばない
- 計算式: 0.6GiB < 10GiB → **$0/月**(Phase 0・1とも)。保持も、デフォルト設定(保持なし・backlog 1日以内)なら課金なしとページに明記。D-16縮退でbacklogが1日超に達した場合のみ$0.27/GiB月(第8節#8)

### 4.5 Cloud Monitoring・Cloud Logging

- Cloud Logging(2026-10-06・<https://cloud.google.com/stackdriver/pricing>): 最初の50GiB/プロジェクト/月が無料・超過分 $0.50/GiB。30日を超える保持は$0.01/GiB月。_Requiredバケットは400日保持で無料
  - 量の積算: 08のログ許可リスト規律(G4⑤で実証済み)でraw_text非混入。日次0.5〜1.5GiB想定 → Phase 0(14日)7〜14GiB・Phase 1(30日)15〜45GiB → **無料枠内で$0**。超過時は+1GiBごとに$0.50(第8節#4)
- Cloud Monitoring: カスタムメトリクス・OTLP取得分はbyte課金。単価表記は「$0.2580/MiB: first 150-100,000 MiB」・無料枠は請求アカウントあたり150MiB

  - 量の積算: 系列≈100本(3群+HTTPメトリクス・ラベルはmethod/path/statusのみ)×15秒周期×86,400秒=日次576,000サンプル×≈150バイト≈86MB/日 → 月次2,592MB≈2,472MiB
  - GiB読み: (2,472−150)MiB = 2,322MiB ≈ 2.27GiB × $0.258 = **$0.59/月**(2週間: (1,148−150)MiB≈0.97GiB×$0.258=$0.25)
  - MiB読み(表記どおり): 2,322MiB × $0.2580 = **$599/月**。差が約1,000倍あるため、**実装前に請求実績か価格例で確定させるべき論点**
- アラートポリシー: 同ページの表で「$0.35/月×ポリシー内メトリクス参照」は**発効日2027-09-01**。つまりPhase 0〜1では課金なし。D-16 80%alert・Queue lag alert等を3〜5本設定しても現時点$0(2027年9月以降は約$1.05〜1.75/月)
- uptime check(100万実行/プロジェクト/月無料)・Cloud Trace(250万spans/月無料): LATCH規模では**$0**

## 9. 未確認事項 — 推測で埋めなかった点とアカウント側の前提

1. **Cloud Monitoringの課金単位(MiB/GiB)**: 価格ページの表は「$0.2580/MiB」と読めるが、実務水準と2桁ずれがあり価格例を取得できていない(§4.5)。初月の請求実績で確定する
2. **東京(asia-northeast1)の各単価**: Cloud SQL・Memorystore・Cloud Runの東京値はリージョン選択式UIのためテキスト取得できず、既定表示基準(主にus-central1)で計算した。Cloud Runの東京が無料枠対象のTier 1に属するかも未確認
3. **ネットワーク下りの公式単価**: 公式ページが取得できず、第三者集計($0.12/GB・2026-05)を使用(§4.6)。実施時に公式ページで確定する
4. **Cloud SQLバックアップの無料枠**: 旧規定「インスタンスストレージの2倍まで無料」が現行ページで確認できず、全量課金で計上(§4.2)
5. **Artifact Registryの$0.10/GiB単価**: 0.5GiB無料は公式スニペットで確認、超過単価は第三者複数一致(§4.6)
6. **Cloud Runの最小構成サイズ**: 1vCPU/512MiBは仮置き。コンテナの実メモリ使用量(backend実測)で差し替える。min-instancesの挙動(コールドスタート時間)は10の非機能試験で実測が必要
7. **Cloud Scheduler**: 60秒周期のexpiry_sweeper・JST 0時のリセットジョブの起動基盤。ジョブ3本程度なら無料枠内の見込みだが、本試算では$0置きしたのみで単価確認はしていない
8. **静的コンテンツ(SPA)の配信先**: prototype/の配信をCloud Runから出すか別基盤(Cloud Storage等)にするかで下り量が変わる(§4.6の積算はAPI中心の仮定)
9. **アカウント側の前提(本試算では仮定しない)**: 請求主体(法人/個人)と請求通貨・新規アカウントの$300無料トライアル適用可否(Firebaseページに「If eligible, get $300 in free credit」の記載あり)・組織(ワークスペース)管理の有無・pgvectorのCloud SQL内バージョン固定方法(PG16での正確な対応バージョン表)・db-g1-small採用時の「本番同環境」要件との整合(§4.2)
10. **外部SDKの実装確認**: Cloud SQL(Pgvector・PostGIS)やPub/Sub実サービスへの接続は、実装時にcontext7での一次確認(2026-09-29のユーザー指示)を別途行う
