## 第I部 なぜLATCHを作るのか

### 1. コンセプト — 探す代わりに、Intentを置いて待つ

「今夜、誰かと軽く飲みたい」。この意思を持った人が、今のサービスでやることは検索して、比較して、連絡して、調整して、ようやく成立させることだ。LATCHはこの動線を前提としない。ユーザーは条件付きの意思をLATCHに置いて、あとは待つ。

> Intentを置く → 待つ → 条件一致 → 提案 → 双方承認 → 成立

留意しておきたいのは、LATCHが扱うのが人そのものの相性ではないことだ。特定の時間・場所・条件・文脈において、2つの意思が成立し得るかどうかである。この切り口が、マッチング設計からスコアリングまで本書のすべての部分に効いてくる(第27節の原則4)。

### 2. 解決する問題 — 中間帯の意思を拾うコストが高すぎる

対象となる意思には共通の形がある。積極的なYESではないが、条件次第でYESになる、という中間帯だ。

> 誰か誘うほどでもない。でも条件が合えば飲みに行きたい。
> わざわざ募集するほどではない。3人以上集まるなら行きたい。

本書の見立てでは、既存サービスはこの中間帯を拾えない。拾おうとすると、ユーザー自身が動くしかない。検索し、相手に当たりをつけ、募集文を書き、日程を調整し、空き状況を確認し、価格を監視し、うまくいかなければ再検索する。これらはすべて目的ではなく、条件の一致する相手・機会を探すためのコストである。目的は飲みに行くことのほうにある。

この探索コストを可能な限りゼロに近づけるのがLATCHだ。「条件が合えばやりたい」という意思だけを預けておけば、成立時にだけ通知が来る状態を作る。預けられる意思の例は次のとおりだ。

- 今夜、天文館で2〜4人なら飲みに行ってもいい
- 年収1,000万円以上なら転職を考える
- この車が190万円以上なら売ってもいい
- 土曜夜なら食事に行ける
- 4人集まるなら参加したい

このときLATCHの価値は、検索・募集・「誰に声をかけるか」という判断からユーザーを解放することにある。条件の合わない相手との不要なコミュニケーションも、最初から発生させない。一番大きな効用は、本人も具体化していない「YESになり得る機会」まで含めて、潜在需要と潜在供給を市場化できることだ。

### 3. 対象ユーザー

主要な対象は「強く探すほどではないが、条件が合えば行動したい」ユーザーである。もう一つの典型は次のような心理だ。

> 今すぐ転職したいわけではない。
> でも条件が良ければ話は聞きたい。

LATCHの設計が主に対象とするのは、この中間帯の意思だ。

### 4. MVPで検証する仮説

MVPは次の5仮説の検証装置である。いずれも成功指標(第23節)から観測できる。

1. ユーザーは「誰かを探す」より、Intentだけ登録して待つ体験を便利と感じる
2. 完全一致ではなくても、意味的に成立する提案を受け入れる
3. 双方YESの予測は、Hard Constraint + Semantic Retrieval + Jev(第12節で定義する判定エンジン。v0.5から第一候補はSystem Oneモデル・生成LLMはフォールバック)で一定精度まで実現できる
4. LATCH候補の通知頻度を抑えれば、通常のSNS通知より高い反応率を得られる
5. 「検索しない・募集しない」という行動様式自体が継続利用につながる

5仮説それぞれの主指標と支持判定基準は、09 v0.3第2.3節で運用開始前に事前固定した。仮説1・5はオンボーディング直後と4週後のアンケート(定量設問+定性設問)を測定に加え、仮説2は提案時点の語彙一致(lexical)/意味近接(semantic)セグメント別YES率で判定する。判定基準の値を事前に固定することで、運用後の恣意的な基準選択を防ぐ。

## 第II部 扱うものとスコープ

### 5. 基本用語

Intentは、ユーザーがLATCHに預ける「条件付きの意思」を指す。冒頭から使ってきた語で、具体例は次のようなものだ。

```text
今日20時以降、
天文館周辺で、
2〜4人、
予算5,000円以内なら、
軽く飲みに行きたい。
```

その条件は2種類に分ける。絶対に満たすべきものをHard Constraintと呼ぶ。日時、場所、予算上限、人数、カテゴリ、ブロック関係が該当し、原則としてAIに判定させず、コードとDBで厳密に落とす。公開設定(visibility、第9節)はHard Constraintに含めない(02 v0.3 D-03再決定)。判定対象ではなく、提案時点で相手へ開示する情報の範囲を決めるユーザー設定として扱う。一方、多少のズレを許容できる意味的・文脈的な条件はSoft Constraintと呼ぶ。「軽く飲みたい」「騒がしくない店がいい」「知らない人ばかりは嫌」「肉系なら何でもいい」のような条件で、EmbeddingやLLMで意味的に評価する。NG条件は判定データの有無で所属が分かれる(02 D-04)。システムが判定できるもの(ブロック)はHard ConstraintとしてLayer 1で除外し、会社関係者の除外のように判定に必要なデータをシステムが持たないものはSoft Constraint側へ降格して条件リストに注意表示を出したうえで、Jevの意味判定に回す。

一次絞り込みを通過して詳細判定に回るIntentをCandidateと呼ぶ。CandidateのうちIntentペア単位のものはMatchCandidateと呼び、データモデルは第17節とする。ユーザーへ提示された候補はLATCH候補と呼ぶ。そして2つ以上のIntentについて、双方または参加者全員の条件が一定水準以上で成立した状態を、プロダクトと同じ名前でLATCHと呼ぶ。Intent同士が実際に成立する可能性を内部的に表すスコアがLATCH Scoreだ。人間同士の恒久的な相性ではなく、その時点・その文脈におけるIntent Compatibilityを示す(算出方法は第13節)。

最後にEvent。Intentの新規作成・更新・削除・期限切れ、時刻の到来、店舗の価格変更や空席発生、在庫変更、外部サービス上の状態変更。こうした再評価を発生させる状態変化を指す。このうちMVPで発生するのは、Intentの作成・更新・削除・期限切れと指定時刻の到来の内部由来5種である(Embeddingの完了を知らせる派生イベントembedding_completedは06 v0.3第9節が定める内部イベントであり、第11節の第2段トリガーとして機能する)。外部データに依存するEventは、外部連携を実装する将来バージョンで追加する(第7節)。

### 6. ユースケース — MVPは「今〜数日以内の食事・飲み」に絞る

MVPが扱うのは、今から数日以内の食事・飲み・軽いアクティビティに限定する。「今日誰かと飲みたい」「3人以上なら焼肉に行きたい」「20時以降なら天文館で食事可能」といった用途だ(「友人限定なら参加したい」は、v0.4で友人関係(friendships)が将来版へ移った(D-03再決定、02 v0.3)ため、MVP対象から外した)。

この絞り込みには理由がある。Intentの寿命が短く、検証サイクルが速い。YES / NOの正解データも取得しやすい。この領域は時間・場所・人数などのHard Constraintも明確で、「置いて待つ」というLATCH独自の体験が一番理解しやすい用途でもある。

コンセプト自体はもっと広い。転職、恋愛・出会い、中古品売買、不動産、旅行、レストラン空席、イベント参加、スポーツ、B2B商談、求人、外注、共同購入、値下げ条件付き購入まで広がり得るが、MVPでは実装しない。MVPの初期リリースは単一エリア(駅周辺3km相当の選定基準)に集中したクローズドベータとし、候補が発生する密度の下限を同一時間Bucket×同一カテゴリ15件、Phase 1の目標をピークActive 100件・日次新規Intent作成150件以上とする(11 D-22)。

### 7. MVP機能範囲

**実装する**

- アカウント / プロフィール(Google・Appleのソーシャルログイン、04 D-21)
- 自然言語Intent入力と構造化
- 下書き保存 — status=draftでサーバー保存し、後から再開して「預ける」(active化)する経路(02 v0.3。プロトタイプの「下書き保存」ボタンの実装を踏まえる。draftはマッチング対象外。05 v0.4)
- Active Intent管理
- Hard Constraint Filter / Vector Search / Cheap Judge / Jev判定
- 1対1 LATCH、および最大4人の簡易グループLATCH
- YES / NO回答と双方承認
- 通知 / LATCH成立後チャット / 期限管理
- ブロック / 通報
- 年齢制限(利用登録は18歳以上、飲酒を含むIntentは20歳未満作成不可。08 D-10の判断で追加、02 v0.2)
- 基本Analytics
- ユーザーあたりのIntent作成数・更新頻度の上限(Jevコスト保護の一部。受け入れ条件には含めない)

**実装しない**

決済、店舗予約、自動購入、外部店舗在庫連携、複雑なRecommendation Feed、広告、完全自動交渉に加え、第6節に挙げた将来領域(転職・恋愛・中古品売買ほか)。

## 第III部 ユーザー体験

### 8. ユーザーフロー

Intent登録は自然言語から始まる。

```text
自然言語でIntent入力
  ↓ Intent Parserで構造化
  ↓ ユーザーが確認・修正
  ↓ Intent保存 → Match Event発火
```

保存されたIntentは、対応するEventが起きるまで待機する。マッチング内部の処理は第IV部で扱う。条件が揃い、双方が承認すると成立する。

```text
提案通知
  ↓ ユーザーA: YES
  ↓ ユーザーB: YES
  ↓ 必要人数を満たす
LATCH成立 → チャット / 集合情報 / 次アクションを解放
```

不成立で終わる経路も明示しておく。次のいずれかが起きた時点で、提案を閉じる。

- 片方がNOと回答した
- 回答期限が切れた
- Intent期限が切れた
- Hard Constraintが変化した
- 必要人数が揃わなかった
- ブロックに該当した(公開範囲違反による不成立経路は、友人関係の将来版化(v0.4、D-03再決定)によりMVPから外した)
- 他のLATCH成立による競合が起きた
- 参加Intentが削除された(成立済みLATCHの解散を含む、08 v0.3第2.5節)

回答期限は提案ごとに設ける期限で、Intent自体の期限(expires_at)とは別物だ。導出規則は min( max(通知時刻+15分, min(通知時刻+2時間, 対象開始時刻−60分)), 参加Intentのexpires_atの最小値)とする。15分の下限は回答期限が「通知してすぐ締切」にならないための線であり、Intent期限とminを最後に取ることで、回答期限がIntent期限を超えることはない(03 v0.3 D-05)。対象時刻まで75分を切って生成された提案は、通知自体を行わない。提案通知は双方(グループでは必要人数全員)へ同時に行う(03 D-20)。

同一のIntentが、同時に複数の成立済みLATCHに属することはない。あるIntentのLATCHが成立した時点で、そのIntentを含む回答待ちの提案は、すべて閉じる。提案側から見れば、これが不成立経路でいう「他のLATCH成立による競合」である。

ブロックはLATCH成立後も即時に適用する。進行中の提案はcancelledで閉じ、成立済みLATCHのチャットは読み取り専用化して新規送信を不可にする。解放済み情報の回収は行わない(08 D-23)。

成立済みLATCHの参加Intentが削除された場合も、当該LATCHは解散(cancelled)とする。残る参加Intentは、Intent期限を経過していなければactiveへ復帰して再提案の対象となり、経過済みならexpiredとする(08 v0.3第2.5節・06 v0.3第6節)。参加Intentが「成立済み」のまま凍結し、以後の提案対象から外れ続ける状態を作らない。

### 9. Intent入力 — 自然言語を構造化して確認する

入力は自然言語を基本とする。フォーム入力を主UIにはしない。

```text
今日20時以降、天文館で2〜4人くらいなら軽く飲みたい。
予算は5000円くらい。会社関係の人は避けたい。
```

Intent Parserはこの文章から最低限、次のフィールドを抽出する。

```yaml
intent_id:
user_id:

category:
  primary:
  secondary:

time:
  start:
  end:
  flexibility:

location:
  center:
  radius:
  flexibility:

budget:
  min:
  max:
  currency:

participants:
  min:
  max:

visibility: # 公開設定。hidden_until_match / summary_only の2値から選択(02 v0.3 D-03。Parserは出力せず確認モーダルで選択)

hard_constraints: []
soft_constraints: []
negative_constraints: []

notification_level: # お知らせ設定。proposals_only / nearby_also / muted(03 v0.4。Parserは出力せず預け方パネルで選択)

expires_at:

raw_text: # 最大300字(UIは入力欄で遮断し、文字数カウンタを表示する。03 v0.4)
```

構造化した内容は、保存前に必ずユーザーへ見せる。修正もできる。AIの解釈をブラックボックスにしない。前提は02〜07で確定した。visibilityは公開設定としてhidden_until_match(条件一致までは非公開)/ summary_only(候補にだけ概要を表示)の2値とし、初期値はhidden_until_matchである(02 v0.3 D-03再決定。UI文言は「公開設定」)。友人関係(friendships)とfriends_onlyはv0.4で将来版へ移した。会社関係者の除外のように判定データを欠くNG条件はSoft Constraint側へ降格し、条件リストに「確実には除外できない」旨の注意表示を出す(02 D-04)。フィールドはcategory・time.start・locationの3つが必須で、未指定の場合のデフォルトは time.end / expires_at が time.start+3時間、participantsがmin=2 / max=2、location半径が1,000m、budgetは制約なし、visibilityは確認モーダルでの明示選択(初期値hidden_until_match)、notification_levelは預け方パネルでの選択(初期値proposals_only)となる(03 v0.4 D-19)。預け方パネルの必須要素には有効期限を含め、4つの選択肢(今夜 23:30 / 明日 12:00 / 明日 23:30 / 3日後まで。既定はtime.start+3時間に最も近い値)から選ぶ。明示指定値は過去・現在+7日超を保存時に拒否する(03 v0.4第3節・05 v0.4)。下書き保存(status=draft)を選ぶとraw_textのみで保存し、必須3フィールドの検証とMatch Eventの発行は「預ける」(active化)まで行わない(05 v0.4)。「5,000円くらい」のような曖昧表現は丸め規則で確定値へ変換し、Parserが失敗したときは構造化フォームへのフォールバックを用意する(07 D-17)。飲酒の関与はParserがalcohol_involvedフラグとして判定し、飲酒を含むIntentの作成可否の検証に使う(08 D-10)。

```text
LATCHは以下の条件として理解しました。(UI文言は「LATCHが読み取った条件」、03 v0.4第10節)

時間: 今日 20:00以降
場所: 天文館
人数: 2〜4人
予算: ひとり5,000円まで
目的: 軽く飲む
NG: 会社関係者
  ※この条件は確実には除外できません。参考条件として扱います(02 D-04の注意表示)
```

### 10. 通知と画面

LATCH Score(第13節)が設定閾値を超えたら通知する。MVP初期値はv0.5まで0.80としたが、G2日本語評価の実測(520ペアで閾値0.80超過が1件のみ)によりv0.6で0.60へ改める。実運用でCalibrationする。この値の妥当性の検証手順は09が確定した(Offline 3閾値比較→A/B Test、値の見直しは運用データ後。D-01)。

通知はプッシュ通知とアプリ内通知(topbarの「お知らせ」popover+未読ドット。プロトタイプのUI文言に固定)の併用とする。プッシュ通知の本文は汎用文に限る。

```text
【プッシュ通知(本文は汎用文。条件サマリを含めない)】
LATCH候補があります。
詳細はアプリでご確認ください。

【アプリ内通知(お知らせ。visibility=summary_onlyの提案。条件サマリを表示)】
今夜 20:00〜
天文館 / 3人
焼肉 / 予算上限5,000円
あなたの条件との一致度が高い候補です。

【アプリ内通知(hidden_until_matchの提案。条件サマリを含めない、v0.4)】
条件が合う候補があります。
一致度が高い候補です。今夜中にご回答ください。
```

プッシュはロック画面・通知履歴・ウィジェット・読み上げ等のOS経路を通じて端末の持ち主以外に表示され得るため、成立前の意思をこの経路に載せない。条件サマリの表示はsummary_onlyの提案に限り、アプリ内通知と提案画面のみで行う(プロダクトオーナー決定、03 v0.4第4節・08 v0.4第2.6節)。hidden_until_matchの提案では条件サマリを送らず、成立時に解放する(02 v0.3 D-03)。通知のタップは提案詳細画面への遷移とし、回答は提案詳細画面の3択([参加する][今回は見送る][辞退する])からのみ行う。バナー上の直接回答はしない(03 v0.4第4節・FR-46)。

成立前の取り扱いにも取り決めが要る。LATCH成立前は、必要以上の個人情報を相互公開しない。双方または必要参加人数がYES(承認)した時点で、詳細情報を解放する(プロトタイプのプライバシーノート「相手の名前やプロフィールは、全員が承認するまで表示しません。」)。

Intent入力(作成)画面を起点とし、残りの要素はtopbarの「Intent N件」カウントと「お知らせ」popoverから到達する領域として実装する(03 v0.4第2節・第10節)。すなわち、Intent入力、Active Intent一覧(Intent N件から到達)、LATCH候補、成立済みLATCH、お知らせの5要素が最低限の構成である。状態は2系統ある。

```text
Intent: draft / active / paused / matched / expired / cancelled
LATCH:  candidate / proposed / partial_accept / matched / rejected /
        expired / cancelled / completed
```

状態の意味と主な遷移は次のとおり定める。Intentは、「預ける」操作で構造化内容を確認して保存した時点でactiveになる(直後にMatch Eventが発火する)。入力途中の内容は下書き保存(status=draft)で保存でき、再開して「預ける」とactive化する(検証はactive化時に通す。02 v0.3・05 v0.4)。以後の遷移は次のとおり。

- LATCHを成立させた時点で matched
- expires_atを過ぎた時点で expired
- ユーザーが停止・削除した時点で cancelled

pausedは一時停止、cancelledは打ち切りを指す。

LATCHは、パイプラインが候補を生成した時点でcandidate、LATCH Scoreが閾値を超えてユーザーへ通知した時点でproposedとなる。ユーザーに提示するLATCHはproposed以降であり、閾値未満のcandidateはシステム内部のデータとして扱う。ただし、そのIntentのお知らせ設定がnearby_also(近い候補も知らせる)の場合に限り、閾値未満の候補の**発生**の通知のみを行う。この通知には条件サマリ・一致度・相手情報を含めない(candidateの詳細を画面に出さない規定は維持、03 v0.4第2節・第3節)。参加者の一部だけがYESの状態がpartial_acceptで、必要人数全員のYESが揃った時点でmatchedになる。NOの回答でrejected、回答期限またはIntent期限の切れでexpired、ブロック・他のLATCH成立による競合でcancelledとなる。成立したLATCHは、対象時刻の経過をもってcompletedとする。

[今回は見送る]の扱いは確定した。見送りは提案を閉じる点でNOと同じ遷移(rejected)だが「この提案の辞退」でありIntentはactiveを維持し、回答種別として区別保持する。NO(辞退)は組み合わせへの拒否であり、同一Intent組み合わせへの再提案を当該Intentの期限まで行わない。見送り後の再提案は、見送りから min(24時間, 対象開始時刻までの残時間の半分) の経過と、再評価でスコアが変化していることまたはどちらかのIntent更新による新候補であることの両方を満たす場合に限る(03 D-07。スコア変化の判定手順は06 v0.3第10節)。

通知頻度の上限は1ユーザーあたり日6件・1Intentあたり同時進行3件とし、超過分は破棄せず保留する。nearby_also(近い候補も知らせる)の存在通知も日次上限(日6件/ユーザー)に含める(同時進行上限(3件)はproposed数の上限のため、candidateのままの存在通知には適用しない。v0.4)。保留はLATCHデータ上のcandidate状態として保持し、期限が来た保留候補はexpiredとして閉じる。キューは対象時刻の近い順に提示し、提示時に回答期限を再計算する(03 D-08・06 v0.3第10節)。保留から期限切れになった割合(保留→expired率)を計測し、保留が実質の破棄になっていないことを監視する(09 v0.3第2.2節)。通知手段はプッシュ通知とアプリ内通知(お知らせ)の併用で、許可を得られないユーザーにはアプリ内通知で到達する(03 D-18)。Intent単位のお知らせ設定(notification_level、v0.4)で提案通知の範囲を選択できる(03 v0.4第3節)。不成立時に相手へ開示するのは「この提案は成立しませんでした」の一文のみで、相手の回答種別と不成立の理由は開示しない(03 D-20)。

## 第IV部 マッチングシステム

この部で、方針、絞り込みの段階、Jevの扱い、Calibration、イベント駆動の処理系を定める。

### 11. 基本方針 — 総当たりをやめ、イベント駆動で計算量を抑える

全Intent同士の総当たり比較は行わない。Intent数をNとすると全組み合わせはO(N²)となり、スケールしない。LATCHのかわりの構造は、イベント駆動+候補検索+段階的評価である。

トリガーとなるMatch Eventの種別は、第5節の定義に従う。MVPで実装するのは内部由来の5種(作成・更新・削除・期限切れ、指定時刻の到来)で、外部由来のEventは、外部連携を実装する将来バージョンで追加する(第7節)。

EmbeddingはIntentの作成・更新後に非同期で行う。よってマッチングパイプラインは2段に分かれる — 作成・更新EventはEmbedding要求のキックまでを第1段とし、Embeddingの完了(派生イベントembedding_completed)がCandidate Retrieval以降(Layer 1〜5)の第2段トリガーとなる。削除・期限切れEventはLayerを経ずに即時処理する(06 v0.3第1節・第9節)。

比較の向きにも注意が要る。起点とするのは新規または更新されたIntentで、そこから既存Intentインデックスへ関連候補を引きに行く。新規Intent同士だけを比べて済ませることはない。たとえば、

```text
既存: A = 今夜、天文館で焼肉なら行きたい
新規: B = 今夜20時以降、天文館で肉系なら行ける

B登録 → 既存Intent DBを検索 → Aが候補としてヒット
      → A ↔ Bを詳細評価 → LATCH成立
```

理想の計算量は、イベント数をE、1イベントあたり詳細評価対象数をKとして O(E×K) に近い構造である。Kには上限を設け、MVPでは Vector検索 K_v=50、Cheap Judge判定 K_c=20、Jev判定 K_j=8、グループ候補Pool=15と確定した(06 D-24)。各上限はその層から次層へ渡す出力数の上限とし、切り詰めは各層のスコア上位(同点はintent_id昇順)で決定的に行う。K_jのみ回数ベース(1イベント処理あたりのJev実行回数)であり、1対1由来の候補に最低4回を保証し、残りをグループ由来のペアに割り当てる(グループ由来がなければ1対1へ繰り上げ)。グループ集合は構成ペアごとに1回を数え、全ペアの判定が揃わない集合は次の再評価で完結するまで提案化しない(06 v0.3第5節)。

### 12. 候補は5段階で絞る

100万Intentが存在する場合の絞り込みイメージを先に示す。

```text
1,000,000
    ↓ 地域            3,000
    ↓ 時間              700
    ↓ カテゴリ          180
    ↓ Hard Constraint    60
    ↓ Vector Search      20
    ↓ Cheap Judge         5
    ↓ Jev                 2
```

図のうち地域・時間・カテゴリ・Hard Constraintの4行がLayer 1の仕事、Vector SearchがLayer 2、Cheap JudgeがLayer 3、JevがLayer 4に当たる。図中の件数は規模感を示す例であり、各段階の処理対象の上限は第11節のK上限に従う。各層の担当は次のとおり。

Layer 1 Hard Filter。SQLとRDBMSのIndex、Geo / Time Index、Rule Engineで、時間・距離・予算・人数・ブロック・カテゴリ・年齢(飲酒)を判定する(v0.4で公開範囲を判定対象から除外。公開設定(visibility)の開示範囲の制御はproposal生成の分岐(05 v0.4)へ移した。02 v0.3 D-03再決定)。飲酒を含むIntentは20歳以上のユーザー同士の間でのみ候補になる(08 D-10)。同一ユーザーのIntent同士も本層で除外する(自己ペアの候補化・自己成立を構造的に遮断する。06 v0.3第2節)。絶対NG条件のうち判定データを欠くものは本層で除外せず、Soft Constraint側へ降格する(02 D-04)。出力はpass / failのみ。

Layer 2 Candidate Retrieval。IntentをEmbeddingしてVector DBに置き、ANN Searchで意味的に近いIntentを高速に引く。「焼肉に行きたい」と「肉系なら何でもいい」を候補として近づけるのがこの層の役割だ。Embedding未完了(または失敗)のIntentは、完了までLayer 1〜2の生成元にも対象にもならない(06 v0.3第3節)。

Layer 3 Cheap Judge。Jevに渡す前に、明らかに成立しにくい候補を低コストで除外する。小型LLM、軽量分類器、ルール、埋め込み類似度、将来の独自モデルが実装候補。

Layer 4 Jev。曖昧な自然言語条件について「成立しそうか」を構造的に判定する判定エンジンで、本プロジェクトではJevと呼ぶ(v0.5: 第一候補はテキスト生成を行わず確率を返すSystem Oneモデル「TypeSafe Jev」であり、429・529・timeout時は生成LLM(Anthropic系)へフォールバックする。04 D-14・07 v0.5第4節)。人間なら「この2つはたぶん合う」と判断する最後の意味判定を担い、全件検索には使わない。

Layer 5 LATCH Engine。Jevの結果、Hard Constraint、過去データ等を統合し、最終的な成立可能性を算出する。

どの層でも、AIを全件探索には使わない。99%以上は検索・Index・DBで削る(原則1)。なおこのファネルはスケール後のイメージで、初期のIntentプールが薄い期間は候補自体が発生しにくい(初期エリアとIntent密度の確定値は11 D-22)。

### 13. Jev利用方針 — 単一スコアを出させず、原子的判断に分解する

Jevに「0〜100点」の単一スコアを直接出させない。判定を原子的な問いに分解する。v0.5では第一候補のTypeSafe Jev(System Oneモデル)のインターフェースがこの方針と合致する — 原子的な問いをSystem One APIの質問群(noul=YES確率・score=順序尺度)として定義し、1リクエストで並列評価させる(07 v0.5第4節)。

```text
would_a_accept_b
would_b_accept_a
purpose_fit
mood_fit
timing_fit
social_fit
latent_yes
```

LATCHでは双方がYESになることが成立条件のため、A → B と B → A を別々に評価する。

```text
P(A accepts B) = 0.91
P(B accepts A) = 0.86
```

基本スコアは弱い側を基準に取る。

```text
MutualScore = min(P(A accepts B), P(B accepts A))
```

平均値を使わないのは、片方だけ高いケースを高評価したくないためだ。A → B = 0.99、B → A = 0.45 のとき平均は0.72だが、この提案が成立する見込みは0.45に近い。LATCH Scoreの初期案はこれを踏まえて次の形とする。

```text
L = H × MutualScore × C

H: Hard Constraint(成立なら1、不成立なら0)
MutualScore: 双方向成立確率
C: Calibration係数
```

MVPでは、P(A accepts B) をwould_a_accept_bの判定値、P(B accepts A) をwould_b_accept_aの判定値とする。purpose_fit、mood_fit、timing_fit、social_fit、latent_yesの5軸は、Jevがこれらの確率を判断するための内部の材料であり、MutualScoreに直接は寄与させない。Hは判定時点のHard Constraintの成立を表し、Layer 1通過後に条件が変わっていた場合の再検証としても機能する。Cの値域は(0, 1]とし、Calibrationデータが蓄積されるまでの初期値は1である。したがってLの値域は[0, 1]となる。

原子判断の中で特に重要なのがlatent_yesである。「この提案を提示された場合、明示的に希望していなくても、本人のIntentの範囲内でYESと言う可能性があるか」を問うものだ。「焼肉に行きたい」と「今日は肉系ならどこでもいい」のような、単語一致を超えた潜在的な成立可能性を評価する。

Jevの入力は構造化データからの正規化テキストに限り、raw_text(入力原文)は送信経路に入らない(v0.5: 第一候補のTypeSafe Jevでは、stateに正規化テキスト2件を載せ、7軸をnoul(YES確率)・score(順序尺度)の質問群として送る。07 v0.5第4節)。第一候補のSystem Oneモデルは出力スキーマを保証するため再試行は設けず、429・529・timeoutの際は生成LLMへフォールバックし、フォールバックも失敗すれば候補は保留する(07 v0.5第1節・第4節)。判定結果は数値のみを保存し、自由文(reason)は生成しない — System Oneモデルはテキストを生成せず、フォールバックLLM時も一貫して無しとする(第21節・07 v0.5第4節)。

### 14. 人間の行動を正解データにするCalibration

Jevの予測が当たっていたかは、提案への回答とその後の行動で検証する。保存するのは次の結果だ。

```text
Intent A / Intent B
予測スコア / 提案内容
Aの回答 / Bの回答
実際に成立したか / 実際に参加したか / キャンセルしたか
```

保存した結果をつなげると、Human Intent → Prediction → Proposal → Actual YES / NO → Actual Action という流れができる。これはモデルの予測値より信頼できるGround Truthであり、LATCHの独自データ資産そのものだ。Jevの予測値と実際の人間行動との差を、このデータで継続的にCalibrationする。結果レコードはcalibration_recordsテーブルとして形式化した(05。構造とデータフローは07第6節)。「実際に参加したか」「キャンセルしたか」は、成立LATCHのcompleted遷移時に1問の自己申告(期限3日・スキップ可、無回答は欠測)で収集する(09 D-09)。削除・退会時はID系を除去した統計値へ匿名化して保持する(08 D-13)。

一定量のデータが蓄積された後は、LATCH専用Ranking Model、Acceptance Prediction、Jev依存度の低減、Personal Preference Model、Group Matching Modelを検討する。

### 15. グループマッチ

LATCHは最終的に1対1だけでなく、複数人Intentの集合を成立させる。

```text
A: 飲みに行きたい
B: 飲みに行きたい
C: ご飯なら行きたい
D: 焼肉なら行きたい
E: 4人以上なら行きたい

可能な集合の例: A+B / A+C / A+B+D / A+B+C+D
(A+B+C+D+Eは5人となりMVPの上限を超えるため対象外)
```

ただし全組み合わせ探索は組み合わせの数が指数関数的に増大するため行わない。候補Poolを小さくしてからGroup Searchする。MVPでは最大4人、候補Poolは最大15人(06 D-24)、同一地域・時間帯・カテゴリ内に限定する。

participantsのmin / maxは、提案者自身を含む人数とする。たとえば「4人以上なら行きたい」Intentを持つユーザーは、自分を含めて4人以上の集合でのみ成立する。成立確定条件は06 D-06で確定した。必要人数は集合サイズ|S|と一致する(集合内全員のYES)。部分成立(4人提案の3人YESでの成立)は行わない。回答期限時に必要人数が揃わなければexpiredで閉じる。複数の成立可能集合がある場合は集約スコア降順(同点は集合サイズの小さい順、さらにintent_id辞書順)で最上位の1集合のみを通知し、その提案が閉じた後に次を評価する。集約スコアは集合内全ペアのMutualScoreの最小値を採り、通知閾値は1対1と同じ0.60(v0.6)を適用する。3人以上の候補はgroup_candidatesテーブル(05)で保持する。

### 16. イベント駆動処理(Queue・重複防止・時間Bucket)

Match Eventはキュー経由で非同期に処理する。

```text
Intent API → DB保存 → Event発行
  → Message Queue → Matching Worker
  → Candidate Retrieval → Jev Worker → LATCH Engine
```

Intent更新が短時間に複数回発生することへの備えとして、debounce、idempotency key、version numberを用い、不要な再計算を防ぐ。Intentは更新ごとにversionを持ち、古いversionに対するMatch Eventは破棄可能とする。debounceは作成Eventには適用せず(即時処理し、初回提案のレイテンシを守る)、更新Eventのみ10秒窓で統合して最新versionのみ処理する(06 v0.3第9節)。Eventの冪等化は match_events のUNIQUE制約(05 v0.3)がDBレベルで保証する。

再評価の起点がEventのみに偏ると、欠落した再評価が恒久に回収されない。よって2つの補償を設ける(06 v0.3第9節)。resume時はversion+1の再評価Eventを発行し、期限前catch-upスキャンが expires_atまで2時間以内かつ直近評価から30分以上経過のIntentを60秒周期で回収する。これにより、開始時刻のBucket経過後のresume、Bucket到来Eventの遅延・欠落のいずれでも、再評価・提案が発生し得る状態を維持する。

処理の失敗にも方針を定める。Match Eventの処理に失敗した場合は上限回数まで再試行し、再試行しても失敗するイベントは失敗理由を保持したうえで隔離する。Jev・Embedding・Intent Parserなどの外部LLM呼び出しに失敗した候補は、判定を保留して提案しない。誤った提案を提示するよりも、提示を見送ることを優先する。

時間経由の再評価でも、全Intentを常時スキャンしない。時間帯Bucket(18:00-18:30、18:30-19:00、…)ごとにIntentを整理し、到来したBucketのIntentだけを再評価対象にする。

```text
20:00
  ↓ 20:00に有効化 / 条件変化するIntentを取得
  ↓ Candidate Retrieval
```

同一評価世代(どちらのIntentも更新されていないペア)の再評価では、Jevを再実行せず既存の判定結果(jev_result)を再利用し、Layer 1の再検証のみを行う。あわせてコスト保護として、1Intentあたり日次40回・1ユーザーあたり日次120回の詳細評価(Jev実行)予算と、同一Intentの再評価を直近評価から30分空ける頻度制限を設ける。予算超過はJevの回数上限到達と同じ縮退(Jev未判定で保留)であり、悪用ユーザーがレート制限の範囲内で日次上限を枯渇させ、全ユーザーの提案停止に持ち込むことを防ぐ(06 v0.3第5節)。

## 第V部 品質・プライバシー・安全

### 20. 非機能要件

性能のMVP目標は次のとおり。

```text
Intent保存: p95 500ms以下
Intent Parser構造化プレビュー: p95 3秒以下(p99 8秒、非機能試験の対象、07 D-17)
Candidate Retrieval: p95 1秒以下
初期LATCH判定: p95 10秒以下
通知: 判定後5秒以内
全件総当たり: 禁止
```

初期LATCH判定のp95 10秒は、層別予算配分(Embedding ≤2秒 / Layer 1〜3 ≤1秒 / Jev ≤5秒 / Layer 5+通知 ≤2秒)と計測起点(active化の保存コミットから通知送信記録、初回投入Event(active作成またはdraft→active化)経由の初回提案を対象)を06 v0.4第1節で確定した。外部LLM呼び出しのtimeoutは、Intent Parserが10秒(再試行なし・即フォールバック、07 D-17)、Embeddingが2秒(再試行なし。失敗はバックフィルで回収)、Jevが6秒(再試行は設けない。第一候補のTypeSafe Jevは出力スキーマを保証するため再試行の規定は廃止し、429・529・timeout時はフォールバックLLMへ切替え、フォールバックも失敗すれば縮退へ)とする(07 v0.5第1節。v0.5で再試行規定を再設計)。

Matching Workerは水平スケール可能とし、Jev判定数には上限を設ける。可用性の目標は、計画停止を除くAPIリクエスト成功率99.5%以上とする。

コスト面の保護も設ける。Jev実行回数の上限は日次30,000回・月次600,000回とし、80%到達でalertを発報(Event源流上位ユーザーのJev消費レポートを添付)、上限到達時はJev実行をスキップして候補を「Jev未判定」として保留する(04 D-16)。月次上限のリセットは暦月初のJST 0時とする。実行回数への計上はv0.5で読み替えた — 実際のAPI呼び出し(第一候補のTypeSafe Jevと、429・529・timeout時のフォールバックLLM切替呼び出し)をすべて計上する(04 v0.5 D-16。旧「Jev出力検証失敗の再試行1回の計上」(04 v0.3 D-16)は、07 v0.5で再試行規定が廃止されたことに伴う読み替え)。日次・月次上限に加え、第16節のJev予算(1Intent日次40回・1ユーザー日次120回)と頻度制限(30分)、API Layerのレート制限(08第5.4節)を合わせた三層の保護とする。LLM API障害時と上限到達時の縮退運転も確定した。いずれの場合も提案は見送り、候補は保留とし、Cheap Judgeまでの結果では提案しない。誤った提案を提示するよりも、提示を見送ることを優先する方針(第16節)を貫く(06 D-15)。

Intent DBとVector DBは定期的にバックアップし、バックアップからの復旧でVector DBを再構築できること。

時刻の参照はすべてClockインターフェース経由とし、適用範囲はAPIの期限判定・期限切れバッチ・30分Bucket・debounce窓・JST 0時のリセットジョブとRedisカウンタを含む(04 v0.3第5節・10 v0.2第1節)。

Observabilityで最低限計測するのは次の3群。

- パイプライン: Event Queue lag / Candidate数 / Hard Filter通過率 / Vector Retrieval件数
- Jev: 実行回数 / latency / cost
- 提案と行動: LATCH Score分布 / 通知数 / YES率 / Mutual Latch Rate / キャンセル率

この3群に加え、アクセス系基本計測(セッション開始イベントによるDAU・再来訪)を計測範囲に含める(04 v0.3。POST /v1/sessions)。Intent作成率・継続率の分母である(09第2.2節)。

### 21. プライバシー — 潜在意思を扱う以上、通常のSNSより厳しく

LATCHは「まだ誰にも言っていない意思」を扱う。プライバシーは個別機能の前に置く前提で、通常のSNSより厳しい線引きを最初から引いて設計する。

- Intentは原則非公開とし、マッチング処理のみで利用する
- LATCH成立前に、相手へIntent全文を公開しない
- ユーザーが削除でき、Intentごとに公開設定(hidden_until_match / summary_only)とお知らせ設定(proposals_only / nearby_also / muted)を選択できる(v0.4。03 v0.4)
- ブロック対象とは絶対にマッチさせない
- ユーザーによるIntent削除・退会時には、Intent本文、構造化データ、embedding(Vector DBを含む)、当該Intentを含むMatchCandidate・GroupCandidate(処理済みを含む)を削除する

表示の最小化も徹底する。ユーザーがIntent内部にセンシティブな条件を持っていても、相手に見せる情報は、成立判断に必要な最小限に留める。

```text
内部: 会社関係者以外で、天文館で、20時以降、3人程度なら飲みたい。
表示: 今夜20時以降 / 天文館 / 3人前後 / 軽い食事・飲み
```

センシティブな条件は内部判定にのみ使用する。表示の最小化はOS通知経路にも及ぶ — プッシュ通知の本文は汎用文とし、条件サマリはsummary_onlyの提案に限りアプリ内通知と提案画面に限る(第10節・08 v0.4第2.6節。hidden_until_matchでは条件サマリ自体を送らない、02 v0.3 D-03)。ロック画面・通知履歴・ウィジェット・読み上げで、成立前の意思が端末の持ち主以外に露出しない。

相手への位置表示は地域名(市区町村・駅・ランドマーク単位)のみとし、座標や距離の数値は表示しない。内部の中心点を約1kmのグリッドへ丸め、その代表点の地名を用いる。変換はセルフホストの地物データ(位置参照情報・OSM)による内部変換で行い、位置情報を外部サービスへ送信しない(08 D-11、04)。

相手への表示と同じ規則を、システム内部の出力にも適用する。ログ、計測、Analyticsの出力には、Intent原文(raw_text)、正確な位置、NG条件を含めない。

Intent Parser・Jev・EmbeddingのためにIntentデータを外部のAIサービスへ送信する場合、送信範囲は判定に必要な最小限(構造化データからの正規化テキスト)とし、raw_textを送信経路に入れない。送信先はJevがTypeSafe AI(api.typesafe.ai・米国、v0.5で明記)、ParserがAnthropic Claude API、EmbeddingがGoogle Gemini API(いずれも第一候補、T1 v0.2)であり、フォールバックLLM(Anthropic Claude API)への送信も同じ記録経路に載る。送信先と送信データの種別を記録し、問い合わせ時に開示できる状態を保つ。オンボーディングで送信先・最小限性・学習利用なしを明示して同意を取得する。プロバイダ契約には、入出力の学習利用禁止・保持期間の最小化・サブプロセッサの開示・データ所在地の明示・漏洩時の通知義務を含める。プロバイダは契約面とデータ取り扱いで足切りを行い、残った候補を機能・性能・コスト・可用性の順で選定する(足切り2条を含め計6条、04 D-14・08 D-14)。

判定結果の保存には個人由来の自由文を含めない(v0.5で確定: System Oneモデルの採用によりreasonを生成しない。フォールバックLLM時も一貫して無しとする)。match_candidates・group_candidatesは評価確定から30日で定期削除し、条件由来の判定値が30日を超えて存続しない構造を維持する(07 v0.5第4節・08 v0.5第2.5節)。

削除・退会時には、回答・行動履歴などCalibration用データをID系を除去した統計値として匿名化保持する(08 D-13)。匿名化は、時刻系の日単位丸め・proposal_snapshotの粒度低下(時間帯ビン化・地域は市区町村単位・二次カテゴリ除去)・母集団が小さい期間の月次バッチ生成(退会時の即時個別変換はしない)で強化し、小規模ベータでも再識別の経路を閉じる(08 v0.3 D-13)。

### 22. 安全要件

MVPの安全要件は、次の3群に整理できる。

- 相手からの防護: ブロック / 通報 / ミュート
- 公開の制御: 公開設定(開示範囲の選択。v0.4) / 年齢制限 / 位置情報の丸め / 正確な現在地の相手への非表示
- プラットフォームの防護: スパム検知 / Intent大量投稿制限 / 不適切コンテンツ検知 / なりすまし対策 / ユーザーあたりのIntent作成数・更新頻度の上限

このうち第25節のSafety受け入れ条件に対応するのは、ブロック、通報、正確な現在地の非公開、そして第21節で定めたIntent全文の非公開の4項目(02 D-12)に、08 D-10により変更管理で追加した飲酒を含むIntentの年齢制限を加えた5項目である(02 v0.2と整合。マッピング表の#27)。ミュート・スパム検知・不適切コンテンツ検知・なりすまし対策はMVPに含めず、Intent大量投稿制限はレート制限(Active Intent 5件/ユーザー・作成20件/日・更新6回/時間)として実装する(08第5節)。年齢制限は次のとおり設ける(08 D-10)。利用登録は18歳以上(生年月日は自己申告、IdPからは取得しない)。飲酒を含むIntent(category=drinking、または文言から飲酒が読める場合)は20歳未満のユーザーが作成できず、20歳以上のユーザー同士の間でのみ候補になる。判定フラグalcohol_involvedの検出漏れはSafetyに直結するため、構造化精度ゲートにrecall 100%・precision下限90%の基準を置く(09 v0.3第4.3節)。位置情報の丸め粒度は約1kmグリッド(第21節)と確定した(08 D-11)。

アクセス制御も要件に含める。すべてのAPIは認証済みユーザーのみ利用可能とし、Intentの参照・更新・削除・回答操作は所有ユーザー本人または提案の参加者のみに許可する。公開設定による開示範囲の制御(proposal生成の分岐、05 v0.4)とブロックの判定は、クライアント入力によらずサーバ側で強制する。認証はGoogleログインとSign in with Appleの2種のIdプロバイダで行い、APIがIdPトークンを検証して独自のJWTを発行する(04 D-21)。LATCH成立後のブロック適用は第8節のとおり即時に閉じる・読み取り専用化で対応し、解放済み情報の回収は行わない(08 D-23)。

North Star Metricは Mutual Latch Rate とする。

```text
双方がYESしたLATCH数 ÷ ユーザーへ提示したLATCH候補数
```

提示した候補のうち実際に双方がYESになった割合であり、仮説2・3・4がひとつに集約された指標である。

数え方を固定する。分母は、当該期間に通知を送信したLATCH候補数とする。1候補につき1と数え、グループ候補も1候補として数える。通知後に回答期限切れ、NO、競合によるクローズになった候補を分母から除かない。分子は、そのうち必要人数全員がYESした候補数とする。合格ラインは、密度構築完了後4週間の中央値をベースラインとし、前期比−5ポイント以内を合格とする手順で運用開始後に確定する(09 D-02、決定手順確定済み)。ベースライン計測期間中の本番変更は凍結し、A/B採用後は再ベースラインを取る(第24節)。

主要KPIは3群に分けて追う。

- 使われ方: Intent作成率 / Intent再作成率 / 1ユーザーあたりActive Intent数 / 7日・30日継続率
- マッチングの質: Candidate生成率 / LATCH候補提示率 / 保留→expired率 / YES率 / Mutual Latch Rate / 実行率 / 無回答率 / キャンセル率
- コスト: 1 IntentあたりJev実行数 / 1成立あたりAIコスト

各KPIの測定定義(分子・分母・集計周期)は09 v0.3第2.2節で確定している。実行率・キャンセル率の分母は回答済みの成立LATCHに限定し、無回答は別指標(無回答率)として計測する。Mutual Latch Rateの集計はlatch_status_events(第17節)からの日次集計による(09 v0.3第2.1節)。

### 24. 品質評価

Offline評価では、過去データについて予測と実際のYES / NOを比較する。指標はPrecision、Recall、Calibration Error、Brier Score、Mutual Acceptance Precision。評価は運用データから作るゴールドセットで行う。構造化精度(第25節Intent#2)はフィールド別完全一致率でゲート管理し、合格基準は category 85% / time.start 90% / location 90%(地域の一致で判定)/ participants 80% / budget 90%(「くらい」表現の丸め後の値で判定)とする(07 D-17、検証は09)。ゲートにはalcohol_involvedを加え、recall 100%(見逃し0件)・precision下限90%を合格基準とする(境界表現を含む飲酒判定専用入力セットは09と10の共有資産。09 v0.3第4.3節)。C係数の再計算は、四半期ごとのECE・Brier判定に基づく手順(09 v0.3第4.4節)で行い、変更はOffline評価通過とA/B適用を条件とする。Cの値域(0, 1]の制約上、Jevが系統的に過小の場合はCで補正できず、打ち手は閾値のA/Bまたはプロンプト改善に限る旨を明示した。

Online評価はA/B Testで行う。対象は通知閾値、Candidate数、Jev判定軸、表示情報量、通知文、回答期限、グループ人数に通知頻度(03 D-08の調整項目)を加える。通知閾値0.60(v0.6)の妥当性(D-01)は、Offline評価の3閾値比較を経てA/B Test(2群4週間・同等性判定)で検証する手順を09が確定した。A/Bはユーザー単位の割付を維持し(時間交互切替はしない)、ペア・集合への処置適用は参加ユーザーの群が混在する場合に対照値を適用する(プロダクトオーナー決定)。判定不能(検出力不足)の場合は既存基準(閾値0.60)を維持する持続規定を置く(09 v0.3第5節・D-01)。ベースライン計測期間中の本番変更は凍結し(緊急修正時は記録して起算を延長)、A/B採用後は再ベースラインを取る(09 v0.3 D-02)。5仮説の検証は、判定基準を事前固定したマッピング(第4節・09 v0.3第2.3節)に従って進める。

## 第VII部 原則と核心

### 27. 設計原則

判断に迷ったとき戻る場所として、8つの原則を置く。

1. AIに全件探索させない。検索・Index・DBで99%以上を削る
2. Hard Constraintはコードで判定する。AIに絶対条件を任せない
3. JevはJudgeとして使う。検索エンジンにはしない
4. 人ではなくIntentを評価する。Person CompatibilityでなくIntent Compatibilityを扱う
5. 片方向の高評価をLATCHとしない。双方の成立を重視する
6. 実際の人間行動を正解データとする。YES / NO / 実際に行ったかがGround Truth
7. 全件再計算ではなくEvent Driven。変化したものだけを再評価する
8. LATCH前はIntentを非公開。潜在意思を公開SNS化しない

### 28. プロダクトの核心

LATCHは人を検索するサービスではない。世界中に存在する「条件付きの意思」を待機状態にしておき、成立可能になった瞬間だけ接続するネットワークである。

技術的な核心は5つの組み合わせにある。Event Driven Matching、Candidate Retrieval、Semantic Judgment、Mutual Acceptance Prediction、Human Feedback Calibration。どれか一つが欠けても、探索コストをゼロに近づけたまま提案の精度を保てない。
