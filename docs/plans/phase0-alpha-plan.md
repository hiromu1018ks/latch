## 1. 経緯と11 §1からの読み替え(記録)

11 §1はPhase 0を「チーム・関係者 20〜50人・1〜2週間・本番同環境での最終確認」と定める。**2026-10-13のユーザー判断により、外部参加者を1人も集められない現実を前提に、参加者を「オーナー自身(n=1)+オーナー運用の第2アカウント」へ読み替える。**

この読み替えが成立する根拠:

1. **Phase 0の完了条件は人数に依存しない**(11 §1・§6。終了条件=02マッピング27項目+追加試験+非機能試験のグリーン=2026-10-06 G4承認済み)。密度構築はPhase 1(招待500人)の仕事であり、Phase 0の目的は本番環境での実走確認にある
2. **機械的な実走確認は既に自動化されている**。実配備URLを対象とする契約remote suite(116/116緑)とfrontend実機E2E(cloudflare-frontend-e2e-20261010-015344.yaml)が、実環境で登録→同意→意図→提案自動生成(49秒以内)→回答→成立→チャット送信まで通している。人数を増やして初めて分かることは本フェーズの目的外
3. **少人数では検証できない「体験」は2アカウントで作れる**。提案〜成立〜チャットは2者のIntentで発生し、自己ペア除外(FR-17)はuser_id単位のため別アカウント同士(例: オーナーのメイン+サブのGoogleアカウント、PC+スマホの2端末)なら正当に成立する
4. **11 §4「偽のIntentは置かない」への整合**。オーナー自身が実ユーザーとして実際の飲食意思を置く(11 §4が想定する「運営チームは実ユーザーとして参加」のn=1版)。Phase 0のデータはPhase 2以降のベースライン計測に使わない(§5)ため、運用主体の偏りは測定を汚染しない

11自体の改版は行わない(規模値は想定例であり、本計画書が実行時の読み替え記録を担う)。**Phase 1(招待500人)の調達可能性は本章の前提が崩れていることを踏まえ、Phase 0終了時に改めて協議する**(§9)。

## 3. 実施設計

### 日常使い(期間を通じて)

- オーナーが自分の実生活の飲食意思をそのまま預ける(1日数件・夜20〜22時中心=11 §4の時間集中)
- スマホ実機での操作(実ブラウザ・モバイル390px姿・tabbar)を主経路とし、PCを第2端末(第2アカウント)に使う
- 観察: 入力→読み解き確認の精度体感・期限3択の実感・待機中の過ごし方・お知らせ/トーストの気づきやすさ

### 同期体験の夜(2〜3回)

目的=提案〜成立〜チャット〜カレンダー〜アンケートの一巡をオーナー自身の操作で通す。手順:

1. 事前に日時(20時台)・エリア(天文館周辺)・カテゴリ(飲みまたは食事)を2アカウントで合わせておく
2. 両端末で同時間帯のIntentを預ける(同一30分Bucket×同一カテゴリ=Layer 1〜5のファネルが同一プールで完結し提案が発生。実配備での実測は49秒以内〔frontend-e2e証拠〕)
3. 提案通知(アプリ内)→04で回答(YES×2)→成立→チャット双方向→カレンダー追加(.ics)
4. 成立後の対象時刻経過→completed→出席申告→アンケート(onboardingは初回active化でdue・week4は28日後に自動due)まで確認できるところまで
5. 翌日の観察: kpi(latch_status_events)・notifications・llm_attempts(実課金量)をD1 SQLで確認(§5)

### やらないこと(スコープ外)

- 外部ユーザーの招待・案内(実施しない)
- D-02ベースラインの記録(Phase 2)
- A/B実験の開始(Phase 3)
- 実データ移行・本番切替の追加判断(別承認のまま)

## 4. 実施環境の現状と機能ギャップ

実配備の稼働資産(CLOUDFLARE-MIGRATION-STATUS・2026-10-12時点):

- API+frontend同一オリジン(Workers Assets)・D1 latch-core(0001〜0008)・cron */5
- 実LLM: Parser=Anthropic claude-haiku-4-5・Embedding=Gemini gemini-embedding-001・Jev=TypeSafe jev-1.13.0(フォールバックAnthropic)。`wrangler secret delete LATCH_LLM_MODE`+`make cf-deploy`でstubへ戻るロールバック確立済み
- 認証: テストIdP鍵(埋め込みJWKS)=開発トークンパネルと組み合わせて利用可

**Phase 0開始前に埋める開発側ギャップ(§7チェックリストへ)**:

1. **POST /v1/sessionsがCF実装に未配線**(D1に計測用sessions表なし=参照実装0008相当未ポート)。O-07のビーコンが実配備で404になる。T10(observability移植)の最小前倒しとしてsessions経路+D1マイグレーション(0009_obs_sessions相当)を整備する
2. **kpi_daily集計ジョブ・kpi_alert・mlr/segment/survey CLIはPostgreSQL参照実装側のみ**(T10未完了)。Phase 0中のKPI観察は次の代替経路で行う: (a)CF実装済みの`recompute_daily_kpi`(latch_status_eventsからproposed/matched/rejected/expired/completedをJST日次集計)・(b)`wrangler d1 execute --remote`での直接SQL(§5のクイックリファレンス)

## 5. 計測・観察計画

Phase 0で見るもの(すべてD1・実配備):

| 観点 | 経路 | 確認頻度 |
|---|---|---|
| 提案・成立・期限切れ件数 | `recompute_daily_kpi`(latch_status_events) | 同期体験の夜ごと+週1 |
| DAU・セッション開始 | sessions表(§7-1で整備)+D1 SQL | 週1 |
| 実LLM課金量 | llm_attempts(actual_provider別件数)・jev usage | 週1 |
| Jev判定分布(体感) | jev結果(match_candidates)を抽出しスコア分布を目視 | 同期体験の夜ごと |
| アンケート回収 | survey_responses(onboarding=オーナー自身の回答) | due時に確認 |
| 通知到達 | notification_deliveries | 同期体験の夜ごと |
| 障害・縮退 | workersのログ(dashboard)・health/503の体感 | 随時 |

クイックリファレンス(代表SQL・`wrangler d1 execute latch-core --remote --command "..."`):

```sql
-- 日次の提案/成立(latch_status_events)
SELECT to_status, COUNT(*) FROM latch_status_events
 WHERE created_at >= <JST日0時のmicros> GROUP BY to_status;
-- セッション開始数(sessions表・§7-1整備後)
SELECT COUNT(*) FROM sessions WHERE created_at >= <同上>;
-- 実LLM呼び出し(actual_provider別)
SELECT actual_provider, COUNT(*) FROM llm_attempts
 WHERE created_at >= <同上> GROUP BY actual_provider;
```

## 6. 凍結規律の運用

- 機能追加を凍結しバグ修正のみ。修正は変更内容と日時をコミットログで記録
- Phase 0は計測の起算に使わないため、緊急修正時の起算リセット規定は不要(11 §6のPhase 2規律と異なる点を明記)
- インシデント対応は11 §7どおり: 重大事故(個人情報漏洩・開示範囲の破損)=新規Intent受付と通知の停止(`wrangler secret delete LATCH_LLM_MODE`+最小インスタンス0等の環境操作)、LLM障害=自動縮退(フォールバック→skipped)に任せ復旧後に再評価

## 8. 完了条件(Phase 0実走の完了)

次が揃ったらPhase 0を終了し、Phase 1(または計画見直し)の協議へ移る:

1. §3の同期体験の夜を2回以上実施し、提案→成立→チャット→(対象時刻経過→)申告→アンケートまで一巡した
