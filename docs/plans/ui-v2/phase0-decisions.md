## D-01 有効期限の選択肢

**選択肢** (a) プロトタイプ固定3択(今日22:00 / 23:59 / 明日5:00)へ変更 — (b) サーバ供給4択(今夜23:30 / 明日12:00 / 明日23:30 / 3日後まで)を維持

**決定** (a)。プロトタイプ02の期限selectのとおり、選択肢は3択「今日 22:00 / 今日 23:59 / 明日 5:00」とする。選択肢体系をサーバ側も含めて3択へ変更する。

**根拠** プロトタイプが正(2026-10-10ユーザー指示)。選択肢の値とラベルもプロトタイプの指定どおり採用する。既定選択(time_start+3時間に最も近い選択可能候補)と、時刻を過ぎた選択肢の選択不可(disabled)は現行規則をそのまま3択へ適用する。

**影響** P1B(小)。completion.pyの選択肢生成・`GET /v1/intents/expiry-options`の応答・契約試験を4択から3択へ更新する。docs 03第3節・05第5節・07第2節expires_at行の選択肢記述を書き換える。逆説的な影響として、「明日 5:00」など夜間の飲食を前提にした時刻が全カテゴリ共通の選択肢になる。長期のIntent(転職・売買)では選択肢が実態に合わない場合があり、プロトタイプ01カードの「期限なし」表示との両立はプロトタイプが沈黙している領域として将来課題に残す(現行のexpires_at補完規則は維持)。

**決定記録** 2026-10-10 ユーザー指示「プロトタイプが正」により(a)で確定。

## D-02 公開設定・通知設定の選択UI

**選択肢** (a) 02に選択UIを復活させる — (b) 仕様側で既定値に固定する

**推奨** (b)。visibility=hidden_until_match・notification_level=proposals_onlyを常に既定値で確定送信し、02の「公開範囲と通知」カードはプロトタイプどおり説明3項目(非公開であること・通知は一文だけであること・期限で自動取り下げ)+期限selectとする。

**根拠** プロトタイプ02のカード文言(「成立するまで、誰にも表示されません」「通知は『LATCH候補があります』の一文だけ」)はhidden_until_match+proposals_onlyの動作をそのまま説明しており、選択の余地を示すUIは存在しない。プロトタイプがこの2値で体験を設計していると読める。

**影響** APIは変更なし(フィールド温存・省略時既定)。docs 03第3節から預け方パネルのselect(公開設定・お知らせ設定)記述を撤去し、05の備考を「UIからの変更導線は将来版」とする。逆説的な影響が2つある。nearby_also / muted / summary_onlyへのUI経路が消えるため、02#13(muted)・#22(2値比較)の機能試験はAPI直叩きで継続すること。また09のA/B(表示情報量)は挑戦者がUIで値を変更できなくなるため、試験時はAPI直叩きか一時的な設定導線が必要になる(03に注記)。

**決定** 確定(2026-10-10。原則=プロトタイプが正による)

## D-03 原文ハイライト(02「あなたの言葉」)

**選択肢** (a) Parser応答へ文字位置(span)を拡張 — (b) クライアントで値マッチング — (c) ハイライトを見送る

**推奨** (b)。ハイライト生成をfrontendの純関数(原文から各条件値に対応する部分文字列を探し`<mark>`+条件番号を付す)で組み、マッチしない条件はハイライトなしで表示する。

**根拠** (a)は07のParser出力スキーマ変更・プロンプト再調整・G1精度ゲートの再実行を伴い、デザイン移行のために過剰である。プロトタイプ02のハイライト(mark+番号sup)は画面の核だが、番号↔条件行の対応は「読み取った条件」5行の側が正であり、ハイライトが一部欠けても画面は破綻しない。

**影響** API・backend変更なし。frontendに新規純関数と試験を追加する。docs 03の02画面記述に実装方式(値マッチング・フォールバック)を一言添える。逆説的な影響として、Parserが正規化した値(「今日 20:00〜」等)と原文表現(「今日20時以降」)の差でマッチしないケースが出る。数値・地名など核となる語で部分一致させる設計とし、マッチ率を試験で担保する。

**決定** 確定(2026-10-10。原則=プロトタイプが正による)

## D-04 「あなたを含むか」人数確認

**選択肢** (a) structured_dataへ項目追加 — (b) 常時「含む」

**推奨** (a)。プロトタイプ02のseg(含む/含まない・未回答でCTA無効)を採用する。「含まない」を選んだ場合はparticipantsの実効値を+1して(あなた+2〜4人=合計3〜5人)送信し、回答自体はstructured_dataの新キー`participants_includes_owner`(boolean)に保存する。

**根拠** 人数確認はプロトタイプ02の必須要素(未回答=「要確認」で預けられない)。現行のparticipants定義は「提案者自身を含む人数」(01第15節・05第2節)で「含む」が前提のため、「含まない」の表現には実効値の+1換算が必要になる。換算はクライアント側の純関数で済む。

**影響** backend対応が要る(P1B・小)。現状`intent_input.py`はstructured_intentの未知キーをignoreするため、`participants_includes_owner`を受けてstructured_dataへ格納する経路を追加する。docs 05第2節のstructured_dataスキーマ表へキーを追記する。契約試験は数件の追加で済む。逆説的な影響として、永続化しない選択(クライアント換算のみ)ならAPI変更ゼロだが、03の「条件を直す」→02で再編集するたびにsegが「要確認」に戻り、摩擦になる。そのため永続化を推奨する。

**決定** 確定(2026-10-10。原則=プロトタイプが正による)

## D-05 回答2択化(「辞退する」廃止)

**選択肢** (a) 認める(03第5節を改版) — (b) 3択維持

**推奨** (a)。04の回答UIは2択(「参加する」cta / 「今回は見送る」=defer)とし、「辞退する」(no)の導線をUIから外す。APIの3値(yes/no/defer)は温存する。

**根拠** プロトタイプ04の回答UIは2択で「辞退する」が存在しない。noは「同一Intent組み合わせへの再提案を期限まで拒否する」強い拒否(03 D-07)で、誤操作の結果が重い。MVPの「置いて待つ」体験ではdefer(見送り)で十分であり、拒否の意思表示は取り下げ(DELETE intents)でも表現できる。

**影響** API変更なし。frontendの`respond.js`を改修する。docs 03第5節(3択→2択)と01第10節(3択記述)を更新する。noはAPI値として温存するため契約試験・02#14(YES/NO回答)は不変。逆説的な影響として、noがUIから到達不能になるためD-07のno側再提案制御は実質休止する(仕組みは温存)。将来の再導入余地を03に記録する。

**決定** 確定(2026-10-10。原則=プロトタイプが正による)

## D-06 回答取り消し(undo)

**選択肢** (a) API追加 — (b) UIから外す

**推奨** (a)。プロトタイプ04のとおり、「回答を取り消す」(joined状態)・「取り消す」(declined状態)のボタンを採用し、回答取り消しAPI(自分の回答を取り消して未回答へ戻す)をP1Bで追加する。

**根拠** プロトタイプ04の4状態表示(open/joined/allIn/declined)はundoを含む構成であり、プロトタイプが正。誤回答の救済をUIで担保する体験である。回答APIの確定性(条件付きUPDATE・競合クローズとの直列化、06第6節)は、取り消しも同一トランザクション内の条件付きUPDATEで扱えば崩さずに拡張できる。

**影響** P1Bで実装(中規模)。エンドポイント(例: `DELETE /v1/latches/{id}/response`または`POST …/response/undo`)で、latches.responsesから自分の回答を除去し、状態をpartial_accept/proposedへ戻す。取り消し不可条件(matched済み・rejected・expired・cancelled・競合クローズ済み・回答期限経過)は409で拒否する。latch_status_eventsへ遷移を記録する。契約試験は取り消し成功・不可条件のぶんを追加する。docs 05(エンドポイント・遷移表)・03(04画面構成)・06(§6直列化への組み込み)に追記する。理由chips(D-07)と組み合わせた場合、取り消し時に理由も破棄する。

**決定** 確定(2026-10-10 ユーザー指示「勝手にUIから外さないで。プロトタイプが正」によりAPI追加へ組み直し)

## D-07 見送り理由chips

**選択肢** (a) API追加 — (b) UIから外す

**推奨** (a)。プロトタイプ04のとおり、declined状態に理由chips(「時間が合わない/場所が合わない/人数が合わない/今日は気分じゃない」・任意・複数可)を採用し、見送り(defer)理由の送信先APIをP1Bで追加する。

**根拠** プロトタイプが正。プロトタイプの文言「次の提案をより合うものにするために使います」が目的を示す。相手へは開示しない(「見送ったことは、ほかの参加候補には伝わりません」と同一の開示規制、03第7節)ため、プライバシー設計と矛盾しない。

**影響** P1Bで実装(小〜中規模)。設計案: response APIへ`reasons[]`(値はtime/place/size/mood)を拡張し、defer回答時のみ受理する(または回答後の別送信)。latches.responsesの要素へreason_codesを保持し、calibration_records.actual_responsesにも同形で反映する(09の判定資料として使える)。undo(D-06)時は理由も破棄する。契約試験は数件追加。docs 05(responses構造)・03(04画面構成)・08(開示規制・理由の取り扱い)に追記する。

**決定** 確定(2026-10-10 ユーザー指示「勝手にUIから外さないで。プロトタイプが正」によりAPI追加へ組み直し)

## D-08 成立の取り消し

**選択肢** (a) API追加 — (b) UIから外す

**推奨** (a)の最小構成。新エンドポイント(例: `POST /v1/latches/{id}/leave`)で自分の参加のみを取り消す。チャットへシステム行(「あなたが参加を取り消しました」)を追加し、自分は以後書き込めない(409)。残りのメンバーの会話は継続し、latches.statusはmatchedのまま変わらない。headcountの再判定(3人成立が2人で成立要件を満たすか)は行わない=成立済みのLATCHは解散しない。

**根拠** プロトタイプ05の取消dialogは部分脱退を明示する(「残りの2人で会うかどうかは、2人が決めます」「条件は待機に戻っていません」)。docsの既存経路である参加Intentの削除(08 v0.3第2.5節)はlatch解散+自分の条件も消えるため、プロトタイプの体験と合わない。calibration_records.cancelled_after(成立後キャンセル記録、05第2節)は既に存在し、attendance経由(completed後3日以内)との間の「任意時点・事前の取消」を埋める経路として自然である。

**影響** P1Bで実装(中規模)。schemas+routes+service+契約試験に加え、messagesのシステム行(送信者なしの扱い)、自分宛の書込拒否(CHAT_READONLYの拡張)、残メンバーへの通知。docs 05・03・08に追記する。逆説的な影響として、チャットの読み取り専用判定が「ブロック適用中」に加えて「脱退済み」の2系統になる。また「解散しない」仕様を明示する必要がある(残メンバー側は人数が減ったまま会話を続ける)。

**決定** 確定(2026-10-10。原則=プロトタイプが正による)

## D-13 下書き・pause/resume

**選択肢** (a) 導線を再設計 — (b) UIから外す(API温存)
