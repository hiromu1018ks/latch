## 2. 実装方式の選択肢と推奨

### 2.1 手順書の形 — 独立文書で11 §7の4区分を手順化(案A・推奨)

- **案A: 運用手順書(runbook)として独立文書(推奨)** — 11 §7の4区分+データ事故復旧を章立てにし、各章を「対象事象→判断フロー→手順(現環境stagingの具体コマンド)→確認→証拠」で書く。本番環境の手順は**確定欄(空欄)**として残し、Phase 0で埋める(12 §6の引継ぎ物)。手順の実行可能性はws-7で実証済みのMakefile資産・手順への参照で構成し、新規コードは書かない
- **案B: 手順をMakefile/scriptsへ自動化** — 重大事故時の停止等をターゲット化すると誤実行の再現性が上がる反面、「人間が判断して実行する手順」の本体(停止範囲の選択・解除条件・記録)が自動化で隠れる。docsに実装要求はなくYAGNI
- **案C: docs/11への追記で完結** — 11は基準を定める設計文書であり、手順(コマンド列・確定欄)を埋め込むと基準の改版単位が重くなる。11 §7は「手順の元」として不変に保つ
- 推奨理由: 11 §7が定めるのは「基準と区分手順」であり、運用の実現手段(現環境ではdocker compose操作)は基準から独立に更新される。分離により「基準(docs/11)・手順(runbook)・実行(log・証拠)」の3層が保てる

### 2.2 手順書の配置 — docs/plans/M4/ws-8-rollback.md(案A・推奨)

- **案A: docs/plans/M4/ws-8-rollback.md(推奨)** — M4単位の成果物としてSTATUS/報告書から追跡しやすい。Phase 0時に本番手順欄を埋めて成長させる(移動が必要になればgit mvで容易)
- **案B: docs/operations/rollback.mdを新設** — 永続性の位置づけは良いが、運用文書の置き場所の慣行がまだなく、単位表の成果物追跡から外れる
- **案C: docs/13として番号文書化** — docs/00の番号文書体系は設計文書であり、運用ルール1(01のD-xx解消更新)の対象になってしまう。手順書は解消すべきD-xxを持たない
- 推奨理由: 配置の判断は追跡性がすべて。Phase 0以降の恒久配置は手順書が成長した時点であらためて決めてよい(確定欄の扱いと同じ)

### 2.3 重大事故停止の手段 — 環境操作の手順化(新実装なし・案A推奨)

11 §7の「新規Intent受付と通知を停止する」に対応する実装済み機能フラグは存在しない(§1.3)。手段の選択:

- **案A: 環境操作による停止の手順化(推奨)** — 2段構成とし、効果の差を手順書に明記する:
  1. **通知・提案生成の停止**: `docker compose -f compose.staging.yaml stop worker1 worker2`(worker=通知書き込みとパイプラインの担い手。APIの既存応答は継続。呼び方はMakefileのSTAGING_COMPOSEと同一)
  2. **新規Intent受付の停止**: nginx(drop-in conf)でPOST /v1/intents・POST /v1/intents/parseを503化してreload(受付のみ遮断・閲覧等の既存APIは継続)。**最終手段としてapi1/api2の全停止**(サービス全停止=全機能停止)も手順に含め、3段階の遮断幅の違いを表で示す
  - 解除手順(逆順+ヘルス確認)+時刻記録(発見・判断・実施・解除の4時点)をセットで規定
- **案B: 受付停止フラグ(LATCH_MAINTENANCE_MODE等)を新実装** — 字義に最も忠実だが、02のスコープに存在しない新機能であり、実装・試験・マイグレーション影響の確認が発生して本単位の「文書整備」の性質を超える。本番で必要と判明した時点でPhase 0以降の変更管理として持ち帰るべき
- 推奨理由: 11 §7は「停止する」という運用判断の規定であって実装形態の規定ではない。staging先行確認(12 M4前置き)の目的は「手順が実行可能で遮断できること」の実証であり、環境操作で足りる。解釈(機能フラグ不在を環境操作で読み替える)はG4時確認事項として記録する

### 2.4 G4証拠対応表 — docs/testassets/results/README.md新設(案A・推奨)

- **案A: results/のREADMEとしてMarkdown対応表(推奨)** — G4 7項目×証拠実体パス×備考の表+欠け証拠の採取手順。現状、docs/testassets/直下のREADME(テスト資産の説明)がありresults/の索引は存在しない。10 §5がresults/を証拠の置き場と規定するため、索引をresults/内に置くのが自然。G4判定(人間)が読む参照文書なのでMarkdown表が素直
- **案B: YAML化で機械検査可能に** — 実体パスの存在チェックを機械化できるが、読むのは人間であり、ws-8の中で1回検査すれば足りる(検査手順は報告書に記録)
- 推奨理由: 対応表の本来の読み手はG4判定の人間(ユーザー)。機械検査は「対応表の各行のパスが実在すること」の1回の照合で済む

### 2.5 欠け証拠(ws-5分3点)の採取 — 手順を対応表に明記し、staging実施はスーパーバイザー検証時に

ws-5報告書「スーパーバイザー検証時の手順4」の3点をそのまま採取手順として対応表に転記する(単位表ws-8「G4 7項目の証拠一覧とdocs/testassets/results/への整理」の範囲と読む):

1. **同意フローのstaging実行記録**: 未同意ユーザーのIntent作成422(CONSENT_REQUIRED)→同意POST→active可の順序観察(ws-3ハーネスのhelpersでユーザー作成済み100人×consentありのため、未同意ユーザーの別途作成が必要・ws-7のcreate_user_nfr型ヘルパと同型)
2. **ログ許可リスト登録表+機械検査結果**: `test_log_allowlist.py`の実行結果と許可リスト一覧(ALLOWED_STRUCTURED_LOGS=latch.llm.send→SendRecord・latch.push.send→PushSendRecord)の写し
3. **ログサンプルのraw_text非混入照合**: docker logsのlatch.llm.send等の出力にraw_text相当が含まれないことのサンプル照合(ws-3報告書のpushログ読取と同型)

証拠形式は10 §5準拠(試験ID・実施日・環境・入力条件・合否)。**staging環境の実施はスーパーバイザーが行う**(ws-5〜ws-7と同一の役割分担・エージェントはstagingに触れない慣行)。

### 2.6 ロールバック手順の実証 — 1世代戻しのwalkthroughを1回実施(証拠化)

「手順書が整備された」ことの実証として、staging環境で次のwalkthroughを1回実行し、記録を証拠にする(10 §5形式・試験ID=ws8-rollback-walkthrough):

1. **デプロイ単位の特定規律の確立**(手順書で新設): 現行のstagingはローカルビルドでありデプロイの版を記録していないため、「デプロイ時のgit SHA+ビルド日時を記録する」規律とデプロイ記録の雛形を手順書に定める。walkthroughではこの記録を先に採る
2. **1世代戻し**: main HEADでstaging再構築(staging-reset)→ヘルス確認→git checkoutで1世代前の作業ツリーを再現し再ビルド+up -d→ヘルス確認(旧版が新スキーマ〔0008〕で起動し動くこと=「アプリの旧版が新スキーマで動作できる」の実証)→現行へ戻す→ヘルス確認
3. **停止手順のドライラン**: §2.3案Aの3段階(worker停止→nginx POST拒否→api全停止)を一巡し、各段でのGET成功・POST遮断をプローブ/手動curlで観察→解除→ヘルス確認
4. **alembic downgradeを実行しない**ことの明示: 手順書に「スキーマは前進させたまま・旧版コードで運用する」を規定(downgrade()関数の存在とは別の運用規律)

実施はスーパーバイザー(§2.5と同じ分担)。ci一時停止・staging-reset等の運用ルール(ws-6/ws-7の手順前段と同型)に従う。
