## 形式と置き場の判断根拠(規定が曖昧な部分)

10 §2は配置場所(docs/testassets/)とバージョン管理のみを規定し、ファイル形式を定めていない。そこで次の判断でYAML形式を採った。

- 草案→ユーザー確認→確定のワークフローでは、レビューで差分が見やすく、コメント(YAMLコメント)で判断の経緯を残せる形式が望ましい
- 確定後は09 §4.3の手順(「入力セットをParserへ流す→出力と期待値をフィールド単位で照合」)で機械的に読み込む前提であり、構造化形式である必要がある
- Markdownは機械的な読み込みに向かず、JSONはコメントを書けないため、両方を満たすYAMLとした

ファイル名の `g1-` プレフィックスはG1ゲート用の部分セットであることを示す。M4フルセット(シードIntent 200〜300件、09 §4.1)の作成時には、この部分セットのケースid(P-xxx / A-xxx / E-xxx)を保持したまま拡張する。idはフルセット全体で一意に保つこと。

## 共通の前提

### 基準日時(相対表現の解決基準)

現在日時を **2026-10-01(木)11:30 JST** に固定する。Parserプロンプトの `{current_date}` にはこの値を注入する(07 §2の規則3「相対表現は現在日付から解決する」の基準)。基準日を変えて再実行する場合は、期待値のうち相対表現由来の日時(今日・明日・土曜等)をすべて更新する必要があるため、変更しないことを推奨する。

- 今日=2026-10-01(木)/ 明日=10-02(金)/ 明後日・土曜=10-03(土)/ 日曜=10-04 / 水曜=10-07

### 期待値はParser出力段階の値

期待値はIntent Parserの出力(07 §2の出力JSONスキーマ)と比較する値であり、アプリ層の補完(03 D-19)を含まない。すなわち `time.end` の+3時間、`participants` の2/2補完、`location.radius_m` の1,000mは期待値に反映しない(該当する場合はnullを期待値とする)。

### 測定対象外のフィールド

- `category.secondary`: D-17の精度基準は「category 85%」であり、測定するcategoryは列挙型の `primary` と解釈する。secondaryは自由文字列で正解の恣意が入りやすく、ゲートの再現性を損なうため、期待値には記載しない(判断。07 §2のスキーマ上は出力され得る)
- `soft_constraints` / `ng_unverifiable`: D-17の測定対象外。ng_unverifiableの検出精度は、フルセット整備時に別途枠を設ける
- `negative_constraints`: MVPでは常に空配列(07 §2 FR-42)。期待値に正例を設けない

### alcohol_involved

07 §2の規則7(category.primary=drinkingは常にtrue、飲酒を示す語の検出でtrue、アルコールを指さない用法はfalse)に基づいて期待値を付ける。G1のalcohol_involved精度ゲート(recall 100%・precision下限90%)の測定はg1-alcohol.yamlで行う。g1-parser-struct.yamlにも参考として期待値を記載する(07スキーマが常に当該フィールドを出力するため)。

### location.nameの判定粒度

09 §4.3のとおり「地域の一致で判定」であり、表記の揺れ(「天文館」「天文館界隈」「天文館あたり」)は同一地域として一致扱いとする。

### author_age(書き手想定年齢)

各ケースに `author_age` を付けている。Parserへの入力はtextのみであり、この値は期待値の判定に一切影響しない。10 §2(「生年月日はD-10の試験のため18〜19歳を意図的に含める」)の精神を先取りしたメタであり、M4フルセットでユーザーとIntentを紐付ける際の土台、および08 D-10の動作試験(18〜19歳ユーザーによるalcohol_involved=trueのIntent作成拒否、02 #27)への流用を想定する。alcohol_involved=true × 18〜19歳の組み合わせを数件 含む。

## 分布(10 §2との対応)

10 §2の分布(夜20–23時40% / drinking 50% / 1対1 70% / 18〜19歳含む)は本来、機能・負荷検証用のフルシードに適用するもの。G1部分セットはParserの測定入力として表現の多様性を優先するため、分布は「精神を参考にした近似」にとどめ、完全一致はM4フルセットで揃える。

g1-parser-struct.yaml(測定対象32件)の実測:

| 項目 | 実測 | 10 §2の目標 |
|---|---|---|
| 時間帯(開始時刻) | 夜(20–23時台)14件44% / 夕(18–19時台)9件28% / 昼(12–13時台)6件19% / その他3件9% | 夜40% / 夕30% / 昼20% / その他10% |
| category.primary | drinking 16件50% / meal 13件41% / activity 3件9% | drinking 50% / meal 40% / activity 10% |
| 人数志向 | 1対1系(言及なし+2人明示)24件75% / グループ系(min≧2の幅またはmin≧3)8件25% | 1対1 70% / グループ(min≧3)30% |

人数志向の差異の理由: Parser測定では人数表現のパターン網羅(言及なし/幅「2〜4人くらい」/下限「3人以上なら」/明示「4人で」)が重要で、min≧3の表現は丸め規則が定義されている「3人以上なら」を中心に3件確保した。min≧3の比率の厳密な一致は、人数表現の分布を肥やせるフルセット(M4)で扱う。

g1-alcohol.yaml(36件)の実測: alcohol_involved期待値 true 24件(67%)/ false 12件(33%)。trueのうち飲酒そのもの(category=drinking系)12件・食事内の言及8件・境界正例4件。falseは全件、酒に触れない活動またはアルコールを指さない用法(境界負例2件を含む)。recall 100%(正例24件の見逃し0件)とprecision 90%(偽陽性2件まで許容)の測定に足る構成とした。

## 測定手順(確定後)

09 §4.3の手順に従う。

1. 基準日時(2026-10-01T11:30:00+09:00)を `{current_date}` に注入して各ケースのtextをParserへ流す
2. 出力と期待値をフィールド単位で照合する(期待値は丸め規則適用後の値)
3. フィールド別の完全一致率を集計し、07 D-17の基準(category 85% / time.start 90% / location 90% / participants 80% / budget 90%)およびalcohol_involved(recall 100% / precision下限90%)と判定する
4. error_cases(エラー付帯ケース)は422 VALIDATION_ERRORが返ることを確認する(一致率の分母・分子には含めない)

Parserやプロンプトを変更するたびに再実行する(09 §4.3)。

## 要確認(needs_review)の扱い

各ケースの `needs_review: true` は、期待値の判断が07 §2の規則の明示的な文言から導けない(規則の空白領域に判断が入る)ことを示す。理由は各ファイル末尾にまとめた。ユーザー確認で期待値を修正した場合は、当該ケースのneeds_reviewをfalseへ戻し、修正の経緈をコメントへ残すこと。

## M4シード(m4-seed)

10 §2の規定(シードIntent 200〜300件・分布完全一致・18〜19歳含む)を満たす機能・非機能試験用のシード。**決定的生成器**(backend/src/latch/testassets/・`make seed-generate`/`make seed-verify`)で生成し、YAMLには生成コマンド引数(base_datetime・seed 42)を記録 — 同一引数での再生成はバイト同一。期待値表は2層(EX-xxx個別期待33件+aggregate集計)で、Layer 1の機械突合はbackend/src/latch/testassets/reference_l1.py(06 §2確定表のPython独立実装)が担う。詳細はm4-seed-plan.md。

### id規約と基準日時

- ユーザー=SU-xxx・Intent=SD-xxx・期待値ケース=EX-xxx(既存P-/A-/E-/SI-/U-と衝突しない)
