## 1. 最終目的地の定義(01から変更しない)

目的地は01第28節の一文である。

> LATCHは人を検索するサービスではない。世界中に存在する「条件付きの意思」を待機状態にしておき、成立可能になった瞬間だけ接続するネットワークである。

効用の定義は01第2節にある。一番大きな効用は、本人も具体化していない「YESになり得る機会」まで含めて、**潜在需要と潜在供給を市場化できること**である。01第6節はこのコンセプトが転職・恋愛・出会い・中古品売買・不動産・旅行・レストラン空席・イベント参加・スポーツ・B2B商談・求人・外注・共同購入・値下げ条件付き購入まで広がり得ると明記し、MVPの「今〜数日以内の食事・飲み」への絞り込みは検証戦略(Intent寿命が短く検証サイクルが速い・正解データが取りやすい・Hard Constraintが明確)でしかない。

この目的地を、進捗が測れるよう8要素に分解する。現在地(2026-10-12)の達成度を併記する。

## 2. 道程の全体構造 — V1〜V4と3つの分岐点

```text
現在地(MVP検証装置完成・Phase 0前)
 └→ V1 概念実証(=11 Phase 0〜4をそのまま実行)
     └→ 【分岐点A】5仮説の判定(09 §2.3)         ← プロダクトオーナー判断
         ├─ 仮説3不支持 → コアの再設計(V1相当へ戻る/前提の見直し)
         └─ 支持 → V2 第2領域への一般化(エンジンの一般性の証明)
             └→ 【分岐点B】第2領域の選定           ← プロダクトオーナー判断(D-V01)
                 └→ V3 供給側の参加(外部Event連携=潜在供給の市場化)
                     └→ 【分岐点C】取引機能の要否    ← プロダクトオーナー判断(D-V02)
                         └→ V4 ネットワーク化・規模展開 = 01 §28
```

各段の性格がV1までとV2以降で異なることに注意する。V1は開発計画(11・12)が既に所有しており、本書の仕事は残課題の見える化だけである。V2以降は仮説判定の結果で進路が変わる条件駆動の段であり、開発を積み上げても進まない——01 §28のとおり、正解データはユーザーの行動からしか得られない。分岐点A〜Cの判断はすべてプロダクトオーナーが行い、00運用ルール5と同じ「決定内容/根拠/影響」の形式で本書に記録する。

## 4. 分岐点A — 5仮説の判定と3つの帰結

判定基準は09 §2.3が運用前に事前固定している。要は次のとおり(正式な表は09を正とする)。

| 仮説 | 主指標 | 支持判定基準 |
|---|---|---|
| 1 待つ体験を便利と感じる | アンケート(直後・4週後)+Intent再作成率 | 4週後5段階平均4.0以上・週次再作成率40%以上 |
| 2 意味的に成立する提案を受け入れる | 語彙一致/意味近接セグメント別YES率 | 意味近接YES率10%以上・語彙一致の50%以上 |
| 3 双方YESを予測できる | Offline Precision+実測Mutual Latch Rate | Precision@0.60が0.60以上・MLR前期比−5pt以内 |
| 4 通知頻度を抑えれば反応率が高い | 通知あたり反応率(制限群vs拡大群) | 制限群が有意に高い |
| 5 検索しない様式が継続につながる | 30日継続率+継続意向 | 継続率30%以上・継続意向4点以上が過半 |

判定の帰結は3つに整理する。

1. **支持(仮説3を含む)** — V2へ進む。仮説1/2/4/5の支持度は無視せず、第2領域の選定基準(第5節)への重みとして使う。例えば仮説2の支持が弱い(意味的寛容性が低い)なら、語彙一致が支配的な領域から展開する。
2. **仮説3不支持** — 最終目的地の技術的前提が崩れる。打ち手は09 §4.4のC係数再計算、07のプロンプト・埋め込み改善、Jev第一候補の再評価(07 v0.5の繰上げ規定)のいずれかで、V1相当へ戻って再計測する。改善で基準を満たせない場合は、01 §28の前提そのものの見直し(目的地の縮小)をプロダクトオーナーが判断する。
3. **部分支持** — 支持された仮説が示す性質を第2領域の選定基準へ反映してV2へ進む。仮説3が支持されていれば、他仮説の不支持は目的地の否定でなく領域適性の情報である。

判定不能(検出力不足)の場合は、D-01の持続規定(判定不能時は対照値0.60維持)と同じ考え方を準用する。すなわち既存基準を維持して縮退せず、測定条件を整えたうえで再判定する。

## 5. V2 — 第2領域への一般化(エンジンの一般性の証明)

**目的。** 飲み領域1つでの成功は、検証装置の成功であって一般性の証明ではない。「ネットワーク」と呼ぶための最小の証明は、エンジンが領域を替えられることである。V2では第2領域を1つ選び、飲みと並列に走らせる。

**「一般化」の操作的定义(完了条件の核)。** 第3領域の追加が、ハードコードでなくパラメータとモジュールの追加で完結し、週規模の工事でできること。第2領域の実装がこの状態に達していることをもって、一般化が証明されたとみなす。

**領域選定の基準(分岐点B・D-V01)。** 01 §6が飲みを選んだ理由を一般化した6軸で評価する。

| 軸 | 問い |
|---|---|
| 検証サイクル | Intentの寿命は短いか(サイクルが速いほど正解データが早く溜まる) |
| 正解データ | YES/NOと実施が観測できるか |
| Hard Constraint | 時間・場所・人数・価格のようにコードで厳密に落とせる条件があるか(原則2) |
| 機微性と安全 | 08の枠(開示最小化・外部送信の同意・削除)が保てるか。飲酒年齢相当の領域別安全規則を作れるか |
| 密度 | 単一エリアでクローズドベータの密度(11 §2相当)が作れるか |
| 供給側接続 | V3への橋になる外部Event源(価格・空席・在庫)がその領域にあるか |

暫定スタンス(未解決・D-V01): イベント参加・スポーツ系(時間・人数・場所がHard Constraintとして明確で、飲みに最も近い)を第一候補に傾いている。対候補は中古品売買(価格のmin/maxがHard Constraintになり、01 §2の「この車が190万円以上なら売ってもいい」例に直結する)。転職・恋愛・出会い・B2B商談・求人は機微性と意思決定の重さ(誤提案の害が大きい・08の同意設計が複雑)からV4以降が妥当と見ている。

**既存資産の再利用と作り直しの境界。**

| そのまま使う | 領域ごとに作る |
|---|---|
| 5層パイプライン骨格(Layer 1 SQL/Layer 2 HNSW/Layer 3/Layer 4 Jev+フォールバック/Layer 5 Engine) | Parserの構造化スキーマ(category列挙の一般化・領域別フィールド定義) |
| Event駆動・冪等性・debounce・再評価 | Hard Constraintの領域別定義(価格min/max・契約条件等) |
| コスト保護3層(源流レート制限/Jev予算/D-16上限)・circuit breaker | 期限とBucketの設計(Intent寿命が領域で違うためD-05式の再検討を含む) |
| Calibration・MLR集計・Observability 3群 | 領域別の安全規則(飲酒年齢相当)とNG条件の分類規則(D-04相当) |
| 認証・同意・ログ許可リスト・ブロック/通報・チャット | 領域別ゴールドセット(T3資産の領域版)と精度ゲート(09 §4相当) |

friendships(05 v0.4に残置)の投入タイミングは領域選定に依存する。友人限定系の領域ならV2で必須になり、それ以外ならV2後でよい(D-V03)。

**V2の完了条件(GV2・案。V2着手時にプロダクトオーナーが確定する)。**

1. 第2領域で11と同型のKPI(MLR・Intent再作成率・30日継続率)が測定でき、D-02相当の警報運用ができている
2. 上記の「一般化の操作的定义」を満たしている(第3領域追加の見積もりが週規模であることの証明)

## 6. V3 — 供給側の参加(外部Event連携=潜在供給の市場化)

01第2節の市場化は需要側だけでは半分である。供給側の参加には2つの形がある。

1. **供給意思のIntent** — 「この車が190万円以上なら売ってもいい」「4人集まるなら店を出す」のように、売り手・店側が需要側と同じIntentモデルで預ける形。スキーマ拡張は小さい
2. **外部状態のEvent** — 店舗の価格変更・空席発生・在庫変更・外部サービスの状態変更(01 §5がEventとして定義し、外部連携は将来バージョンと保留していたもの)を再評価のトリガーとして流入させる形。需要Intent×外部状態のマッチングがここで初めて動く

設計原則は01 §27から継承する。Event Driven(変わったものだけ再評価・原則7)、コスト保護(外部Eventの流量は内部5種と別枠のレート制限・予算・K上限が必須。02で実装済みの3層保護の枠を拡張する)、プライバシー(外部データの取り込み契約・送信記録・許可リストの08拡張版が必要)。

**分岐点C(D-V02)。** 02「実装しない」のうち決済・店舗予約・自動購入・外部店舗在庫連携の要否を、V3着手時に再判断する。暫定スタンス(未解決): 01 §28は「接続するネットワーク」であり、提案→双方承認までを目的地とする。取引は取引機能を持たないマッチング完結型のままが本来の形で、成立後の予約や決済は領域ごとの外部への手渡しで足りると見ている。この判断を変えない限り、V3のスコープは外部Eventの取り込みと需要×供給の提案に限る。

**V3の完了条件(GV3・案)。** 外部Event由来の再評価が予算とK上限を守って動作していること、需要×供給の提案が成立しMLRとして測定できていること、外部データの契約・許可・ログが08拡張版どおりであること。

## 7. V4 — ネットワーク化・規模展開(=01 §28)

V2/V3で領域と需給の一般性を証明したのち、規模の軸を広げる。内容は4つである。

- **エリア展開** — 11 §2の単一エリア前提を解除する。解除の基準(密度・MLR・運用体制)をD-V05として確定する
- **プラットフォーム** — モバイル(iOS/Android)への着手(04 §2の後続段階・D-V04)
- **グラフ本格化** — friendships→friends_only→friend_of_friend(2ホップ)の段階的投入と、users.trust_score(01 §17の予約フィールド)の利用判断(D-V03)
- **領域間の横断** — 領域をまたぐIntent(「飲みでもカラオケでも」)と、領域をまたぐ提案の可否

V4の完了条件は「完了」というより定常状態の定義になる(GV4・案)。01 §28の一文が、規模・領域・需給の両側で反証なく運用されていること。観測項目は、MLRが各領域でベースラインを維持していること、探索コストの除去という効用がユーザーの行動(検索・募集をしないで再作成する)として継続観測できること、01 §12のファネルが設計値どおりに観測できることである。
