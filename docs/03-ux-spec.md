## 1. 本書の目的と位置づけ

LATCHの体験は「置いて、待って、通知が来たらYESかNOだけ」である(01第28節)。本書はこの体験を壊さないための画面構成、通知設計、回答操作、不成立時の表示を確定させる。04以降の技術文書は本書の決定を実装の前提とする。とくに通知頻度(D-08)は仮説4(通知を抑えれば反応率が上がる)の検証装置そのものなので、初期値を固定し、調整は09のA/B Testに委ねる。

## 2. 画面一覧と必須要素

01第10節が要求する5要素を起点に、画面を6つに整理する。実装の起点は**Intent入力画面**であり、`prototype/`に同画面が実装済みである(v0.4。実装状況は下表の備考欄)。残りの画面はプロトタイプの構成とデザインシステムを踏襲して追加する。

| 画面 | 必須要素 | 備考 |
|---|---|---|
| Intent入力 | 自然言語入力欄(300字上限・文字数カウンタ)/ 読み取った条件のリストと行単位のインライン修正 / 条件の追加 / 預け方(有効期限・公開設定・お知らせ設定の選択)/ 下書き保存 / このIntentを預ける(⌘Enter)/ 確認モーダル | 第3節。**プロトタイプ実装済み** |
| ホーム | Intent入力導線 / Active Intent一覧 / LATCH候補(proposed) / 成立済みLATCH / 未読表示 | 01第10節の5要素。Active Intent一覧はtopbarの「Intent N件」カウントから到達する一覧領域として実装する(プロトタイプのtopbar構成を踏襲)。未読表示はお知らせボタンのドット(notification-dot) |
| 提案詳細 | 条件サマリ(visibilityによる分岐)/ 一致度 / 回答操作 / 回答期限の残時間 / グループなら必要人数 | 第5節。visibility=hidden_until_matchでは条件サマリを表示しない |
| 成立済み詳細 | チャット / 集合情報 / 次アクション | 第6節 |
| お知らせ(アプリ内通知) | アプリ内通知一覧 / 既読管理 | 第4節。UI名称は「お知らせ」(topbarのベルpopover)。プロトタイプは空状態を実装済み(「まだ新しい候補はありません/条件が合うと、ここに静かに届きます。」) |
| 設定 | 通知許可 / ブロック管理 | v0.4で友人管理(相互承認)を削除(02 v0.3 D-03再決定) |

LATCH状態のうちユーザーに見せるのはproposed以降であり、candidateの詳細(条件サマリ)はシステム内部のデータとして画面に出さない(01第10節)。お知らせ設定でnearby_also(近い候補も知らせる)が選ばれている場合に限り、閾値未満の候補についても**その発生(存在)**の通知のみを行う。この通知に条件サマリ・相手情報は含めない(第3節・第8節)。

## 3. Intent入力フロー

入力は自然言語一本で始める。フォーム入力を主UIにはしない(01第9節)。v0.4からフローはプロトタイプの実装(単一画面+モーダル確認)に固定する。

```text
[Intent入力画面] 自然言語で記入(300字上限・文字数カウンタ付きの入力欄)
  ↓ Intent Parserで構造化(後続実装で連携)
[同一画面の条件リスト] 構造化結果の表示(時間/場所/人数/予算/目的の行)
  / 行単位のインライン修正 / 条件の追加(その他・曜日・移動・雰囲気)
  [右側の預け方パネル] 有効期限 / 公開設定 / お知らせ設定 の選択
  ↓ 下書き保存 → status: draftで保存し、トースト「下書きを保存しました」を表示(入力画面に留まる)
  ↓ このIntentを預ける(⌘Enter / Ctrl+Enter)
[確認モーダル] 有効期限・公開設定のサマリ表示 / 「あとは、置いておくだけ。」
  ↓ Intentを確認する(保存の確定。POST /v1/intents status: active)
  → 同一画面に留まる(遷移しない)。Active Intent一覧はtopbarの「Intent N件」から到達する
```

条件リストは01第9節の表示形式を踏襲し、時間・場所・人数・予算・目的を構造化して見せる(文言はプロトタイプに固定 — 「時間: 今日 20:00以降」「場所: 天文館」「人数: 2〜4人」「予算: ひとり5,000円まで」「目的: 軽く飲む」。第10節参照)。現行プロトタイプはテキストと条件リストを連結しない静的モックであり、Intent Parserの連携は後続実装とする。ここで5つの確定事項がある。

**文字数の上限。** 入力欄は300字を上限とし、入力欄の右下に文字数カウンタ(「41 / 300」形式)を常時表示する(v0.4。プロトタイプ実装に固定)。上限超過の入力は入力欄で遮断する。

**必須フィールドの催促。** category、time.start、locationの3つは必須とし(第8節D-19)、Parserが推定できなかった場合は「預ける」をブロックして指定を促す。AIの解釈を曖昧なまま通さない。現行プロトタイプの実装は「テキストが空のとき預けるボタンを無効化する」までを担い、必須3フィールドの催促・時刻検証の表示はParser連携とともに追加する(検証の強制はサーバ側、05 v0.4第5節)。

**判定不能NG条件の注意表示(02 D-04)。** 会社関係者の除外のように、判定に必要なデータをシステムが持たないNG条件を検出した場合、条件リストにNG行を付し「この条件は確実には除外できません。参考条件として扱います」の注意表示を添える。同意したうえでSoft Constraintとして保存する。黙って降格させない。NG行の行型はプロトタイプにまだなく、Parser連携とともに追加する。

**預け方(公開設定・お知らせ設定)。** 確認モーダルで公開設定を明示する。公開設定は**hidden_until_match(条件一致までは非公開)/ summary_only(候補にだけ概要を表示)**の2値で、初期値はhidden_until_matchである(02 v0.3 D-03再決定。プロトタイプの既定選択と一致)。hidden_until_matchでは提案画面に条件サマリを表示せず、成立した時点で条件サマリ・表示名・プロフィールを解放する(第5節・08 v0.4第2.2節)。summary_onlyでは提案先に条件サマリのみ表示する。raw_text・NG条件・名前・プロフィールはどちらの値でも成立まで表示しない。

**お知らせ設定(v0.4新設)。** 預け方パネルの「お知らせ」は、このIntentに係る提案通知の範囲を選ぶIntent単位の設定で、次の3値から選択する。初期値はproposals_onlyである。

| 値 | UI文言 | 動作 |
|---|---|---|
| proposals_only | 一致したときだけ | 閾値超過の提案(proposed)のみ通知する |
| nearby_also | 近い候補も知らせる | 閾値未満の候補についても**その発生**の通知のみを行う。条件サマリ・一致度・相手情報は通知に含めない(候補の詳細は画面に出さない規定は維持、第2節)。nearby_alsoの通知もD-08の日次上限(日6件/ユーザー)に含める(同時進行上限(3件)はproposed数の上限のため、candidateのままの存在通知には適用しない) |
| muted | 通知しない | 提案通知を送らない。お知らせ一覧には提案を表示しないが、提案自体はホームのLATCH候補から確認できる |

**有効期限の選択(FR-13)。** 預け方パネルの必須要素に有効期限(expires_at)を含め、次の4つの選択肢から選ぶ方式に確定する(v0.4。プロトタイプ実装に固定)。

| 選択肢(UI文言) | 意味 |
|---|---|
| 今夜 23:30 | 当日の23:30(JST) |
| 明日 12:00 | 翌日の12:00(JST) |
| 明日 23:30 | 翌日の23:30(JST) |
| 3日後まで | 現在時刻+72時間 |

**既に過ぎている選択肢の扱い(v0.4)。** 選択肢の時刻が現在より過ぎている場合(例: 23:45以降の「今夜 23:30」)は、当該選択肢を選択不可(disabled)にする。既定の選択も、選択可能な選択肢のうちtime.start+3時間に最も近い値とする(activeの作成では過去時刻が422となるため、05 v0.4)。既定選択のこの計算はプロトタイプに未実装であり(現行は先頭選択肢が既定表示)、実装時に追加する(第10節「既知の差分」)。

既定の選択はtime.start+3時間に最も近い選択肢とする(D-19のデフォルトtime_start+3時間との整合)。選択値はPOST/PATCHのstructured_intent.expires_atとして絶対時刻で受け渡され(05 v0.4)、activeの作成・更新では過去時刻・現在+7日超は422で拒否される(05 v0.4の時刻検証)。下書き保存(draft)では検証を適用しない(05 v0.4第5節)。02第4節#4(有効期限を指定して保存し、期限経過後の状態を確認する)はこの経路で完結する。確認モーダルの文言と構成(「あとは、置いておくだけ。」等)は第10節に固定したとおりである。

## 4. 通知設計

通知は3層で表示を分ける。プッシュ通知の本文は汎用文とし、条件サマリ(人数・時間帯・地域名・カテゴリ・予算)はアプリ内通知(UI名称「お知らせ」)と提案画面のみに表示する(FR-21、プロダクトオーナー決定)。プッシュはロック画面・通知履歴・ウィジェット・読み上げ等のOS経路を通じて端末の持ち主以外にも表示され得るため、成立前の意思(01第21節)をこの経路に載せない。表示規制の全文は08 v0.4第2.6節である。**条件サマリを表示するのはvisibility=summary_onlyの場合に限る(v0.4)** — hidden_until_matchの提案では、次の様式の条件サマリ部分を出さず「条件が合う候補があります」の本文と一致度・回答期限のみとする(第5節)。

```text
【プッシュ通知(本文は汎用文。条件サマリを含めない)】
LATCH候補があります。
詳細はアプリでご確認ください。

【アプリ内通知(お知らせ・visibility=summary_onlyの提案。条件サマリを表示)】
LATCH候補があります。

今夜 20:00〜
天文館 / 3人
焼肉 / 予算上限5,000円

あなたの条件との一致度が高い候補です。

【アプリ内通知(hidden_until_matchの提案。条件サマリを含めない、v0.4)】
条件が合う候補があります。
一致度が高い候補です。今夜中にご回答ください。
```

通知手段はプッシュ通知とアプリ内通知(topbarの「お知らせ」popover+未読ドット。プロトタイプのtopbar構成に固定)の併用とし、許可を取得できないユーザーにはアプリ内通知で到達する(第8節D-18)。プッシュは「候補が発生したことの合図」を担い、内容の確認と回答はアプリ内で行う。通知のタイミングは双方(グループでは必要人数全員)への同時送信とする(第8節D-20)。提案通知の頻度は1ユーザーあたり日6件、1Intentあたり同時進行3件を上限とし、超過分は保留して順次提示する(第8節D-08)。nearby_also(近い候補も知らせる)の存在通知も日次上限(日6件/ユーザー)に含める(同時進行上限(3件)はproposed数の上限のため、candidateのままの存在通知には適用しない。v0.4)。

**タップの遷移先(FR-46)。** プッシュ通知・アプリ内通知のいずれから入った場合も、タップで提案詳細画面へ遷移する。バナー上の直接回答ボタンは設けない。回答前の詳細確認(条件サマリ・一致度・回答期限・必要人数)を徹底し、ロック画面上での誤操作を構造的に防ぐためである。回答は必ず提案詳細画面の3択(第5節)から行う。

## 5. 提案画面と回答操作

提案詳細画面の必須構成は次のとおり。

- 条件サマリ(アプリ内通知と同形式。相手のraw_text・NG条件は表示しない — 01第21節の最小化規則)。**visibility=hidden_until_matchの提案ではこの要素を表示しない(v0.4、02 v0.3 D-03)**。表示内容は「条件が合う候補があります」の本文と、下記の一致度・回答期限(+グループなら必要人数)のみとし、条件サマリ・表示名・プロフィールは成立した時点で解放する(08 v0.4第2.2節)
- 一致度(LATCH Scoreの区切り。内部スコアの生値ではなく「高」等の表示とする。区分はlatches.proposal.match_level、05 v0.4)
- 回答操作: [参加する] / [今回は見送る] / [辞退する] の3択。プッシュ・アプリ内通知から入った場合も、提案詳細ではこの3択が提示される。通知からの直接回答はない(第4節)。見送りと辞退(NO)の意味の違いは第8節D-07で確定する
- 回答期限の残時間表示(「あと1時間23分で締切」)。期限は第8節D-05の規則で導く。表示値はresponse_deadlineであり、latches.expires_atはこの期限を超えない(D-05の導出式)
- グループ提案では必要人数と現況(「あと2人の回答が必要」)を人数のみ表示する。必要人数は集合サイズ|S|と一致し(06 v0.3 D-06)、誰が回答済みかの個人の特定は、成立前の情報最小化の原則から表示しない

## 6. 成立後の体験

必要人数のYESが揃いmatchedとなった時点で、次を解放する(01第8節)。

- チャット(成立LATCH単位の閉じたルーム)
- 相手の表示名・最小限のプロフィール
- 集合情報(対象日時・場所の要約)
- 次アクションの提示(チャット開始の誘導、対象時刻のリマインド)

成立済みLATCHは対象時刻の経過でcompletedとなる。完了後も閲覧は可能とするが、チャットの新規送信は閉じる。

## 7. 不成立・期限切れの表示と開示範囲

提案が閉じる理由は7経路ある(01第8節)が、ユーザーへの表示は次の2種類に集約する。

- 自分の操作によるもの(NO・見送り・Intentの停止削除): 自身の操作履歴として表示する
- それ以外(相手の回答、回答期限切れ、Intent期限切れ、Hard Constraint変化、人数不足、ブロック、競合): 「この提案は成立しませんでした」の一文で統一する(公開範囲違反の経路はv0.4で友人関係の将来版化により削除、02 v0.3 D-03)

相手がNOか見送りか無回答か、ブロックされたのかは、一切開示しない。理由の開示は相手の意思に属する機微情報であり、ブロック事実の推察にも使われるためだ。この二値化は第8節D-20の決定であり、ホームのLATCH候補一覧から当該提案は終了済みとして扱われる。matched済みLATCHの参加Intentが削除された場合も、残った参加者への表示はこの一文のみとする(08 v0.3第2.5節)。

## 8. 未決事項の決定

### D-05 LATCH回答期限の初期値と導出規則

- 決定内容: 回答期限は次の式で導く(v0.3で修正)

```text
回答期限 = min( max( 通知時刻 + 15分,
                    min( 通知時刻 + 2時間, 対象開始時刻 − 60分 ) ),
              参加Intentのexpires_atの最小値(latches.expires_at) )
```

- 変更の内容(FR-48): 従来式(「min(通知+2時間, 対象開始−60分, expires_at)、下限は通知+15分」)では、下限の引き上げによって回答期限がexpires_atを超える境界があった。expires_atが近いIntentではUIに表示した期限が満ちる前に提案がexpiredになり、期限内有効なはずの回答が409となる。修正式は15分下限をexpires_at以外の2項に適用し、最後にexpires_atとminを取ることで、回答期限 ≦ expires_at を常に保証する。05第6節の遷移表と06第6節の期限判定(response_deadlineとexpires_atの両方を参照)と整合し、表示値と実際の締切が一致する。なお、導出した回答期限が通知時刻を過ぎない場合(参加Intentのexpires_atが通知時刻以前)、当該候補は通知しない(75分ルールと同一の扱い)
- 根拠: 対象が今〜数日以内の食事・飲みであり、対象時刻を過ぎた提案に価値はない。対象時刻の60分前までに確定しない提案は実行が間に合わない。15分の下限は「通知してすぐ期限切れ」を防ぐが、下限の適用対象からexpires_atを外すことで、Intent期限との整合を壊さない。対象時刻まで75分を切って生成された提案は、通知自体を行わない。初期値の妥当性は第24節のA/B対象(回答期限)に含める
- 01への影響: 第8節に回答期限の導出規則を追記。初期値の妥当性検証は09のA/Bで行う

### D-07 「今回は見送る」の意味と再提案条件

- 決定内容: 見送りはNOとは別の回答とする。見送りは「この提案の辞退」であり、Intentはactiveを維持する。NO(辞退)は「このIntent組み合わせへの拒否」とし、同一Intent組み合わせへの再提案を当該Intentの期限まで行わない。見送り後の同一Intent組み合わせへの再提案は、(a)見送りから min(24時間, 対象開始時刻までの残時間の半分) の経過、(b)再評価でスコアが変化している、またはどちらかのIntent更新による新候補である、の両方を満たす場合に限る。見送りも提案を閉じる回答であり、提案の状態遷移はNOと同じrejected相当とする。ただし回答種別(NO/見送り)は記録として区別保持し、この再提案制御の判定に使う
- 根拠: 仮説4が想定するユーザーは「条件次第でYES」の中間帯であり、1回の辞退で候補供給を絶つのは早すぎる。一方、無条件の再送は通知過多を招く。対象領域は今〜数日以内の短寿命Intentで、多くは数時間でexpireするため、抑制期間はIntentの残存時間に比例させる。残り時間の半分とすれば短いIntentでは抑制が自動的に短くなり、24時間を上限として長めのIntentでの連投を防ぐ。スコア変化の条件と合わせ、同一候補の単純再送を排除する。スコア変化の判定手順(比較元の保持・変化の閾値)は06 v0.3第10節が確定した
- 01への影響: 第10節に見送り・NOの定義と再提案規則を追記し、rejected遷移に見送りを含む旨(回答種別は区別保持)を明記する

### D-08 通知頻度の上限と超過時の扱い

- 決定内容: 1ユーザーあたり提案通知は日6件まで(0時にリセット)、1Intentあたり同時進行(proposed)の提案は3件まで。上限を超えた候補は破棄せず保留し、既存提案のクローズまたはリセット後に、対象時刻の近い順を主キーとし、同点の場合にLATCH Scoreの高い順(タイブレーク)で提示する。保留中に候補側の対象時刻が来たものはexpiredとして閉じる。保留の表現・提示時の回答期限の再計算・再評価の差分化は06 v0.3第10節が確定した
- 根拠: LATCH候補の通知頻度を抑えること自体が仮説4の検証条件であり、通常のSNS通知との差別化の核心である。破棄しないのは、保留が長く続くことの損失(期限切れ)で済ませ、候補の消失という体験の破壊を避けるためだ。初期値は09のA/B Test(通知頻度)で調整する
- 01への影響: 第10節に頻度上限の初期値と超過扱いを追記

### D-18 通知手段と通知許可を取得できないユーザーへの扱い

- 決定内容: 一次手段をプッシュ通知、常時併用をアプリ内通知(UI名称「お知らせ」: topbarのベルpopover+未読ドット。v0.4)とする。プッシュ許可はオンボーディングで要求するが、拒否しても利用可能とし、アプリ内通知にフォールバックする。許可の再要求は、候補が初めて発生した時点など文脈のあるタイミングに限り、設定画面からいつでも取り直せる。プッシュの本文は汎用文とし、条件サマリはsummary_onlyの提案に限りアプリ内通知と提案画面に表示する(FR-21、08 v0.4第2.6節と同一の規定。v0.4でvisibility分岐を追記)。この表示規制はプッシュ許可の有無と独立に適用する。通知基盤の技術選定は04 v0.2で確定済みである(FCM統一、APNsはFCM経由)
- 根拠: 通知は「待つ」体験の完成装置だが、許可を強制すれば登録の摩擦(仮説1)と衝突する。見逃しのリスクは未読ドットと回答期限の残時間表示(第5節)で軽減する。プッシュを「合図のみ」に絞るのは、プッシュ許可したユーザーほど成立前の意思が第三者に露出する構造的なねじれを解消するためである(FR-21)。条件サマリの表示はお知らせと提案画面で維持され(summary_onlyの場合)、「待つ」体験の内容は損なわない
- 01への影響: 第10節に通知手段と許可なしの扱い、プッシュ本文の汎用文化と条件サマリの表示位置を追記。解消責任は本書に一元化する

### D-19 Intentフィールドの必須・任意とデフォルト

- 決定内容: 次のとおり確定する

| フィールド | 区分 | 未指定時のデフォルト |
|---|---|---|
| category | 必須 | —(推定不能なら条件リストで選択を促す) |
| time.start | 必須 | —(条件リストで指定を促す) |
| time.end | 任意 | time.start + 3時間 |
| location | 必須 | —(条件リストで指定を促す) |
| location.radius | 任意 | 1,000m(既定半径)。条件リストで修正できる |
| budget | 任意 | 制約なし |
| participants.min / max | 任意 | min=2 / max=2(1対1) |
| visibility(公開設定) | 必須 | hidden_until_match(確認モーダルで明示選択。「条件一致までは非公開 / 候補にだけ概要を表示」の2値。02 v0.3 D-03) |
| expires_at | 任意 | time.start + 3時間に最も近い選択肢(選択肢は第3節の4値「今夜 23:30 / 明日 12:00 / 明日 23:30 / 3日後まで」) |
| notification_level(お知らせ設定) | 任意 | proposals_only(預け方パネルで選択。proposals_only / nearby_also / muted。第3節、v0.4新設) |
| hard / soft / negative_constraints | 任意(Parserが抽出) | 空リスト(制約なし)。判定不能なnegative条件はSoft Constraint扱い(02 D-04) |
| time.flexibility / location.flexibility | 任意 | なし(固定扱い。Hard Constraintとして厳密に判定) |
| raw_text | 必須 | —(入力原文をそのまま保持。最大300字。UIはmaxlengthで入力を遮断し、文字数カウンタを表示する。第3節、v0.4) |

- 補足として、「5,000円くらい」のような幅のある予算表現は上限(max)へ丸め、minは基本的に使わない。expires_atのデフォルトでMVP対象(今〜数日以内)を超える値にはならず、明示指定値も過去・現在+7日超は保存時に拒否される(05 v0.4の時刻検証。draftでは適用しない)
- v0.4追記(prototype整合): visibilityの2値・expires_atの選択肢4値・notification_levelの3値・raw_textの300字上限は、プロトタイプの預け方パネル・入力欄の実装に固定した。これらはUI文言とともに第10節の対応表で管理する。条件リストの「条件を追加」ラベル(その他・曜日・移動・雰囲気)はUI上の入力補助であり、格納先はすべてstructured_data.soft_constraints(MVPではLayer 1の判定対象外のsoft条件として扱う、05 v0.4のstructured_dataスキーマ)である。曜日・移動のうち時間・場所のHard判定に繋げられるものは、将来のParser拡張でtime系・location系へ昇格する(07の抽出規則の拡張時に改版する。MVPでは指定曜日のHard判定は行わない)
- 根拠: 対象領域は短寿命の飲食なので、終了時刻と有効期限の未指定は対象時刻を基準に補完するのが自然であり、無期限は認めない。participantsの未指定を1対1とするのは、MVPの主眼が1対1であり、グループ希望は「3人以上なら」のような言語表現からParserが抽出できるため、予測可能な初期体験を優先した。radius行の明示は、既定半径1,000mが表から読めなかった不備(FR-35)の解消である。v0.4の追加行は、実装済みのプロトタイプにdocsが追随して値を固定したものである(プロダクトオーナー決定)
- 01への影響: 第9節にフィールド区分とデフォルト規則を追記。丸め規則の実装は07(v0.2で確定済み)

### D-20 提案通知のタイミングと不成立時の開示範囲

- 決定内容: 提案通知は双方(グループでは必要人数全員)へ同時に送る。不成立時に相手へ開示する情報は「この提案は成立しませんでした」の一文に集約し、相手の回答種別(NO・見送り・無回答)と不成立の理由は開示しない(第7節)
- 根拠: 順次通知は先に通知された側の回答が相手側に表示されない期間を生み、成立までのレイテンシが伸びる。時間敏感なIntentではこの遅延が価値を直接毀損する。開示の二値化は、NOの理由という機微情報を守り、ブロックされた事実の推察も防ぐ
- 01への影響: 第8節・第10節に通知タイミングと開示範囲を追記。グループ提案の検証は06 D-06の確定を受け09第3節で補完済み

## 10. プロトタイプとの対応(v0.4新設)

フロントエンドの実装基準は`prototype/`(Vite + vanilla JSのWebプロトタイプ、単一画面「新しいIntent」)である。本書とプロトタイプが食い違う場合はプロトタイプ側を正とする。プロトタイプには下記のデザインシステムとUI文言が実装済みであり、後続の画面(提案詳細・成立済み詳細・設定・ホーム一覧)もこれを踏襲する。
