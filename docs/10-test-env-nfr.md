## 1. テスト環境構成

04の技術スタック(PostgreSQL+PostGIS+pgvector / Pub/Sub / Redis / コンテナ基盤 / FCM / Cloud Monitoring)を本番と同じ種類で立てるが、規模を縮小する。環境は3つに分ける。

| 環境 | 規模・構成 | 用途 |
|---|---|---|
| ci | 最小構成(常設)。API 1インスタンス、Worker 1、DB共用 | 自回帰の機能試験(毎コミット) |
| staging | 縮小構成。API 1〜2、Worker 0〜2、単一ゾーン | 機能検証の27項目(02 v0.2第4節)、非機能のスモーク |
| load | 隔離環境。Workerは本番同様にオートスケール | 負荷試験、総当たり検出(02#5の本格検証) |

**時刻操作。** 時刻の参照はすべてClockインターフェース経由に実装し、staging・loadではテスト用のClock制御を注入できる。適用範囲は次のとおりである(FR-41、04 v0.3第5節と同一) — (1)APIの期限判定(response_deadline・expires_atとの比較、06 v0.3第6節。DBのclock_timestamp()を使わないためClock操作で期限切れを再現できる)、(2)Intent期限バッチ・LATCH期限切れバッチ(expiry_sweeper、60秒周期)、(3)30分Bucket再評価のBucket境界、(4)debounceの10秒窓(06 v0.3第9節)、(5)JST 0時のリセットジョブとRedisカウンタのJST日付キー(04 v0.3第5節)、(6)作成・更新の時刻検証(過去不可・上限7日、05 v0.3)。expires_at・response_deadline・30分Bucketの前進はClock操作で再現し、実時間の待ちを排除する。

**疑似イベント注入。** Pub/Subへのテスト用パブリッシャーでMatch Event 5種(01第5節)と派生イベントembedding_completed(06 v0.3第9節、第2段トリガーの到着待ちの再現用)を手動発火できる。LLM呼び出しはLLM Gatewayのテストモード(記録済み応答を返すスタブ、またはレイテンシ注入付き)で決定的にする。FCMはドライラン(送信内容を記録のみ)とし、通知の到達と本文の表示規制(FR-21)は記録で検証する。

**認証のテスト構成(D-21)。** 本番と同じJWT検証経路(JWKS参照)を通しつつ、staging専用の鍵ペアを注入し、テストユーザーのJWTを発行する内部ツールを用意する。Google/Appleの実IdPには依存しない。

## 2. テストデータ

シードIntentは09のゴールドセット(200〜300件)を共用資産として使う。配置はdocs/testassets/にシード定義と期待値表をバージョン管理し、09(Offline評価・構造化精度)と本書(機能・非機能)で同一の資産を参照する。期待値表には、alcohol_involvedの判定精度ゲート(09 v0.3第4.3節)用の**飲酒判定専用入力セット(30件以上)**を含める — alcohol_involved=trueの正例に加え、「ワイン会」「日本酒好きの集まり」「バーでの誕生日会」のような飲酒を明示しない境界表現、および「コーヒーを飲む」等のアルコールを指さない用法の負例を含める(FR-20)。

機能・負荷検証用の追加シードは、02 D-22の密度前提(単一エリア・飲食中心)を反映した分布で生成する。合成ユーザー(実在しない氏名・連絡先)とし、生年月日はD-10の試験(20歳未満の飲酒Intent拒否)のため18〜19歳を意図的に含める。

| 項目 | 分布 |
|---|---|
| 時間帯 | 昼12–13時 20% / 夕18–20時 30% / 夜20–23時 40% / その他 10% |
| カテゴリ | drinking 50% / meal 40% / activity 10% |
| 人数志向 | 1対1 70% / グループ(min≧3)30% |

機能試験に次の配置ケースを含める(FR-17)。

- **自己ペアの除外。** 同一ユーザーの2 Intent(同一時間帯・地域・カテゴリ、embedding上の類似も高い)を配置し、いずれのEvent処理でも当該ペアがmatch_candidatesに生成されないこと、提案通知が発生しないことを確認する(06 v0.3第2節のLayer 1自己除外)
- **自己重複集合の除外。** 同一ユーザーのIntentを2つ含むような3〜4人集合の構成要件を作り、group_candidatesに当該集合が生成されないことを確認する(06 v0.3第7節のHard互換条件・05 v0.3の集合内user_id一意制約)。テストデータの分布(第2節)には自己重複を検出する意図的な配置を含める

部分YES(partial_accept)の再現は、stagingで3〜4人セットの提案に対し一部のみyes回答を投入し、残りを未回答のままClockをresponse_deadline後へ進める(06 D-06の期限時確定条件の検証)。提案の通知順序は、同一Poolから複数集合を発生させ、proposedになった集合がaggregate_score降順の1つだけであることをgroup_candidatesの記録で確認する。

機能検証フェーズの完了が非機能フェーズの開始条件である(パイプライン全体が正常動作しない状態での性能測定は意味を持たない)。

02のマッピング表27項目は、本書v0.1時点で01第25節から除外していたD-10・D-23を含め、02 v0.2で#27(年齢制限)として正式に加わった。両仕様は次のとおり本書の追加試験としてstaging(機能検証フェーズ)で実行する。

- **D-10(#27・飲酒Intentの年齢制限)**: 18〜19歳のテストユーザー(第2節)によるalcohol_involved=trueのIntent作成が拒否されること(422 UNDER_AGE)、およびalcohol_involved=trueのIntentが20歳未満ユーザーとの候補に現れないこと(Layer 1)を確認する。判定規則の精度面は第2節の飲酒判定専用入力セット(09 v0.3第4.3節のゲート: recall 100%・precision下限90%)で検証する
- **D-23(成立後のブロック適用)**: matchedのLATCHで一方がブロックを設定した際、そのユーザーの進行中の提案がcancelledで閉じること、当該LATCHのチャットが読み取り専用化され新規送信が不可になること、表示が「このチャットは利用できません」であることを確認する
- **プッシュ通知の表示規制(FR-21、08 v0.4第2.6節)**: 閾値超過の候補を発生させ、通知ドライラン記録(第1節)のプッシュ本文が汎用文「LATCH候補があります。詳細はアプリでご確認ください」であること、および条件サマリ(人数・時間帯・地域名・カテゴリ・予算)がプッシュ本文に含まれないことを確認する。飲酒カテゴリ(drinking)の提案でも様式が同一であることを含める。summary_onlyの提案については、アプリ内通知(お知らせ。UI語彙は03 v0.4第10節)・提案画面に条件サマリが表示されること(03 v0.4第4節)を、hidden_until_matchの提案については、お知らせにも提案画面にも条件サマリを表示しないこと(02 v0.3 D-03・05 v0.4のproposal生成分岐)も併せて確認する(v0.3)

## 4. 非機能検証

### 4.1 性能試験(01第20節の4目標+Parser)

負荷条件は、04のMVP規模想定(Match Event 1日数千〜1万)のピークを3倍に設定する。Intent保存API 50 rps、Match Event 100イベント/秒のバースト、Jevはレイテンシ注入(p50 2秒 / p95 5秒)、Parserはレイテンシ注入(p50 1秒 / p95 2.5秒、D-17の目標をそのまま破らない注入)で実運用を模擬する。測定はCloud Monitoringのレイテンシ分布による。

| 目標 | 出典 | 測定方法 | 合格 |
|---|---|---|---|
| Intent保存 p95 500ms | 01第20節 | 保存APIのレイテンシ分布 | p95 ≦ 500ms |
| Intent Parser構造化プレビュー表示 p95 3秒・p99 8秒 | 07 D-17(FR-38) | POST /v1/intents/parseのレイテンシ分布(入力確定からプレビュー応答まで) | p95 ≦ 3秒・p99 ≦ 8秒 |
| Candidate Retrieval p95 1秒 | 01第20節 | Layer 1〜2処理時間(トレースID紐付け) | p95 ≦ 1秒 |
| 初期LATCH判定 p95 10秒 | 01第20節(層別予算配分は06 v0.3第1節) | Event発火(active化の保存コミット)から通知記録までのend-to-end。初回投入Event(active作成またはdraft→active化、06 v0.4第1節)経由の初回提案を対象とする | p95 ≦ 10秒 |
| 通知は判定後5秒以内 | 01第20節 | LATCH Engine確定からFCM記録まで | ≦ 5秒 |

初期LATCH判定の測定対象は初回投入Event(active作成またはdraft→active化。v0.3、06 v0.4第1節)経由の初回提案とし、更新Event経由の再評価(debounce 10秒窓込み)は別計測とする(06 v0.3第1節の計測起点の決定に従う)。draft→active化は作成Eventと同一の即時処理(窓なし)であるため、active作成とdraft→active化の双方を同じ測定対象に含め、実施時には投入経路をトレース属性で区別して記録する(v0.3)。第2段トリガー(embedding_completed)までの区間もトレースで分離し、層別予算(Embedding ≤2秒 / Layer 1〜3 ≤1秒 / Jev ≤5秒 / Layer 5+通知 ≤2秒)のどの区間が予算を超えたかを特定できるようにする。

### 4.2 総当たり検出の負荷試験(02#5から委譲)

Active Intent数を1万 → 5万 → 10万と段階的に増加させ、各段階で同一のイベント注入(新規Intent作成100件)を行い、1イベントあたりのVector Retrieval件数・判定レイテンシ・Jev実行回数を観測する。合格は、処理件数とレイテンシがIntent数に応じて急増しない(イベント数比例の範囲に収まる)こと、Vector Retrieval件数がK_v=50以内でIntent数と無関係に安定することである。02#5の本格検証は本試験が担う(02第4節前置きどおり)。

### 4.3 可用性測定

計画停止(デプロイ)を除外タグ付きで区別したうえで、APIリクエスト成功率を合成監視プローブ(1分間隔)で測定する。試験としては、稼働中のAPIコンテナを1インスタンス強制停止し、残存インスタンスでの処理継続と自動復旧を確認する。合格は試験期間中の成功率99.5%以上(01第20節)。

### 4.4 バックアップ・復旧試験

定期バックアップから新しいDBインスタンスへ復元し、Embeddingモデル識別子の記録(01第18節)を使ったVector再構築(再エンベディング)を経てサービスを再開する一連の手順を試験する。復旧後、Intent検索・マッチング・通知が正常であること、およびcross-checkとして復旧前後のactive Intent数が一致することを確認する。RPO・RTOは目標値を持たず(01に規定なし)、試験ごとに実測を記録する。

### 4.5 縮退運転の試験(06 D-15の裏付け)

- **LLM API障害**: LLM Gatewayにエラー注入(100%エラーおよびtimeout)を行う。確認事項は、(1)Jevがスキップされ候補は「Jev未判定」で保留されること、(2)提案が発生しないこと、(3)circuit breakerが開放し、一定時間後に半開で再試験すること(しきい値は06 v0.3 D-15の初期値: エラー率50%超またはp95レイテンシ超過×測定窓1分で開放、60秒後に半開)、(4)Parser失敗時は、LLM障害が503 LLM_UNAVAILABLE(再試行ボタン)、必須欠落が422 VALIDATION_ERROR(フォームフォールバック)として区別されること(07 v0.3 D-17・05 v0.3のエラーcode列挙)、(5)Embedding失敗Intentは保存され、回復後にバックフィルされ、完了時にembedding_completedでパイプラインへ復帰すること
- **復旧後の再評価(FR-18)**: 縮退によってskipped保留された候補が、復旧後に再評価されることを確認する — 上限の日次リセット(0時JSTのリセットジョブ、04 v0.3第5節)後の最初のMatch Event、およびLLM障害回復後のMatch Eventで、skipped候補が再評価対象になること。時間Bucket再評価・頻度制限(30分)解除後の次のEventによる回収(06 v0.3第5節・第9節)もClock操作で確認する。これにより、単一障害を「その夜の提案ゼロ」で終わらせない網羅性を検証する
- **D-16上限到達(04)**: Jevカウンタを日次上限(30,000回)の手前まで投入して進める。80%(24,000回)でalertが発報され(alertにEvent源流上位ユーザーのレポートが添付されること含む)、上限到達でJev実行がスキップ・「Jev未判定」記録・提案なしとなること、0時(JST)のリセットで復帰することを確認する。月次上限(暦月初JST 0時リセット)はClock操作で月初境界を進めて日次カウンタとの独立性を確認する
- **resume・Bucket遅延の回収(FR-18)**: (a)同一ユーザーの2 Intentを配置し、一方をpauseしたうえで対象開始時刻のBucketをClockで経過させ、その後resumeする。resume時にversion+1の再評価Eventが発行され(05第6節)、Embeddingの再実行なくCandidate Retrievalから再評価され、提案が発生し得る状態に復帰することを確認する。(b)Bucket到来Eventのスケジューラを一時停止して欠落を作り、期限前catch-upスキャン(06 v0.3第9節)が回収することを確認する — expires_atまで2時間を切った未処理のIntentが、直近の詳細評価から30分経過後に再評価され、その際Embedding済みIntentが対象に含まれembedding IS NULLのIntentが除外されること

### 4.6 K上限の裏付け試験(06 D-24)

1イベントで一次候補が100件超になる状況(同一地域・時間帯・カテゴリにIntentを密集)を意図的に作り、Vector出力 ≦50、Cheap Judge判定 ≦20、Jev判定 ≦8回(回数ベース。1対1最低4回保証・グループ由来最大4回の配分規則、06 v0.3第5節)、グループPool ≦15が守られることをmatch_candidates・group_candidatesとJev実行回数の記録で検証する。切り詰めの決定性は、同一入力での2回実行が同一結果になることで確認する(スコア上位、同点はintent_id昇順、06)。

### 4.7 Queue障害試験

処理が必ず失敗する毒ペイロード(不正なIntent参照を含むMatch Event)を注入する。retry上限(5回、06第9節)まで再試行したのち、失敗理由を保持してmatch_events.status=quarantinedへ隔離され、滞留が後続イベントに波及しないことを確認する。あわせて、削除済みIntentへの参照Eventがquarantinedではなくprocessedで破棄されること(正当な遅延Eventとして破棄、06 v0.3第9節)と、UNIQUE制約(05)による同一Eventの重複処理排除(2回投入してもmatch_candidatesが二重生成しないこと)を確認する。Queue滞留を作りQueue lagメトリック(01第20節)のalertが発報することも確認する。

## 5. 試験の合格判定と証拠

## 6. 本書の位置づけ

本書は試験方法に専念し、設計値の確定を行わない(00ロードマップ合意)。すべての合格基準は設計文書の確定値の引用であり、試験中に基準の変更が必要になった場合は、元の設計文書(01・04・06等)の改版を経て本書へ反映する。解消する未決事項(D-xx)は存在しない。初期リリース地域(D-22)は11リリース計画書で確定した(駅周辺3km相当の選定基準・密度下限15件)が、本書のテスト環境はテスト用エリアの合成データで構成しており、本番地域の確定に依存しない。
