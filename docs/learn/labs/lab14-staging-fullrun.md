# Lab 14 stagingのフル実行を回す: きれいな世界で、約束34試験を証明する

- 種別: チュートリアル(手を動かして必ず成功体験を得る。ci環境には触れません)
- 前提知識: 第28章(stagingハーネスの設計)・第26章とLab 12(決定的シード)。
  Lab 11(staging環境の立て方)を経験していると、イメージの話がスムーズです
- 所要目安: **35〜45分**。うち `make staging-reset` が約6〜7分・テスト本体が約10分
  (この2つの大部分は待ち時間です)。お金はかかりません(stubで動くため。第28章28.4)
- このLabでできるようになること: staging-resetで「きれいな常設世界」を作り直し、
  自分で生んだ300件のシードを置いて、34試験の受け入れ試験を一気通貫で回せる。
  終わったとき、02#対応表つきの証拠YAMLが `docs/testassets/results/` へ
  出力されているのを自分の目で確認できる
- 次に読むもの: 証拠YAMLの読み方は第28章28.6に戻ると深くなります。このLabが
  第24章の「stagingが自立したらLabを」という引き継ぎの実現です

## 0. このLabで何をするか

Lab 11であなたは、staging環境を立てて**時計**を動かしました。このLabでは、その世界の
上で**試験**を動かします。登場人物は3つです。

| 登場人物 | 何をするもの | 入り口 |
|---|---|---|
| staging-reset | 世界を作り直す(コンテナ・DB・地物データ) | `make staging-reset` |
| m4-seed.yaml | 投入する材料300件(Lab 12で生んだもの) | `docs/testassets/m4-seed.yaml` |
| staging_tests | 約束を34試験で証明するハーネス(第28章) | `make staging-test` |

このLabで回す試験は「staging-reset直後の、きれいな世界」を前提にします(第28章
28.3)。誰かが試験を回したあとの世界で再実行すると、前回の検証データが残っていて
落ちることがあります。**このLabは、必ずresetから始めてください。**途中でやり直すときも
resetへ戻るのが確実です。

前提を1つ確認します。stagingはci環境とは別プロジェクト(latch-staging)なので、
このLabで何をしても、あなたがこれまでのLabで使ってきたci環境には触れません(Lab 11と
同じ安心の仕組みです)。以降、すべての手順をリポジトリのルート(`latch/`)で実行します。

## 1. 鍵とイメージを確認する

stagingの鍵と、起動に使うイメージを確認します。

```bash
make staging-keys
```

何が起きるか: `.staging/keys/` に、staging専用のテストIdP鍵ペアを作ります
(Lab 11と同じものです。すでにあれば作り直します)。このLabの途中で再実行しないで
ください(前の鍵で発行したトークンが無効になります)。

次にイメージです。このLabではコードを1行も変えないので、**イメージの作り直し
(build)は通常いりません**。過去にLab 11をやっている、またはマージ後のmainで
stagingを立てたことがあれば、イメージは既にあります。ただし、コードを更新(git pull等)
したあとでstagingを立てる場合、起動済み/作成済みのイメージは古いコードのままのことが
あります(第1章の注意と同じ話)。そのときは先にbuildします:

```bash
docker compose -f compose.staging.yaml build api1 api2 worker1 worker2
```

何が起きるか: api2台・worker2台のイメージを、現在のコードから作り直します。
キャッシュが効けば数秒、なければ数分かかります。初回・build済みのどちらでも
手順は変わりません(buildは1回だけ、試験の前に通せば十分です)。

## 2. 世界を作り直す: staging-reset

いよいよ世界の作り直しです。

```bash
make staging-reset
```

何が起きるか: 4つの仕事を順にやります。①既存のstagingコンテナと**データ置き場
(ボリューム)の削除**、②8コンテナの起動(全員の健康診断を待つ)、③DB定義の
最新化(マイグレーション)、④地物データの取込。所要は約6〜7分です(2026-10-04の
実測では6分38秒)。出力の末尾は、地物データの取込の記録で終わります
(地物の件数はデータによります):

```
[import-isj] area=ci-provisional isj_town: 46 rows
[import-osm] area=ci-provisional osm_poi: 563 rows
```

続いて、世界が生きているかを3つの窓で確かめます(Lab 11 §2と同じです)。

```bash
curl -s -o /dev/null -w "18000: %{http_code}\n" http://127.0.0.1:18000/health
curl -s -o /dev/null -w "18001: %{http_code}\n" http://127.0.0.1:18001/health
curl -s -o /dev/null -w "18002: %{http_code}\n" http://127.0.0.1:18002/health
```

期待される出力(3行とも200):

```
18000: 200
18001: 200
18002: 200
```

`18000` はnginx経由・`18001`/`18002` はapi1/api2直です。もし`18000`だけが
`502` を返したら、入口のnginxが裏のapiを見つけられていません。次の1行で直ります
(nginxは起動時にapiの居場所を記憶するため、apiが作り変わったとき記憶が古くなる
ことがあります):

```bash
docker compose -f compose.staging.yaml restart nginx
```

(2026-10-04の検証では、reset直後のfresh起動ならrestartは不要でした。502が出た
ときの直し方として覚えておいてください。)

## 3. 材料を置く: seed-generateとseed-verify

材料となるシードYAMLを、**実行日の翌日**を基準日として生み直します(Lab 12 §1と
同じ。例は日本時間の10月4日に実行したもの。あなたが実行する日で読み替えて
ください):

```bash
make seed-generate ARGS="--base-datetime 2026-10-05T11:00:00+09:00"
make seed-verify
```

期待される出力(2つ目のコマンド):

```
cd backend && uv run python -m latch.testassets.verify
OK: ../docs/testassets/m4-seed.yaml の機械検査に合格(a構造/b分布/c意図的配置/d aggregate照合/e地名)
```

ここで1つ、gitに聞いてみましょう。

```bash
git status --short docs/testassets/
```

Lab 12 §1では「何も出ない」が正解でした。このLabでは、基準日がコミット済みのものより
先に進むため、**`m4-seed.yaml`が差分ありと表示されます**:

```
 M docs/testassets/m4-seed.yaml
```

出ても驚かないでください。基準日がコミット済みのもの(2026-10-04生まれ)と違う日は、
日付まわりの行が変わります(第26章26.3・Lab 12 §5で分類したとおり「変わるのは
日付まわり・件数と集計は変わらない」です)。次のコマンドで確かめられます:

```bash
git diff docs/testassets/m4-seed.yaml | rg "layer1_pass"
```

期待される出力:

```
(何も表示されない)
```

集計が差分に出ない=材料の中身は同じ・日付だけが動いている。ハーネスはこのYAMLを
読んで世界に投入します。試験が終わったら、この差分は `git checkout
docs/testassets/m4-seed.yaml` で戻せます(§6で戻します)。

## 4. 予測を書いてから、回す: staging-test

**実行する前に予測を書いてください**(my-notes.mdへ)。いま手元のYAMLの
`layer1_pass` は627です(生んだ直後の出力に表示されたはずです)。ハーネスのS0は、
「DBに実際に並んだ候補ペア」と「この627」を突合します。この突合は、数字が**ぴったり
等しい**ことを検査するでしょうか。それとも、ある方向の包含(片方がもう片方を
含むこと)を検査するでしょうか。第28章28.8の「2経路」の話を思い出して予測して
ください。

いよいよフル実行です。**約10分かかります**(待ち時間の内訳は第28章28.5の
とおり・60秒tickをそのまま待つためです)。長いので、実行してからはコーヒーを
一杯どうぞ。

```bash
cd backend && uv run pytest staging_tests -q
```

何が起きるか: `make staging-test` と同じ実行です(Makefileのこのターゲットの中身は
この1行です。オプションの `-q` は「簡潔に表示する」指定)。34試験が、S0〜S5の
旅路の順に実行されます。

期待される出力(末尾。所要は環境によります):

```
..................................                                       [100%]
34 passed in 598.91s (0:09:58)
```

34個の `.` が34試験の緑です。**34 passed**。あなたがLab 12で生んだ300件のシードが
置かれた世界で、第24章と第28章で読んだ約束の証明が、全部緑で終わりました。

さきほどの予測の答え合わせをします。正解は**包含**でした。S0は「DBに生成された
ペア集合」が「期待集合(627)」の**部分集合**であることと、代表EX 7組が実在することの
2点を検査します(証拠YAMLでは「生成集合⊆pass集合+代表EX実在」という名前で記録されて
います)。等しいとは言わない理由は、DBの699行にはペア検索と集合検索の**2経路**の行が
含まれるからです(第28章28.8)。

## 5. 証拠YAMLを読む

pytestの緑だけが合否ですが、このハーネスの本体は証拠YAMLです(第28章28.6)。
出力先を見てみましょう。

```bash
ls -t docs/testassets/results/ | head -3
```

期待される出力(先頭が**いま実行した日時**のファイル。ここでは2026-10-04の0時台に
実行した例):

```
ws3-staging-result-20261004-000446.yaml
ws3-staging-result-20261003-231505.yaml
g2-jev-result-20260930-144518.yaml
```

1行目があなたの実行で出たもの、2行目はws-3のマージ時に記録済みの証拠です。
**同じYAMLが実行ごとに別ファイルとして積み上がる**のが出力の設計です(過去の証拠を
上書きしない)。中身を読みます。先頭と、合否の集計を確認しましょう:

```bash
head -10 docs/testassets/results/ws3-staging-result-20261004-000446.yaml
rg "verdict:" docs/testassets/results/ws3-staging-result-20261004-000446.yaml | sort | uniq -c
```

期待される出力(先頭。実行日時はあなたのものに):

```yaml
unit: M4-ws-3
executed_at: '2026-10-04T00:04:46.614463+09:00'
environment: latch-staging
items:
- id: S0-env
  name: 環境前提(8サービス・head・geo・鍵)
  test: test_s0_environment_prerequisites
  verdict: pass
  observed:
    alembic_head: '0007'
```

集計の期待される出力(2026-10-04の実行例):

```
33   verdict: pass
```

33項目全部がpassです(34試験→証拠は約束単位で33項目。#15など、約束1つを2試験で
証明するものがあるため、第28章28.6のとおりです)。あなたの実行日時のYAMLで
同じ集計になれば、このLabの成功体験の完成です。

最後に、約束(02#)と証拠の対応を1つ、自分の目で確かめます。マージ時に記録済みの
証拠YAML(実行日の欄が `20261003-231505` のもの)で読んでみます:

```bash
rg -A8 "^- id: 02#8$" docs/testassets/results/ws3-staging-result-20261003-231505.yaml
```

期待される出力(マージ時の証拠の実測値。あなたの実行で出たYAMLに読み替えても
構いません。そのとき数値は少し前後します):

```yaml
- id: 02#8
  name: 時刻到来再評価(保留→proposed昇格)
  test: test_s1_item08_retention_promotion
  verdict: pass
  observed:
    retained_before: 406
    promoted_delta: 23
    clock_set_to: '2026-10-05T00:05:00+09:00'
```

`retained_before: 406` は「日次上限で保留になっていた候補が406件あった」、
`promoted_delta: 23` は「0時跨ぎでそのうち23件が提案へ昇格した」の観測値です。
時計を進めたのはハーネス(第28章28.5の旅路1)。昇格させたのは、常設のworkerが
60秒tickで動いた結果です。**あなたは1秒も待たずに「0時を跨いだ」**——これが、
このハーネスの動かし方の核心です。

## 6. 片付ける

世界を止めて、材料の差分を戻します。

```bash
make staging-down
git checkout docs/testassets/m4-seed.yaml
git status --short docs/testassets/
```

`staging-down` では止まったコンテナの名前がログに並びます。最後の `git status`
の期待される出力:

```
(何も表示されない)
```

`staging-down` はコンテナを止めて取り除きます(データ置き場は残るので、次に
staging-resetでまた作り直します)。`git checkout` で、§3で生んだ日付まわりの差分を
元に戻しました。

あなたの実行で出た証拠YAML(`ws3-staging-result-あなたの実行日時.yaml`)は、
実行の記録として手元に残って構いません(git管理下に入るのはコミットしたとき
です。残しておきたくないなら、ファイルを削除しても問題ありません。マージ時に
記録済みの証拠YAMLは、消さないでください)。

my-notes.mdに、次の3つを書き残すのをおすすめします。

1. **§4の34 passed**。この緑が「部品の正しさ」と「約束全体の守られ方」の

2. **§5の02#8の観測値**。`retained_before` と `promoted_delta` の数字から、

3. **証拠YAMLが実行ごとに積み上がる設計**。過去の証拠を上書きしないことの
   意味を、第24章の「証拠」の言葉と繋げて書く

疑問が残ったら、それもノートに書いてください。あなたがこのLabで回した試験は、
ws-3のマージ時に行われた証明と同じ手順です。同じ手順が、あなたの環境・あなたの
実行日で同じ34試験を緑に通す——第26章で学んだ「再現できる」が、テストデータだけで
なく**試験そのもの**にも成り立っているのを、このLabは示しています。
