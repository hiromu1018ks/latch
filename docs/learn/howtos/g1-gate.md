# G1精度ゲートを実行するには(Parserの精度を自分で測る)

- 種別: 手順書(how-to。「どうやる?」に答えるレシピです)
- 前提知識: 第5章(スタブと実LLMの住み分け・422/503の切替・ParserOutput)
- この手順書の使い道: Parserやプロンプトを変更したとき・Parserの精度を確認したいときに開く
- 次に読むもの: なし(必要になったときに開く文書です)

## このレシピでできること

第5章で、Parser(LLM)は「律儀でない協力者」であり、出力は境界で検証してから
システムに入れると学びました。では、**そのParserが実際どれくらい正確か**は、
どう確かめたらいいでしょうか。

「30件以上の入力セットをParserへ流し、出力と期待値をフィールド単位で照合して、
一致率が基準を超えているかを見る」という検査を、このプロジェクトでは
**G1精度ゲート**(G1 = M1マイルストーンの合格条件1番。ゲート=門番)と呼んでいます。
基準は次の2本です(仕様書 docs/07 §5 D-17・docs/09 §4.3)。

- 構造化精度: category 85% / time.start 90% / location 90% / participants 80% / budget 90%
- alcohol_involved(飲酒判定): 見逃し0件(recall 100%)・誤検出は下限90%(precision)

2026-09-28、実プロバイダ(Anthropic Claude API・Haiku 4.5)のadapterがマージされ、
この検査を1コマンドで実行できるようになりました。対象は実APIなので、**実行には
お金がかかります**。見込みは全体(71呼び出し)でおよそ$0.3未満、1呼び出しあたり
約$0.004です。まずは部分実行(`--limit 5`・約$0.05)で様子を見る手順にします。

なお、ゲートに「合格」と出ても、それでM1合格が自動決定するわけではありません。
合否の承認は人間(運用ルール)です。このコマンドの役目は、**判断に使う証拠を
機械的に集めること**までです。

## 手順1: .env に2行を整える

実APIの鍵(APIキー=利用権の証となる秘密の文字列)は、リポジトリの外の `.env`
というファイルで管理します(git管理外。`.env.example`が見本)。実行には次の2行が
必要です。

```bash
LATCH_LLM_MODE=real
LATCH_ANTHROPIC_API_KEY=sk-ant-...(あなたの鍵)
```

設定済みかどうかは、値を表示せずに確認できます。

```bash
rg -c '^LATCH_LLM_MODE=real$' .env && echo "LLM_MODE OK"
rg -n '^LATCH_ANTHROPIC_API_KEY=.+' .env >/dev/null && echo "API_KEY OK(空でない)"
```

期待される出力(両方設定済みのとき):

```
1
LLM_MODE OK
API_KEY OK(空でない)
```

`LATCH_LLM_MODE` はLLM呼び出しのモード指定です。`real` は「Parser系統のみ実API」
(Embedding/飲酒評価Jev系統はM2までスタブのまま)、既定の `stub` は「全部スタブ」。
apiコンテナ(compose)へはこの変数を渡さない規約なので、`make up` で立つ開発環境と
CIは常にstubのまま動きます。実APIは、この手順書の経路だけで使われます。

## 手順2: まず --limit 5 で確かめる(約$0.05)

いきなり全件ではなく、各入力セットの先頭5件だけ流します。`backend/` に移動して
実行してください(資産の既定パスが `../docs/testassets` なので、場所が重要です)。

```bash
cd backend && uv run --env-file ../.env python -m latch.g1gate --limit 5
```

2026-09-28にこの手順書のために実行したときの出力です。

```
P-001: ok
P-002: ok
P-003: ok
P-004: ok
P-005: ok
A-001: ok
A-002: ok
A-003: ok
A-004: ok
A-005: ok
E-001: 422 VALIDATION_ERROR
E-002: 422 VALIDATION_ERROR
E-003: 422 VALIDATION_ERROR
report: ../docs/testassets/results/g1-result-20260928-203258.yaml
overall_passed: False (incomplete=False)
```

読み方です。`P-` は構造化精度のケース、`A-` は飲酒判定のケース、`E-` は「構造化
できない入力」で、**422が返ること自体が正解**のケースです(第5章の422/503の
切替を思い出してください。E-3件が422は期待どおり)。最後の2行がレポートファイルの
場所と総合判定です。この実行は exit code 1(不合格の意)で終わりました。

### exit 1 でも「壊れて」いない——実LLMは揺らぐ

`overall_passed: False` に驚かないでください。上の実行では、P-003(入力
「土曜の夜、サワー飲みに行きたい!天文館界隈で、予算5000円まで」)で、
「夜」だけの時刻指定を20時と丸める規則による期待値 `20:00` に対して
LLMが `19:00` を返し、time.start の一致率が 4/5 = 0.8 になって、基準の0.9を
切りました。同じケースでlocationは期待「天文館」に「天文館界隈」を返して
いますが、こちらは地域として一致とみなされ `match: true`——「表記の揺れは
同一地域として一致扱いする」という照合規則(docs/07 §5 D-17)が働いています。

同じ日(20:21)に実装チームが同じ `--limit 5` を実行した記録
(`docs/testassets/results/g1-result-20260928-202115.yaml`)は
`overall_passed: true`(5/5全部一致)です。同じ入力・同じ鍵・同じコマンドでも、
結果が変わりました。

これが「実LLMは律儀でない協力者」の具体的な姿です。LLMは毎回まったく同じ
計算をする機械ではなく、確率的な揺らぎを持つ相手です(入力のJSONの**形**は
structured outputsというAPI側の仕組みが保証しますが、**中身**——「21時から」を
21時と読むか20時ごろと読むか——までは保証できません)。だからG1ゲートは、1件の
当たり外れでなく、**セット全体の一致率**で判定するように作られています。5件なら
1件で0.2も動きますが、32件なら1件で0.03です。部分実行(`--limit`)はharnessの
動作確認用であり、**合否の材料にはしない**と運用で決まっています。

なお、不合格には「揺らぎ」とは別の種類もあります。規則そのものに隙があって、
何度測っても同じ所で落ちるタイプです。実例と直し方は、この後の
「不合格の原因を特定する」の節で扱います。

## 手順3: 全件を実行する(見込み$0.3未満・3〜6分)

部分実行でharnessが動くことを確認したら、全件(32+36+3=71呼び出し)を実行します。
Makefileに登録済みのターゲットが使えます。

```bash
make g1-gate
```

中身は `cd backend && uv run --env-file ../.env python -m latch.g1gate` です。
`--limit` を外すと全件になります(makeのターゲットへ `--limit 5` を後付けでは
渡せないので、部分実行のときは手順2のように直接コマンドを打ちます)。

71呼び出しを直列(1件ずつ順番)に流すので、所要は3〜6分の見込みです
(design §2.11。並列にしないのは、レート制限(APIを短時間に大量に呼びすぎない
配慮)と、精度測定が目的で速さの測定はM4だからです)。出力は手順2と同じ形式で
71ケース分が流れ、レポートが
1枚書き出されます。全件実行のタイミングは、Parserやプロンプトを変更したとき
(09 §4.3)と、G1判定を取るときです。全件の成否レポートはG1判定(人間)への
入力になり、`docs/testassets/results/` に証拠として保管されます。

## レポートの読み方

出力先は `docs/testassets/results/g1-result-<実行日時>.yaml` です(git管理。
試験ID・実施日・環境・入力条件・合否を残す場所として docs/10 §5に定められています)。
構造はこうなっています(手順2の実測レポートからの抜粋です)。

```yaml
meta:
  trial_id: g1-20260928-203258          # 試験ID(実行日時から自動生成)
  executed_at: '2026-09-28T11:32:58.341823+00:00'
  llm_mode: real
  model: claude-haiku-4-5
  parser_prompt_sha256: 80768d52...     # プロンプト全文の指紋
  input_sets:                           # 入力セットの指紋(どの版で測ったか)
    parser_struct: {file: g1-parser-struct.yaml, sha256: 37169a64...}
    alcohol: {file: g1-alcohol.yaml, sha256: b88d5c58...}
  base_current_datetime: '2026-10-01T11:30:00+09:00'  # 測定の基準日時
parser_struct:
  fields:
    category:    {match: 5, total: 5, rate: 1.0, threshold: 0.85, passed: true}
    time_start:  {match: 4, total: 5, rate: 0.8, threshold: 0.9,  passed: false}
    ...
overall_passed: false
```

見るべきところは3つです。

1. **`meta` の指紋**: プロンプトと入力セットのSHA256(ファイルの内容から計算する
   要約値。同じ内容なら同じ値になる)が記録されるので、「どのプロンプトで・どの
   入力セットで測った結果か」が後から証明できます。測定の再現に必須の情報です。
   プロンプトを改訂すれば指紋も変わるので、改訂前の結果と改訂後の結果の区別が
   1目でつきます(実例は次の節)
2. **`fields` の rate と threshold**: フィールド別の一致率と基準。`match: 4, total: 5`
   のように分子分母も残るので、数字の意味を取り違えません
3. **ケース別の `actual`**: レポート後半には全ケースの期待値と実測値(Parserの
   生の出力全体)が並びます。失敗したときの分析——どの入力で・どのフィールドが・
   どう外れたか——はここから読み取ります

飲酒判定(`g1-alcohol.yaml` 由来)は、TP/FP/FN/TN(recall・precisionの材料になる、
「正しく飲酒と判定した件数」等の4種類の集計)として集計され、`recall` と
`precision` で判定されます。

## 不合格の原因を特定する: 見逃し1件から規則を直した実例

手順2で見たP-003のずれは、測るたびに結果が揺れる**揺らぎ**の不合格でした。
ところが同じ日の全件実行には、揺らぎでは説明のつかない不合格が1回あります。
レポートから原因を特定し、規則を直し、再実行で合格まで持っていった実例なので、
不合格に遭ったときの手本として記録しておきます。

**何が起きたか**。2026-09-28の全件実行(レポート `g1-result-20260928-203517.yaml`)は、
構造化ゲートこそ合格したものの、飲酒判定で見逃しが出ました。**FN**(false
negative。飲酒が期待されたのにfalseと判定されたケース)が24件中1件。recallは
95.8%で、基準の100%に届かず不合格です。見逃したケースは、レポートのケース
一覧から機械的に探せます。`backend/` で実行します。

```bash
rg -n 'classification: fn' ../docs/testassets/results/g1-result-20260928-203517.yaml
```

期待される出力:

```
2697:    classification: fn
```

1件だけ見つかります。この行の前後にケースの身元が書かれているので、範囲を
付けて読みます(`rg -n -B 2 -A 12 'classification: fn' …`)。

```yaml
  - id: A-034
    expected: true
    classification: fn
    actual: false
    actual_raw:
      category:
        primary: drinking
        secondary: null
      alcohol_involved: false
```

入力テキストは「barでコーラだけ飲むつもり。今日21時、天文館のbarで」。期待値は
true(飲酒を伴う場に身を置く機会として扱う。08 D-10)ですが、Parserはfalseを
返しました。actual_rawを読むと、category.primary は正しく drinking と取れている
のに alcohol_involved が false。場所が飲酒の場だと理解できているのに、「本人は
コーラ」という部分を優先してfalseとした読みです。当時のプロンプト規則7には
「飲酒の場にいるが自分は飲まない」場合の規定がなく、「アルコールを指さない用法は
false」という規則に引きずられていた。コードをいくら読み直しても不具合は見つかり
ません。原因は**仕様の隙**——プロンプトの書き漏らしです。

**直し方**。規則7へ2項目が追記されました(オーナー承認のうえ、docs/07は
v0.5→v0.6へ改版)。

- バー・酒場など飲酒の場を表す語があるときは、飲まないつもりでも(「コーラに
  する」等)true。場所の語を飲み物の意向より優先する
- 「ノンアルコールビール」のようにアルコールでないことが明示された飲み物は
  trueの根拠にしない

プロンプトの変更は仕様変更なので、docs/07本文と `prompt.py` の定数に同じ文面を
入れます。この一致は第5章5.8のピン留め試験が見張っていて、docs/07を直すだけで
試験コードは1行も変わらない仕組みです。

**再実行**。改訂後の全件実行(`g1-result-20260928-210042.yaml`)では、A-034は
TP(期待true・実測true)に是正され、recall・precisionとも1.0、両ゲート合格
(`overall_passed: true`)。先ほどのrgコマンドをこのレポートに向けて打つと、
fnは1件もなく、何も返りません。`meta.parser_prompt_sha256` が `80768d52…` から
`5e7e9102…`へ変わっていることも、改訂後のプロンプトで測った証拠として記録に
残っています。

不合格を見たら、まず「揺らぎか、隙か」を1ケースの身元から切り分けてください。
材料はレポートのactual_rawに「どこまで正しく取れていて、どこから間違えたか」が
全部残っていること。揺らぎなら再実行で結果が変わりますが、隙は規則を直すまで
同じ所で落ち続けます。

## 401が出たら: 環境変数がSDKを書き換える実話

実装チームが実際に遭遇した事件を、トラブルシュートの見本として記録しておきます
(報告書 `docs/plans/M1/ws-6-report.md` §5.1)。

**現象**: スモーク実行が401(認証エラー)で失敗する。エラー文面は
`'token expired or incorrect'`。

**原因**: 開発に使っていたマシンのシェルには、Claude Code用のプロキシ設定として
環境変数 `ANTHROPIC_BASE_URL=https://api.z.ai/api/anthropic` が設定されていました。
anthropic SDK(Anthropic公式の、APIを呼ぶための便利ライブラリ)は、コードで
`api_key` を明示的に渡していても、**この環境変数を勝手に読んで接続先を切り替えます**。
そのため、有効な本物のAnthropic鍵が、コードの意図とは違うz.aiプロキシへ送られ、
プロキシ側の独自の401(文面が公式と違う)が返っていました。

この事件が見つかりにくかった理由は2つあります。鍵自体は有効だった(公式APIへの
直接curlで200を確認)、コードも正しかった(公式APIを向くつもりで書かれていた)。
**壊れているのは、コードと鍵の間にある「SDKが環境を読む」挙動**でした。

**修正**: LATCHは接続先を常に明示的に渡すことで、環境変数に左右されないように
しました(`llm/anthropic.py` の `base_url` 指定。Settingsの `LATCH_ANTHROPIC_BASE_URL`
で変えられる。通常は既定の公式APIのまま)。この「汚染環境下でも公式APIを向く」ことを
立証するunit試験も付いています(`test_anthropic_provider.py` の
`test_default_client_targets_official_api`)。

**一般則として**: 依存ライブラリは、あなたが渡した引数以外に**環境変数を読む**
ことがあります。「コードは正しいのに動かない」ときは、自分のコードだけでなく、
ライブラリが周囲の環境から何を拾っているかを疑ってください。そして、重要な値は
暗黙の既定に任せず、明示的に渡して固定する——これがこの事件の教訓です。

## make test に実APIは混ざらない

コストのかかる実API呼び出しが、うっかり `make test` の中で走ってしまわないか。
この心配への答えが、ws-6の設計の柱の1つです。

- 実APIを呼べる経路は `python -m latch.g1gate` というCLI**だけ**。pytestには実APIを
  叩く試験が1つもありません(markerの付け忘れで混入する余地自体がありません)
- CLIは起動時に `LATCH_LLM_MODE=real` と鍵の有無を検証し、不足なら exit code 2 で
  拒否します(stubのまま実測したと錯覚させないため)
- 鍵は `uv run --env-file ../.env` によって make の経路でのみプロセスへ渡ります。
  composeのapi/workerへは渡らないので、CI・開発環境は常にstubです

だから `make test`(575件・3秒台)は、鍵なしでも、オフラインでも緑のままです。
