## 7.1 使うほどお金が減るサーバーを守るには

ここまでの章で読んできたAPIは、どれも「正しいリクエストを正しく処理する」ことを
考えてきました。この章の主題は違います。悪意のあるなしにかかわらず、
**量が多すぎるリクエスト**を、どうやって入口で断るかです。

LATCHが他のWebサービスと少し事情が違うところから説明します。LATCHのマッチングは
AI(LLM)を使います。つまりこのサーバーは**処理すればするほどお金がかかる**仕組みです。
利用者が無料だからといって、運営のコストがゼロではありません。Intentが1件保存される
たび、やがてマッチングの評価(Jevと呼びます。M2で実装)が動き、そのたびにAIの
利用料が発生します。

ここに、量の問題が入り込みます。第6章で見たとおり、Intentの保存や更新は「出来事
(match_events)」を1行ずつ記録します。保存・更新を繰り返せば、そのたびに新しい
出来事が生まれ、そのたびに将来のAI評価の回数が増えます。仕様書のレビューで指摘された
具体例がこれです——**同一ユーザーがIntentの更新を反復すると、Match Eventが大量に
発生し、AIコストの上限を食い潰せる**(01レビューF-32)。悪意がなくても、スマホの
通信不良で保存ボタンを連打するだけで起きてしまいます。

この経路を塞ぐ判断が、仕様書の08 §5.4でなされました。**入口(APIを受付する段階)で
「多すぎる」を断る**。これがレート制限(rate limit=速度の制限)です。

もう一つ、大事な構えがあります。入口の制限は**1つの鍵で済ませない**こと。入口を
通過したリクエストの先には、AI評価1回ごとの予算(Jev予算。1Intentあたり日次40回など。
M2で実装)という第2の鍵が控えています。入口で源流を絞り、通過した先でも1件ずつ
上限を守る。この重ね方を**多層防御**と呼びます。たとえ入口の上限値の決め方が緩すぎた
としても、第2層があるので被害が無限に広がりません。逆に、入口だけで完璧を狙うと
上限値の調整が神経質になります。この章で読む実装には、ところどころ「厳密さを
求めすぎない」判断が出てきますが、その安心材料はこの多層構成です。

## 7.2 上限4種と、429と422の使い分け

ws-4で実装された上限は4種です。08 §5.4から、そのまま表にします。

| 何の上限か | 値 | 単位 | 超えたとき |
|---|---|---|---|
| ActiveなIntentの数 | 5件 | ユーザーごと | 422 ACTIVE_INTENT_LIMIT |
| Intentの作成 | 20件 | 1日(ユーザーごと) | 429 RATE_LIMITED |
| Intentの更新 | 6回 | 1時間(Intentごと) | 429 RATE_LIMITED |
| API全体のリクエスト | 60回 | 1分(ユーザーごと) | 429 RATE_LIMITED |

値の根拠は「正常な利用を損なわない下限」と「攻撃経路を塞ぐ上限」の間に置かれています。
ふつうの利用ならActiveは数件・修正は数回で足りる。だから5件・6回でも困りません。
一方で連打や反復更新は、この枠ではるかに足りない。その差の分だけ守れている、という
置き方です。

ステータスコードが2種あることに注目してください。第4章で422は「送られた内容に
問題がある」、第5章で503は「サーバー側の部品の障害」と学びました。今回新しく
登場するのは **429(リクエストが多すぎる)** です。違いを一言でいうと——

- **429は「速さ」の制限**です。時間が進めば自然に回復します。1分待てば次の60回、
  翌日になれば次の20件。断られた当事者は、待つか、それ以外のことをするかすればよい
- **422は「今の姿」の検証**です。Active 5件の上限は、時間が経っても自動では解決し
  ません。既存のIntentを止めるか、期限が切れるのを待つしかない。だからエラーメッセージも
  「既存のIntentを停止するか、期限切れを待ってください」という内容(案内)になります

この違いは、このあとの7.3で「数える場所」の違いとして、コードの上に現れます。

## 7.3 数える場所の住み分け: 変わりやすい回数はRedis、今の姿はDB

「20件/日」を実装するとき、まず疑問になるのが「**今何件目か**を、どこに置くか」です。
答えが、この実装の最初の工夫です。**回数を数える3種(作成・更新・API全体)はRedis、
Active数の1種はDB(PostgreSQL)** と、住み分けました。

### 回数はRedisのカウンタに

回数という数の性質を考えてみてください。どんどん増える。でも、窓(1分・1時間・1日)が
進めば、過去の値はもう要らない。保存しておく価値は一時的です。これは第1章で
「付箋」と呼んだRedisの性質そのものです。メモリ上で超高速に読み書きでき、
Redisには `INCR`(インクリメント=1ずつ足す)という、まさにカウンタのための
コマンドがあります。

第4章の書き込み経路を思い出してください。何かを数えるたびにDBへ行を挿入していたら、
守るための仕組みがDBを一番忙しくさせます。本末転倒です。

### Active数はDBで数える

一方、Active数は性質が違います。これは「回数」ではなく**今の姿**です。第6章の
状態遷移を思い出してください。Intentは pause されればActiveでなくなり、resume されれば
戻り、DELETEされればcancelledになり、期限が切れれば expired になります。Active数とは、
この遷移の結果としてのDBの状態そのものです。真実の源(そこにだけ正しい値がある
場所)は、**intents表**です。

もしActive数をRedisのカウンタに置いたらどうなるでしょう。作成で+1、pauseで−1、
resumeで+1、DELETEで−1……と、遷移のたびに足し引きを配線することになります。
配線を1つでも忘れるか間違えれば、カウンタは実際のActive数から永久にずれます。
ずれ方が「多めに数える」側なら、枠がいつまでも空かず、ユーザーが新しいIntentを
作れなくなります。「少なめに数える」側なら、上限が無意味になります。

DBで数えるなら、こう書くだけです(`backend/src/latch/intents/store.py` の
count_active。条件の根拠は設計メモ§2.3):

```sql
SELECT COUNT(*) FROM intents
WHERE user_id = :uid AND status = 'active'
  AND (expires_at IS NULL OR expires_at > :now)
```

最後の条件は、このプロジェクト特有の事情への対応です。期限切れのIntentのstatusを
expiredへ掃く仕組み(expiry_sweeper)の実装はM3なので、現状は期限が切れた行もDB上は
`status='active'` のまま残ります。しかし遷移表(05 §6)上、期限切れのactiveは
すでにexpired相当。そこで計上の条件から除外しています。除外しないと、期限の切れた
IntentがいつまでもActive枠を占有し、「期限切れを待って枠を空ける」という422の
案内が嘘になってしまいます。

### 数えるだけでは足りない: 競合の話

ところで、COUNTしてからINSERTするまでの間にも、リクエストは届き続けます。
「COUNTしたら5件だった、よし6件目も作ろう」——そのINSERTが終わる前に、同じ
ユーザーの別リクエストがCOUNTして、やはり5件を見て6件目を作る。並行すると
6件・7件と突破できます。どちらのリクエストの処理も正しいのに、読みと書き込みの
間の隙間を通って組み合わせると壊れる、という問題です。

ここで第6章の道具が再登場します。**users行への FOR UPDATE**。Active化する前に
そのユーザーのusers行に鍵をかけてから、COUNT→保存までを同一トランザクションで
行います。すると同一ユーザーのActive化操作が並行に走らず、1つずつ直列に
なります。users行は1行・ロック時間は短く、入口に60req/分の制限もあるので、
ここが詰まる実害はありません。コードは `backend/src/latch/intents/service.py` の
`_check_active_limit` にあります。

```python
    async def _check_active_limit(
        self, conn: AsyncConnection, user_id: uuid.UUID, *, now: datetime
    ) -> None:
        """Active数検証(§2.3: users行ロック→COUNT→判定を同一トランザクションで)。"""
        await self._store.lock_user_row(conn, user_id)
        count = await self._store.count_active(conn, user_id, now=now)
        if count >= self._limiter.active_limit:  # type: ignore[union-attr]
            raise ActiveIntentLimitError(
                "active intent limit reached; pause or let expire an intent"
            )
```

3行が、鍵→数える→判定の順に並んでいます。ロックも計上もDBの世界で完結するので、
RedisカウンタとDBの状態がずれる心配も、ここにはありません。

## 7.4 リセットを予約しない: 「1日」を鍵の名前で表す

2つ目の工夫は、この章でいちばん面白いところです。**「20件/日」の「日が変わったら
0に戻す」を、どう実装するか。**

カウンタをRedisに置くと決めた時点、残った問題はこれです。素朴に考えると、
2つの方法が浮かびます。

**案1: TTLで自動消滅**。第1章で見たRedisの便利機能で、鍵に寿命を設定できます。
「24時間後に消えるカウンタ」を作れば、リセットの仕事をRedisに任せられそうです。
しかし08 §5.4の元になった04 §5は、これを**明示的に否定**しています。理由は
時差です。TTLの寿命は「設定してから24時間後」であり、その時計はUTC(世界標準時)
基準で動きます。一方、サービスの利用者にとっての「1日」は日本時間(JST)の0時に
区切られます。JSTの0時はUTCの15時。**TTLでリセットすると、カウンタの「1日」が
日本の「1日」と最大9時間ずれる**のです。夜の23時に20件作ったユーザーが、
翌朝の0時1分に作ろうとしても「まだ1日経っていない」と断られる。これでは
「20件/日」の約束を守ったことになりません。

**案2: リセットジョブ**。JSTの0時ちょうどに起きてカウンタを消すプログラム
(スケジューラのジョブ)を用意します。時差の問題はなくなりますが、新しい心配が
できます。そのジョブが1日に1回、単一の責任を負うことになる——ジョブが失敗したら?
起動が遅れたら? 0時を過ぎてもカウンタが消えていなければ、やはり翌日の20件が
作れないままです。0時を過ぎて最初のリクエストが来たときに自分で掃除する
(自己修復)仕組みも考えられますが、それは「ジョブが通常やる仕事の別実装」を
もう1つ抱えることです。

**採用された案は、リセットを「予約」しないことでした。**発想を逆にします。
カウンタを消すのではなく、**鍵の名前に日付を埋め込む**のです。実際の鍵の形を
`backend/src/latch/ratelimit/store.py` から見てください。

```
rl:create:{user_id}:{yyyymmdd}        ← 作成20件/日。yyyymmdd は JST の暦日付
rl:update:{intent_id}:{yyyymmddHH}    ← 更新6回/時。日付+時
rl:api:{user_id}:{yyyymmddHHMM}       ← API60req/分。日付+時+分
```

`rl:create:00000000-…:20260928` という鍵の値が20になったとします。翌日、
同じユーザーが作成に来たら、limiterは **`rl:create:00000000-…:20260929` という、
まだ存在しない別の鍵**をINCRします。存在しない鍵のINCRは1を返す。つまり
新しい日は、最初のリクエストの時点でカウント1から始まります。前日の鍵が
20のまま残っていても、誰もそれを見に行きません。

**リセットとは、実際には「翌日の鍵を開けること」**でした。消す処理も、
切り替えの瞬間を管理する者も、どこにも要らない。時間が進むこと自体が、
自然に次の鍵へ移してくれます。古い鍵はTTL(作成カウンタなら48時間)で
勝手に掃除されますが、これは掃除であって、リセットの役割を担ってはいません。
TTLが多少ずれても、リセットの正しさには一切影響しない、という分担です。

### 固定窓という名前と、その弱点

この方式には名前があります。時間を0時ぴったり(分なら0秒ぴったり)で区切って
できる窓で数えるので、**固定窓(fixed window)** と呼びます。対比されるのは
**滑らかな窓(sliding window)**——「直近24時間」と、窓の端を現在時刻に合わせて
ずらし続ける数え方です。滑らかな窓なら「どの24時間区間でも20件以下」を
厳密に守れますが、実装はRedisのsorted setへの記録と範囲除去が必要になり、
試験もメモリ消費も重くなります。

固定窓の弱点は、境界の両側に寄せられることです。23:59に20件、0:01に20件。
合計 **2分間で40件** が作れてしまいます(瞬間2倍)。分窓でも同じことで、
21:00:59と21:01:00にまたがれば2分で119リクエスト通ります。

なぜこれを許容できるのでしょう。7.1の多層防御を思い出してください。この上限に
課された役目は**源流の抑制**にとどまります。そして通過した先には、AI評価の
回数そのものを制限するJev予算(第2層)が控えています。境界2倍くらいの寄せは
第2層が受け止める。厳密さのために滑らかな窓の複雑さを導入するより、単純で
試験しやすい固定窓+多層構成を選ぶ——設計メモ§2.2に「境界2倍は許容できる」と
明記されているのは、この計算です。

### なぜJSTで、なぜClock経由か

日付を鍵に埋めるなら、その日付の基準が問われます。答えはJST。利用者の生活の
1日に合わせるのが「20件/日」の意味だからです。そして、その日付の取得は
**Clockを経由します**。`backend/src/latch/ratelimit/limiter.py` の該当部分です。

```python
    def _minute_bucket(self) -> str:
        return self._clock.now().astimezone(JST).strftime("%Y%m%d%H%M")

    def _day_bucket(self) -> str:
        return self._clock.jst_date().strftime("%Y%m%d")
```

`jst_date()` は第3章で読んだ `core/clock.py` のメソッドで、`now()` をJST暦の
日付に変換します。時・分の入ったバケットは、`now()` をJSTへ変換してから
書式化。`strftime` の `%Y%m%d` が「20260928」のような文字列を作ります。

第3章の規律——製品コードが実時間を直接参照しない、時刻はすべてClock経由
(C2)——は、このパッケージにもそのまま効いています。毎コミットで走る番人テスト
(`test_arch_no_direct_time`)は ratelimit 配下も検査対象で、違反は赤になります。
そして効率の話も第3章と同じです。**JST 0時の直前と直後を作れるのは、偽の時計
(FakeClock)だけ**です。実時間で23:59を待ってテストする必要はなく、
`clock.advance(timedelta(minutes=1))` の1行で日付境界を作れます。7.7で
実際のテストを読みます。

## 7.5 コードで読む: store.py と limiter.py

パッケージ全体は小さな4ファイル(本体230行あまり。組立の `__init__.py` を含めても
280行強)です。第6章のintents(11ファイル)と比べると目立ちません。全体像を先に置きます。

```
backend/src/latch/ratelimit/
  __init__.py    make_rate_limiter(SettingsからRateLimiterを組む工場)
  errors.py      RateLimitError 基底 + RateLimitedError(429) + RateLimitDependencyError(503)
  store.py       Redis操作を閉じ込める(RateLimitStore)
  limiter.py     判断する側(RateLimiter・RateLimits)
```

authパッケージで見た「StoreにRedis操作を閉じ込め、判断はserviceがする」の
構成と対称です。`store.py` の中核はわずかこれだけです。

```python
    async def _incr(self, key: str, ttl_s: int) -> int:
        pipe = self._redis.pipeline()
        pipe.incr(key)
        pipe.expire(key, ttl_s)
        result = await pipe.execute()
        return int(result[0])
```

`pipeline` は「複数のコマンドをひとまとめで送る」Redisの仕組みです。INCR(足して
値を返す)とEXPIRE(寿命を設定)を毎回併せて送ります。EXPIREを毎回上書きすると
寿命が延びますが、鍵の寿命は掃除用なので、延びていても無害——7.4で見た分担どおりです。
INCRの返り値が「足した後の値」であることが、次の議論の鍵になります。

### INCRは判定より先: 429も、カウント済み

`limiter.py` の判定メソッドと、4種のチェックの1つを見てください。

```python
    async def _check(self, count: int, limit: int) -> None:
        if count > limit:
            raise RateLimitedError("rate limit exceeded")

    async def check_create(self, *, user_id: uuid.UUID) -> None:
        """Intent作成20件/日(draft・active両方。POST /v1/intents全体)。"""
        count = await self._guard(
            lambda: self._store.incr_create(str(user_id), self._day_bucket())
        )
        await self._check(count, self._limits.create_per_day)
```

流れは常に **INCR→判定** の順です。まず数を足し、足した後の値で上限と比べる。
「判定してから足す」書き方と何が違うのか、並行リクエストを想像すると分かります。
判定→カウントの順だと、判定の読みとカウントの書き込みの間に別のリクエストが
割り込め、双方が「まだ大丈夫」と見て突破できます。INCRが先なら、Redis上で
足し算と値の受け取りがほぼ1回の操作で済むため、その隙間がありません。

この順序の帰結として、**429で断られたリクエストも、カウントは消費済み**です。
上限に達した後の連打は、すべて429になります(カウントはさらに伸びていく)。
窓が進めば自動回復します。また、422で失敗した作成(必須3が欠けていた等)も
作成カウントを消費します。失敗まで数えるのは厳しすぎる気がするかもしれませんが、
1日20件の余裕と正常利用(数件)の差を考えれば影響は小さく、判定とカウントの
隙間を潰すことの価値を優先した判断です(設計メモ§2.4の告白4)。

上限そのものは `RateLimits` というデータクラスにまとめられ、`Settings` から
組み立てられます。`settings.py` 末尾に4行あります。

```python
    # --- レート制限(M1 ws-4。08 §5.4)---
    rate_limit_api_per_min: int = 60
    rate_limit_create_per_day: int = 20
    rate_limit_update_per_hour: int = 6
    rate_limit_active_intents: int = 5
```

第1章で学んだとおり、Settingsのフィールドは環境変数で上書きできます
(接頭辞 `LATCH_`)。たとえば `LATCH_RATE_LIMIT_API_PER_MIN=5` とすれば
1分5回で試せます。試験や負荷検証で上限を引き下げたいとき、コードを変える
必要はありません。

### Redisが死んだら開ける: fail-closed

`_check` の手前にあった `_guard` に戻ります。

```python
    async def _guard(self, incr: Callable[[], Awaitable[int]]) -> int:
        try:
            return await incr()
        except RateLimitDependencyError:
            raise
        except Exception as exc:
            raise RateLimitDependencyError("rate limit dependency unavailable") from exc
```

Redisへの接続が切れるなど、INCRが失敗したときの処理です。ここでの判断は
**fail-closed(障害時は閉じる)**——レート制限のチェックができないなら、
リクエストは503 DEPENDENCY_UNAVAILABLE(第5章と同じ、部品障害のエラー)で
断ります。「チェックできないなら制限なしで通す(fail-open)」は選ばれませんでした。

理由を考えてみてください。fail-openなら可用性は保てる気がします。しかし
このサービスでは、**認証の失効リストも同じRedis**にあります(第1章1.7)。
Redisが死んだ時点で、ログアウト済みトークンの拒否もできない状態です。ということは、
レート制限を開けてもAPI全体の可用性はすでに失われている。穴だけ開いて得が
ないのです。ならば挙動を一貫させ、全部まとめて503にする——同じ型の判断は
第5章のLLM境界(スタブと実LLMでエラーを分ける理由)でも出てきました。
「障害の種類ごとに、別の挙動をしてよいか」を契約として決める、ということです。

## 7.6 組み立てと順序: 401→429→422

ここまでで部品は揃いました。残る問いは、これを**どこに**、**どんな順で**差し込むかです。

決められた順序は **401(未認証)→ 429(レート制限)→ 422(ドメイン検証)** です。
理由は2つ。未認証のリクエストにユーザーの状態を見せない(認証が先は当然)。
そして、攻撃的な流量には、ジオコーディングのSQLやLLMの呼び出しといった
**重い処理を消費させる前に429で返す**(レート制限が検証より先)。

### API全体60req/分: 依存関数という強制点

API全体への適用は、FastAPIの**依存関数**で実現されています。
`backend/src/latch/ratelimit/deps.py` の `api_rate_limited` です。要点だけ
引用します。

```python
async def api_rate_limited(
    request: Request,
    claims: Annotated[AccessTokenClaims, Depends(require_authenticated)],
) -> AccessTokenClaims:
    """認証成立後に user_id 単位でINCRする(未載荷/Noneのlimiterは素通り)。"""
    limiter = getattr(request.app.state, "rate_limiter", None)
    if limiter is None:
        return claims
```

第2章で学んだ `Depends(get_clock)` と同じ仕組みです。引数の `claims` 自体が
`Depends(require_authenticated)` から来ていて、**この依存は認証を内包しています**。
認証が先・レート制限が後という順序が、コードの構造そのもの(引数が解決されてから
関数本体が走る)として保証されているわけです。順序を構造で守る、第2章以来の考え方です。

users・intents・auth(logout)の各ルータは、これまで
`dependencies=[Depends(require_authenticated)]` としていた箇所を
`Depends(api_rate_limited)` へ差し替えました。全ルートで差し替え忘れがないかは
専用の試験(`tests/unit/test_rate_limit_wiring.py`)が毎コミットで番人します。
なお `/health` だけは依存を付けないままです。運用プローブ用でv1 API契約の外
(第2章で見たとおり)だから、レート制限の対象外です。

ミドルウェア(全リクエストを一括で掴む仕組み)を使わなかった理由も設計メモに
あります。ミドルウェアでは user_id を得るためにJWTの解析を2回実装することに
なり、/health を除外する分岐も自前で書くことになる。依存関数なら「v1 API契約に
のみ適用」が構造で表せます。

### 作成・更新・Active数: serviceへの注入

作成20件/日・更新6回/時・Active 5件の3つは、IntentService の中で判定されます。
limiterはコンストラクタ引数として**Optional(既定None=無効)**で注入され、
`if self._limiter is not None:` のもとでフックします。createなら user解決の直後に
`check_create`(429)、active化なら `_check_active_limit`(422)、既存の検証
(必須3→時刻→年齢→ジオコーディング)へ、という順です。

検証の順序の真実が1箇所にまとまるように、とルータではなくserviceに置く——
第6章6.2で読んだ「serviceが検証を統制する」構成の踏襲です。Optionalにしてある
おかげで、limiterを渡さずにserviceを直接組んでいる既存のunit試験は、1行も
直さずに動き続けます(第3章のDIの実利がまた出てきました)。

なお更新6回/時の対象には resume も含まれます。resumeは「更新」種の出来事を
1行発行する(第6章6.6)ので、pause/resumeの連打で出来事を量産する経路を
残さないためです。pause(出来事を発行しない)とDELETE(1回しか成功しない)は
対象外。どこまで「更新」と数えるかは、設計メモ§5の告白1として記録されています。

### 認証前の2つの窓口: provider+subject単位

`POST /v1/auth/token` と `POST /v1/auth/refresh` は認証がまだ成立していない
窓口なので、user_idがありません。この2つへの60req/分は、IdP検証で確定する
**provider+subject**(どのIdPで確認された、どの利用者か)を単位に数えます。
IdP検証の直後にINCRするので、無効なidp_tokenの連打は401のまま(401優先が保たれる)。
そして鍵に埋めるsubjectはメールアドレスになり得る個人情報なので、sha256で
ハッシュ(不可逆な要約)してから埋めます——authパッケージがrefreshトークンを
SHA-256で保存するのと同じ規律です。Redisの鍵名に個人情報を残さない。

### main.py の組み立て

最後に接続です。`main.py` のlifespanが変わりました。それまでredis_clientは
認証を組み立てるときだけ生成していましたが、レート制限のために**常時生成**し、
`app.state.rate_limiter` へRateLimiterを載せます。`create_app` には
`rate_limiter=` の差し替え口が増え、429/503をenvelopeへ変換する例外ハンドラが
1つ追加されました——第4章で読んだ `UsersError` のハンドラと同じ形です。

## 7.7 テストで読む: FakeClockがJST 0時を作る

この単位でunit テストは43件増えました(うちratelimitパッケージ配下が25件。
この時点で全体463件。その後の追加を経て現在は643件です)。特に読む価値が
高いのが `tests/unit/ratelimit/test_jst_boundary.py` です。7.4の「日付が変われば
別の鍵」を、時刻を実時間で待たずに証明しています。日次の境界の試験をそのまま
引用します。

```python
async def test_daily_bucket_rolls_at_jst_midnight(redis, clock):
    # JST 2026-09-28 23:59 → 00:00 で日付キーが切り替わる
    clock = FakeClock(datetime(2026, 9, 28, 14, 59, 0, tzinfo=UTC))
    limiter = _limiter(redis, clock, create_per_day=1)
    await limiter.check_create(user_id=UID)  # 当日1件目OK
    with pytest.raises(RateLimitedError):
        await limiter.check_create(user_id=UID)  # 同日2件目429
    clock.advance(timedelta(minutes=1))  # JST 0時突破
    await limiter.check_create(user_id=UID)  # 新しい日付キー→受理
    keys = sorted(await redis.keys("rl:create:*"))
    assert len(keys) == 2
    assert "20260928" in keys[0] and "20260929" in keys[1]  # JST暦日付
```

読みどころを3つ挙げます。

1つ目、最初の `FakeClock(datetime(2026, 9, 28, 14, 59, 0, tzinfo=UTC))`。
UTCの14:59はJSTの23:59です。**偽の時計に「JST 0時の1分前」を設定している**。
実時間がいくつであろうと、この試験の中では常に23:59から始まります。
2つ目、`clock.advance(timedelta(minutes=1))` で1分進め、0時を突破させる。
時刻の経過そのものを、コマンド1つで演出できています。3つ目、最後の2行で
**鍵が2本存在すること**(昨日の鍵と今日の鍵)を確認している。「リセット=消す」
ではないので、昨日の鍵は20のまま残っているはず、という7.4の説明のとおりの
観察結果です。

Redisそのものも、ここでは **fakeredis** というスタブ(Redisのコマンド解釈を
真似てメモリ上で動かす部品)に差し替えられています。第5章のProtocolスタブと
同じ発想で、実Redisを立てずに鍵の一覧まで検査できます。失敗時(503への包み)は
`BrokenRedis` という、pipelineを呼んだ瞬間に例外を投げるスタブで試します——
「壊れ方を指定できる」という、スタブの利点の好例です(第5章5.2)。

この単位には integration 試験(`test_ratelimit_api.py`・9件)もあります。実api・
実Redis・実DBで、60回目の受理と61回目の429、5件active化した後の6件目の422、
resume連打の429までを通しで確認します。compose常設環境で
`docker compose build api` の後に `make test-ci` で走る、第6章で学んだ2層構成の
外側の試験です。

## 7.9 この章の再統合

- LATCHのサーバーは処理すればするほどAIコストがかかる。反復更新による出来事の
  量産という攻撃経路を、入口で断つのがレート制限。通過後のJev予算と合わせた
  多層防御の第1層
- 上限4種のうち3種は429(時間が進めば回復する「速さ」の制限)、Active 5件だけは
  422(待っても解決しない「今の姿」の検証。案内は停止か期限待ち)
- 数える場所は性質で決めた。増え続けて窓が進めば要らない「回数」はRedisのINCR。
  pause・resume・期限で変わり続けるDBの状態そのものは、DBのCOUNT+users行の
  FOR UPDATEで直列化して数える
- リセットは予約しない。鍵の名前にJSTの日付を埋め、日が変われば別の鍵を開ける。
  TTLは掃除役に徹する(UTC基準で動くのでリセットには使えない)。窓の端で
  瞬間2倍が起きうる固定窓だが、第2層があるので許容する
- INCRは判定より先。429で断られたリクエストもカウント済みで、判定とカウントの
  隙間をRedis上で潰す。Redis断絶はfail-closedで503——失効リストも同じRedisで
  死んでいる以上、開けても可用性は戻らない
- 順序は401→429→422。api_rate_limited は require_authenticated を内包し、
  順序を構造で保証する。作成・更新・Active数はserviceが統制し、limiterは
  Optional注入で既存試験を壊さない。認証前の窓口はprovider+subject単位で、
  subjectはsha256でハッシュして鍵へ
- FakeClockが「JST 0時の直前」を作り、advance 1分で境界を越えられる。
  時刻参照の単一経路(C2)は、テストの決定性としてここに返ってくる

第4章で経路、第5章で信頼できない入力への関所、第6章で保存・状態・記録を学び、
この章で量への守りを見ました。ここまででM1のサーバー側は受け付けから保存・
防御まで揃います。フロントエンド(ws-5)が、このAPI群を画面から叩く側として
実装されました。429や422を「画面の言葉」でどう伝えるか——その答えは第8章
(`concepts/08-frontend-bridge.md`)です。

## 7.10 用語集(この章で登場した言葉)

| 用語 | 一言でいうと |
|---|---|
| レート制限 / 429 | 量が多すぎるリクエストを入口で断つ仕組み / そのときのステータスコード |
| 多層防御 | 鍵を複数重ね、1層の緩さを他層で受け止める構え |
| Jev | マッチングのAI評価。M2で実装。1回ごとにコストがかかる |
| INCR | Redisの「1足して、足した後の値を返す」コマンド |
| 固定窓 | 0時ぴったりなど固定の境界で区切って数える時間窓 |
| 滑らかな窓(sliding window) | 窓の端を現在時刻に合わせてずらし続ける数え方。厳密だが複雑 |
| バケット / バケットキー | 時間の区切り(日付・時・分)のこと / それを名前に埋め込んだRedisの鍵 |
| TTL | データの寿命。ここでは掃除役のみ(UTC基準のためリセットには使えない) |
| fail-closed | 依存部品の障害時、判定不能なら「通さない」側に倒す判断 |
| fail-open | 障害時、判定不能なら「通す」側に倒す判断(不採用) |
| sha256 / ハッシュ | 元に戻せない要約を作る計算 / それで個人情報を鍵名に残さなくする |
| PII(個人情報) | メールアドレスなど、本人を特定できる情報 |
| 依存関数 / ミドルウェア | 窓口ごとに差し込む前処理 / 全リクエストを一括で掴む前処理 |
| fakeredis | Redisのコマンド解釈をメモリ上で真似るスタブ |
| pipeline | Redisの複数コマンドをひとまとめで送る仕組み |
