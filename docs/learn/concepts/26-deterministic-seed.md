## 26.1 この章の題材: 300件のテストデータを、手で書かないで用意する

これまでの章で、LATCHの試験を「手を動かして観察する」側から見てきました。この章で出会うのは、
試験を支える**材料づくりの設計**です。

M4では、staging環境(第25章)で機能試験のフル実行が控えています。そのためのIntent(やりたいこと)の
材料は、仕様書が「シードIntent 200〜300件」という規模を決めています(10 §2)。300件のIntentを
手で書くことを想像してみてください。1件3分でも15時間です。そして本当に困るのは、書いたあとです。

- **300件の分布を手で保つのは無理がある**。仕様は「時間帯は昼2割・夕3割・夜4割・
  その他1割」「カテゴリは飲酒5割・食事4割・活動1割」と比率まで決めています(10 §2)。
  手で書くと、書いているうちに夜が増えて昼が減る
- **「このシードの29件目だけ書き換えた」となったら、機械は何を信じればいいのか**。
  手で編集した資産は、「ほかの299件は本当に正しいのか」を毎回疑い直すことになります
- さらにM4の後の単位では、同じ仕組みで**1万件・10万件**の生成(負荷試験用)が控えています。
  手書きの方式は、この要求に伸びません

M4 ws-2で作られたのが、**決定的生成器**(けていてきせいせいき)という道具です。
「決定的」の意味はただ一つ——**同じ引数で実行したら、何度でも同じものが生まれる**。
この一言に、この章のすべてが詰まっています。

## 26.2 先に読んでおく資産の地図: 4つの資産の住み分け

本単位の前に、`docs/testassets/` には確認済み(confirmed)の資産が3つあります。M4のシード
(m4-seed)は、これらを壊すことなく加わりました。住み分けを表で押さえておきます。

| 資産 | 何のためにあるか | m4-seedとの関係 |
|---|---|---|
| g2-jev-goldset.yaml | Jev評価用の304 Intent+520ペア。G2実施済み | **不変**。語彙(表現の引き出し)の母集合として参照される |
| g1-alcohol.yaml | 飲酒判定専用の入力36件。G1実施済み | **不変**。期待値表はこれを参照する(新しく作らない) |
| g1-parser-struct.yaml | Parserの構造化精度ゲート用32件 | **不変**。idの接頭辞(SU-/SD-/EX-)を新しくして衝突を防ぐ |
| m4-seed.yaml(本単位) | 機能試験用のシード300件+ユーザー100人 | 本体。生成器から生まれる |

「既存の304件を間引いて再編する」方式も選択肢として検討されましたが、不採用になっています
(design §2.1)。理由の中心は、この章の主役である**再現性**です。既存データの再編は手作業が
入り、再編した結果を機械が再現する方法がなくなります。代わりに取られた方式が、既存資産を
**語彙の母集合**として参照し、本体は生成規則から生み出す、という形です。評価ペア520件は
G2評価の前提そのものなので、「ペアの構成は変えない」が硬い制約として守られています。

## 26.3 「決定的」とは: 同じ引数なら、何度生んでも同じもの

### 乱数シードという種入れ

生成器は、ランダムな選び取り(時間帯のくじ・語彙のくじ)を使います。ところが「ランダム」は
この章の敵でなければなりません。実行するたびに別のものが生まれてしまったら、再現できないからです。

ここで使われる仕組みが**乱数シード**です。コンピュータの「ランダム」は、実は種(シード)と
呼ぶ出発点の数字から、決まった手順で次々と値を作る仕組みです。種が同じなら、生まれる値の
並びは完全に同じになります。「種入れが同じなら、育つ草むらは同じ」——そういう約束です。
LATCHの生成器は、種を **42** に固定しています。この数字自体には意味がありません
(どの値でも決定性は保てる。ただ一度決めたら、変えると生成物が全部変わるため、記録しておく
必要がある。記録先はYAMLの `meta` です)。

### バイト同一: 1バイトも変わらない

同じ引数で生成を2回実行すると、でき上がるファイルは**バイト同一**(1バイトも違わない)に
なります。これは第25章の3つの `server_time` がそろう話と似ていますが、要求がさらに厳しい。
時刻のそろいは「同じ時刻を指す」ことですが、バイト同一は「ファイルの文字1つから改行まで、
全部が等しい」ことです。実際に確かめられるのは簡単で、生成した直後にgitに聞きます。

```bash
make seed-generate ARGS="--base-datetime 2026-10-04T11:00:00+09:00"
git status --short docs/testassets/
```

何も出なければ、gitは「差分ゼロ」を宣言したことになります。つまり、**手元の生成結果は、
コミット済みの資産と1バイトも違わない**。このLab(Lab 12)で実際に観察します。

なぜそこまで厳しいのか。テスト資産は「設計→機械検査→マージ」というレビューを通った
**証拠**だからです(第24章)。もし再生成のたびに中身が少し変わるなら、レビューを通った
あの内容はもう手元にない。バイト同一であれば、「レビューしたもの=手元にあるもの」が
機械的に保証されます。

### 基準日という引数: 時刻は5日以内の未来へ

生成コマンドには、`--base-datetime`(基準日時)という引数を渡します。Intentの時刻は、
この基準日から**1日後〜5日後**の範囲に割り付けられます。

なぜ引数にするのか。Intentの保存APIには「過去の日付は受け付けない・7日先まで」という
時刻検証(第6章6.3)があり、その内側に収めるためです。さらに実務的な理由があります。
stagingへの投入日は試験の実施日で、実施日が延びることがある。基準日を引数にしておけば、
**投入の直前に生成し直して日付をずらせる**。そして再生成で変わるのは日付まわり
(基準日自体・それに連動する誕生日とIntentの時刻)だけで、件数・分布・期待値の集計は
変わりません。この観察もLab 12でやります。

## 26.4 分布を規則に組み込む: 意図的配置を先に置き、残りを比率で埋める

300件は、大きく2段階で組み立てられます(generator.pyのdocstringに要約があります)。

**第1段階: 意図的配置64件**。期待値表(EX-xxx・後述)の素材になるIntentたちは、
**乱数を使わずに**直接組み立てられます。たとえば「同一ユーザーの2 Intentでペアが
作られないこと」(FR-17の自己ペア)を確かめるための3組、「18〜19歳の食事Intentと
20歳以上の飲酒IntentのペアがLayer 1で落ちること」(D-10)の素材、時間や距離・予算の
ちょうど境界ケース。**試験で見たい現象は、必然的に作る**——ここはくじに任せません。

**第2段階: 残余236件の比率配分**。残りの枠に、仕様の分布比率(昼60/夕90/夜120/
その他30・飲酒150/食事120/活動30・1対1 210/グループ90)を当てはめて埋めます。
1件ごとの中身(文面・場所・人数)は、**語彙プール**(vocab.py。g2実績を母集合とする
表現の引き出し)から決まった手順で選びます。

この2段構えが「手で書かない」の実体です。**見たい現象は必然として置き、全体の形は
比率から生やす**。300件のどの1件も手で書いたものはなく、その結果、再生成すれば
全部が同じ形で戻ってきます。

## 26.5 期待値表の2層: 人が読むEXと、機械が照合するaggregate

生まれた300件が「正しい形」かどうかを、どう確かめるのでしょう。この単位の鍵が、
期待値表の**2層構造**です。

300件から選べるペアの総数は、C(300,2)=**44,850**あります。Layer 1 Hard Filter
(第11章)の判定は、この44,850全部に対して定義できます。ここで選択肢が2つあります。

| 案 | 内容 | なぜダメか/よいか |
|---|---|---|
| 全部書く | 44,850ペアの判定をYAMLに列挙 | 数MBの機械専用データになり、人が差分を読めない |
| **2層に分ける**(採用) | 人が読む個別期待+機械が照合する集計 | レビュー対象が読める量に収まる |

採用された2層が、実際のYAMLにこう入っています( `docs/testassets/m4-seed.yaml` の
`expectations` 節から。実在の部分です)。

**第1層: 個別期待(EX-xxx・33件)**。意図的配置と境界ケースごとに、「このペアはこうなる」を
人が読める形で書きます。

```yaml
- id: EX-004
  kind: pair
  intents:
  - SD-007
  - SD-008
  expected: fail
  fail_reason: age_alcohol
  basis: 'D-10(10 §3 #27)・06 §2(飲酒は双方20歳以上)'
```

`expected` は判定(pass/fail)、`fail_reason` は落ちた理由の分類、`basis` は根拠となった
仕様の節番号です。**「なぜこうなるか」まで資産に書いてある**のがポイントです。33件の内訳は、
ペア判定24件+集合の構成検査4件+「作成拒否が正」の素材5件(18〜19歳が飲酒Intentを作ろうと
すると422で断られる。第4章・D-10の動作試験の材料)です。

**第2層: 集計(aggregate)**。残る44,000件超の判定は、数として確かめます。

```yaml
aggregate:
  pair_total: 44850
  layer1_pass: 576
  layer1_fail: 44274
  fail_breakdown:
    self_pair: 305
    category_mismatch: 25926
    time0: 17263
    distance: 80
    people: 574
    budgetmin: 9
    blocked: 0
    age_alcohol: 117
```

通過は576件。落ちる44,274件は、落ちた理由ごとの件数(内訳)で書きます。内訳の合計が
`layer1_fail` と一致するので、「書き漏らした理由」の心配も不要です。個別のEXは
「この現象が意図どおり起きたか」を、aggregateは「全体の形が崩れていないか」を、
それぞれ受け持ちます。

## 26.6 検査は、別の実装で再計算する

ここまでで「生成器」と「期待値」が出てきました。最後の登場人物が**検査器**(verify.py)です。
`make seed-verify` で動く、YAMLを機械検査する道具です。検査は5つあります
(a構造・b分布・c意図的配置・d集計照合・e地名)。

その中でも考え方の面白いのが、(c)と(d)に使われている仕組みです。ペアの判定を検査するとき、
生成器の計算結果をもう一度読んで「はい、合ってます」と照合する……のでは足りません。
**生成器が間違った判定方法を持っていたら、検査器も同じ間違いを写してしまう**からです。

そこでLATCHでは、判定の**別の実装**を用意しました。`reference_l1.py`(参照実装)です。
製品コードの判定はSQL+PostGIS(第11章のHard Filter)で書かれています。参照実装は
**同じ判定条件を、Pythonで独立に**書いたものです(docstringに、SQLの条件と1対1対応を
コメントで明記してあります)。

- 生成のとき: 生成器が参照実装で44,850ペアを判定し、集計をYAMLに書き込む
- 検査のとき: 検査器が**改めて**参照実装で全ペアを判定し、YAMLの集計と一致するか照合する

同じ道具を2回呼ぶ検査と違って、この構成では「生成時に書かれた数字」と「検査時に計算し直した
数字」が独立に成立します。YAMLに壊れ(第24章で読んだ、値を手で書き換えるなどの破損)が
入っていたら、再計算との食い違いとして機械が検出します。実際にどのように検出されるかは、
Lab 12で1行書き換えて確かめます。

「判定条件は2か所に書かれる」ことは重複に見えますが、この重複には名前と目的があります。
**二重実装の突合**——SQLとPythonという異なる言語・異なる書き方で同じ条件を実装し、
両者が一致することで、どちらかの書き間違いを暴く。これは試験の設計として、第24章の
「対応表で不足を探す」作法と兄弟です。

## 26.7 地名7地点: 設計の前提を、データで確かめた話

最後に、この単位で起きた実例を1つ紹介します。教材として残す価値のある話です。

生成器は、Intentの場所を「許可リスト」から選びます。最初の設計では、既存資産(g2)の実績に
ある**9地点**を使う予定でした。ところが実装の試験段階で、矛盾が見つかります。設計の
別の部分(検索範囲の西端の座標)と、9地点のうちの1つ(鹿児島中央駅前・経度130.5390)が、
食い違っていたのです。

この矛盾を、スーパーバイザーは机上で解決せず、**実データを調べて**解決しました。判定基準は
明快です。staging投入は保存APIの正規経路で行われるため、各Intentは**正転ジオコーディング**
(地名の文字列→座標の変換。第11章11.2)を通ります。そして変換は「正規化した名前の完全一致」
で探すため、**DBに存在しない地名は変換できず、保存はエラーになる**。つまり「実データに
存在しない地名」は、どんなに文脈が正しくてもシードに使えない——シードの前提そのものに
関わる話です。

ci環境のDBを実査した結果、「天文館通り」「鹿児島中央駅前」「鹿児島中央駅周辺」の3つが
正転でヒットしないことが確定し、許可リストは**7地点**(天文館・高見馬場・呉服町・
加治屋町・浜町・城山・鹿児島駅前)に絞られました。座標も「stagingのサーバーが実際に
返す代表点」と同じ値に合わせてあります。結果として、staging投入時の正転結果とYAMLの
期待座標が一致するため、後続の単位の試験が素直に成立します。

もし「9地点でいいだろう」という前提のまま進んでいたら、発覚はstaging投入のとき——
つまり後続単位の試験のど真ん中でした。距離の多様性(最遠のペア約2.5km・最近約0.4km)が
7地点でも保てることも、実座標で確認のうえ記録されています。**設計の数字を疑うときは、
手元の実データで確かめる**。この実査の経緯は、設計メモと生成規則の記録
(m4-seed-plan.md)に、根拠つきで残っています。

## 26.8 この章の再統合

- 大量のテストデータを手で書くと、分布の維持・変更時の疑い直し・大規模化で破綻する。
  LATCHは「決定的生成器」で答えた: 同じ引数なら何度でも同じものが生まれる
- 決定性の支えは3つ。乱数シード42(種入れが同じなら生まれも同じ)・バイト同一の再生成
  (gitで差分ゼロを確認)・基準日という引数(時刻は基準日から1〜5日後へ。投入直前に
  生成し直せる)
- 300件の組み立ては2段階。見たい現象は乱数なしで必然的に置き(意図的配置64件)、
  全体の形は仕様の分布比率で生やす
- 期待値表は2層。人が読む個別期待(EX-xxx・33件。expected・fail_reason・根拠の節番号)と、
  機械が照合する集計(44,850ペアの判定と、落ちる理由ごとの内訳)
- 検査は、生成器の数字を写すのではなく、**別の実装**(SQLをPythonで独立に書き直した
  参照実装)で再計算して突き合わせる。二重実装の突合は、書き間違いを暴く仕組み
- 地名9→7の実査は、この単位の作法の実例。机上の都合で決めず、実データで正転ヒットを
  確認してから許可リストを決める

## 26.9 用語集(この章で登場した言葉)

| 用語 | 一言でいうと |
|---|---|
| 決定的生成器 | 同じ引数で実行すれば何度でも同じものを生み出す、テストデータ作りの道具 |
| 乱数シード | 「ランダム」の出発点の数字。種が同じなら生まれる値の並びも同じ(本単位では42) |
| バイト同一 | ファイルの中身が1バイトも違わないこと。再生成の完全な再現性の証明 |
| 基準日時(base-datetime) | 生成器への引数。Intentの時刻はここから1〜5日後に割り付けられる |
| 語彙プール | 文面・場所・表現の引き出し(vocab.py)。既存資産を実績のある語彙の母集合として参照 |
| 意図的配置 | 試験で見たい現象を、乱数に任せず必然的に置く配置(境界ケース・自己ペア等) |
| 期待値表 | 「入力に対してこうなるはず」をまとめた表。m4-seed.yamlのexpectations節 |
| 個別期待(EX-xxx) | 意図的配置・境界ケースごとの、人が読める期待(33件・根拠の節番号つき) |
| 集計(aggregate) | 全ペアの判定総数・通過数・落ちる理由ごとの件数。機械が照合する |
| 参照実装(reference_l1) | 製品の判定(SQL+PostGIS)をPythonで独立に書き直した実装。検査の計算に使う |
| 二重実装の突合 | 同じ条件を別の実装で2か所に書き、一致で互いの書き間違いを暴く作法 |
| 正転ジオコーディング | 地名の文字列から座標へ変換すること。名前の完全一致で探すため、DBに無い地名は失敗する |
| 許可リスト | 生成器が場所を選ぶ元。実データで正転ヒットを確認済みの7地点 |

## 26.10 確認問題

1. 手書き300件に対する「手で書かない」方式の利点を、分布・変更・大規模化の3面から
   説明してください
2. 乱数シード42を100に変えると、何がどうなりますか。また、なぜシード値を記録しておく
   必要があるのでしょうか
3. バイト同一が「同じ時刻を指す」より厳しい要求である理由を、テスト資産が証拠である
