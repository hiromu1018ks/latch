## 31.1 「動く」を証明したあと、「壊れても大丈夫」を証明する

この教科書の第24章と第28章で、あなたは「できた」を証明する試験の話を読みました。
staging環境という本物に近い世界の上で、仕様書の機能試験27項目を一気通貫に回す
ハーネスです。あの試験が確かめているのは「**ユーザーが正常に使っている限り、
システムは約束どおり動く**」ということです。

では「サーバーが1台死んだら?」「データベースが壊れたら?」「負荷が上限を超えたら?」
という問いには、あの試験は何も答えていません。ユーザーが正常に使っている世界に、
そうした出来事は混ざっていないからです。

ここからが第31章の題材です。docs 10(test-env-nfr・試験環境と非機能試験の仕様)の
第4節は、速さの約束
(第30章で読んだ性能5目標)に続けて、**壊れたときの約束**を並べています。壊れた
ときの約束の特徴は、目標値を置けない場所があることです。バックアップからの復旧
(RTO=どれだけ速く復旧できるか)については、docs 10は「目標値を持たず、試験ごとに
実測を記録する」と定めています。「速く復旧せよ」と書けない理由は、まだ実測がないと
目標が定められないからです。まず測って、その数を眺めてから、次の判断をする。
第30章の「測り方自体を設計する」という姿勢の、もう半分の応用です。

M4 ws-7(2026-10-05マージ)の仕事は、この「壊れても大丈夫」の証明の器をstaging
環境に置くことでした。先に結論を並べると、作られたものは4つです。

1. 1分間隔でAPIを叩き続けて成功率を数える**合成監視プローブ**(31.3)
2. 滞留した処理を数えて警報を鳴らす**Queue lag alert発報器**(31.6)
3. Jevの使用カウンタを直接書ける**運用CLI**(31.7)
4. 4領域の試験を一気通貫で回す**ハーネス19件とMakefileターゲット9本**

そしてこの章のもう一つの題材は、試験の実施中に起きた**発見**です。設計どおり
`docker kill` でAPIコンテナを止めたところ、コンテナは二度と生き返りませんでした。
15分待っても「停止中」のままです。これは障害ではなく、Dockerの正式な仕様どおりの
動きでした。31.4で、この発見をどう読むかをじっくり読みます。

## 31.2 壊し方は4つ — 仕様の第4節が並べている順

docs 10の第4節は、速さのあとに壊れ方を4つ並べています。順に見ていきます。
それぞれ「壊す対象」と「壊したあとに確認すること」がセットになっています。

| 領域 | 仕様の節 | 壊す対象 | 確認すること |
|---|---|---|---|
| 可用性 | §4.3 | 稼働中のAPIコンテナ1台 | 残り1台で処理が続くこと・自動で復旧すること・成功率99.5% |
| バックアップ復旧 | §4.4 | データベース(復元を試す) | 復元→再エンベディング→再開・復旧前後でactive Intent数が一致 |
| 縮退 | §4.5 | Jevの費用上限(D-16)・一時停止の再評価 | 上限到達で実行が止まること・0時のリセットで復帰すること |
| Queue障害 | §4.7 | 処理できないEventを混ぜる | 毒を隔離し、後続の正常処理に波及しないこと |

表の「縮退」は、機能の一部を意図的に止めたまま運用を続けることです。ここでは
Jev(第13章のAI判定)を費用上限で止めることを指します。

読み方のコツは、「壊す対象」が4つとも**別の場所**を指していることです。API(入り口)・
データベース(記憶)・費用の上限(予算)・処理の列(キュー)。どこが壊れてもサービスは
止まってほしくないので、それぞれの壊れ方について、約束が1つずつ置かれています。

もう一つの読み方として、「壊し方」には2種類あることに気づきます。可用性とQueue障害は
**物理的な壊し方**(プロセスを止める・悪い入力を混ぜる)で、バックアップ復旧と縮退は
**仮定で条件を作る壊し方**です(「もし定期バックアップから復元する日が来たら」「もし
費用が上限に達したら」)。後者は、まだ起きていない事態を「もし壊れたら」と仮定して
試します。そのため、仮定をどう作るかの設計が試験の本体になります。31.7のカウンタ
直接書き込みは、その代表例です。

この4領域のうち、LLM障害の系統(呼び出し先のAIが落ちたときの切り替え)は、実は
もう一度別の単位で試されています(M2 ws-8・第16章のcircuit breaker)。今回はstaging
の実環境で、LLM以外の4領域を通します。

読み進める順序は、表の順とは違うことを先に断っておきます。この章は4領域をまんべんなく
読む章ではありません。観察点と設計判断が最も濃かった可用性を厚く読み(31.3〜31.5)、
Queue障害の警報の置き場所(31.6)と縮退の境界(31.7)を経て、バックアップ復旧は
最後に実測値とともに振り返ります(31.8)。4領域を回す器(ハーネス19件・Makefile
ターゲット9本)そのものの設計は、設計メモ(`docs/plans/M4/ws-7-design.md`)と
コード(`backend/staging_tests_nfr/`)を読むのが最短です。

## 31.3 成功率99.5%は、「何を数えないか」の決めごとから始まる

可用性の約束はdocs 01(要件)第20節(非機能要件)に書かれています。読み上げますと:

> 計画停止を除くAPIリクエスト成功率99.5%以上

この約束には2つの部分があります。「99.5%以上」という数と、「**計画停止を除く**」と
いう除外です。数の方は分かりやすい。99.5%なら、1000回のリクエストのうち5回までの
失敗が許されます。

約束の本体は後ろの半分にあります。なぜ「計画停止を除く」必要があるのか。たとえば夜間に
サーバーを1台ずつ入れ替えて更新する(デプロイ=新しい版を配置すること)運用を
考えてください。入れ替えの数秒間、そのサーバーは応答しません。障害ではありません。
**計画された正常な作業**です。この数秒も失敗に数えると、計画停止を行うたびに
成功率が下がり、いつか約束を破ることになります。約束を守るために更新作業を
やめる、という本末転倒が起こる。だから仕様は「計画停止は数に入れない」と最初から
決めているのです。

ここで試験の設計者は悩みました。「除く」という言葉は便利な半面、**人間が後から
「この窓は除こう」と言えばいくらでも除ける**という危うさを抱えています。数値の
信頼性を落とさないためには、除外を「その場の判断」でなく「機械に確かめられる仕組み」
にしておく必要があります。

そこでプローブには**除外タグ**という仕組みが付きました。試験を実行している間、
試験を止めずに、プローブのそばに1つのファイル(マーカー)を置くか消すかできるように
してあります。ファイルが存在する間に受けたサンプルには「計画停止」という印が付き、
集計の分母から自動で外れます。該当するコードはこの1行です:

```python
# backend/src/latch/loadgen/probe.py(32〜34行目・既定のマーカー位置)
# マーカーの既定位置(ファイル位置基準・cwd非依存。loadgenのSEED_DIR教訓)
REPO_ROOT = Path(__file__).resolve().parents[4]
DEFAULT_MARKER = REPO_ROOT / ".staging" / "probe-outage.marker"
```

サンプル1件1件の記録には `tagged_planned_outage` という印が付いて証拠YAMLに残り、
集計関数 `summarize` は印付きサンプルを数えず・印付きだった件数を別途出力します。
実際の試験では、api2を意図的に一度止めて戻す操作を試験窓(試験の観測時間枠。以後
この呼び方を使います)の中で行い、その間の
6サンプルが印付きで分母から外れることを確認しました。証拠YAMLには
`main_total: 44`・`main_excluded_planned_outage: 6`・`main_counted: 38` と、
「全体44件・除外6件・数えた38件」が並んでいます。除外が**起きたことの記録**として
残るわけです。

もう一つの設計は、観察の粒度を2本に分けたことです。合否を判定する側は1分間隔
(試験窓60分で60サンプル強)。一方で、死んだサーバーが何秒で復旧するかを観察する
には1分間隔では粗すぎます。この粗さを補うのが、合否判定外の10秒間隔の観察用
プローブ(dense)の併設です。合否に使う数と、観察に使う数を分けるのは、第30章の「合否判定は1分
間隔側のみ・密側は観察記録」と同じ整理です。判定に使わない数は、判定を歪めない
場所に置く。

## 31.4 docker killで壊したコンテナは生き返らない — Dockerの「自然死」と「手動停止」

この章の主役です。じっくり読みます。

### 31.4.1 うまくいくはずだった手順

staging環境のAPIは2台構成です(api1・api2・第25章のLab 11で立てたあの世界です)。
定義ファイルには、各コンテナが死んだときどう振る舞うかの**restartポリシー**
(再起動の方針)が書かれています:

```yaml
# compose.staging.yaml(47行目。この行はapi1とapi2の共通定義x-api-commonの
# 中にあり・2台ともこの1行を継承する)
  restart: unless-stopped
```

`unless-stopped`(「自分の手で止めない限り、再起動する」という意味の名前です)は、
「プロセスが勝手に死んだら、Dockerが自動でコンテナを起こし直す」という約束です。
この約束があるから、可用性試験は「1台を強制停止して、残りで処理が続くことと、
**自動復旧**を確認する」という内容になります。設計の時点から、手順はこうでした:

1. `docker kill latch-staging-api1-1` でapi1を強制停止する
2. nginx(前段の門番)が死んだ側への送信を検知し、生きているapi2へ振り直す
3. restartポリシーがapi1を自動で起こす
4. api1が健康に戻ったら、2台での負荷分散に復帰する

`docker kill` は、コンテナの主プロセスに SIGKILL(殺す、という意味の合図)を送る
コマンドです。SIGKILLは受信したプロセスが捕まえられない・後始末できない強制終了で、
「本当に突然死んだ」状況の再現に向きます。手順自体は何も悪くありませんでした。
悪くなかったのですが——

### 31.4.2 起きたこと: 15分待っても復帰しない

実際に試験窓の中で `docker kill` を実行すると、api1は停止しました。nginxはapi2へ
振り直しました。ここまでは設計どおりです。ところが、**api1は再起動しません**。
状態を見ると「停止済み」のまま。15分以上待っても変わりません。試験窓1回分を
破棄して、方法を変えることにしました。

結論は、Dockerの正式な仕様でした。`restart: unless-stopped` の「unless-stopped」
は「**人間が自分の手で止めた場合を除く**」という意味ですが、Dockerにとって
「人間が止めた」に数えられる操作が2つあります:

| 操作 | 起こること | Dockerの解釈 |
|---|---|---|
| `docker stop` | 停止の合図(SIGTERM)を送って終了を待つ | 意図的な停止。再起動しない |
| `docker kill` | 強制終了の合図(SIGKILL)を送る | **これも人間の停止。再起動しない** |

直感に反するのは最後の行です。「kill=強制的に殺す=突然死では?」と思いますが、
Dockerの視点では、**killもstopも「ユーザーがdockerコマンドで明示的に止めた」**という
同じ種類の出来事です。裏を返すと、restartポリシーが自動再起動するのは「docker
コマンドの手を借りない死」——プロセスの内部エラーやメモリの枯渇など、プロセス自らが
落ちる場合——に限られます。**突然死か手動停止かの区別は、死に方の激しさにありません。
誰の手による死なのか、という点にあります。**

### 31.4.3 ならば「自然死」を演出する: SIGTERMという答え

試験が確かめたいのは「プロセスが死んだあと、残りで処理が続き、ポリシーによって
自動復旧する」です。dockerコマンドの手を借りない死であれば、死に方の激しさは本質では
ありません。方法を変えます。**コンテナの中の主プロセス(PID 1)に、直接
SIGTERM(終了の合図)を送る**のです。SIGTERMはSIGKILLと違い、受け取ったプロセスが
後始末をしたうえで終了できます。実際、api1のuvicorn(Webアプリを実行する器)は
SIGTERMを受け取って graceful(丁寧)に終了しました。これはDockerの視点では
「dockerコマンドの手を借りない死=自然死」であり、restartポリシーの対象です。

結果です。SIGTERM送信後、**30秒で api1は running・healthy(健康診断合格)に戻りました**。
自動再起動の回数を数えるカウンタ(restarts)の値が増え、起動時刻の記録(StartedAt)も
更新されています。nginxは死んだ窓の間
api2だけに振り続け、dense(10秒間隔)の観察プローブは失敗ゼロで通し続けました。
「1台が死んでも入口が振り直し、ポリシーが起こし直す」——試験の本体はこの方法で
確かめられました。

### 31.4.4 この発見から残すもの

読者には3つの学びが残ります。

**1つ目は仕様そのものです。** コンテナ運用で「死んだら勝手に生き返る」と思って
いると、いざというときに理由の分からない「停止したまま」に遭遇します。restart
ポリシーの対象は自然死だけ。手動のstop・killは例外です。この話を覚えておけば、
「restartが効かない」という状況に会ったとき、最初に「死に方は自然死だったか」を
疑えます。

**2つ目は手順の設計の教訓です。** 試験が確かめたい本質(死→残存で継続→自動復旧)を
一文にしてから手段(docker kill)を選んでおくと、その手段が使えないと分かったとき、
本質は変えずに手段だけをSIGTERMへ読み替えられます。読み替えた事実は報告書に記録し、次の確認の
材料(G4時確認事項)に置きました。**設計時の計画が実環境で通らないこと自体は珍しく
ない。黙って計画を変えず、読み替えを記録として残すこと**です。
これは第30章の「4回かかったperfの記録」と同じ作法です。

**3つ目は、一回の失敗が「仕様の読み直し」になったことです。** 15分待っても復帰
しない状況は、restartポリシーが壊れているのか・イメージが古いのか・それとも仕様の
理解が違うのか、複数の仮説が並びます。Dockerのドキュメントを戻って読み、表の2行目
(kill=人間の停止)にたどり着いて初めて、観察結果が説明できました。観察が仕様の
理解を修正した、という順序。教科書どおりに読めないとき、教科書(仕様)を疑うより
先に、自分の読みが仕様のどこで折れているかを突き止めるのが、この話の教訓です。

## 31.5 観測者自身も壊れる — トークンの寿命と仮想時計

障害試験は「観察者」を用意する必要があります。観察者もまた、時間が経つと壊れる
品物を持っています。この試験で2つ見つかった例を紹介します。

**ひとつは認証トークンの寿命です。** プローブは認証の要らない `/health` だけでなく、
認証の要る `/v1/users/me` も打ちます(本物の利用に近い窓を両方観察するためです)。
アクセストークンの有効期限は1時間で、試験窓も60分。このままだと試験の終わりで必ず
トークンが切れます。この途中で壊れる事故を防ぐため、プローブにはトークンのキャッシュ
を付けました。**発行から50分が経ったら、次のリクエストの前に新しいトークンを取り直す**
仕組みです。60分の試験窓と60分の寿命が
ぴったり重なる構図を避けるため、あえて10分の余裕を持たせて先回りする方式です。
観察者が長い試験の途中で自ら壊れる、という事故を構造的に消しています。

**もうひとつは時計の先行です。** ここが初心者には一番信じがたいところだと思いますが、
staging環境のサーバーは実時間ではなく**仮想時計(ControlledClock・第25章)**で
「今」を判断します。試験の中で時計を進めて月をまたぐと、サーバーの世界の「今」は
実時間より先に行ってしまいます。たとえば時計を1ヶ月進めた後の実世界では1日しか
経っていなくても、サーバーの世界では31日経っています。試験用に「30日間有効」の
認証トークン(IdPトークン)を発行していた部分が、ここで折れました。IdP(Identity
Provider)とは、認証を任された外部サービスのことで、IdPトークンは「本人がIdPで
確認済みだ」と証明するトークンです。仮想時計が
先行した状態でプローブがIdPトークンを発行するとどうなるか。サーバー側の検証は
仮想時計の「今」で有効期限を見るため、**実時間ではまだ1日も経っていないのに、
サーバーからは切れたトークン**に見えます。プローブは401で拒まれます。

対策は、IdPトークンの有効期間を30日から**365日**へ伸ばすことでした。発行に使うのは
試験専用の鍵で、伸ばすのも試験用トークンの寿命だけです。本番の設計を変える話では
ありません。それでも一時しのぎに見えるかもしれません。
けれども、この変更の背後には「サーバーが『今』を決める時計が1つ(第25章の
ControlledClock)であり、観察者はその世界の住人として振る舞う必要がある」という
設計の帰結があります。**試験の観察者は、システムの外の時間ではなく、システムの
中の時間で生きなければならない**。365日は、その原則を最も安く守る数でした。

## 31.6 警報器は、止まない側に置く

Queue障害(§4.7)の試験では、「処理の列(キュー)に滞留がたまったら知らせる」警報器を
作ります。滞留の作り方は仕様が決めていて、worker(裏方プロセス・第9章)を止めて、
Event(処理の知らせ)を流し続ける方式です。止まったworkerの外で列が伸びていく
姿を観察します。

ここで設計の選択肢が割れました。システムには、すでに60秒ごとに列の状態を数値にして
出す観測タスク(collector・第29章)があり、それはworkerの中で動いています。
「では警報もその観測タスクに足そう」——最初の設計メモにはそう書かれていました。
そしてこの案は、**矛盾していました**。workerを止めて滞留を作る試験では、workerと
一緒に警報器も止まる。鳴らしたい瞬間に鳴らない警報器を作ってしまう。先方の
コードに書かれていたコメント(「この数値を消費する」)は、実は置き場所の指定では
なく、「同じ数値を消費する」という意図の共有でした。

決まった案は、警報器を**API側**に置くことです。API(api1・api2)は滞留を作る試験で
止めない側なので、workerが止まっても警報器は動き続けます。同時に、警報器は既定で
無効(`LATCH_ALERT_QUEUE_ENABLED` という設定がfalse)で、staging環境だけ上書きで
有効にします。この有効化も既存の定義ファイルは1行も変えず、**override(上書き用の
差し替えファイル)**を後ろから重ねるだけで済ませました:

```yaml
# compose.staging.nfr.yaml(コメント行を除く全文)
services:
  api1:
    environment:
      LATCH_ALERT_QUEUE_ENABLED: "true"
  api2:
    environment:
      LATCH_ALERT_QUEUE_ENABLED: "true"
```

既存の世界は触らず、上書きで変える。これは試験の器を置くときの基本の型です
(バックアップ復旧試験のDB向き先の差し替えも、同じ型のoverrideファイルで
行いました)。

警報器には、もう1つ小さな工夫があります。**鳴るのは、条件が続いている間に1回だけ**。
滞留が続く限り、60秒ごとに「まだ滞留しています」と叫ぶ警報器は、それ自体が騒音に
なります。さらにstagingのAPIは2台なので、2台の警報器がばらばらに鳴る事故も起こり得ます。
工夫は、プロセス内の「鳴いた」印に加えて、Redisに1つの**取られる鍵**を置く方式に
しました。最初に鍵を取った側だけが鳴き、他方は黙ります。鍵には寿命(TTL)を付け、
鳴いた側が死んだ場合でも、寿命が切れたあとは別の側が再び鳴けるようにします。この
鍵の取り合いの仕組みを**アームキー**(アーム=撃鉄を起こす。発報できる状態にする、
という意味)と呼びます。
そして滞留が解消されたら、**resolve(解決)の記録**を1つ出して鳴き声を閉じます。
警報には必ず解除が対になる。これは費用上限の警報(D-16・第12章)と同じ規律です。

実測です。worker2台を止めて滞留を作り、仮想時計を310秒進めて「最も古い滞留の
経過時間」の条件を越えると、**2台のapi合算で警報1回**が鳴りました(取られる鍵の
おかげで2台同時に鳴かない)。workerを戻して列が消化されると、**resolve 1回**で
閉じました。警報が鳴ったことと鳴らなくなったこと、両方が記録に残るのです。

## 31.7 3万回打たない境界試験 — カウンタを直接置く

縮退試験(§4.5)のD-16は、Jev(AIへの判定依頼・第13章)を守る費用上限です。1日
30,000回が上限で、80%に達したら警報、上限に達したら実行を止めて候補を「Jev未判定」
として保留、JST 0時のリセットで復帰——第12章で読んだ4つのカウンタの話です。

試験では「上限に達したら止まること」を確かめたい。素朴な疑問が生まれます。
**本当に30,000回の判定を打つ必要があるのか?** 答えはノーです。Jevには実際のEventの
先に、Intentあたり1日40回・ユーザーあたり1日120回・30分の頻度制限という予算が先回り
します。素直に打って30,000回に届かせるには1万件級の母集団が必要で、境界の観察の
ためには割に合いません。実際、負荷試験(第30章)では大規模投入で自然に上限近くまで
到達していますが、あれは性能観察のための大規模投入であって、境界を精密に観る方法と
しては別の話です。

そこで、上限を「到達」させる代わりに「置く」ことにしました。カウンタの実体はRedis
(手元の付箋のサーバー・第1章)の
鍵(`jev:daily:20261005` のような日付入りの名前)なので、そこへ直接値を書き込める
小さな運用CLI(`latch-nfrtools`)を作ります。手順はこうです:

1. 日次カウンタを23,999に書き込む(`d16 set daily 23999`)
2. 実際のEventを1件投げる → カウンタは24,000になり、**80%の警報が鳴る**
3. 29,999に書き込む → 実際のEventを1件投げる → **上限超過で実行が止まる**
   (候補は「Jev未判定」のまま保留・提案数は増えない)
4. 仮想時計でJST 0時を跨ぐ → 新しい日付の鍵に切り替わり、実行が復帰する

この方法の要点は、「境界までの道のり」を省略し、「境界そのもの」を実経路で通す
ことです。実際の処理(INCRでカウンタを増やし、その戻り値で判定する)は本物を通り、
警報が鳴るのは戻り値が**ちょうど**しきい値に等しいとき1回だけ、という細かい挙動まで
確かめられます。偽物で置いたのは道のりだけで、門番の判定は本物。こうした「どこを
本物にして、どこを近道にするか」の線引きが、仮定で試す障害試験の腕の見せ所です。
実際、測定では警報は1回だけ鳴り、上限超過では提案がゼロのまま(244件→244件)、
0時越えで鍵が切り替わって実行が戻ることが確認されました。

月次上限との独立性も同じ手で確かめます。月次カウンタを479,999に置いて1回打つと、
**月次の警報だけが鳴って日次の警報は鳴らない**。両者が別々の鍵で数えられている
ことを、互いの値の増減で証明します。

なお、1点正直な観察の記録を添えます。「上限に達したあとも列の滞留が残り続ける」という
観察が、前の単位(第30章の報告書)に残っています。今回はその観察を裏取りするため、上限到達後の
列の推移を追ったところ、滞留は4件から60秒でゼロになりました。条件が違います。あちらは
1万件級の母集団と30分ごとの再評価の循環が重なった状況で、今回はペア単位の小さな
母集団です。**同じ機能でも、規模と条件が変われば観察される挙動は変わる**。前の観察と
矛盾しているようで、矛盾していない。こうした条件の違いを報告書に書き残すのも、
実測を扱う仕事の一部です。

## 31.8 実測が残した数と、割り切った判断

最後に、この単位の実測値を一覧しておきます。証拠は `docs/testassets/results/` の
YAML 6件と `ws-7-report.md` です。

**バックアップ復旧の復旧所要時間(RTO)**。目標値は規定されていないため、測って
記録すること自体が試験の成果です:

| 区間 | 実測 |
|---|---|
| 復元先のDB(第2台)の起動 | 9秒 |
| バックアップの復元(pg_restore) | 1秒 |
| api/workerの向き先切り替え | 8秒 |
| 再エンベディングの回収(8件) | 約10秒 |

「データベースを丸ごとバックアップから復元して、意味の数値(embedding・第10章)を
作り直し、サービスに戻す」一連の手順が、数十秒の世界で通ることを初めて実測しました。
復旧の前に(active Intentの数を数える)前後の一致検査(cross-check)では6件=6件で
一致しています。

**可用性の判定**。main(1分間隔)38サンプルで失敗ゼロ・成功率100%・機械判定は
「合格」。ただし、この数には事情が付いています。試験窓の途中(96分)で実施マシンが
スリープしたため、計画の60分窓は**実効44分**になりました。観察点(安定→強制停止と
復旧→計画停止→事後安定)はすべて網羅していたため、実施側の人間は「44サンプルで
成立とする」と裁定しました。機械の判定が自動で下すのは「数の条件(99.5%)を満たすか」
だけで、窓の成立そのものの最終判定は人間の側に残してあります(第30章の「測定器と
判定者の分離」と同じ構造です)。

**Queue障害の3つの毒と1つの重複**。悪い入力(構造を破ったJSON)は5回の再試行のあと
隔離(quarantined)され、失敗の理由が記録に残る。すでに削除されたIntentへの参照は
隔離ではなく**破棄**(processedで閉じる)され、「なぜ破棄したか」の理由が記録に残る。
同じEventを2回投げても候補は二重に作られず(700件→700件のまま)。毒のあとに投げた
正常なペアは提案まで到達し、毒が後続に波及しないことを確認しました。

**縮退の待ち伏せの記録**。resume(一時停止からの再開)では、Embeddingをやり直さずに
再評価が起きることを確かめました。確かめ方は、embeddingの列が変わらないことを
DBで照合する方法です。catch-up(遅れて来たBucketの回収)では、embeddingが空の
Intentが回収対象から外れることを、1件の除外観察で証明しました。どちらも第18章で
読んだ2つの再評価経路の動きを、実環境で閉じた話です。

## 31.9 この章のまとめ: 壊し方の設計は、観察の設計

4つの領域を通じて繰り返し現れたのは、**「壊す」ことそのものは簡単で、何を観察し、
何を数え、何を数えないかの設計が試験の本体**だということです。成功率99.5%は
「数えない窓」の仕組みとセットに、自動復旧の確認は「自然死の演出」とセットに、
滞留の警報は「止まない置き場所」とセットに、上限の境界は「カウンタを置く近道」と
セットになりました。

そして、設計どおりの手順が実環境で通らなかったとき(docker kill)、通ったとしても
条件が前の観察と違うとき(pending 4→0)、それぞれを**読み替えの記録・条件の違いの
記録**として残しました。観察が計画を修正し、修正が次の読み手(あなたを含む)への
教材になる。壊して観察する仕事の本当の成果は、壊れたシステムを直すことでなく、
**次に同じ場所を壊す人が読める記録**として残るほうにあります。

| 可用性 | 壊れていても使い続けられる度合い。ここでは「計画停止を除く成功率99.5%」 |

| 自然死 / 手動停止 | dockerコマンドの手を借りない死(再起動対象)/ stop・killなど明示的な停止(再起動対象外) |

| quarantine(隔離) | 5回の再試行でも処理できなかったEventを、理由を保持して隔離しておくこと |
