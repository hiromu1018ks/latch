## 25.1 この章の題材: 1つの世界に、時計は1つ

第3章で、時計を差し替えられる設計(Clock)を読みました。テストでは `FakeClock` に差し替えて、
「あたかも1日経った」世界を数秒で作れる。ここまでの話は、**1つのプロセス**の中の話でした。
テストコードが1個の偽時計を持って、アプリに渡す。話が完結するのはその箱の中だけです。

M4のstaging環境では、ここから世界が広がります。stagingとは、本番と同じ構成を小さく再現した、
常設の実コンテナ環境です(10 第1節の定義を、この教科書風に言い換えたもの)。中身はこうです。

| 箱(コンテナ) | 役割 | 個数 |
|---|---|---|
| nginx(エンジンエックス) | 入口。届いたリクエストを2台のapiへ振り分ける係 | 1 |
| api | 第2章で読んだFastAPIのアプリ | 2 |
| worker | 第9章以降で読んだ裏方プロセス | 2 |
| db・redis・pubsub | データベース・小物置き・配達係 | それぞれ1 |

注目してほしいのは、**apiとworkerが複数ある**ことです。nginxが「入口1つ・中身2台」を作り、
どちらかが止まってももう1台が応答を続けられます(本番のロードバランサーの小さな模型です)。

ここで第3章の発想をそのまま持ち込むと、問題が起きます。api1に `FakeClock`(10月4日)、
api2に `FakeClock`(10月3日)、worker1は……と、箱ごとに別々の時計を持たせたらどうなるでしょう。
時計が狂っている家の中の話は、もう「テストが安定する」どころではありません。

- **アクセストークンの期限判定が、たまたま届いたapiで変わる**。同じトークンなのに、api1では
  「有効」、api2では「期限切れ」になる
- **60秒周期のバッチ(第18章のsweeper)が、worker1とworker2で違う時刻を見て動く**。
  「期限が切れた行を1回だけ閉じる」という約束の下地が崩れる
- 「3時間後で期限切れ」に保存したIntentが、どの箱で見ても同じ「3時間後」にならない

時刻が食い違うと、これらは全部**静かに**起きます。エラーで落ちてくれないぶん、厄介です。
こういうことです。**時刻は「そのシステムの世界の時間」であり、世界を構成するプロセスが
複数いれば、時計も複数のプロセスにまたがって1つでなければならない**。この章の残りは、
それをどう実現したかの話です。

## 25.2 下準備の確認: 環境は3層になった

先へ進む前に、環境の名前をそろえておきます。M4で、動かす環境が1つから3つに増えました。

| 環境 | 何のためにあるか | 中身の特徴 |
|---|---|---|
| ci(シーアイ) | 毎コミットの自動試験 | 第1章で読んだ5サービス。試験はテストプロセスの中で動く(in-process) |
| staging(ステージング) | 本物に近い環境での機能検証 | 本番と同じ種類の部品を縮小構成で。api2台+nginx・Clock制御が効く |
| load(ロード) | 負荷試験と総当たり検出 | stagingと同じ構成を**完全に分離して**もう1組(ポート番号28000系) |

stagingとloadの2つは、`compose.yaml` とは別の定義ファイルで作られています
(`compose.staging.yaml`・`compose.load.yaml`)。Docker Composeには「プロジェクト」という
区切りがあり、プロジェクト名が違えばコンテナ名・ネットワーク・データ置き場(ボリューム)が
自動的に分かれます。stagingは `latch-staging`・loadは `latch-load` という名前の、
**ci環境とは無縁の別世界**として立てられます。dbのデータ置き場が違うため、ci環境のデータを
書き換えてしまう事故も構造的に起きません。

ポート番号も、stagingは18000番台・loadは28000番台と、ci(8000番台)と衝突しない番号に
決められています。1台のPCの中に3つの世界が同居するための、番地の決め事です。

なお、この章で扱うのはstagingの側です。load環境の詳しい話(負荷試験・総当たり検出)は、
その単位の教材ができたときの題材にします。

## 25.3 解決の発想: 「基準点」を箱の外に置く

では、複数のプロセスで1つの時計を共有するには、どうすればいいでしょう。
考え方の軸は、第3章のDIと同じ「**作らせない、外から渡す**」です。時計の中身を、どのプロセスの
中にも置かず、全員が覗きに行ける**外の置き場**に置いてしまう。staging構成には、はじめから
「外の置き場」が参加しています。Redisです。

その置き方の設計を、`ControlledClock`(コントロールドクロック=制御できる時計)と読みます。
第3章までのClock家族に加わった、**第4の時計**です。

### 基準点という発想

`ControlledClock` は「いま何時か」を直接覚えていません。代わりに、**基準点**と呼ぶ
対応付けを1つだけ覚えています。

> 実時間のX秒のとき、仮想時間はY秒だった

基準点を「時計の写真」にたとえると分かりやすいです。17時ちょうどの時計の写真を1枚置いて、
誰かが「いま何時?」と聞いたら、「あの写真から何秒経ったか」を足して答える。写真は1枚なので、
見る人が誰でも同じ答えが出ます。時刻を動かしたくなったら、**写真を撮り直す**(新しい基準点を
書き込む)。この単純な仕組みです。

実際のコードでは、Redisの1つのキーに、基準点をJSONで保存します
(`backend/src/latch/core/clock.py` 66〜95行より。キー名は `latch:clock:control`):

```python
class ControlledClock(Clock):
    """staging/load用の共有制御Clock(10 §1「時刻操作」・M4 ws-1 design §2.2)。

    Redis 1キーに「基準点(実時刻↔仮想時刻の対応)」を置き、api 2台+worker
    の複数プロセスが同一キー参照で同一の仮想時刻を見る。操作はホスト側CLI
    (python -m latch.core.clock_cli)から行う。
    - キー不在 = オフセット0 = 実時間(「制御していない状態」はSystemClockと等価)
    - Redis到達不能は例外でfail-closed(例外を握って実時間へ落とさない。
      stagingのRedisは常設restart: unless-stopped)
    - rate(速度倍率)は設けない(YAGNI): sweeper/Runnerの待機はasyncio.sleep
      (実時間)のため速くならない。Clock操作で期限を未来へ動かすのが10 §1の
      規定手段
    """

    DEFAULT_KEY = (
        "latch:clock:control"  # ci環境のRedisとは別インスタンスのため名前衝突なし
    )

    def __init__(self, client, *, key: str = DEFAULT_KEY) -> None:
        # clientは同期redisクライアント(get/setを持つオブジェクト。unit試験はfakeredis)
        self._client = client
        self._key = key

    def read_base(self) -> tuple[float, float] | None:
        """基準点(real, virtual)の生値をunix秒floatで返す。キー不在はNone。"""
        raw = self._client.get(self._key)
        if raw is None:
            return None
        data = json.loads(raw)
        return float(data["real"]), float(data["virtual"])
```

「いま何時か」の計算は、この基準点と「写真から何秒経ったか」の足し算です。

```python
def _compute_now(base_real: float, base_virtual: float, real_now: float) -> datetime:
    """基準点+実時間経過から仮想時刻を計算する(純関数 — unit試験は決定的)。"""
    return datetime.fromtimestamp(base_virtual + (real_now - base_real), tz=UTC)
```

`now()` は、基準点を読み(`read_base`)、この計算に渡すだけです
(`backend/src/latch/core/clock.py` 115〜119行):

```python
    def now(self) -> datetime:
        base = self.read_base()
        if base is None:
            return datetime.now(UTC)
        return _compute_now(base[0], base[1], datetime.now(UTC).timestamp())
```

最後の1行は、第3章3.7で読んだ**番人テスト**の存在を思い出させます。実時間の直接参照
(`datetime.now(UTC)`)が製品コードに書けるのは `clock.py` だけ。`ControlledClock` は
`clock.py` の中に実装されているので、この参照は合法です。番人への登録のしかたから先に決めて、
実装の場所をそこに合わせた、というのが実際の順番でした(設計メモに引用確定値として記録して
あります)。規約(この場合は番人)が先にあり、実装がそれに従う。プロジェクトの作り方として
繰り返し出てくる形です。

`_compute_now` が**純関数**として切り出されている点にも注目してください。第3章3.6で読んだ
unit試験の作法——外部の何にも依存しない計算は、決定的に試せる——がここでも生きています。
基準点2つと現在の実時間を渡せば、何回実行しても同じ答えが返る。試験は実Redisなしで書けます。

### 基準点の足し算の実例

数値で1回、追いかけてみましょう。`set` された基準点が次の値だったとします。

- `real` = 1791001149.0(実時間のある一点・unix秒。1791001149秒は2026年10月3日の15時台です)
- `virtual` = 1791126000.0(仮想時間の対応点。2026-10-04T00:00:00+09:00、つまり日本時間の
  翌日の0時ちょうど)

これが「実時間の15時台に、仮想時間は翌日0時だった」という写真です。その10秒後に `now()` を
呼ぶと、`1791126000 + (実時間 - 1791001149)` = 仮想時間の0時10分です。Lab 11で実際に
観察する「`set` した時刻から、実際の時間の速さで進み続ける」現象の正体がこの足し算です。

## 25.4 時計を操る: setとadvance

基準点の読み方を読んだので、操り方を読みます。操作は2つあります。

```python
    def set(self, when: datetime) -> None:
        """基準点を「いま実時間→when仮想時間」へ書き換える。

        後退可(FakeClock.setと同一契約)。
        """
        if when.tzinfo is None:
            raise ValueError("ControlledClock.set は tz-aware な時刻を要求する")
        self._write_base(
            datetime.now(UTC).timestamp(), when.astimezone(UTC).timestamp()
        )

    def advance(self, delta: timedelta) -> None:
        """仮想基準点をdeltaだけ前進させる(実アンカーは保持 — 経過分はnow()が加算)。"""
        base = self.read_base()
        if base is None:
            base = self._initialize_base()
        self._write_base(base[0], base[1] + delta.total_seconds())
```

**`set` は写真の撮り直し**です。「いまの実時間から見て、仮想時間をここへ動かす」という
基準点を書き込む。タイムゾーンなし(naive)の時刻を渡すと拒否するあたりも `FakeClock` と
同じ契約で(第3章3.3)、後退もできます。「過去の日付を指定したら拒否される」という試験には、
過去側に動かす必要があるからです。

**`advance` は写真の仮想時間の部分だけを前へずらす**操作です。docstringに
「実アンカーは保持」とあるのがポイント。基準点の実時間側を残したまま、仮想時間側だけを
足し合わせます。これが `set` との違いです。`set` は「仮想時間を、いまの実時間のここに動かす」、
`advance` は「いま見えている仮想時間から、この秒数だけ進める」。Lab 11では
`advance 86400`(86400秒=1日)で「1日だけ進める」をやります。

ここまで読むと、`ControlledClock` と `FakeClock` は、どちらも「操作できる時計」です。
違いを1つ挙げると、`FakeClock` の時計は操作した瞬間にぴったり止まっているのに対して、
`ControlledClock` の仮想時間は**操作したあとも実時間と同じ速さで進み続ける**ことです。
写真を撮り直しても、時間はその後も経っていく。偽の世界を完全に止める道具と、本物の世界の
時計の針をずらす道具の差です。この差は、stagingの目的に合わせて生まれたものです。
常設環境では、sweeperの60秒周期のように「実時間でゆっくり動く処理」を観察したい。
時計の針をずらしながら、それ以外は本物の時間で動く世界がそこに必要だからです。

## 25.5 3つの設計判断と、その理由

コードそのものは薄いです。`ControlledClock` の設計で大事なのは、**何を作らなかったか**を
含む3つの判断です。設計メモ(`ws-1-design.md` §2.2)に選択肢ごとの比較と一緒に記録が
残っています。1つずつ読みます。

### 判断1: キーがなければ、実時間とみなす

`now()` の最初の分岐を思い出してください。基準点が読めなかったら(`read_base` がNone)、
実時間をそのまま返します。

```python
        base = self.read_base()
        if base is None:
            return datetime.now(UTC)
```

「制御されていない状態」を、エラーでも「まだ初期化されていない特別な状態」でもなく、
**オフセット0の実時間**として扱う設計です。stagingを立てた直後は、誰も基準点を書いていないので、
api・workerは実時間で動きます。つまり**何もしない普通の状態が、既存の `SystemClock` と
まったく同じ挙動**に見えるわけです。

ここに「キーがない=まだ初期化されていない」という独自の状態を作っていたら、どうなっていたか。
環境を立てるたびに「まず初期化の手順」という導線が要り、忘れたときの挙動の説明が1つ増えます。
対応付けがない状態を素直に「ずれなし」に読めるおかげで、stagingの立て方に初期化の手順は
要りません。

### 判断2: Redisに届かなければ、例外で止まる

`read_base` は、キーが**ない**ときと、Redisそのものに**届かない**ときを区別します。
後者では例外が投げられます(実装は読み取りメソッドの呼び出しにそのまま任せています)。
docstringの「Redis到達不能は例外でfail-closed」がこの判断です。

「fail-closed(フェイルクローズド)=失敗したら閉じる」は、危険な側へ静かに倒れ込むのを
避ける設計の呼び名です。対になる言葉がfail-open(開いたまま倒れる=通したまま倒れる)で、
たとえるなら、停電のとき信号が**赤**になるのがfail-closed、**青のまま**になるのがfail-openです。

なぜClockでこれが大事か。次の2つの世界を比べると分かります。

- **fail-openの世界**: Redisが止まると、apiとworkerは気づかず実時間で動き続ける。試験している
  人は「Clock操作が効かないな、おかしいな」と後で気づく。その間に、仮想時間の前提で作った
  データが、実時間の挙動で書かれていく
- **fail-closedの世界**: Redisが止まると、apiとworkerは時刻の問い合わせで例外を起こす。
  すぐに異常に気づける。原因(Redis)を直せば動く

stagingは「時計をずらして、期限の挙動を試す」ための環境です。Clockが静かに実時間へ
戻ってしまうと、その試験の信頼が全部崩れます。だから失敗は**音を立てて**落ちるべき、という
判断です。

### 判断3: 速さ倍率(rate)は作らない

時刻の制御というと、「時計を10倍速で回す」機能を想像した人もいるかもしれません。
10倍速の時計は、便利なようで、このプロジェクトでは役に立ちません。理由は、実装の外にあります。

LATCHの裏方では、処理の多くが次のtickまで `asyncio.sleep`(一定秒、実際に待つ)で待っています
(第18章のsweeperの60秒周期がその代表)。`asyncio.sleep` は、仮想時間ではなく**実際の時間**で
待ちます。Clockを10倍速にしても、寝ている係は実時間で60秒寝たままです。結局、速くなるのは
「`now()` の答え」だけで、待ち動作は速くならない。期待と違う道具は、使う人を混乱させるだけの
危険があります。

だから「速くしたい」はClockでは解決せず、**Clock操作で期限を動かす**ほうに解決を寄せました。
「1日後の挙動を見たい」なら、1日待つのではなく、時計を1日進める(`advance 86400`)。
これは仕様書(10 第1節「時刻操作」)に規定された、試験の公式手段です。

「役に立つ保証のない機能を、役に立つと分かるまで作らない」という判断には名前があって、
**YAGNI(ヤグニ=You Aren't Gonna Need It、あなたはそれを必要としない)**と呼ばれます。
設計メモにも素直に「YAGNI」と記録してあります。作らない判断も、理由と一緒に記録する——
このプロジェクトの設計メモの作法が、作らなかった機能にも適用されている例です。

## 25.6 差し替え点は1つのまま: make_clock

ここまでで「第4の時計」の中身は読めました。最後のピースは、**誰が、いつ、この時計を選ぶのか**
です。答えは、第3章で読んだ組み立て(`create_app`)です。ただし、選び方が1段階賢くなりました。
`make_clock`(メイククロック=時計を作る)という組立用の関数が追加されています
(`backend/src/latch/core/clock.py` 136〜155行):

```python
def make_clock(settings: Settings, *, redis_client=None) -> Clock:
    """clock_mode設定でSystemClock/ControlledClockを選ぶ組立ヘルパー(design §2.2)。

    create_app()・worker/__main__.pyの既定構築経路。clock引数を明示する既存DI
    (unit/integration試験)はこの関数を通らないため無傷。redis_clientはunit
    試験がfakeredisを注入するためのDI(既定=redis_urlから構築。redis-pyは
    遅延接続のため構築のみでI/Oは起きない)。
    """
    mode = settings.clock_mode
    if mode == "system":
        return SystemClock()
    if mode == "controlled":
        if redis_client is None:
            import redis as redis_sync  # 遅延import(clock.pyの依存を最小化)

            redis_client = redis_sync.Redis.from_url(
                settings.redis_url, decode_responses=True
            )
        return ControlledClock(redis_client)
    raise ValueError(f"unknown clock_mode: {mode!r} (system/controlled)")
```

読み方は素直です。設定値 `clock_mode`(どこで時計を作るか、モードの設定)が `"system"` なら
`SystemClock`、`"controlled"` ならRedisクライアントを作って `ControlledClock` を組み立て、
それ以外の値ならエラーで落とす。stagingとloadのコンテナでは、環境変数 `LATCH_CLOCK_MODE`
が `controlled` に設定されます。ci環境では設定なし=既定の `system` のままなので、
**ci環境では何も変わっていません**。

大事なのは、この追加が第3章の設計を壊していないことです。

- アプリとworkerは、組み立て時に `make_clock(settings)` の**結果**を渡される。時計を自分で
  作らせない(第3章3.5の原則のまま)
- 試験は従来どおり `create_app(clock=FakeClock(...))` と、時計を直接渡す。`make_clock` を
  経由しないので、試験は何も変わっていません
- 変わったのは「引数を省略したときの**既定値**を誰が決めるか」だけ。それが `SystemClock` の
  直接指定から、`make_clock` の選択に変わりました

「差し替え点が1つ」という第3章の文句は、差し替え先が増えてもそのまま保てました。
選択肢が増えるときは**選ぶ人**を1か所にまとめ、使う側は選ばない。この組み立て方には、
時計に限らず効く話です。

## 25.7 手元から操る: clock_cli

最後は、時計の操作口です。Redisの基準点を書き換えるには、Redisへ届けばどこからでもいい
わけですが、stagingでは**ホスト側(コンテナの外)のCLI**から操作します。新しく
`backend/src/latch/core/clock_cli.py` に作られた、次のコマンドです。

| コマンド | 何をするか |
|---|---|
| `python -m latch.core.clock_cli show` | 制御状態(基準点)と、仮想時間・実時間を並べて表示する |
| `... clock_cli set <ISO8601>` | 基準点を書き換えて、仮想時間を指定した時刻へ動かす(後退も可) |
| `... clock_cli advance <秒>` | いまの仮想時間から指定秒だけ前進させる |

Makefileには `make staging-clock ARGS="..."` というショートカットが用意されています。
このCLIが書き込むのは、ただのRedisのキーです。すると、そのRedisを見ているapi・workerの
`now()` が、次の問い合わせから新しい時間を返し始める。**プロセスを1つも再起動せずに**、
動いている世界の時計の針が動きます。CLIから先に環境を覗いて、反応を観察する——
その一連の流れを、Lab 11で実際にやってみます。

もう1つ、仕掛けを紹介しておきます。このCLIは「どこに届けるか」を設定で決めます(送り先の
Redisは `LATCH_REDIS_URL` という環境変数で上書きできる)。staging宛なら16379番、load宛なら
26379番を指定するだけです。プロジェクトの最初から貫かれている作法——**設定は環境変数で
上書きできて、コードの書き換えなしで届け先を変えられる**——が、ここでも働いています。

## 25.8 この章の再統合

- テストの `FakeClock` は1プロセスの話。api2台・worker2台の常設環境では、プロセスごとに
  時計を持たせると時刻が食い違い、トークンの期限判定や60秒周期のバッチの前提が崩れる
- `ControlledClock` は、基準点(実時間↔仮想時間の対応付け)をRedisの1キーに置き、
  `now()` = 仮想基準点 + 実時間の経過分 で答える。見る人が誰でも同じ写真から同じ答えを
  出す仕組み
- 操作は `set`(基準点の撮り直し)と `advance`(仮想時間だけ前進)。操作後も実時間の速さで
  進み続ける点が、完全に止めた `FakeClock` と違う
- 作らなかったものが設計の質を決めた: キー不在=実時間(初期化手順が要らない)・
  Redis不在=例外(fail-closed。静かに実時間へ落とさない)・rate不採用(YAGNI。
  `asyncio.sleep` は実時間で待つので倍速は期待どおりに効かない)
- 組立は `make_clock(settings)` に集約された。差し替え点は1つのまま、選ぶ人だけが増えた。
  ci環境には `clock_mode` の設定がないため、ciでは何も変わっていない

### 4つの時計の対応表

第3章からこの章までで出会った、Clock家族の対応表です。時刻の動かし方と、動く場所を
合わせて見てください。

| 実装 | 役割 | 動く場所 | 時刻の操作 |
|---|---|---|---|
| `Clock`(契約) | 「`now()` を呼べばUTC付きで返す」の約束。単体では作れない | — | — |
| `SystemClock` | 本番用。実時間を返す(実時間参照が許される唯一の実装) | 本番・ci・staging(制御なし時) | できない |
| `FakeClock` | テスト用。偽の時間の世界を作り、完全に止めておける | テストコードのプロセス内 | `set`・`advance`(アプリの外から) |
| `ControlledClock` | staging/load用。複数プロセスが見る共有の針 | Redisの1キーを介して全プロセス | CLIの `set`・`advance`(動いたまま) |

## 25.9 用語集(この章で登場した言葉)

| 用語 | 一言でいうと |
|---|---|
| staging環境 | 本番と同じ種類の部品を縮小構成で立てた、常設の検証用環境 |
| load環境 | stagingと同構成を完全に分離して立てた、負荷試験用の環境 |
| Docker Composeのプロジェクト | composeで立てる1組の世界の名前。名前が違えばコンテナ名・ネットワーク・ボリュームが自動で分かれる |
| ボリューム | コンテナの外に置くデータ置き場。プロジェクトごとに別々に作られる |
| nginx | 入口で受けて、複数のapiへ振り分ける係。本番のロードバランサーの小さな模型 |
| in-process | 試験を、アプリと同じプロセス(1つの箱)の中で動かす方式。ciの試験のやり方 |
| ControlledClock | Redisの1キーに基準点を置き、複数プロセスで同じ仮想時間を見せる第4の時計 |
| 基準点 | 「実時間のX秒のとき、仮想時間はY秒だった」という対応付け。時計の写真 |
| fail-closed | 失敗したとき、危険な側へ静かに倒れず、例外や停止で確実に止まる設計。停電で信号が赤になる |
| rate(速度倍率) | 時計を何倍速で進める設定。今回は `asyncio.sleep` が実時間で待つため作らないと決めた |
| YAGNI | 役に立つと分かるまで機能を作らない主義。You Aren't Gonna Need It |
| make_clock | `clock_mode` の設定値を見て、4つの時計から該当の1つを組み立てる関数 |
| clock_cli | staging/loadのRedisに届いて、基準点を表示・書き換えるホスト側のCLI |

2. `ControlledClock` の `now()` が、キーを読んで仮想時間を計算するまでの流れを、
   「写真」と「経過秒」の言葉で説明してください
3. `set` と `advance` の違いを、「基準点のどの部分を書き換えるか」で説明してください
4. 「キー不在=実時間」の判断は、stagingの立て方からどんな手順を消しましたか
5. 10倍速の `rate` を作った場合、期待どおりに動かない処理を第18章から1つ挙げ、
   なぜ動かないのか説明してください
6. Clockの4つの実装について、それぞれ「時刻の操作はできるか」を対応表から答えてください
