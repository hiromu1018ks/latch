## 3.1 時刻はなぜ難しいのか

ソフトウェアで「今何時」を扱うことは、見た目より難しいのです。理由は3つあります。

**理由1: テストが再現できない**。もし各所が `datetime.now()`(呼んだ瞬間の実時刻)を直接使うと、
「この処理は締め切り1時間後に締め切られる」のような試験をするには、実際に1時間待つしかありません。
しかたなく1時間待ったとしても、テストを実行するたびに時刻が違うので、**昨日通ったテストが
今日は運悪く失敗する**ことが起きます。これを「テストが不安定(フレーキー)」と呼び、
テストへの信頼を一番削る問題です。

**理由2: タイムゾーン**。同じ「9月27日23時」でも、日本時間と世界標準時(UTC)では9時間のずれが
あります。時刻データに「どこの時間帯か」の情報が付いているか(タイムゾーン付き、aware)と
付いていないか(素のデータ、naive)で、比較や変換の挙動が変わります。naiveのままで比較すると、
静かに間違った答えを返すのがたちの悪いところです。

**理由3: 意図的な時刻操作**。LATCHには日本時間の0時にリセットする処理、月初の処理、
連続操作をまとめる10秒の窓など、**時刻の境界で意味が変わる処理**が多数あります。
境界の直前・直後を確かめたいのに、実時間では「23時59分59秒ちょうど」を狙って試験できません。

LATCHはこの3つすべてに、ひとつの設計で答えました。**「今何時か」を知る経路を1本に集約し、
その中身を差し替えられるようにする**。その経路が Clock で、プロジェクトの依存制約C2
(「Clockを最初に作る。時刻参照はすべてClock経由」)として、他のどんな実装より先に作られました。

## 3.2 必要なPythonの基礎: クラス・継承・抽象

`clock.py` を読むために、Pythonの「クラス」まわりの言葉をここで固定します。すでに知っている人は
読み飛ばして、3.3から始めてください。

**クラス**とは、「データと、そのデータを扱う関数をひとまとめにした設計図」です。
設計図から作った実体を**インスタンス**と呼びます。次のコードでは、`SystemClock` が設計図、
`SystemClock()` とカッコを付けて呼んだ結果がインスタンスです。

```python
clock = SystemClock()      # 設計図から実体を作る
clock.now()                # 実体に対して「今何時?」と聞く
```

クラスの中に定義する関数を特に**メソッド**と呼びます。メソッドの第一引数は慣習で `self` と
書き、「この実体自身」を指します。

**継承**とは、既存のクラスの機能を受け継いで新しいクラスを作ることです。
`class SystemClock(Clock):` と書くと「`Clock` の性質を引き継いだ `SystemClock`」という意味に
なります。継承元を**親クラス(基底クラス)**、継承した側を**子クラス**と呼びます。

**抽象メソッド**は「子クラスで必ず実装しなさい」という親クラス側の命令です。
実装の中身を決めないまま名前だけを宣言しておき、`@abstractmethod` の飾りを付けます。
抽象メソッドを持つクラス(**抽象基底クラス**、ABC)からは直接インスタンスを作れず、
子クラスがそのメソッドを実装して初めて実体が作れます。書き忘れると、インスタンスを作った
瞬間にエラーで教えてくれます。**「契約の忘れを機械が検出する」**仕組みがここに出てきます。

## 3.3 clock.py を全行読む

では本題です。`backend/src/latch/core/clock.py` は61行しかないので、区切りごとに全部読みます。

### (1) 冒頭: importとJSTの定義

```python
from datetime import UTC, date, datetime, timedelta, timezone

# 日本に夏時間はないため、固定オフセット+9時間で確定させる。
JST = timezone(timedelta(hours=+9))
```

`from datetime import ...` は、Python標準の `datetime` ライブラリ(日時を扱う部品集)から
必要なものだけを持ってくる宣言です。持ってきているのは、世界標準時の情報(`UTC`)、
日付(`date`)、日時(`datetime`)、時間の長さ(`timedelta`)、時間帯(`timezone`)の5つです。

`JST` は「日本の時間帯」を表す変数で、UTCから+9時間の固定オフセットと定義しています。
日本には夏時間がないので、+9時間固定で一生ものです。なぜ変数に置くのかというと、
「+9」という数字をコードの各所に書き散らすと間違いの元になるからです。1度だけ定義して
名前を付ける。これが定数管理の基本です。

### (2) Clock: 契約を定義する側

```python
class Clock(ABC):
    """時刻参照の単一経路(C2)。now()はtz-aware UTC、JST暦日付はjst_date()。"""

    @abstractmethod
    def now(self) -> datetime:
        """tz-aware UTC の現在時刻を返す。naive datetime は返さない。"""

    def jst_date(self) -> date:
        """now() を JST 暦日付へ変換する(JST日付キー・リセットジョブ判定用)。"""
        return self.now().astimezone(JST).date()
```

`Clock` は「時計とは、`now()` を呼べば世界標準時つきの現在時刻を返すものだ」という**契約**そのものです。
`now()` に `@abstractmethod` が付いているので、`Clock` 単体では実体を作れず、子クラスが必ず
`now()` を実装しなければなりません。

`jst_date()` の方は `@abstractmethod` が付いていません。実装が親クラスに書けるものは
親に書いてしまい、子はそれをそのまま使います。中身は「`now()` を日本時間に変換して日付だけ取る」
の1行です。**`self.now()` と書いてあるのが味噌で**、これにより、子クラスが `now()` を
どう実装していても(本物の時計だろうと偽物だろうと)、`jst_date()` は自動的に正しく追従します。

### (3) SystemClock: 本番用の実装

```python
class SystemClock(Clock):
    """本番用。実時間の現在時刻を返す(実時間参照が許される唯一の実装)。"""

    def now(self) -> datetime:
        return datetime.now(UTC)
```

契約を満たすのは、`now()` を1つ実装するだけです。`datetime.now(UTC)` は「引数に時間帯を渡して
呼ぶと、その時間帯つきの現在時刻を返す」という標準ライブラリの使い方です。
docstring(関数の直後に書いた `"""..."""` の説明文)に「実時間参照が許される唯一の実装」とある通り、
**製品コードで実時間に触れてよいのは、プロジェクト全体でこの1行だけ**です。
この規律を機械で守る仕組みは3.7で出てきます。

### (4) FakeClock: 試験用の実装

```python
class FakeClock(Clock):
    """テスト用。set()/advance() で決定的な時刻を再現する(10 第1節「時刻操作」)。"""

    def __init__(self, initial: datetime) -> None:
        if initial.tzinfo is None:
            raise ValueError("FakeClock は tz-aware な初期時刻を要求する")
        # Clock契約(now()はtz-aware UTC)を守るため非UTC表現は正規化する。
        self._now = initial.astimezone(UTC)
        self._lock = threading.Lock()
```

`FakeClock`(フェイククロック=偽時計)は、「好きな時刻の世界」を作る時計です。
`__init__` は**インスタンスが作られる瞬間に自動で呼ばれる初期化メソッド**で、
作るときに渡された初期時刻を `self._now` に保存しています。先頭の `_`(アンダースコア)は
「外から触らないで」の慣習的な印です。

2つの防御に注目してください。素の(naiveな)時刻を渡すと `ValueError`(値が間違っているという
例外)で拒否します。タイムゾーン付きでも日本時間などUTC以外で渡されたら、UTCに変換して
保存します。これにより「Clockから出てくる時刻は常にUTC付き」という契約が、どの使い方でも
破れないようになっています。実はこの正規化は、コードレビューで「日本時間のままで持てるのでは」
という指摘を受けて追加された堅牢化です。設計は書きっぱなしでなく、レビューで育つのです。

```python
    def set(self, when: datetime) -> None:
        """任意時刻へ移動する(後退も可。「過去不可」境界試験の両方向に使用)。"""
        ...
    def advance(self, delta: timedelta) -> None:
        """時刻を delta だけ前進させる(期限・debounce・バッチ周期の再現に使用)。"""
        ...
```

この2つのメソッドが「時刻の操作」を可能にします。`set` は時計の針を好きな時刻に合わせる、
`advance` は針を好きなだけ進める。**後退もできる**のがポイントで、「開始日時に過去を指定したら
拒否される」のような試験には、過去側と未来側の両方が必要になるからです。

`threading.Lock` は「複数の処理が同時に `self._now` を書き換えて壊れるのを防ぐ鍵」です。
asyncioの世界で並行処理する前提の部品には、このような小さな保険を入れておく作法があります。

## 3.4 タイムゾーンの話: なぜUTC統一か

3.1で挙げた理由2を、このプロジェクトの流れで整理します。LATCHの方針はこうです。

- **内部の保持・比較・保存は、全部UTCのタイムゾーン付き時刻で行う**
- **日本の暦日付が必要な処理だけ、`jst_date()` で変換して使う**(「今日の分のカウント」のような、
  日本の暦で区切らないと意味が変わる処理)

なぜ「全部日本時間」にしないのか。データベースの時刻列(timestamptz)も、イベントの順序比較も、
内部では「時間軸上の一点(インスタント)」として扱うのが自然だからです。一点同士の比較に
時間帯は不要で、表示や暦日付が必要な瞬間に初めて変換すれば十分。全員が手元の時間帯で
持つと、「同じ瞬間なのに文字列が違う」データが混ざり、比較のたびに変換ミスの可能性が
持ち上がります。LATCHの仕様書も「時刻はtimestamptz(JST運用)」と定めており、
「保存はUTCの一点、運用上の暦はJSTで切る」というこの設計と整合しています。

実際に偽時計で確認してみましょう(`backend/tests/unit/test_clock.py` に類似の試験があります)。

```python
from datetime import UTC, datetime, timedelta
from latch.core.clock import FakeClock, JST

fake = FakeClock(datetime(2026, 9, 27, 14, 59, 59, tzinfo=UTC))
fake.jst_date()          # → 2026-09-27(日本時間では 23:59:59)
fake.advance(timedelta(seconds=1))
fake.jst_date()          # → 2026-09-28(日本時間で 0時0分0秒を跨いだ!)
```

UTCの視点では1秒しか進んでいないのに、日本の暦日付は翌日に変わります。
日本時間の0時リセット処理は、この境界を正確にまたぐ必要があり、それを1秒のadvanceで
試験できるのがClockの価値です。

## 3.5 DI(依存性注入): 「作らせない、渡す」

第2章で `Depends(get_clock)` を通過しました。ここで、なぜあの面倒な仕組みを挟むのかを、
「ない世界」との比較で理解します。

まず、依存を**自分で作る**コードを考えます。

```python
async def health():
    clock = SystemClock()          # 関数の中で自分で時計を作ってしまう
    return {"status": "ok", "server_time": clock.now().isoformat()}
```

この書き方の何が悪いのか。この `health` の試験を書こうとすると、`server_time` は実時間由来に
なるので、「期待する値」を試験側で作れません。毎回違う値が返るからです。壊れてもいないのに
運が悪ければ失敗する、3.1の理由1がここで現実化します。

依存性注入(DI)は、この問題への対処として「**使う部品は自分で作らず、外から渡してもらう**」
というただのルールに整理できます。第2章で見たとおり、LATCHでは2段構えで実装されています。

1. 組み立てのときに `create_app(clock=...)` で受け取り、棚(`app.state.clock`)に置く
2. 使うときに `Depends(get_clock)` で棚から取り出して、関数の引数に届けてもらう

これにより、**本番では `create_app()` が `SystemClock` を置き、試験では `create_app(clock=FakeClock(...))`
が `FakeClock` を置く**。`health` の中身は1文字も変わりません。変えられるのは棚に置くものだけ。
この「経路が共通で、差し替え点が1つ」という性質が、テストを安定させます。

試験側の差し替え方法は2つ用意されています(`tests/unit/test_app_health.py` に両方の試験があります)。

```python
# 経路1: 組み立て時に渡す
app = create_app(clock=FakeClock(datetime(2020, 1, 1, tzinfo=UTC)))

# 経路2: FastAPIの差し替え機能を使う(DIの部分だけ後から交換)
app.dependency_overrides[get_clock] = lambda: other_clock
```

経路2は「`get_clock` が呼ばれたら、代わりにこの関数の結果を使え」とFastAPIに上書きする機能です。
M1以降で実装が進むと、組み立て時に渡せない場面(既に組み上がったアプリの一部だけ交換したい)が
出てくるため、両方の経路が試験で守られています。

## 3.6 pytestとテストの分類、そしてTDD

### テスト関数とフィクスチャ

pytestは、`test_` で始まる名前の関数を自動で集めて実行するツールです(第2章でも触れました)。
`assert` が成り立たなければその試験は赤になり、**どこで・何が・どう違ったか**を表示します。

```text
FAILED tests/unit/test_app_health.py::test_health_returns_ok_and_clock_time
AssertionError: assert '2026-09-27T12:00:00+00:00' == '2026-09-27T11:00:00+00:00'
```

失敗メッセージは「左が実測・右が期待」のような対応で読めます。この表示を読む練習が、
Lab 2の主題です。

`@pytest.fixture` の付いた準備関数がテストに材料を渡す仕組みも第2章で見ました。
`tests/conftest.py` は「そのディレクトリのテスト全体で共有するフィクスチャを置く特別な名前の
ファイル」です。`fake_clock` と `app` と `client` の3点セットが定義されており、
各テストは必要なものを引数に書くだけで受け取れます。

### unit と integration

LATCHのテストは2層に分かれています。

- **unit(単体)**: 部品を単独で試す。外部プロセス(DB・Redis・サーバー)を一切使わない。
  302件・約3秒。`make test`
- **integration(結合)**: 実DB・実Redis・実apiプロセスでの組み合わせを試す。
  実データベースの表が本当にできるか、実Redisで失効が働くか。72件。`make test-ci`

層を分ける理由は速さと原因の切り分けです。unitが2秒なら、コミットのたび・コードを1行変えるたびに
全部回せます。integrationは遅いので、まとまったタイミングで回す。unitが緑でintegrationが赤なら、
「部品は合っているが、繋ぎ目が悪い」と見当が付けられます。

### TDD: 赤を先に見る

TDD(テスト駆動開発)は「**期待(テスト)を先に書き、意図的に赤を確認してから、実装を書いて緑にする**」
作法です。LATCHの実装はすべてこの順番で行われました(計画書の各タスクに「テスト→実装の順」
と書かれています)。

なぜ赤をわざわざ見るのか。テストを先に書いても一発で緑だった場合、**そのテストは何も
証明していない**可能性があります(書き方が悪くて常に合格する、間違ったものを試している)。
一度赤を見てから緑にすることで、「このテストは本当に失敗を検出できる」という保証が付きます。
2章のLab 2で「テストを壊して赤になるのを観察する」のは、これと同じ保証を自分の手で得る作業です。

## 3.7 番人テスト: 規律を機械で守る

最後に、このプロジェクト独特の工夫を紹介します。「時刻はClock経由」という規律は、
口約束やドリル(注意書き)ではなく、**テストで強制**されています。

`backend/tests/unit/test_arch_no_direct_time.py` は、製品コード(`backend/src/latch/`)全体を
機械的に走査し、`datetime.now`・`time.time` などの直接参照を見つけたら失敗する試験です。
例外は `core/clock.py` だけ。つまり誰かが規律を破るコードを書いた瞬間、`make test` が赤くなり、
**コミットする前に機械が止めてくれます**。

「コーディング規約」というと文書に書いて人間が守るものを想像しがちですが、守れるものは
テストとして書く方が確実です。LATCHではこの「規律=テスト」の発想が繰り返し使われています
(ジオコーディングの「ネットワーク送信禁止」も同じ手法のarch testで守られています)。

正直な限界も書いておきます。この番人は**文字列(トークン)で探している**ため、
`from datetime import datetime as _dt` のような別名を付けると `_dt.now()` は検出をすり抜けます。
この限界は実装時のレビューで把握・記録済みです。番人は完璧ではないので、
「文化+番人」の二重構えで規律を守る、というのが実態です。

## 3.8 この章の再統合

- 時刻の扱いには「再現性・タイムゾーン・境界操作」という3つの難しさがあり、
  LATCHは「時刻の経路をClockに1本化し、中身を差し替え可能にする」ことで全部に答えた
- `Clock` は契約(ABC)、`SystemClock` は本番実装、`FakeClock` は操作できる偽実装。
  実時間に触れてよいのはシステムクロックの1行だけ
- DIは「作らせない、渡す」というだけのルール。差し替え点が1つにまとまることで、
  本番と試験が同じ経路を共有する
- テストはunit/integrationの2層。302件約3秒のunitが、壊して試せる開発の土台を作っている
- 規律は文書でなくテスト(番人)で守る。ただし番人にも限界があることは自覚しておく

次のLab 2では、この章で学んだすべてを「実際に壊して」確かめます。
