## 30.1 この章の題材: 「速い」を証明するには、測り方自体を設計する

前章(第29章)で、LATCHは自分の様子を数として数え続けるようになりました。
しかし「数を数える」と「速い/遅いを証明する」の間には、まだ溝があります。

試しに「このシステムは速いですか?」という問いに答えることを想像してください。
人によって答えは揃わないでしょう。「いつも0.1秒で返ってくるけど、たまに10秒
かかる」というシステムを、あなたは「速い」と呼びますか?約束がなければこの
質問には答えられませんし、約束があったとしても、**その約束どおりの条件で測った
という保証**がなければ、出した数は証拠になりません。

この「測り方への保証」を作るのが、M4 ws-6(2026-10-04マージ)の仕事でした。
先に結論を並べると、この単位で作られたものは5つです。

1. 測る値の形を確定する——性能5目標を「p95・p99」という分布の値で読む(30.2〜30.3)
2. 測りたい条件を作る——LLMの遅れを、乱数でなくハッシュで決定的に再現する
   遅延分布の注入(30.4)
3. 測りたい投げ方を作る——応答を待たずに決まった時刻で投げる注入器(30.5)
4. 遅さの場所を分けて見る——処理の各区間ごとのヒストグラム(30.6)
5. 規模が増えたときの答えを出す——母集合10万件での総当たり検出(30.7)

どれも「測る」だけで聞くと地味です。けれども順番に読むと、「測定」という
一見単純な仕事の中に、設計判断がいくつも埋まっていることが分かります。
この章の残りで、その判断を一つずつ読みます。

## 30.2 性能の約束は絶対値で書かれている

docs 10(test-env-nfr)の第4.1節は、このシステムの速さについて
5つの約束を定めています。読み上げますと:

| 約束 | 目標 |
|---|---|
| ① Intentの保存 | p95が500ミリ秒以内 |
| ② 構造化プレビュー(Parser) | p95が3秒以内・p99が8秒以内 |
| ③ 候補の検索(Vector Retrieval) | p95が1秒以内 |
| ④ 初期のLATCH判定(Event発火から通知の記録まで) | p95が10秒以内 |
| ⑤ 通知 | 判定確定から5秒以内 |

見慣れない形の数が出てきました。この「p95」こそが、この章の最初の
学びどころです。30.3で丁寧に読みます。

もう一つ大事なのは、これらの約束が**負荷条件下で**判定されるということです。
誰も使っていない静かなシステムで0.1秒なのは簡単です。docs 10の負荷条件は、
「Intent保存APIへの50リクエスト/秒の定常流入+Match Event 100件/秒の
バースト」です。この条件の中で上の5つの数を出すから、試験になる。
そして約束の対象になっている処理のうち、AI(LLM)を呼ぶ2つ(ParserとJev)には、
**遅れを注入する条件**も決められています。Parserの呼び出しには「p50 1秒・
p95 2.5秒」、Jevの呼び出しには「p50 2秒・p95 5秒」の遅れを再現する——
これは「このリポジトリの初期実装が既定で呼ぶ第一候補の応答速度」でなく、
**フォールバック先(第13章の切り替え先)の、遅い場合の上限を想定した条件**
です。遅い世界で5つの約束が保たれることを示したいので、遅い方を用意します。

もう一つ、言葉を確定しておきます。この試験の合否判定は**絶対値合格**と
呼ばれます。前に測った値と比べて速いか(相対比較)ではなく、**約束した値と
直接比べて**合格/不合格を決める方式です。比較相手が「約束」なら、測定値に
交渉の余地はありません。

なお、正式な合格判定はゲート(G4)で人間が行うことになっています。この章
(と報告書)が扱うのは「約束の条件を用意して、値を測り、数として記録する」まで。
判定と証拠の分離も、このリポジトリの規律のひとつです。

## 30.3 平均は嘘をつく: 分位点という値の読み方

### p95とは、何番目のことか

「このAPIの応答時間は平均0.8秒です」という報告の問題を、具体例で見ます。
100件のリクエストのうち90件が0.1秒で終わり、10件が10秒かかったとします。
平均は(90×0.1 + 10×10)÷100 = **約1.1秒**。数字だけ見れば「1秒台の
システム」です。しかし実際にこのシステムを使った100人のうち、10人は
**10秒待たされました**。「平均1秒」は、この10人の体験をまったく表していません。

平均が隠してしまうのは**分布の形**です。そこで使うのが**分位点**(ぶんいてん)
という値です。応答時間を速い順に並べて、「この順位のところでは何秒か」を
読み取る値です。p95は「95パーセント点」と読み、**100件を速い順に並べたときの
95番目の応答時間**のことです。「100回中95回は、この時間で終わっている」と
いう意味です。先の例では、95番目はもう「10秒」グループにいるので、
p95=10秒。「たまに10秒」が数として出てきます。p99なら99番目(さらに
遅い方の1%まで見る)、p50は50番目——**p50は「中央値」のことです**。
平均でなく中央値が使われるのは、上と同じ理由(極端に遅い数件が全体の
数を引っ張るのを防ぐ)です。

順位の数え方には複数の流儀がありますが、このリポジトリでは**nearest-rank**
(ニアレストランク)という定義を使います。「95パーセント点は、全体をN件とした
ときの、大きい方に切り上げたceil(0.95N)番目」という、シンプルな区切り方です。
100件なら95番目、6090件なら5736番目。複雑な補間を採らない利点は、
「p95=この値」と言ったとき、**その値は実在する観測のどれか**です。
「存在しない値の間の推定」にしない、という選択です。

### 分布を「区間ごとの回数」で持つ: bucketの再訪

第29章で、ヒストグラムは「観測した値をあらかじめ決めた区間に振り分けて
数える」という話を読みました。ここでその区間——**bucket**(バケツ)——を、
もう一段深く読みます。ws-6で追加された定義がこれです。

```python
# 層別・E2Eの共通bucket(M4 ws-6)。10 §4.1注入値(p50 1秒/2秒・p95 2.5秒/5秒)と
# 予算境界(Embedding 2秒・Retrieval 1秒・L5+通知 2秒)とE2E目標10秒を含む
LATENCY_BUCKETS = (0.1, 0.25, 0.5, 1.0, 2.0, 2.5, 5.0, 10.0)
```

(`backend/src/latch/obs/metrics.py` 44〜46行)

この1行に、bucketの境界選びの考え方が詰まっています。境界の数字
(0.1・0.25・0.5・1.0・2.0・2.5・5.0・10.0)は、でたらめな目盛りではありません。

- 注入する遅延の値(p95 2.5秒・p95 5秒・p50 2秒)が境界に含まれている
- 層ごとの予算の境界(Embedding 2秒・Retrieval 1秒・L5+通知 2秒)が含まれている
- 初期判定E2Eの目標(10秒)が、最大の境界になっている

なぜ境界が大事なのか。ヒストグラムからp95を計算するとき(このプロジェクト
ではPrometheusの`histogram_quantile`という関数が計算します)、計算機は
**「95%の回数が乗った区間」を見つけて、その区間の中で値を補間します**。
区間の中の細かい位置は分からないので、「区間の幅と両端から線形に推定」する
しかない。だから、**正確に再現したい値が境界上にあるなら、推定はほぼ
その値どおりになる**。逆に、注入値(5秒)が区間の途中(たとえば3.7秒と
6.1秒の間)に埋もれていたら、推定値は注入値からずれ込む。**境界は、
読みたい位置に目盛りを打つ**ことだ、と読めます。

### 「10.0秒」に張り付いた実測: 解像度の上限を読む

bucketの理解を試す実測があります。perf試験(30.8節)の証拠YAMLの測定値です。

```yaml
measurements:
  save_p95_s: 0.05892857142857133
  parse_p95_s: 2.737762237762238
  retrieval_p95_s: 0.6249999999999998
  embedding_p95_s: 10.0
  proposal_p95_s: 10.0
  jev_p95_s: 5.483378378378375
  e2e_p95_create_s: 10.0
  notify_p95_s: 4.922996048513589
```

(`docs/testassets/results/ws6-load-20261004-123006.yaml` 21〜33行の抜粋)

他の値は細かい桁まで揺れているのに、`embedding_p95_s`・`proposal_p95_s`・
`e2e_p95_create_s`の3つだけが、ぴったり10.0です。**これは偶然ではありません。
bucketの上限(10.0秒)を超えた観測は、すべて「10秒以上」という最後の1つの
区間に落ちる**からです。つまりこの10.0という値が意味するのは「**10秒以上
だった観測のうち、95パーセント点が上限より先にある**」という、解像度の
切れ目に張り付いた状態です。

なぜ上限より先の観測が多発したのかには事情があります(30.8節で読むD-16縮退——
予算の番人が作動して、処理が繰越しの待ちに入った、という"仕様どおりの動き"が
長い区間を生みました)。ここで学びたいのは読み方の規律です。

1. p95がbucket上限と**ぴったり等しい**とき、その値は「上限ちょうど」ではなく
   「上限以上」を意味する(解像度上限に達している)
2. 「10.0秒よりどれくらい先か」を知りたければ、bucketにさらに遠い境界を
   足す必要がある(要件が変わればbucketを拡張する判断はあり得る。実際、
   G4時の確認事項として記録されています)
3. 逆に、上限未満の値(5.48秒など)は、その位置の目盛り(5.0と10.0の間)の
   補間推定として信頼できる——ただし「補間推定」であり、逐次記録ではない

測定値は「出てきた数字をそのまま読む」のでなく、**その数字がどの器で
採られたのか(解像度はどこまでか)とセットで読む**。この章全体を通じて
いちばん大事な読み方です。

## 30.4 測りたい分布を決定的に作る: ハッシュで遅延を振り分ける

30.2で「Parserにはp50 1秒/p95 2.5秒、Jevにはp50 2秒/p95 5秒の遅れを
注入する」と読みました。ここには即座に疑問が湧きます。**p50とp95という2つの
値を、どうやって「同時に」再現するのか**。

見通しをよくするため、悪い案から見ます。

- **全員にp50値を注入する**: 分布が1点に潰れるので、観測されるp95も
  p50値のまま。約束の「p95」を測れない
- **全員にp95値を注入する**: 今度は全観測が最悪値になる。これは実態より
  遅い世界で、過大な注入になる(「負荷条件下で実運用を模擬」という条件に反する)
- **乱数で50%と5%に振る**: 分布は作れる。しかし**実行のたびに違う結果に
  なる**。docs 10第1節は「スタブで決定的にする」ことを規定しています
  (第26章の決定的生成器と同じ価値観です)。乱数では、失敗した試験を
  同じ条件で再現できない

採用されたのは、**入力から決定的に区間を選ぶ**方式です。`llm/stub.py`の
実装を読みます。

```python
# 決定的ハッシュ割付のレンジ境界(256スロット・ws-6 design §2.2案A)。
# 0〜127→p50値(50.0%)・128〜239→中間値(43.75%)・240〜255→p95値(6.25%)。
# 下位2グループの累積93.75%<95%のため・nearest-rank定義の95%ランク
# (ceil(0.95N)番目の標本)は常にp95値グループに含まれる
_DELAY_SPLIT_P50 = 128
_DELAY_SPLIT_MID = 240


def distributed_delay_ms(p50_ms: int, p95_ms: int, key: str) -> int:
    """決定的ハッシュ割付の遅延ms(10 §4.1のp50/p95分布再現・M4 ws-6)。

    sha256(key)の先頭バイトのレンジで50%/43.75%/6.25%へ振る。中間値は
    線形補間。同一key→同一遅延(10 §1「スタブで決定的にする」)。
    理論分布としてnearest-rankの50分位点=p50値・95分位点=p95値。
    機械検証はtests/unit/llm/test_llm_stub_latency.py(固定key集合で計画時
    実計算済み: keys=[str(i) for i in range(10000)]・p50=1000/p95=2500で
    counts={1000: 5058, 1750: 4329, 2500: 613}・p50ランク=1000・p95ランク=2500)。
    """
    slot = hashlib.sha256(key.encode()).digest()[0]
    if slot < _DELAY_SPLIT_P50:
        return p50_ms
    if slot < _DELAY_SPLIT_MID:
        return p50_ms + (p95_ms - p50_ms) // 2
    return p95_ms
```

(`backend/src/latch/llm/stub.py` 73〜96行)

仕組みを分解します。呼び出しのたびに渡される`key`(正規化テキストのような、
その呼び出しに固有の入力)をSHA-256というハッシュ関数にかけ、その先頭
1バイト(0〜255の256段階)を取り出します。この値が:

- 0〜127なら(全体の50%)→ p50値の遅延
- 128〜239なら(43.75%)→ 中間値(p50とp95のちょうど中間)
- 240〜255なら(6.25%)→ p95値の遅延

ハッシュは同じ入力から同じ値を必ず出すので、**同じ入力に対する遅延は
常に同じ**。乱数を一切使っていないのに、観測の集まりには50/43.75/6.25の
割合で分布が生まれます。「分布の形」は持たせて、「再現性」も壊さない。
両立の工夫そのものです。

### なぜ中間のグループが必要で、なぜ94%で切るのか

2つの細かい設計に、ページを割く価値があります。

1つ目、**中間のグループ**(線形補間値)は、p50とp95の間の分布に「間」を
与えるためです。2点だけ(50%が2秒・6.25%が5秒)だと、その間の遅延
(3秒・4秒)が一切観測されず、bucketの2.5秒・5.0秒の区間に乗る回数が
減ります。中間値(3.5秒)を43.75%に配ると、分布が区間を埋めて、
ヒストグラムの推定がなめらかになります。

2つ目が鋭い点です。**下位の2グループ(p50値+中間値)の合計は93.75%で、
95%を超えられない**。この数字が切れています。考え直してみましょう。
もし下位を45%・中間を50%に配ってp95値を5%にしたら、どうなるでしょう。
nearest-rankの95番目は「95%ラインに乗る標本」です。下位2グループの合計が
95%に達してしまう配置だと、95番目の標本が**中間値のグループ**に紛れ込み、
観測されるp95は「5秒」でなく「中間値」になってしまいます。**観測したい
分位点の位置が、グループの切り方そのものに依存する**——そこで「下位の
合計は94%未満(=93.75%)に抑え、95番目を必ずp95値のグループに落とす」
という割付が選ばれました。design §2.2には「45%/5%の旧案は採らない」と、
この理由つきで明記されています。

実計算の結果もdocstringに刻まれています。1万件のkeyに対して
{1000ms: 5058件・1750ms: 4329件・2500ms: 613件}となり、
50番目の値(p50ランク)=1000ms・95番目の値(p95ランク)=2500ms。
**「理論の割付」と「実際の分位点」が一致することを、機械で検証した**値が
そのまま書いてあります。unit試験(`tests/unit/llm/test_llm_stub_latency.py`)は
この集合を固定して、誰かが割付を変えたら赤になるよう守られています。

なお、embedding系統の呼び出しには分布注入を作っていません。docs 10の
負荷条件にembeddingの注入規定がないためで、「規定のないものを勝手に
作り込まない」(YAGNI・第25章で読んだ判断)の適用です。既存の固定値注入
(環境変数でミリ秒を指定)は無変更のまま残り、分布の設定値が0のときは
従来どおり固定値・両方0なら遅延なし、と**優先順位**(分布>固定ms)で
切り替わります。既存の試験が全部無傷で動くのはこのためです。

## 30.5 投げる側にも設計がある: 応答を待たない注入器

負荷をかける注入器が持つべき性質は何でしょう。「毎秒50回リクエストを
投げる」——この一言の中に、大きな分かれ道があります。

自然な実装は「投げる→返事を待つ→投げる→…」です。しかしこの方式には、
**測定を歪める仕組みが内蔵されています**。サーバーが遅くなると、返事が
遅くなり、その分だけ次のリクエストが遅れて出ていく。つまり**一番負荷を
かけるべきとき(サーバーが遅いとき)に、投げる間隔が伸びて負荷が下がる**。
遅い応答が次の投入を遅らせることで、「本来なら観測できたはずの、最も遅い
応答」のサンプルが欠落していく。この現象には名前がついていて、
**coordinated omission**(コーディネーテッド・オミッション)と呼ばれます。
測定値が実際より甘く(よく見えて)出てしまう、古典的な落とし穴です。

採用されたのは、この逆の方式です。**予定時刻の表を先に作り、返事は待たずに
予定時刻どおり投げ続ける**方式で、これは「オープンモデル」と呼ばれます
(対して返事を待つ方式は「クローズドモデル」と呼ばれます)。実装を
`loadgen/schedule.py`で読みます。

```python
def constant_rate_plan(*, rate_per_sec: float, count: int, kind: str) -> list[SendPlan]:
    """固定到着率の予定列(0, 1/rate, 2/rate, ...秒・決定的)。"""
    interval = 1.0 / rate_per_sec
    return [SendPlan(at=i * interval, kind=kind, seq=i) for i in range(count)]
```

(`backend/src/latch/loadgen/schedule.py` 27〜30行)

送出予定を「開始時刻から何秒後か」の数列として先に作る(`constant_rate_plan`:
50rpsなら0秒・0.02秒・0.04秒…)。実行側はこの予定時刻まで待って、
リクエストを投げるだけです。応答の完了は予定時刻に影響しません。

```python
async def run_open_model(
    plans: list[SendPlan],
    *,
    sender,
    clock: Clock,
) -> RunStats:
    """オープンモデル実行(予定時刻まで待つ・応答は送出間隔に含めない)。

    sender(plan)は応答時間を内部で測るためawaitするが・その完了は次の
    送出予定を遅らせない(create_taskで投げっぱなし・送出ループは予定時刻
    だけを見る)。例外は集計して続行(注入器の失敗が試験を止めない)。
    戻り値の統計は全応答完了後に返す(収束待ち=wait_settledは別・Task 8)。
    """
```

(`backend/src/latch/loadgen/schedule.py` 59〜71行)

「sender(plan)はawaitするが・その完了は次の送出予定を遅らせない」という
記述が核心です。投げたリクエストは`asyncio.create_task`で別の処理として
走り出し、送出ループ自体は「次の予定時刻」だけを見て進みます。**サーバーが
どんなに遅れようが、投入の間隔は守られる**。サーバーが遅いときこそ、
予定どおりの負荷で押し続けるから、本来観測すべき遅い応答がサンプルとして
残ります。これがcoordinated omissionへの原理的な回避です。

時刻の参照が`clock`(Clock)経由なのも第3章以来の規律どおりで、予定列は
決定的に生成されます。「待ち」自体は実時間の`asyncio.sleep`ですから、
この注入器は**実時間で動く測定装置**として正しい形をしています。

もう一つ、読み分けを確定しておきます。注入器はクライアント側でも
応答時間を測ります(RunStatsの`client_p95_ms`)。perf本命の実測では
1787.5ミリ秒でした。**しかし測定の主系統はここではありません**。クライアント
側の値には、ネットワーク往復・クライアント自身の処理(トークンの準備など)が
混ざります。「決められたレートで投げる」という注入器の本業に対して、
クライアント側の値は**参考値**と位置づけられ、5目標の判定はサーバー側の
Prometheusヒストグラムで行います。大事なのは**「どの値で約束と照合するか」
を先に決め、それ以外は参考に落とす**という数の読み分けです。

補足として、この注入器が既存ライブラリでなく自作された理由にも触れておきます。
負荷試験の定番道具(k6・Locust)は設計メモで一次確認のうえ不採用です。
理由は主に2つ。1つは、母集合の作成・鍵・トークン発行といった試験の
周辺処理が既存のPython資産と密接に結びついており、別言語(JS)や別の
依存(gcpライブラリ)を持ち込むと2言語化・依存追加のコストが採用の
メリットを上回ること。もう1つは、既定の道具の「応答を待つ」型の
ペーシングには、上で見たオープンモデルの特性がない(または間接的)
こと。**「測る道具」も、道具が作る測定値の質から選ぶ**という判断です。

## 30.6 「どこが遅いか」を分けて見る: 層別予算のヒストグラム

初期判定E2Eの目標が10秒を超えたとき、最初にやるべきことは何でしょう。
「E2Eが遅い」という1つの数では、対処のしかたが決まりません。Embeddingが
遅いのか、検索が遅いのか、AI判定(Jev)が遅いのか、提案確定と通知が遅いのか——
**区間を分けて初めて、どこに手を入れるかが決まる**。

docs 12第7節はこの考えを「層別予算」として定めています。Embeddingは2秒まで・
Layer 1〜3の検索は1秒まで・Jevは5秒まで・Layer 5+通知は2秒まで、という
**区間ごとの上限**です。そして設計の確定値として「どの区間が予算を超えたかを
特定できること」が求められていました。

第29章までのメトリクスは、これに足りていませんでした。Jevの区間だけは
観測済み(`jev_latency_seconds`)。HTTP全体もありました。しかしEmbeddingの
区間・検索の区間・提案確定〜通知の区間・そして「Event発火から通知の記録まで」
の全体(E2E)は観測点がなかった。ws-6で足されたのが3本のヒストグラムです。

| 新しいメトリクス | 観測する区間 | ラベル |
|---|---|---|
| `pipeline_layer_seconds` | embedding / retrieval / proposal の各区間 | layer |
| `latch_initial_e2e_seconds` | Event発火(active化の保存コミット)から通知の記録まで | route |
| `notification_latency_seconds` | 提案確定からpush送信の記録まで | なし |

(`backend/src/latch/obs/metrics.py` 188〜212行。名簿は15個から19個に増えました。
第29章29.3の名簿と見比べてください)

これで層別予算の4区間が、3本の新メトリクス+既存の`jev_latency_seconds`で
全部観測できるようになりました。試験側も、第29章で読んだ**名簿の守り**
(メトリクスの宣言を機械的に列挙して許可リストと突き合わせる)をそのまま
引き継いでおり、意図しない数の追加は赤で止まります。

### E2Eの観測は「誰を」測るかを決めるのが難しい

3本のうち、実装に一番判断があったのはE2Eです。単純に「すべての判定の
Event発火〜通知記録」を観測すると、値が混ざりすぎて読めません。

- **経路の混ざり**: 新規作成(active作成)で発火したEventと、下書きからの
  active化で発火したEventでは、処理の中身が違う(後者はdraft→activeの
  切り替えが挟まる)
- **再評価の混ざり**: 初回の判定でなく、更新や30分バケット(第14章)による
  再評価が紛れると、「初めて見たとき、どれで提案に至るか」という目標④の
  意味が崩れる

そこで観測対象は「**初回投入Event(created種=active作成とdraft→active化を
含む)経由の初回提案**」に絞られました。再評価は対象外。さらに経路ごとの
分布を分けて記録するため、ヒストグラムに`route`ラベル(create/activate)が
付いています。

起点の時刻にも注意が必要です。active作成なら`intents.created_at`
(=保存コミット時刻)。しかしdraft→active化の経路で「draftの作成時刻」を
起点にしたら、**起草した人間の考えた時間がすべて測定値に混ざります**
(書き始めてからactiveにするまで2時間なら、2時間が「判定の遅さ」に
カウントされる)。だから起点は**active化の保存コミット時刻**です。
「測る値が何を含み、何を含まないか」を明示的に選ぶ——分位点の話と同じ
読み規律が、観測点の置き場所にも効いています。

## 30.7 10倍になっても遅くならないを数で示す: 総当たり検出

性能5目標が「速さの約束」だとしたら、総当たり検出は「**規模の約束**」です。
docs 10第4.2節の問いはこうです。**Active Intentの数が1万→5万→10万と
増えても、処理件数とレイテンシは急増しないか**。サービスが成長して
母集団が10倍になったとき、検索や判定が10倍遅くなるようでは、成長が
破綻します。

### なぜ上位50件で打ち切りなのかが、ここで利く

答えの核心は、第11章で読んだ**K_v=50**(Vector Retrievalの上位50件で
打ち切る)にあります。検索が「全件を精査する」方式なら、母集合が10倍に
なれば精査も10倍になる。しかしLATCHの検索は「意味の近い順に50件だけ
取る」方式です。**取ってくる件数が母集合の大きさと無関係に固定**されている
ため、「1回の検索の重さ」が母集合に比例して増えない構造を最初から
備えています。総当たり検出は、この構造上の約束が**実際の数値として**
保たれることを確認する試験です。

合格の機械判定は「**Vector Retrievalの件数がK_v=50以内で、Intent数と
無関係に安定**」です。証拠YAMLでは、3段階(1万・5万・10万)すべてで
`vector_le_50_ok: true`——50を超えた観測はゼロ——が出ています。

### 母集合は「存在するだけ」にする: DB直接投入の理由

10万件の母集合をどう用意するか。API経由でIntentを10万件作る方式を
想像すると、2つの壁に当たります。

1. **レート制限**: 第7章で読んだとおり、1ユーザーのActive Intentは5件まで・
   作成は1日20件まで・APIは60リクエスト/分まで。これは「源流を守る」
   ための正規の制限で、試験のために外すのは本末転倒です
2. **観測の汚染**: 10万件の作成処理がパイプラインをフル稼働させ、
   **測りたいもの(注入100件への応答)**の観測区間に投入処理自体が
   混ざってしまいます。判定予算(D-16)を投入分で消費する問題もあります

そこで母集合は、**Eventを発行せずDBに直接書き込む**方式が採用されました
(`loadgen/massload.py`)。決定的生成器(第26章)のYAMLを読み、
usersとintentsをまとめてINSERTし、embeddingの列に決定的なベクトル
(`_stub_vector`)を直書きする。Layer 1の検索条件(status='active'・
expires_at未来・embedding非null)を満たす行を作るので、**検索対象として
「存在する」だけのIntent**ができます。正規のEvent経路を通るのは、
観測対象の注入100件だけ。**測るものを母集合から物理的に分離する**のが
この方式の要点です。

投入の速度も出ています: 1万件=0.2秒・10万件=2.0秒(決定的生成器の
万件対応を含む実測)。10万件が2秒というのは、pgvectorの索引の構築を
含めても軽い処理だという示唆として読んでおくと、母集合の増減が
「投入の重さ」でなく「検索の振る舞い」の問題であることが分かります。

### 段階比較表を読む: 「増えない」の見え方と、見分けの難しさ

実測の段階比較はこう出ています(報告書§4・窓30分)。

| 指標 | 1万 | 5万 | 10万 |
|---|---|---|---|
| Retrieval p95 | 0.8812秒 | 0.9292秒 | 0.5125秒 |
| Vector件数 ≤50の機械判定 | true | true | true |
| Jev実行回数の増分(30分合計) | 1124.37 | 1868.57 | 2673.28 |

読みどころは2つあります。

1つ目は明快な方。**Retrieval p95は増幅していません**。母集合が10倍に
なっても、検索のp95はむしろ下がっている(0.88→0.51秒)。K_v=50固定の
構造が、数として出ています。

2つ目は、ここからが実測の難しさです。**Jev実行回数の増分は増えています**
(1124→2687、10倍段階で2.38倍)。これは「遅くならない」約束に反するので
しょうか。実はこの数には、**母集合に比例した背景流量**が乗っています。
母集合のIntentは、ただ存在するだけのものでもありません。30分ごとの
バケット再評価(第14章)の対象にもなります。母集合が10倍なら、**何も注入しなくても**
定期再評価が10倍発生する。だから30分窓の合計には、注入100件への応答と
は別に**背景の増加**が乗っています。報告書はこの区別を明示して、
「注入への応答の急増と背景流量の寄与を分けた判定はG4の人間側」と記録して
います。さらに「急増しない」の量的な線(何倍まで許すか)はdocsに規定が
ないため、**コード側で勝手に線を引かず**、証拠の形式(機械判定+段階
比較表+増幅率の参考値)を固定して、線の引き方ごと人間の判定に残すという
規律をとっています。docsが線を引いていないなら、実装側も線を引かない——
測定の世界でも同じ約束が生きています。

## 30.8 測定は環境と運用の産物でもある

ここまでで「値の形」「条件の作り方」「観測の分離」を見ました。残る第4の
設計面が、**測る環境**です。2つの話をします。

### 同じマシンの隣人が数を汚す: ci一時停止運用

測定中に同じホスト(あなたのPC)でci環境(db・api・worker)が動いていると、
CPUやディスクの取り合いが起きます。これはp95のような**上限に近い値を
測る試験には致命的**です。ノイズは公平に散らばってくれません。遅い側に
だけ出ます。
そこで手順として**ci一時停止運用**が定められました: `make down`(データは
保持)→ load環境で試験 → `make load-down` → `make up`(ci復帰)。性能試験の
間だけ、マシンを試験に貸し切る。なおこの停止/復帰をMakefileのターゲットに
組み込まない判断も記録されています(運用の判断を含む操作は、隠れて動く
自動化に入れない)。

### 1回で済まなかったperf: 4回の実行が暴いたもの

perf試験は、実は1回では済みませんでした。**4回の実行の記録**は、報告書の
§9.2に正直に残されています。単に「途中で失敗した」という記録ではありません。
**1回ごとの失敗が、測定を歪めていた要因を1つずつ暴いた**のであり、
その列挙こそが測定の質の証拠です。表に整理します。

| 実行 | 起きたこと | 暴れた要因と対処 |
|---|---|---|
| 1回目 | 6090件のうち595件で接続失敗 | 注入器の接続プール上限(100本)が足りなかった→上限を500へ |
| 2回目 | 投入が約27リクエスト/秒で頭打ち | トークン交換の署名処理がAPI側で直列化。測定前にトークンをまとめて取得する**ウォームアップ**を追加 |
| 3回目 | 投入はほぼ成功、**提案が0件** | load環境にstubの判定値設定(noul=0.90等)が漏れていて、既定値ではスコアが閾値に届かなかった→composeに設定を追加 |
| 4回目 | 6090件全成功・error=0(本命) | (測定後の解析で、D-16の日次上限が発動し評価が繰越しへ縮退したことが判明) |

読みどころが3つあります。

1つ目は、**3回目の「提案0件」は遅さの問題でなく条件の漏れだった**点です。
ここで数が出ていたら、その値は「遅い世界の測定値」ではなく「そもそも
提案が生まれない世界の値」でした。**測定値の前に「測っている世界は
約束の世界と同じか」の確認が要る**——3回目の失敗が教えるのはこれです。

2つ目は、**2回目の壁(約27リクエスト/秒)が「APIの実特性」として記録された**
点です。RSA署名(第4章の認証で出てきた鍵の計算)がAPI側の処理を直列化
するための上限で、これは「足りなかったから直した」で終わらず、
**認証スループットの実特性**として確認事項に残されています。
測定の副産物は、無駄にならない。

3つ目は、**4回目にも"想定外"が乗っていた**点です。D-16(第12章で読んだ、
Jev回数の日次上限30000の番人)が**実際に発動**し、上限に達したあとの
評価は繰越し(後日実施)に縮退しました。これは**仕様どおりの動き**です。
番人として働いた点は成功体験です。しかし波紋は続きました。
縮退した評価が30分バケットの再評価として回り続けるため、**「処理が
収束した」の判定(pending=0の安定)が成立せず**、2400秒待っても
収束しない。そこで「収束を待たずに採取する」という読み替えを明示して
採取し、その状況はG4の確認事項に記録されました。**測定の終わり方
(いつ・どんな状態で採取するか)も、測定の設計の一部**です。

第12章12.8で「実際の30,000回を試験で回すのは重いので、Storeを差し替えた
初期値から境界を検査する」と読んだことを覚えていますか。この単位で、
**本物の30,000回が実際に発動しました**。負荷試験は、普段は差し替えで
済ませている番人の実力試験でもあったわけです。

もう1つだけ、運用の記録を足します。総当たりの初回実行では、シェルの
作業ディレクトリが違って全ステップが失敗していたのに、**結果をパイプで
つなぐ(`| tail`など)書き方のせいで「終了コード=失敗」が隠れ、
成功と誤認した**事故が起きています(その後、データを全リセットして
3段階をやり直しました)。対処は**検証チェーンからパイプを排除する**こと。
「失敗が見えない仕組み」は、測定の信頼性にとってプール上限と同レベルの
歪み要因です。報告書がこの事故を正直に書き残しているのは、第29章で
読んだ「近似を告白する」文化の運用版です。

## 30.9 この章の再統合

「速い」を証明する仕事は、4つの層の設計判断として読めました。

1. **値の形**: 約束はp95・p99で書く。分布の読み方には器(bucket)が伴い、
   器の解像度の限界(張り付き)とセットで数を読む
2. **条件の作り方**: 遅延の分布はハッシュで決定的に作る(再現性と分布の
   両立)。負荷は応答を待たず投げ続ける(オープンモデル)——さもないと
   coordinated omissionが遅さを隠す
3. **観測の分離**: 層別予算の区間ごとにヒストグラムを置き、E2Eは「誰を
   測るか」を絞り込んで初めて意味のある数になる
4. **環境と運用**: マシンを貸し切る(ci一時停止)・条件の漏れを疑う(3回目)・
   収束の定義を含めて採取の設計をする(4回目)

そして総当たり検出が示したのは、「10倍の母集合でも検索が遅くならない」が
**構造(K_v=50)の約束**として最初から備わっており、その約束が実測で
保たれる——ただし背景流量との見分けという判定の難しさを含めて、という
実態です。正式な合格判定がG4の人間側にあるのは、測定器と判定者の
分離です。数は「読まれる」ために作る。この単位の全ての設計は、
この一文に向かって並んでいました。

## 30.11 確認問題

1. 90件が0.1秒・10件が10秒のシステムの平均とp95を計算してください。
   どちらが「ユーザーの体験」をよく表しますか。その理由を、分布という言葉で
   書いてみてください
2. `embedding_p95_s: 10.0` という実測値が「ちょうど10秒」を意味しない理由を、
   bucketの構造を使って説明してください。さらに「10秒より先の値を知りたい
   ときの打ち手」を1つ挙げてください
3. 遅延の振り分けに乱数でなくSHA-256のハッシュを使う理由を、「失敗の再現」
   と「分布の再現」の2つの観点から説明してください
4. 下位2グループの合計が94%で切られているのはなぜか。95%ぴったりにしたら
   nearest-rankの95番目はどこに落ちるか、自分の言葉で説明してください
5. 「応答を待ってから次を投げる」注入器がなぜ遅さを隠すのか、coordinated
   omissionという名前とセットで、時系列で説明してください
6. perf試験が4回かかったことについて、「各回の失敗が暴いた歪み要因」を
   それぞれ1行で並べ、その記録が測定の信頼性にどう効いているか、
   自分のノート(`my-notes.md`)に書いてみてください
7. `python -m latch.loadgen --help` を一度実行してみてください。5つの
   サブコマンド(users・perf・massload・bruteforce・probe)のうち前の4つが
   この章のどの節に対応するか、対応表を自分で作ってみてください
   (probeは障害系の試験で使うため、対応する節はこの章にありません。
   第31章で読みます)

(解答例は用意していません。自分の言葉で答えられたら合格です。
詰まった節が、読み返すべき節です)
