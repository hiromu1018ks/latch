## 28.1 この章の題材: 代用の証明を、約束どおりの場所でやり直す

第24章で読んだG3ハーネスは、仕様書02 §4の約束(#13〜#23)を試験に翻訳したものでした。
ただし、あの章の最後で「環境の話」がありました。02 §4は約束の実施場所をstaging
(本番に近い検証環境)と指定しているのに、stagingの構築がまだだったため、ci環境で
**代用実施**してG3の証拠にした——という話です。

この章の題材は、その代用を約束どおりの場所でやり直す仕事です。M4 ws-3(2026-10-03
マージ)で、staging環境の上で機能試験27項目の該当分を自動で回す**ハーネス**が作られ
ました。34試験を約10分で一気通貫に実行し、試験IDつきの証拠YAMLを出力します。第24章
でci環境で実施した約束のうち、#13〜#23の11項目はこの単位でstaging再実行され、
「stagingの準備が整うまでの代用」が約束どおりの証明へ置き換わりました。

なお試験の設計そのもの(対応表・ないことの証明・対照)は第24章で読んだとおりです。
この章で読むのは、それを**本物に近い常設の世界**で動かすために何が必要だったかです。
答えを先に言うと、世界に入る材料を全部固定することでした。テストデータ(シード)・
AIの判定値・時計の3つです。順に読みます。

## 28.2 常設の世界には、別の緑がある

「unit1335+integration269の合計1604件が全部緑なのに、なぜもう1回回すのか」という疑問が最初に
立ちはだかります。答えは、2つの緑が証明しているものが違うからです。

第24章24.3で読んだとおり、ci環境のintegration試験は、テストプロセスの中で
エンジンを直接呼びます(in-process)。Workerプロセスは立てず、Layer 5の提案エンジンを
試験コードが自分で呼ぶ。この方式の強みはタイミングの揺らぎが入らないことでした。
裏を返すと、それは「知らせの運搬や、60秒周期で動く裏方を含めた**世界全体**」を
試しているのではない、ということでもあります。

stagingハーネスは反対側の立場に立っています。ハーネス自身はHTTPの窓口(nginx)を通じて
APIを叩き、DBを読むだけ。提案を作るのは、常設のworker2台が**自分たちの周期(60秒tick)**
で動く世界です。ハーネスは「材料を置いて、それを迎えに行く」側。この構成での緑は、
「本番と同じ形の世界に材料を置いたら、約束どおりの結果が外から観測できる」の意味です。
部品の正しさの積み上げと、約束全体がその世界で守られていること——両方を緑にして
はじめて、2 §4のマッピング表(約束と合格証拠の対応表)が完結します。

実際、フル実行を7回繰り返す過程で「単位の試験では誰も見ていなかった挙動」が複数
見つかりました(28.8)。これは結構な追い風で、常設の世界で回す価値の実例になっています。

## 28.3 ハーネスの本体: 既存の実行系に触れずに、世界ごと試す

ハーネスの置き場所から読みます。`backend/staging_tests/`という新ディレクトリで、
既存のテスト置き場 `backend/tests/` の**隣**に置かれました。あえてtests/の中では
ありません。理由は、pytestの設定(`pyproject.toml` の `testpaths=["tests"]`)にあります。
`testpaths` は、コマンドで試験ファイルを指定しなかったとき、pytestが**どこの中身を
名簿にするか**の約束です。staging_testsはこの範囲の外にあるため、
`make test`(unit)・`make test-ci`(unit+integration)はstaging_testsを**収集しません**。

```bash
make test        # unit 1335件だけ。staging_testsは含まれない
cd backend && uv run pytest staging_tests   # stagingの34試験だけ。明示的に指定する
```

この住み分けには実用的な理由が2つあります。第一に、staging試験は
「`make staging-reset`で作り直した、きれいな常設世界」を前提にします。きれいさを
前提とする試験が、いつでもどこでも回るべき資産(unit/integration)に混ざっていると、
混ざった瞬間に「いつ・どこで回ってよいか」の約束が壊れます。第二に、既存の実行系
(Makefile・設定)に1行も触れずに済むため、ci環境の挙動が変わる恐れがゼロです。
「試験を足したのに、既存の試験の振る舞いが変わった」——これは本単位が最も避けたい
事故で、置き場所の選択だけで防いでいます。

34試験は、S0〜S5の6本のファイルに旅路の順で並んでいます。S0は世界の前提確認
(コンテナ8個の健康・DB定義の版・地物データ・鍵の存在)です。ここで注目したいのが、
前提が崩れていたときの落ち方です。conftest.pyは、たとえばDBの版が違ったらこう落ちます
(`backend/staging_tests/conftest.py` 152〜161行):

```python
def ensure_env_prerequisites(db) -> None:  # noqa: ANN001
    """環境前提の名前つき失敗(設計§4-2 — 原因不明の連鎖失敗を防ぐ)。"""
    # API疎通はfixture apiの初期接続エラーで判るためここではDB/geo/鍵/headのみ
    ver = await db.fetchval("SELECT version_num FROM alembic_version")
    if ver != EXPECTED_HEAD:
        raise AssertionError(
            f"alembic headが{EXPECTED_HEAD}ではありません(実際={ver})。"
            "ws-5マージ後のmainからworktreeを作り・make staging-reset(または"
            "staging-migrate)を再実行してください"
        )
```

エラーの文面に、**原因と直し方**が書いてあります。前提の崩れを素通りさせると、後続の
34試験が原因不明の失敗で雪崩を打ちます。最初の1行で、名前をつけて落とす。第24章
24.6で「早く落ちる試験は切り分けがやすい」と読んだ原則の、環境版です。

## 28.4 決定性の3本柱: シード・判定値・数えられる量

常設の世界を試験に使う最大の難所は、**同じ材料・同じ手順なのに、結果が実行ごとに
揺れること**です。揺れる世界では、期待値が置けません。期待値が置けない試験に、合否は
言えません。この章の中心がここです。ws-3が世界を固定するために揃えた3本の柱を、
それぞれ読みます。

### 柱1: シード——入る材料を300件、バイト単位で固定する

材料には、第26章で作った決定的シード(m4-seed.yaml・Intent 300件+ユーザー100人)を
使います。同じ引数で生み直せば1バイトも違わない300件を、stagingの世界へ保存APIの
正規経路で投入します(直接DBへ書かない。世界の「正しい入り方」ごと試すためです)。
シードの側が決定的なので、「どのユーザーがどのIntentを持っているか」は実行ごとに
完全に同じになります。

### 柱2: 判定値の固定——既定のままでは、提案が1件も成立しない

2本目の柱が、この章で一番の作り込みです。順番に説明します。

LATCHでは、候補のペアをAI(Jev・第13章)が「お互いに参加したがるか」を数値で判定し、
その数値からlatch_scoreが計算されます(`latch_score = C × min(would_a, would_b)`。
第14章14.2)。そしてscoreが閾値0.60を超えたペアだけが、提案(proposal)になります。
試験の世界ではAIに本物のAPIを呼ばせないため、stub(応答を返すだけの代役・第5章)が
Jevを務めます。ところがstubの既定の応答値は0.5に固定してあります。0.5は閾値0.60に
届かない。つまり**stubのままで世界を動かすと、提案が1件も成立しない**。提案の存在を
前提とする検査(#13以降のほぼ全部)は、このままでは1つも実行できません。

解決は「判定値を固定する」です。実はこれは仕様書の文言そのもので、10 §3のstaging行は
「Jevスタブで双方向判定値を固定」と規定しています。ci環境のintegration試験はStubLLMを
直接組み立てるので値を自由に差し替えられました。ところがstagingのworkerプロセスは、
設定(settings)からgateway(LLM呼び出しの統一入口・第13章13.2)を組み立てます。
**設定ファイルからstubの応答値へ届く経路**が、この単位の新設部分です。

経路は3段です。第1段が設定項目の追加(`backend/src/latch/settings.py` 49〜50行):

```python
    llm_stub_jev_noul: float = 0.5
    llm_stub_jev_score: float = 2.0
```

第2段がgatewayの組み立て側(`backend/src/latch/llm/gateway.py` 311〜327行)。stubの
既定応答の**写し**に、設定値を書き込んでからStubLLMへ渡します:

```python
def _stub_jev_response(settings: Settings) -> dict:
    """settingsのstub判定値からDEFAULT_JEV_RESPONSE同一形状の応答を組む(ws-3)。

    10 §3表staging行「Jevスタブで双方向判定値を固定」のenv→settings→
    stub応答の経路。既定値(0.5/2.0)のときはDEFAULT_JEV_RESPONSEと値が
    完全一致する(ci/test-ci挙動不変・回帰ピン:
    tests/unit/test_llm_stub_response_settings.py)。
    """
    response = copy.deepcopy(DEFAULT_JEV_RESPONSE)
    for key in _NOUL_KEYS:
        response["answers"][key]["noul"] = settings.llm_stub_jev_noul
    for key in _SCORE_KEYS:
        response["answers"][key]["score"] = settings.llm_stub_jev_score
    return response
```

第3段がstaging環境の設定ファイル(`compose.staging.yaml`・YAMLアンカー1か所):

```yaml
  LATCH_LLM_STUB_JEV_NOUL: "0.90"
  LATCH_LLM_STUB_JEV_SCORE: "3.6"
```

noul(双方が相手を受け入れる確度)を0.90にすると、`latch_score = C × min(would_a,
would_b)` は0.90となり閾値0.60を余裕を持って超え、第14章のmatch_level=high
(0.90以上)の経路も通ります。3.6はscore軸(purpose/mood/timing/socialの4軸)の
生値で、/4で正規化すると0.9になる値です。

この変更で大事なのは、**ci環境が何も変わらないこと**です。settingsの既定値(0.5・2.0)
はstub.pyの定数と完全一致するように選んであり、ci環境はこの設定を書いていないので
stub応答は1ビットも変わりません。「既定値=現行定数」を機械が担保する試験
(回帰ピン・regression pin)がunit側に置かれていて、将来誰かが既定値を動かしたら
赤で知らせてくれます。製品コードに足すときは「既存の世界に影響しない既定値」を選び、
それをピンで固める——これは設定を足す変更全般に効く作法です。

### 柱3: 固定期望は「数えられる量」に置く

判定値を全ペア一律0.9にすると、新しい問題が現れます。Layer 1を通ったペアが**軒並み**
提案対象になるため、1人のユーザーが1日に受けられる提案の上限(D-08・日6件)を
超える候補が保留(candidate)になります。保留はJSTの0時跨ぎで解放される(第14章
14.5)ため、「いつ・どの候補が提案になるか」は処理の実行順序で揺れます。

ここでの判断は「揺れる場所に固定期待を置かない」でした。具体的には:

- 固定値で断言するのは、**事前に数えられる量**だけ。シード300件からLayer 1を通る
  ペア数(627)は、第26章の参照実装(reference_l1)で事前に計算できます。ハーネスは
  この数字とDBの実在行(699行)を突合します
- 提案の成否自体に依存する検査(#15〜#19など)は、ハーネスが自前で作る**専用シナリオ
  Intent**(そのユーザーの適合ペアが上限に届かないよう孤立配置)で行い、シード母集合の
  提案群に依存しない
- シード母集合側の保留は、むしろ材料として使います。保留が大量に発生することを
  事前集計(S0で84件と数える)し、「0時跨ぎで昇格する」試験(#8)の前提にする

「世界が揺れうる場所」を避けて通るより先に、揺れの正体を数える。そして数えられるもの
だけを期待にする。決定的な試験設計の実践形です。

## 28.5 時計の旅路: 期限を待つのでなく、迎えに行く

試験で一番長くかかるのは、時間が経つのを待つ部分です。回答期限は最長2時間・Intentの
期限は最長7日後。実時間で待っていたら、試験が終わりません。第18章のsweeperを
試したLab 6では、DBの期限を過去へ書き換えて代用しました。stagingハーネスでは、
第25章の共有時計 `ControlledClock` を使って、**世界全体の時計**を前進させます。

ハーネスはpytestの中から、clock_cliと同じコード経路でRedisの基準点に触れます。旅路は
3回の前進です:

| 前進 | 時刻(ISO明示) | 何が起きるのを迎えに行くか |
|---|---|---|
| 1 | 基準日の翌日0時05分 | JST 0時跨ぎ。日次上限のリセットジョブ+保留キューの再評価で、保留だった候補が提案へ昇格(#8) |
| 2 | 2日後の朝6時 | 部分YES(一部だけ回答済み)の提案が、回答期限の経過でexpiredに確定(#16) |
| 3 | 6日後の0時10分 | Intent期限切れバッチが、有効期限を過ぎたIntentを一括で閉じる(#16') |

旅路には3つの規律があります。第1に**前進のみ**。`set` は後退もできる(第25章25.4)
のに、ハーネスは後退を1度も使いません。後退すると「すでに閉じた行」と「まだ未来の
時刻」がDBの中で同居し、矛盾の説明が難しくなるからです。前にしか進めない規律で、
世界の状態を単調に保ちます。第2に**時刻はISOで明示**(例: `2026-10-05T00:05:00+09:00`)。
「実行日の翌日」のような相対表現をコードに書かないのは、タイムボム(将来の日付で
壊れる手順)を避けるこのプロジェクトの作法です。実際のコードでは
`backend/staging_tests/test_s1_candidate_items.py` 384〜387行:

```python
    # D1 00:05 JST へ前進(base_datetimeの翌日・ISO明示・後退は行わない)
    base = datetime.fromisoformat(state["meta_base"])
    target = (base + timedelta(days=1)).replace(hour=0, minute=5)
    clock.set(target)
```

(基準日そのものはシードYAMLのmetaから読んで、そこからの相対で計算しています。
固定するのは「時刻の取り方」であって、日付をファイルに焼かない点が工夫です。)

第3に**60秒tickは短縮しない**。裏方の周期を60秒から2秒に変えれば試験は速くなりますが、
それは「仕様が定めた周期で動くこと」の証拠を弱くします。tickをそのままにする代わりに、
ハーネスは**条件ポーリング**(条件が満たされるまで間隔をあけて調べ直す待ち方)で
待ちます(`backend/staging_tests/helpers_wait.py` の `wait_until`。上限はtickの2〜3倍の
120〜180秒で、切れたら「何を待っていたか」入りのメッセージで落ちます)。速さと証拠の
強さを交換しない判断です。試験全体で10分かかるのは、ほぼこの待ち時間の合計です。

旅路の最後の工夫は、**大きな前進はシナリオの末尾に置く**こと。シードのIntentは
基準日から1〜5日後の世界に置いてあるので、早く6日先へ進めると材料が期限切れで
消えます。時刻の旅路と材料の寿命を同じ表で管理する——常設世界の試験では、
「いつ・どの材料が有効か」も設計の一部です。

## 28.6 証拠YAML: 約束と証拠を1行で結ぶ

34試験の合否は、pytestの出力(passed/failed)にも現れますが、それだけでは約束の
証明になりません。約束側のID(02 §4の#番号)と、観測事実を結びつけて残すのが
証拠YAMLです。各試験は `record_item` で1件を記録し、全部の試験が終わった時点
(sessionfinish)でYAMLとして書き出されます(`backend/staging_tests/conftest.py`
37〜69行):

```python
def record_item(
    *, item_id: str, name: str, test: str, verdict: str, observed: dict
) -> None:
    """証拠1件を収集する(試験ID・入力条件・合否・観測値)。"""
```

書き出されたYAMLの1項目はこうです(実在の証拠ファイル
`docs/testassets/results/ws3-staging-result-20261003-231505.yaml` から):

```yaml
- id: 02#8
  name: 時刻到来再評価(保留→proposed昇格)
  test: test_s1_item08_retention_promotion
  verdict: pass
  observed:
    retained_before: 406
    promoted_delta: 23
    clock_set_to: '2026-10-05T00:05:00+09:00'
```

注目したいのは、`id`(約束側の番号)と `test`(試験コードの名前)が**別の欄**に
なっていることです。この2つは1対1ではありません。たとえば#15(双方YESで成立・
チャット解放)は、回答工程と観察工程の2試験で証明されます。約束の単位と試験の単位を
分けて記録しておくと、報告書は「約束→試験」の対応表をYAMLから機械的に組み立てられ
ます。第24章24.2の「対応表から始めて不足だけ書く」は、ここでは「試験から証拠を
対応表の形で出す」方向に裏返しで効いています。

もう1つ。証拠YAMLは**試験が赤のときも書き出されます**(sessionfinishは成功失敗に
関わらず走るため)。どこまで進んで、どの約束で落ちたかが、失敗の証拠として残る
設計です。

## 28.7 裁定A: テストデータも、実装の契約と突合してはじめて正しい

この単位で教材として残したい実例がもう1つあります。途中で起きた**矛盾**の話です。

シードの設計には、飲酒(Intentのalcohol_involved=true)と年齢の約束を検証する材料が
含まれています。18〜19歳のユーザーの「飲酒Intent」と、20歳以上のユーザーの飲酒Intent
が組み合わさってLayer 1で落ちる——それを確かめるための15件です。ところがいざstagingへ
投入すると、この15件の作成が**422(入力の受け付け拒否)で失敗**しました。

理由は、シード側の知らなかった実装の契約(データの渡し方の約束)にあります。Intentの
カテゴリがdrinking(飲酒)なら、保存時にalcohol_involvedをtrueへ強制する
マッピングが動く。だから「18歳の・飲酒だけど飲まない(alcohol false)Intent」は、
**システム上そもそも作れない**。シードの設計は「作れるはず」と思って配置したのに、
作れなかったのです。

ここでの対応が見事でした。ws-3は途中で手を止め、矛盾を報告しました。そしてスー
パーバイザーの裁定(裁定A)は「シードの側を直す」を選びました: 生成器が18〜19歳の
ユーザーにdrinkingを配らない(飲酒Intentは20歳以上に限定して配る)。300件という
規模は不変で、Layer 1を通るペア数は再計算されて更新されました(576→627。第26章
26.5の集計が、このとき入れ替わっています)。修正の記録は、当該の期待値(EX-004)の
根拠欄に追記されています(`docs/testassets/m4-seed.yaml`):

```yaml
  - id: EX-004
    kind: pair
    ...
    basis: 'D-10(10 §3 #27)・06 §2(飲酒は双方20歳以上)。2026-10-03裁定で両側meal化(20歳以上×alcohol true
      vs 18-19歳×alcohol false)'
```

この実例が教えているのは、**シードの機械検査には限界がある**ということです。
第26章の `make seed-verify` は、YAMLの内部整合(分布・集計・意図的配置)を突合します。
しかし「この配置が、実装の保存経路に受け付けられるか」は、YAMLの外の知識です。
生成器・YAML・実装の3つが、それぞれの世界で「正しい」を主張し合うだけでは、矛盾は
いつまでも検出されません。突合するには、**実際に投入するしかない**。だからフル実行は
矛盾を確定させる装置でもあり、矛盾が起きたら隠さずに止まる(S0の投入が名前つきで
落ちる)というこの単位の設計が、そのまま活きました。

テストデータは「実装が受け付ける入力」でもある。データと実装は互いに独立ではなく、
突合してはじめて揃う。これはテスト資産を「設計の写し」と考えるときの、実用的な
警告です。

## 28.8 実行して分かったこと: 単位の緑と、約束全体の緑の差

フル実行は7回繰り返されました。1回目で全グリーンにはなりませんでした。落ちた原因は
ほぼ全部、**単位の試験では観測されていなかった実装の挙動**(報告書は「実装意味論への
適応」と記録しています)でした。2つだけ紹介します。

1つ目。第11章で読んだLayer 1の候補検索は、実は**2経路**あります。1対1ペアを探す
経路と、グループ用の集合(3人以上)を探す経路です。シードの期待値627はペア検索の
見通しで数えた数ですが、DBの実在行は699行ありました。699-627=72行は集合検索の行。
どちらが正しいのかではなく、**何を期待値に含めるべきか**が、実行して初めて明確に
なった例です。ハーネスは「ペア検索∪集合検索」の両方を突合対象にしました。

2つ目。グループのPool検索(第15章15.2)は時間を**30分刻みの区切り**で分割して探します。
21:00のIntentと21:30のIntentは、30分の区切りが違うため同じ区切りに入らず、集合が
生成されません。単位の試験は「同じ区切り」に置いて動かしていたので気づかなかった
挙動です。stagingでは、区切りを跨ぐ配置がシード側に自然に現れたため、初めて見えました。

これらの発見で大事なのは**直し方**の側でした。7回のフル実行を通じて、製品コード
(src/)への変更は裁定Aのシード生成器の修正1件だけ。残りは全部、ハーネス側の
「期待値や観測方法を、実装の実際の挙動と突合する」修正でした。単位の緑は「部品と
組み合わせが正しい」まで。約束全体がこの世界で守られているかは、常設の世界を
動かして観測するしかない。そして観測の差分は、ほとんどが試験側の学びとして回収できる
——フル実行の仕事の実感は、ここにあります。

## 28.9 この章の再統合

- unit/integrationの緑は「部品と組み合わせの正しさ」。stagingフル実行の緑は、
  本番と同じ形の常設世界で、約束(02 §4)が外から観測できる形で守られていること。
  2つの緑は別のことを証明するので、両方が要る
- ハーネスは `backend/staging_tests/`(tests/の外)に置いた。既存の実行系に
  触れない・きれいな世界を前提とする試験の混入を構造的に防ぐ。前提の崩れは
  名前つき失敗で最初の1行で落とす
- 決定性の3本柱。①シード(バイト同一の300件)②判定値の固定(env→settings→
  stub応答の新経路。既定値=現行定数でci挙動不変・回帰ピンで担保)③固定期待は
  参照実装で数えられる量に置き、揺れうる提案群には依存しない
- 時計は前進のみ・ISO明示・tickは60秒のまま。期限を待つのではなく迎えに行き、
  待ちは条件ポーリングで上限つき
- 証拠YAMLは約束ID(02#)と試験名を分けて記録し、約束→試験の対応表を機械で
  組める形にする。失敗のときも書き出される
- 裁定Aの実例: テストデータも実装の契約と突合してはじめて正しい。生成器・
  YAML・実装がそれぞれ正しいだけでは、矛盾は実際に投入するまで出ない
- 7回のフル実行で見つかった実装の挙動差分は、全部ハーネス側の学びとして回収。
  製品コードの変更はシード生成器の1件だけ

## 28.11 確認問題

1. ci環境のintegration試験とstagingフル実行は、証明しているものが何が違いますか。
   「部品の正しさ」と「約束全体の守られ方」の言葉で、それぞれの緑が言える範囲を
   説明してください
2. staging_testsを`backend/tests/`の中に置かなかった理由を、`testpaths` の働きと
   「きれいな世界の前提」との関係で説明してください
3. stub Jevの既定値(0.5)のままでは、stagingでどんな検査が実行できませんか。
   latch_scoreの式と閾値0.60を使って説明してください
4. 判定値を固定する変更は、ci環境の挙動を変えません。その保証を、settingsの
   既定値の選び方と回帰ピンの2つから説明してください
5. 時計の旅路で「後退を使わない」規律は、どんな問題の回避ですか。
   「すでに閉じた行」と「未来の時刻」の同居を例に説明してください
6. 60秒tickを2秒に短縮すれば試験は速くなります。それでも短縮しない判断の
   根拠を、「確定値どおりに動くことの証拠」という言葉で説明してください
7. 裁定Aの矛盾(18〜19歳の飲酒Intentが422で作れない)は、seed-verifyの
   5項目検査では発見できません。発見には何が必要でしたか。機械検査の限界と
   「実際に投入する」ことの意味から書いてください
8. 7回のフル実行で見つかった挙動差分(Layer 1の2経路・グループの30分Bucket等)は、
   なぜ単位の試験では見つからなかったのでしょうか。あなたの言葉で、
   「単位の緑」と「約束全体の緑」の差として説明してください
