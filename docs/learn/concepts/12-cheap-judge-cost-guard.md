## 12.1 意味が近いだけでは決められない: 3つの要素を混ぜて50件を20件へ

第11章の終わりで、候補は「意味が近い順に並んだ最大50組」として帳簿
(match_candidates)に乗りました。この50組をそのまま次の層へ渡したら何が起きるか。
Layer 4(次章で読みます)は **Jev**(ジェブ)というAI判定で、1ペアずつ
「この2人は本当にマッチするか」を聞く層です。AIへの問いは1回ごとにお金がかかる。
50ペア×登録者の数だけ聞いていたら、費用も時間も膨らみ続けます。

Layer 3 **Cheap Judge**(チープ・ジャッジ。安上がりな審査員)は、AIに聞く前に、
**自分で計算できる要素だけで**さらに関を絞る層です。計算式はこれ1つです
(06 §4)。

```text
cheap_score = 0.5 × 類似度 + 0.3 × ルールスコア + 0.2 × 語彙の重なり
```

3つの要素を、混ぜる前に1つずつ見ておきます。

- **類似度** — 第11章11.4でLayer 2が計算したcosine類似度のこと。
  `retrieval_score` に記録した値を、**再計算せずそのまま**使います
- **ルールスコア** — 「時間の近さ」と「予算の近さ」の平均。Layer 1が落とし
  きれなかった「条件の近さ」を数値化するものです
- **語彙の重なり** — soft constraints(「個室がいい」「静かなところ」のような
  希望の文言。第5章)がどれだけ重なるか。文字の切り出し方で数えます(12.3)

「Cheap(安い)」の名前の由来はここにあります。この層は**追加のAPI呼び出しが
ゼロ**で、依存ライブラリもゼロ、同じ入力には必ず同じ値を返す(決定的。第11章
11.5と同じ語)。式の重み 0.5 / 0.3 / 0.2 は、docsが公式に決めた値(確定値)です。
ただしその位置づけは**調整する前提の初期値**で、運用データを見ながら変えて
よい約束になっています(06 §4)。「いまの正式な値」と「置き換える前提の値」が
同時に成り立つのは、変わるときはdocsの改版を伴って変わるからです
(この規律は第11章のK_v=50などと同じです)。類似度に最大の0.5を
配分したのは、「意味の近さ」がこの中でいちばん情報量が多い要素だから、という
設計判断です。

Layer 3を通った候補のうち、次層へ渡るのは **上位20件**(`K_CHEAP = 20`。
`layer3.py:21`)。50から20へ。この「その層から次層へ渡す出力数の上限」という
考え方も第11章のK_v(=50)と同じです(06 §8 D-24)。

## 12.2 「近さ」を0〜1の数に置き換える: 飽和と中立

ここで、この章でいちばん大事な考え方を出します。時間の差は**分**、予算の差は
**円**で測ります。単位が違うものは、そのまま足し合わせられません。3000円の差と
90分の差、どちらが「大きい」のでしょうか——比べようがありません。そこで、
どちらも **0〜1のスケールへ置き換えてから**混ぜます。量をある範囲へ収まるように
置き換えることを、**正規化**(せいきか)と呼びます。

この層の正規化は2つの工夫の上に立っています。1つは**飽和**、もう1つは**中立**です。

**時間の近さ**。2つのIntentの開始時刻の差(分)から、次の式で作ります
(`layer3.py:68` の `time_closeness`)。

```text
時間の近さ = 1 − min(差の分, 180) / 180
```

差が0分なら1.0、90分なら0.5、180分なら0.0。`min` が括弧の中に入っているのが
工夫で、差が180分を超えても**0.0のまま**になります。これが飽和です
( `TIME_SATURATION_MIN = 180`。`layer3.py:23` )。なぜ180分かというと、
Intentの実効寿命が3時間だからです(03 D-19。第6章で見た、終了時刻の補完も
「始まり+3時間」でした)。寿命を3時間過ぎた相手とは時間帯が成立しないので、
それ以上の差をつけても「遠い」ことに変わりはない。差が600分だろうが3000分
だろうが、同じ0.0で構わない、という切り捨てです。飽和があるから、スコアは
必ず0〜1に収まり、式の中で暴れません。もし飽和がなければ、差600分のペアは
1 − 600/180 = −2.3 と計算されて0〜1の枠を飛び出し、ほかの要素をせっかく
0〜1に揃えた意味が崩れてしまいます(確認問題2で同じことを問います)。

**予算の近さ**。同じ形の式です(`layer3.py:77` の `budget_closeness`)。

```text
予算の近さ = 1 − min(|差の円|, 3000) / 3000
```

差0円で1.0、1500円で0.5、3000円以上で0.0(飽和)。3000円という飽和点は、
第11章11.2で見たペア予算のfail線(500円)の6倍です。
典型的な飲食の予算帯の上限相当、という初期値で、これも運用データで調整する
対象です(design §2.2)。

ルールスコアは、この2つの平均です。**時間で見た近さと予算で見た近さを、同じ
重みで混ぜる**という、ごく素直な作りになっています(`layer3.py:88` の
`rule_score`)。

```python
def rule_score(
    *,
    origin_time_start: datetime,
    cand_time_start: datetime,
    origin_budget: int | None,
    cand_budget: int | None,
) -> float:
    """ルールスコア: (時間近さ + 予算近さ) / 2(design §2.2の等分)。"""
    return (
        time_closeness(origin_time_start, cand_time_start)
        + budget_closeness(origin_budget, cand_budget)
    ) / 2.0
```

ここで、1つ困ったことに気づくかもしれません。予算は**指定しないことも
できる**のです(第5章。NULL=制約なし)。片方だけ指定、両方とも指定なし——
そんなペアの「予算の近さ」はどう計算すればいいでしょうか。

答えは、**計算しない**です。情報がないのに近さをでっちあげず、**0.5を返す**。
0.0でも1.0でもない、どちらでもない値。これが**中立**(neutral)です
(`NEUTRAL = 0.5`。`layer3.py:25`)。`budget_closeness` の冒頭にありました。

```python
    if budget_a is None or budget_b is None:
        return NEUTRAL
```

なぜ0.5でなければならないのか、0.0(零点)ではだめな理由から考えます。予算を
指定していない人は「縛りがない」だけで、条件が悪いわけではありません。零点に
したら、予算を書かなかったことを理由に候補の順位ががた落ちします。では1.0
(満点)ではどうか。今度は逆に、予算を書かないことが**最善の戦略**になってしまう。
ちゃんと「3000円まで」と書いた人より、何も書かない人のほうが常に上位を占める
世界はおかしい。**情報がないことは、満点にも零点にも加算しない**——0.5はその
中立線です。

## 12.3 言葉の重なりは、文字のペアで数える

3つめの要素、**語彙の重なり**に入ります。soft constraintsの文言どうしの
「重なり」を数えるのですが、その前に「重なりをどう数えるか」という問題が
あります。日本語は単語の間に空白を置かないので、文を単語に区切るには専用の
道具(形態素解析器。かたちそかいせきき)が要ります。LATCHは**それを使わない**
と決めました。理由は決定性です(06 §4)。形態素解析器は辞書の版本によって値が
揺れ、依存も増える。「焼肉好き」が今日は{焼肉, 好き}に切り分けられ、辞書を
更新した翌日は{焼肉好き}1語になる——そんな揺れは、同じ入力に同じ値を返すと
いうこの層の約束と衝突します。

代わりに使うのが**文字bigram**(バイグラム)です。文を**2文字ずつ、1文字ずつ
ずらして**切り出します。「焼肉好き」なら、焼肉→肉好→好き、の3個。切り出した
ものを**集合**(重複なしの集まり)として持ちます(`layer3.py:102` の
`_bigrams`)。

```python
def _bigrams(texts: tuple[str, ...]) -> frozenset[str]:
    """文字bigram集合(NFKC正規化・2文字未満は空・text間をまたがない)。"""
    grams: set[str] = set()
    for text in texts:
        normalized = unicodedata.normalize("NFKC", text)
        if len(normalized) < 2:
            continue
        grams.update(normalized[i : i + 2] for i in range(len(normalized) - 1))
    return frozenset(grams)
```

読みどころを3つ挙げます。

1つめ、`unicodedata.normalize("NFKC", text)`。**NFKC正規化**と呼ばれる、
文字の表記ゆれを揃える標準の変換です。全角の「AB」と半角の「AB」を同じ字に
するなど、見た目が同じなら同じ字扱いにできます。bigramの前に通すことで、
表記のゆれが重なりの計算を汚しません。2つめ、`if len(normalized) < 2: continue`。
2文字に満たない文言はbigramを1つも作れないので、空扱い(何も足さない)です。
3つめ、bigramは**1つのtextの中でしか**作りません。「個室」と「焼肉」という
2つの文言から「室焼」というbigramは作らない。文言の切れ目をまたぐ文字の組は、
たまたま隣り合っただけの中身のない組だからです。

2つの集合の重なりは、**Jaccard係数**(ジャッカードけいすう)で測ります
(`layer3.py:113` の `vocab_overlap`)。

```text
Jaccard係数 = 共通する要素の数 ÷ どちらかにある要素の総数
```

「焼肉」{焼肉} と「焼肉好き」{焼肉, 肉好, 好き} なら、共通は1個、合わせて
3個。1/3です。完全に同じ集合なら1.0、1つも重ならなければ0.0。**重なりの
規模がそのまま0〜1の値になる**ので、ここでは追加の正規化が要りません。

中立の考え方も、ここに同じ形で現れます。**両方の集合が空**(どちらも希望の
文言なし)のとき、重なりは「分からない」ではなく「定義できない」です。
Jaccardの分母(どちらかにある要素の総数)が0になるので、割り算そのものが
立ちません。これも0.5を返します。片方だけ空のときは話が違い、こちらは0.0
(共通する要素が1つもない、という事実がある)です。同じ「空」でも、両方空なら
情報がなく中立、片方空なら共通なし、と扱いが分かれる。12.2の予算のNULLと
見比べてください。**「情報がない」と「一致しない」は別物**なのです。

最後に、数える文言の**選び方**に1つ約束があります(`layer3.py:42` の
`soft_texts`)。soft_constraintsの各文言には、第6章6.4で見たNG条件の降格
(downgraded_from_ng=true)の印が付いていることがあります。降格された文言は
**語彙の計算対象から除外**します。NG条件はLayer 1が落とすための情報で、
「希望の言葉」として数えてよいものではないからです(06 §4)。

## 12.4 計算したら全部帳簿に書き、上位20件だけ次へ渡す

3つの要素が揃ったので、合成して、記録して、絞ります。この節は短いですが、
第11章との対応で読むと、設計の**一貫性**が見えてくる場所です。

**合成**は1行です(`layer3.py:126`)。

```python
def cheap_score(similarity: float, rule: float, vocab: float) -> float:
    """0.5/0.3/0.2 の線形合成(06 §4)。丸めない。"""
    return WEIGHT_SIMILARITY * similarity + WEIGHT_RULE * rule + WEIGHT_VOCAB * vocab
```

**記録**は、Layer 2を通った**全件**に及びます。50件全員のcheap_scoreを計算し、
50件全員の `cheap_judge_score` を帳簿に書く。20位以内に入らなかった候補も
記録するのです(design §2.3)。なぜか。計算は決定的で費用ゼロなので全件計算に
デメリットがなく、一方で「全候補の値が記録に残る」ことには価値があるからです。
重み0.5/0.3/0.2は運用データで調整する前提の値でした。全件のスコアが記録に
残っていれば、重みを変えたら順位がどう動くかを後から計算し直せます
(docs/09のOffline評価で使います)。上位20件ぶんしか記録がないと、その検討は
二度とできません。

帳簿への書き込みは第11章11.6のUPSERTがそのまま使われ、列が1つ増えました
(`candidates.py:22`)。

```python
_UPSERT = text("""
    INSERT INTO match_candidates (
        intent_a_id, intent_b_id, intent_a_version, intent_b_version,
        retrieval_score, cheap_judge_score, status, created_at, updated_at
    ) VALUES (
        :intent_a_id, :intent_b_id, :intent_a_version, :intent_b_version,
        :retrieval_score, :cheap_judge_score, 'pending', :now, :now
    )
    ON CONFLICT (intent_a_id, intent_b_id, intent_a_version, intent_b_version)
    DO UPDATE SET
        retrieval_score = EXCLUDED.retrieval_score,
        cheap_judge_score = EXCLUDED.cheap_judge_score,
        updated_at = EXCLUDED.updated_at
""")
```

`cheap_judge_score` がINSERTにもDO UPDATEにも入っている。同一バージョン組の
再評価では、Layer 2のスコアとLayer 3のスコアが**同じ1文で**塗り替わります。
statusはこの層では触りません。`pending`(評価待ち)のままです。`skipped`や
`evaluated`への遷移は、次層のJev実行の直前・直後が担当すると決まって
います(design §1.4-1。実装は第13章で読みます)。

**絞り**は `select_top_kc` です(`layer3.py:131`)。

```python
def select_top_kc(scored: list[ScoredCandidate]) -> list[ScoredCandidate]:
    """上位 K_c=20(cheap_score降順・同点はintent_id昇順 — D-24・design §2.3)。"""
    return sorted(scored, key=lambda s: (-s.cheap_score, s.intent_id))[:K_CHEAP]
```

ソートのキーに注目してください。第1キーは `-s.cheap_score`(降順)、第2キーは
`s.intent_id`(昇順)。**同点はintent_id昇順で崩す**——第11章11.5でLayer 2の
ORDER BYに付けたのと、まったく同じ規律です。まったく同じ内容のIntentが同じ
cheap_scoreで並ぶのは現実に起こる(第11章11.5で見た「同点は起こる」の議論が
Layer 3でもそのまま成立します)ので、並びを決定的にする第2キーが必要です。

もう1つ、**丸めない**という規律がdocstringに書かれています。計算したfloatを
四捨五入してDBに書く、という処理をあえて入れない。丸めの桁数は同点判定を
左右します。小数第3位で丸めていたら、丸める前は違っていた2つの候補が同点に
なり、intent_id昇順の順位が入れ替わるかもしれない。「同一入力→同一結果」を
桁の指定に依存させないため、値はfloatのまま計算し、floatのまま書きます
(design §2.2)。

## 12.5 ついに繋がる: embedding_completedからLayer 1〜3が同じトランザクションで走る

第11章で「配線はまだ実装されていない」と正直に書いた部分が、この単位で
実装されました。**Layer 1〜3が、初めてEventから駆動されます**。

出発点は第10章10.8の `embedding_completed` です。このイベントを処理する
Stage1の `_process_once` に、新しい分岐が生えています(`stage1.py:287` から)。

```python
            elif event_type == _EVENT_EMBEDDING_COMPLETED:
                # Layer 1〜3をこのトランザクションへ同乗(design §2.7)。
                # 失敗→ロールバック→再試行5回→quarantinedの既存経路に載る
                if self._matching_hook is not None:
                    await self._matching_hook(conn, intent_id)
```

**matching_hook**(マッチングフック)は、第9章9.7でembedding_hookに見た
「あとで実体を埋めるための差込口」と同じ形の引数です。Stage1は「ここで何かを
呼ぶ」ことしか知らず、実体はWorkerの組み立て(main.py)が差し込みます。
embedding_hookとの違いが1つあります。第10章10.8でEmbeddingの実体が
**トランザクションの外**へずらされたのを覚えているでしょうか。外部APIを
最大2秒待つ処理は、DBトランザクションの中に置けなかったのです。ところが
マッチングは**DB内の処理**です。SQLを数本実行して終わる。だから今度は逆に、
**Event行をprocessedにするUPDATEと同一のトランザクションに同乗**させました。
失敗すればトランザクションごとロールバックされ、第9章9.7の再試行5回→
quarantinedの経路にそのまま載ります。同じ「フック」という形の中で、処理の
性質(外部APIか、DB内か)によって埋める場所が変わる——第9章・第10章で積んだ
読みが、ここで報われます。

呼ばれる実体は `worker/main.py:303` の `_run_matching` です。

```python
    async def _run_matching(self, conn, intent_id: uuid.UUID) -> None:
        """embedding_completed 起点の Layer 1〜3 実行(design §2.6・§2.7)。

        ...docstringの続き...
        """
        if self._reeval is not None and not await self._reeval.allow(intent_id):
            logger.info(
                "matching reeval suppressed intent_id=%s (within 30min window)",
                intent_id,
            )
            return
        await run_candidate_retrieval(conn, self.clock, intent_id)
```

前半に、見慣れない門番が1人います。`ReevalGuard`(リイーバルガード。再評価
ガード)です。マッチングを実行する**前に**「このIntent、直近30分以内に評価
していないか?」と問い、評価済みなら**何もせず帰ります**。なぜそんな門番が
要るのか。Intentはちょこちょこ更新されるものだからです。表示名を直す・予算を
変える——内容が変わるたびにEventが流れ、embeddingが走り、マッチングが焼き
直しになる。でも20分前に評価した結果と大差ない場面がほとんどでしょう。
そこで06 §5は、**同一Intentの再評価は、直近の詳細評価から30分空ける**と
決めました。スキップされたEventは破棄されずに、通常どおりprocessedで
閉じます。評価の機会は、次の更新Eventか、30分経過後の再評価(ws-6で実装)で
拾い直されます。

ガードの中身は、Redisの **SET NX EX** という1回の命令です(`store.py:70` の
`set_reeval_nx`)。

```python
    async def set_reeval_nx(self, intent_id: str) -> bool:
        """reeval:{intent_id} の SET NX EX 1800(06 §5・design §2.6)。

        True=確保成功(評価してよい)・False=30分以内の再評価。
        """
        return bool(
            await self._redis.set(
                f"{self._prefix}reeval:{intent_id}", "1", nx=True, ex=_REEVAL_TTL_S
            )
        )
```

`SET reeval:{intent_id} "1" NX EX 1800` を読み解きます。`EX 1800` は「この鍵の
寿命は1800秒(30分)」。`NX`(not existsの略)が肝で、「**鍵がまだ無ければ**
セットする。既にあれば、何もしないで失敗を返す」という指定です。セットに
成功したらTrue=「30分以内に評価していないので、評価してよい」。失敗したら
False=「鍵がある=30分以内に誰かが評価した」。この判定は**たった1回の命令で、
かつ原子的**に行われます。「鍵があるか確認して、なければセットする」を2回の
命令で書くと、確認とセットの間に別の処理が割り込んで、二重に評価が走る
すき間が生まれます。NXがそのすき間を最初から潰しているのです。

## 12.6 次の層は有料: 4つのカウンタが「実行してよい」を決める

ここまで来て、候補は20件に絞られました。この章の後半は、次層(Layer 4の
Jev)への**前払いの保険**です。Jevは課金APIですから、呼び出しが暴走すれば費用は
際限なく膨らみます。この単位は、Jevの実行を守る部品——**コスト保護**——を、
Layer 3と一緒に作りました(Jevの実行そのものは次章の担当。ここで作るのは、
実行の直前に呼ばれる**番人**です)。

番人は `worker/cost/guard.py` の `JevCostGuard` です。守るべき上限は4つ
(06 §5・04 §4 D-16)。

| カウンタ | 上限 | 何のため |
|---|---|---|
| 1Intentあたり | 40回/日 | 1つのIntentが評価を独占しない |
| 1ユーザーあたり | 120回/日 | ユーザーの全Intentで共有する回数。Active 5件を全部悪用してもここで頭打ち |
| 全体で日次 | 30,000回/日 | 費用の1日あたりの上限 |
| 全体で月次 | 600,000回/月 | 費用の1か月あたりの上限 |

判定の中心は `request_execution` です(`guard.py:89`)。Jevを実行したい側が、
実行の直前に呼びます。

```python
    async def request_execution(
        self, intent_id: uuid.UUID, user_id: uuid.UUID
    ) -> JevDecision:
        """4カウンタINCR先行判定(design §2.4-2)。denyもカウントを消費する。"""
        day = self._day_bucket()
        month = self._month_bucket()
        try:
            intent_count = await self._store.incr_intent(str(intent_id), day)
            user_count = await self._store.incr_user(str(user_id), day)
            daily_count = await self._store.incr_daily(day)
            monthly_count = await self._store.incr_monthly(month)
        except Exception as exc:
            raise JevCostDependencyError("jev cost store unavailable") from exc
        ...(80%アラートの判定がここに入る。この節の末尾で説明します)...
        if intent_count > INTENT_DAILY_LIMIT:
            return JevDecision(allowed=False, deny_reason=DENY_INTENT_DAILY)
        if user_count > USER_DAILY_LIMIT:
            return JevDecision(allowed=False, deny_reason=DENY_USER_DAILY)
        if daily_count > DAILY_LIMIT:
            return JevDecision(allowed=False, deny_reason=DENY_GLOBAL_DAILY)
        if monthly_count > MONTHLY_LIMIT:
            return JevDecision(allowed=False, deny_reason=DENY_GLOBAL_MONTHLY)
        return JevDecision(allowed=True, deny_reason=None)
```

注目するのは順序です。この関数は**数えて(INCRして)から**判定しています。
直感では「上限を確認してから、大丈夫なら数える」のが正しそうに見えます。
しかしその順では、同時に走った2つの要求が両方とも「まだ40回だから大丈夫」と
確認し、両方が実行されて41回目が突破される——**判定とカウントの間にすり抜け**
が生まれます。先にINCRしてしまうと、RedisのINCRは原子的(同時に来ても1つずつ
確実に足す)なので、戻り値は「自分が足したあとの値」で確定します。41を踏んだ
要求はdenyされる。**denyされた要求も、カウントは消費したまま**です。無駄に
見えるかもしれませんが、これが超過幅を「最大1要求分」に抑える代償です
(design §2.4-2)。許可される要求の数は、各カウンタで必ず上限以下に収まります。

Redisが止まっていたらどうなるか。`except` のブロックが答えです。例外を
`JevCostDependencyError` に包んで投げます。**fail-closed**(フェイル・クローズド。
故障したら閉じる)——番人自身が調子悪いときに、チェックなしで実行を通して
しまうことがないよう、例外で止まります(第7章のレート制限と同じ規律)。
呼び出し側はこの例外を再試行の経路に載せます。

上限に達してdeny(拒否)された場合、その候補は**諦められはしません**。「Jev未判定」
として保留(match_candidates.status=skipped)され、日次リセット後や障害回復後の
再評価経路で拾い直されます(06 §8 D-15)。この「保留の記録」を書き込むのは
Jev実行の直前、つまり次章の実行部です。**保留という扱い自体はこの単位で確定**
しています。上限はコストの保証であり、利用者の機会の没収ではない、という位置づけ
です。

最後に、80%アラートを1行で。日次24,000回・月次480,000回(各80%)に**達した
瞬間**、運用者へのアラートが1回だけ発報されます。仕掛けはINCRの戻り値が
**丁度24,000に等しいときだけ**発報する、というもの(guard.py:102 の
`if daily_count == DAILY_ALERT:`)。INCRが原子的なので、丁度24,000を踏むのは
全世界で1回だけ。2回目以降の要求は24,001以上を返すので、アラートは重複し
ません。月次上限の到達時には、復帰予定(暦月初のJST 0時)を添えた別のログが
1回だけ出ます。アラートの宛先(メールか、ログか)は運用設計に委ねられて
いるため、今は構造化ログを出す関数を差し替え可能な形にしてあります
(`structured_log_alert`。design §2.4-5)。

## 12.7 リセットは時計の仕事: 第7章の「鍵の名前に日付」を踏襲する

「1日40回」の「1日」は、いつ切り替わるのでしょうか。ここで第7章7.4を思い出
してください。レート制限のカウンタは、**TTLでもリセットジョブでもなく、鍵の
名前に日付を埋めることで**リセットを表現したのでした。`rl:create:{user_id}:
{yyyymmdd}` という鍵なら、JST 0時を跨ぐと自動的に「翌日の別の鍵」になり、
0から始まる。消す処理そのものが存在しない、という設計です。

Jevのコストカウンタは、これと**まったく同じ方式**を踏襲します(design §2.5)。
鍵の形は `store.py` のdocstringに一覧になっています。

```text
  日次:   INCR jev:daily:{yyyymmdd}                TTL 48時間
  月次:   INCR jev:monthly:{yyyymm}                 TTL 45日
  Intent: INCR jev:intent:{intent_id}:{yyyymmdd}    TTL 48時間
  ユーザ: INCR jev:user:{user_id}:{yyyymmdd}        TTL 48時間
  再評価: SET reeval:{intent_id} "1" NX EX 1800
```

`yyyymmdd`(日付)も `yyyymm`(月)も、**Clockから導きます**(`guard.py:76` の
`_day_bucket` が `self._clock.jst_date().strftime("%Y%m%d")`)。第3章の読みが
ここでも効きます。実時間を直接参照したら、テストで日付を操作できません。
FakeClockを差し替えれば、日次上限の試験も「今日」を変えるだけで書けます。

月次のリセットも同じ理屈です。鍵の名前の `yyyymm` が暦月初(JST)に切り替わる
ので、600,000回のカウンタは新しい月に0から始まります。TTLの45日は掃除用で
あって、**リセットの表現には1ミリも関与しません**。この分離の価値は第7章で
確認したとおりです——TTLは設定した瞬間から数えるので、JST 0時基準の「1日」
とは必ずずれる。掃除にずれがあっても、リセットの正しさには影響しない、という
分担です。

さらにこの方式には、**リセットジョブが死んでいても正しい**という性質が
あります。鍵名をつねに実行時のClockから導くので、「昨日の鍵を使い続けて
しまう」ような状態は構造的に起こりません。04 §5のいう「リセットジョブ失敗時
の自己修復」を、ジョブなしで内蔵していることになります。残るリセットジョブ
の役割は、日次リセット後に**保留されていた候補の再評価をキックする**こと——
カウンタのリセットそのものではなく、溜まった仕事の回収のほうです。この
ジョブはM3 ws-2で実装され、旧キーの掃除も担っています(第18章18.8)。

## 12.9 この章の再統合

- Layer 3 Cheap Judgeは、AIに聞く前に**自分で計算できる要素だけ**で50件を
  20件へ絞る層。cheap_score = 0.5×類似度 + 0.3×ルールスコア + 0.2×語彙の
  重なり。追加APIコストゼロ・依存ゼロ・決定的
- 異なる単位(分・円)を混ぜるため、近さは0〜1へ正規化する。3時間と3000円の
  **飽和**でスケールを抑え、NULLや空の**中立0.5**で「情報がない」を満点にも
  零点にもしない
- 語彙の重なりは形態素解析器に頼らず**文字bigramの集合**と**Jaccard係数**で
  数える。決定性を保つため(依存・辞書の揺れを避ける)。降格文言は計算対象外
- 計算は全件に及び、**全件のcheap_judge_scoreを帳簿に記録**する(重み調整の
  ための記録)。次層へ渡す上位20件の並びは「降順・同点はintent_id昇順」で
  第11章と同じ規律。**丸めない**のは同点判定を桁に依存させないため
- embedding_completed から Layer 1〜3 までの配線がつながった。マッチングは
  DB内の処理なので、Eventをprocessedにする**同一トランザクションに同乗**し、
  失敗は第9章の再試行経路に載る。再評価はreevalガード(`SET NX EX 1800`)で
  30分に1度に抑える
- 次層のJevは課金API。4つのカウンタ(1Intent 40回/日・1ユーザー120回/日・
  日次30,000・月次600,000)がINCR先行で判定し、denyも消費する=すり抜けなし。
  番人障害時はfail-closed。denyされた候補は「Jev未判定」として保留され、
  リセット後に再評価される
- カウンタのリセットは第7章と同じ**日付キー切替**(鍵名にyyyymmdd)。TTLは
  掃除専用。日付はClockから導くので、リセットジョブ不在でも正確で、テストは
  FakeClockで書ける

50件から20件へ。意味の近さに、時間・予算・言葉の重なりという「自分で計算
できる近さ」を混ぜて選び抜き、全件を帳簿に残した。そして次層の有料APIを
呼ぶ前に、回数を数える番人と、30分に1度の再評価という節度まで、この単位で
用意が整いました。この20件に**お金を払って**判定を仰ぐLayer 4(Jev)は、
次章の題材です——この章の番人を呼ぶのは、その実行部でした。
