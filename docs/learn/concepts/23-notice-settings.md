## 23.1 残っていた2画面: 消費するAPIは既に全部あった

プロトタイプ6画面(03 §2)のうち、M3 ws-7までにホーム・LATCH詳細・チャットが
実装されました(第8章・Lab 9)。残るは2つです。**お知らせ**(topbarのベルを
押すと開く一覧)と**設定**(通知の許可とブロックの管理)です。

この2画面には、これまでの章とは違う面白さがあります。**ws-8の時点では、
backendを1行も変えずに作れた**のです。お知らせが消費する
`GET /v1/notifications` と `POST /v1/notifications/{id}/read` はws-3で
(第19章)、ブロックの3つの窓口はws-5で(第21章)、チャットの読み取り専用化は
ws-4とws-7で、それぞれ実装済みでした。画面はまだないのにAPIだけが先に
あった——本章は、** APIを消費して表示を作る側**の設計だけを読みます。

その後もこの構えは続いています。2026-10-02のマージ(m3-g3fix)で、お知らせの
応答に `my_response` という材料が1つ加わり、成立を伝える新しい通知
(latch_matched)が書かれるようになりましたが、文言を組み立てる側(画面)の
構造は変わっていません。材料が増えても組み立て側がそのまま立っていること
こそ、「文言はクライアントが組み立てる」設計(第19章19.5)の実証です。
本章の後半23.2・23.3で、この追従の実際を読みます。

読むべき取り決めは4つに集まります。

1. **文言は表で決める**(23.2) — 行の表示をtype×statusの2軸で確定する
2. **一箇所に置く**(23.3) — 不成立の一文とその分岐を、1つの関数で全画面へ行き渡らせる
3. **開いた=見た**(23.4) — ドットの語義を決め、既読を冪等な204の上に載せる
4. **外の機能は注入する**(23.5) — ブラウザの通知許可を試験可能な形で扱う

どれも「画面のコード」の話に見えて、実は第8章以来の作法——計算は純関数へ、
外の世界は境界へ——の同じ型がもう1周出てきただけです。順に見ていきます。

## 23.2 文言は表で決める: type×statusの2軸から漏れなく組む

お知らせの一覧には、4種の通知が混ざって並びます(第19章)。候補の提案
(proposal)・近くにいるかもしれない人(nearby_candidate)・実際に会ったかの
問いかけ(attendance_request)・成立の連絡(latch_matched)です。最後の1つは
2026-10-02のマージ(m3-g3fix)で加わりました。表示の問題は、この4種だけでなく、
**組み合わせ**で決まることです。

理由はこうです。notificationsの行は、届いた時点で中身がもう変わりません。
ところがその通知が指しているLATCHは、その後も動き続けます。提案の通知を
受け取ったあと、あなたが断ったのか・期限が切れたのか・無事成立したのか。
行を開く時点のstatusは、届いた時点とは違うかもしれません。

そこでws-8の設計は、行の文言を「通知の種類」だけでなく「今のlatch.status」
との2軸で確定しました。実装は `view.js` へ追記された1つの純関数です。

```javascript
// view.js:119-137(一部)
// お知らせ行の文言(type×latch.statusのマトリクス・design §2.3・m3-g3fix §2.5)。
// 終了行はclosedText(latch)で自分の操作履歴(no/defer)へ分岐(03 §7・⑫)。
// nearbyは存在通知のみ。latch_matchedは見出し+導線+バッジ(条件サマリ不含)。
export const notificationLines = (item, nowIso) => {
  if (item.type === "nearby_candidate") return [NEARBY_NOTICE_TEXT];
  if (item.type === "attendance_request") return [ATTENDANCE_QUESTION];
  const latch = item.latch;
  if (!latch) return [NOTICE_FALLBACK_TEXT]; // 防御(全type)
  if (item.type === "latch_matched") {
    // 解散後(statusがexpired等)は一文統一(03 §7)。条件サマリは成立通知行に
    // 含めない(hidden_until_match提案は最小構造のままで表示可否が分かれる)
    if (CLOSED_STATUSES.has(latch.status)) return [CLOSED_TEXT];
    return [
      MATCHED_NOTICE_TITLE,
      NEXT_ACTION_TEXT, // 成立後詳細と同一の導線文言(文言単一ソース)
      STATUS_TEXT[latch.status] ?? latch.status, // バッジ(成立済み/完了)
    ];
  }
  if (CLOSED_STATUSES.has(latch.status)) return [closedText(latch)]; // 操作履歴へ分岐
  if (MATCHED_NOTICE_STATUSES.has(latch.status)) {
    // 見出し+条件サマリ+バッジ「成立済み」(回答を促す一文は出さない)
    ...
  }
  // proposed / partial_accept — 様式どおり(見出し+サマリ+一致度の文)
  ...
};
```

引数はAPI応答の1行(item)と現在時刻(nowIso)だけ。ブラウザも通信も知らない、
第8章8.6の純関数と同じ型です。分岐の全体を表にすると、こうなります
(design §2.3・m3-g3fix §2.5)。

| type | latch.status | 行の文言 | タップ先 |
|---|---|---|---|
| proposal | proposed / partial_accept | 「LATCH候補があります。」+条件サマリ+一致度の文 | `#/latches/{id}` |
| proposal | matched / completed | 見出し+サマリ+バッジ「成立済み」(回答を促さない) | `#/latches/{id}` |
| proposal | expired / rejected / cancelled | **あなたの回答による**(下記) | `#/latches/{id}` |
| nearby_candidate | 全status | 「近い条件の候補があるようです。」 | **なし** |
| attendance_request | completed | 「実際に会いましたか?」 | `#/latches/{id}` |
| latch_matched | matched / completed | 「LATCHが成立しました。」+「チャットで挨拶を交わしましょう」+バッジ(成立済み/完了) | `#/latches/{id}` |
| latch_matched | expired / rejected / cancelled(解散後) | **「この提案は成立しませんでした」だけ** | `#/latches/{id}` |
| (全type) | latch === null(防御) | 「LATCHからのお知らせがあります。」 | なし |

表の行ごとに、根拠をひとつずつ確認しておきましょう。

**終了行の文言は、あなた自身の回答が材料です。** 第17章17.6とLab 9で読んだ
とおり、不成立の表示は詳細画面で二値化されます——自分の操作履歴(no・見送り)
か、それ以外の一律文言か。お知らせの終了行も、2026-10-02のマージからこの
分岐を追うようになりました。応答のlatch要素に `my_response`(あなたがその
提案へ出した回答。yes/no/defer・未回答はnull)が加わり、noなら
「辞退しました」、deferなら「今回は見送りました」が出ます。いずれでもない
場合は一律の一文のままです。

ws-8がお知らせを作った時点では、応答に `my_response` はありませんでした。
二値化する材料がなければ、理由は推測できない。だから当時の設計は「お知らせの
終了行は、自分で閉じた提案も含めて一律の一文」と決めていました(設計§5-2②)。
材料が揃ったm3-g3fixで、この判断は03 §7本来の形へ解消されます。03 §7の規定は
文言を2種類に集約するものです——「自分の操作によるものは、自身の操作履歴として
表示する」「それ以外は『この提案は成立しませんでした』の一文で統一する」。
あなたの回答だけが乗る my_response は、ちょうど前者の材料になります。
開示の境界は動いていません。latch要素に乗るのは**あくまであなた自身の回答
だけで**、相手がnoだったのかブロックで閉じたのかは、どんな行にも書かれて
いません。自分の操作は操作履歴に、相手の事情は一律の一文に。1つの欄の追加で、
2種類の文言がそろって仕様どおりになった形です。

**成立通知の行は、提案の行とは別の行として並びます。** 提案が成立すると、
backendは参加者全員へ type=latch_matched の通知行を書きます(あなたが最後に
yesを入れたときも含め、全員同時です。03 §4 D-20)。これで一覧には、成立した
提案について proposal の行と latch_matched の行が並ぶことになりますが、これは
重複ではなく分担です。proposal の行は「その提案が今どう見えるか」——条件
サマリが見えるかどうかも含めて——を担い、成立通知の行は「成立したこと」と
次の導線だけを担います。文言は見出し「LATCHが成立しました。」と
「チャットで挨拶を交わしましょう」(成立後詳細画面と同一の導線文言)とバッジ。
条件サマリを出さないのは、見せるかどうかが提案ごとに分かれる
(hidden_until_matchの提案はproposalが最小構成のまま。第19章19.5)からで、
サマリは提案の行と詳細画面が既に担っています。なお、自分がyesを入れたLATCHが
成立すれば、あなたの目にもお知らせが1件増えます。「成立」は提案を閉じる操作と
は違って、仲間が揃ったという皆への事実なので、自分の分が記録に並ぶのは
自然なことです。

**matched/completed行で「回答ください」を出さないのは、嘘にならないためです。**
JOINで埋め込まれるのは今のstatus(第19章)なので、成立済みの提案の行に
「回答を」と促すのは誤りです。ここは見出しとサマリのあとにバッジ
「成立済み」(STATUS_TEXTの流用)を置いて終わり。

**nearby行にタップ先がないのは、candidateが詳細APIの対象外だからです。**
近くにいる人(nearby)の通知が指すのは、まだ提案になっていないcandidate状態の
latches行です(第14章14.6)。`GET /v1/latches/{id}` はcandidateを返しません
(404)。リンクを張れば開けない画面へ連れていくだけなので、行はリンクに
しません。文言も「近い条件の候補があるようです。」の一文だけ——条件サマリも
相手の手がかりも出しません(nearbyの応答は最小構成なので、そもそも出せる
情報が入っていない、という第19章の構造的担保が下支えします)。

**attendance_requestの行は、問いかけだけです。** 第20章20.5の実施自己申告
(D-09)は、詳細画面から1タップで答える設計でした。FR-46(03 §4)が通知の行や
バナーからの直接回答を禁じているので、行は「実際に会いましたか?」とだけ
表示し、タップ先の詳細画面で3日窓の導線が現れます。

表を先に確定する意味は、漏れのチェックにあります。type(4種+latchなし)
× status(7種)のマトリクスを埋めてみれば、「この組合せは何を表示する?」
という問いが残りません。実装と試験はこの表の書き写しになります(latch-notice
.test.jsには「design §2.3のマトリクス」と「m3-g3fix: my_response分岐+成立
通知行」の2つのdescribeが、表が生まれた順に並んでいます)。**仕様を表にして
から、表をコードに写す。**
第14章のD-08日次上限の数え方と同じ作法が、画面の文言でもう1回出てきました。

## 23.3 一文統一: CLOSED_TEXTを1箇所に置く

前節の表で、終了行には2種類の文言が並びました。自分の操作履歴(「辞退しました」
「今回は見送りました」)と、一律の一文「この提案は成立しませんでした」です。
この一文、実はws-7のときに既に定数になっていました。

```javascript
// texts.js:5
export const CLOSED_TEXT = "この提案は成立しませんでした";
```

`texts.js` はws-7が確保した文言の定数置き場です(第8章ではindex.htmlに直書き
されていた表示文言を、JSから組み立てる画面の分だけ集めたファイル)。ただし、
ws-8以降の画面はこの定数を**直接は参照していません**。参照しているのは、
「今どの一文か」を決める純関数 `closedText`(view.js:89-94)です。

```javascript
// view.js:88-94
// 不成立の二値化(03 §7): 自分の操作履歴か統一文言か
export const closedText = (latch) =>
  latch.my_response === "no"
    ? ANSWERED_TEXT.no
    : latch.my_response === "defer"
      ? ANSWERED_TEXT.defer
      : CLOSED_TEXT;
```

noならANSWERED_TEXT.no(「辞退しました」)、deferならANSWERED_TEXT.defer
(「今回は見送りました」)、それ以外はCLOSED_TEXT。詳細画面の不成立姿(ws-7)
と、お知らせの終了行は、**この同じ1つの関数を呼びます**。03 §7が注文した
「不成立は一文に統一」の担保の起点は、CLOSED_TEXTという1行の定数を全画面が
参照することでした。m3-g3fixで分岐が加わったいまは、関数がその役を引き受けて
います。文言そのものの置き場所はtexts.jsに集まったままで、直したくなったら
直す場所は1つです。

試験の書き方にも、この統一を保証する工夫があります。

```javascript
// tests/latch-notice.test.js:56-60
it("proposal×終了3種(expired/rejected/cancelled)はCLOSED_TEXTの1行のみ(一文統一)", () => {
  for (const status of ["expired", "rejected", "cancelled"]) {
    expect(notificationLines(item("proposal", notificationLatch(status)), NOW))
      .toEqual([CLOSED_TEXT]);
  }
});
```

期待値が文字列の直書き `"この提案は成立しませんでした"` ではなく、importした
定数そのものです。もし誰かがview.jsだけ文言を直してtexts.jsを直し忘れたら、
この試験は「定数と表示の不一致」を検出できます。**期待値を値でなく参照で
書く**——第19章でプッシュ文面の定数群を全文固定した試験と同じ考え方です。

この試験はm3-g3fixのあとも無変更で通ります。fixtureが `my_response` を
設定しなければ `closedText` はCLOSED_TEXTを選ぶからです。そして分岐そのものは、
別のdescribe(m3-g3fixで新設)が担っています。

```javascript
// tests/latch-notice.test.js:294-310(要約)
it("proposal×終了はmy_responseで分岐(no=辞退しました/defer=今回は見送りました/未設定・yes=統一文言)", () => {
  expect(notificationLines(
    item("proposal", notificationLatch("rejected", { my_response: "no" })), NOW))
    .toEqual([ANSWERED_TEXT.no]);        // 「辞退しました」
  expect(notificationLines(
    item("proposal", notificationLatch("expired", { my_response: "defer" })), NOW))
    .toEqual([ANSWERED_TEXT.defer]);     // 「今回は見送りました」
  // 未設定(undefined)・yesは統一文言のまま(詳細画面closedTextと同一)
});
```

この形になった背景には、ひとつ利いた話があります。m3-g3fixで終了行を
一律文言から分岐に変えるとき、画面側の変更は `return [CLOSED_TEXT]` を
`return [closedText(latch)]` に差し替える1行だけでした。詳細画面の側は
**無変更**です。材料(my_response)を足したbackendの仕事と、文言を組む画面の
仕事が独立していたから、接点の1行を替えるだけで済みました。第8章8.5で読んだ
「期限の計算をexpiry-options APIの1実装に集約する」は、計算の単一実装原則
でした。CLOSED_TEXTと`closedText`はその**文言版**です。同じ知識(不成立の
表示)を2箇所に書くと、片方だけ直る未来が必ず来る。1つの関数を参照させる
だけで、その未来を構造から消せます——そして実際、変更が来たときに構造は
1行でそれを受け止めました。

## 23.4 「開いた=見た」: ドットの語義と、冪等な204の上の既読

ベルの横の**未読ドット**(03 §2)は、小さな部品ですが規則を決めておく
必要があります。「いつ点いて、いつ消えるのか」です。

ws-8が決めた語義は「**開いていない新着がある**」です。この語義から、
実装の規則が3つ導かれます。

1. **起動時に1回だけ取得して点灯を判定する**(`main.js:105`)
2. **popoverを開くたびに最新を取り直す**(開いた時点の状態を見せる)
3. **開いた行を既読にする**(開いた=見た。行クリックは条件にしない)

3番目がいちばん考えどころでした。素直に思いつくのは「行をクリックしたら
その行を既読にする」ですが、それでは未読のまま閉じられたpopoverがドットを
点け続けます。開いたのに見ていない行がある、という状態が残るからです。
「開いた=見た」にすれば、popoverが開いた時点で表示された行は全部既読に
なり、ドットの語義と画面の状態が一致します。実装はこうです。

```javascript
// notice.js:46-58
const markRead = async () => {
  const unread = items.filter((item) => item.read_at == null);
  await Promise.allSettled(
    unread.map((item) =>
      client
        .call("POST", `/v1/notifications/${item.id}/read`)
        .then(() => {
          item.read_at = new Date().toISOString();
        }),
    ),
  );
  updateDot(); // 失敗した行は次回開いた時の未読対象のまま
};
```

未読の行それぞれにPOST readを並行で送り(`Promise.allSettled` は個別の
失敗を握って全部の完了を待つ)、終わったらドットを再判定します。失敗した
行はread_atが埋まらないまま残るので、次に開いたとき、もう1回送られるだけ
です。**再送が無害である保証**がここで効きます。第19章19.6で読んだとおり、
既読APIは既読済みでも204を返す冪等な窓口です。二重に送っても壊れない。
だから「失敗は握って次回に任せる」という荒っぽい規則が、安全に成立します。

popoverを開いたことの検知は、少しだけ技巧的です。

```javascript
// main.js:107-111
// popoverを開いたことの検知は追加リスナ(chromeのリスナが先に登録済みのため
// このリスナの実行時にはhiddenは開閉後 — 開いたときだけ取得・既読化)
$("#noticeButton").addEventListener("click", () => {
  if (!$("#noticePopover").hidden) notice.open().catch(() => {});
});
```

popoverの開閉そのものは `chrome.js`(ws-7・第8章の画面装飾の担当)のリスナが
担っていて、ws-8はこれを**無変更**のまま使います。自分は2つ目のclickリスナを
追加するだけ。リスナは登録した順に実行されるので、この追加リスナが動く時点
でhiddenはすでに開閉後の状態です。開いた直後(hidden=false)なら取得と既読化を
走らせ、閉じた直後なら何もしない。**既存の部品に触らず、隣に置く**——
第8章でapiClientを差し替えずmain.jsで結線だけ足したのと同じ姿です。

取得に失敗したときの挙え方も、既存の作法を引き継いでいます。popoverを開く
ときの `GET /v1/notifications` が失敗したら、**前回の表示をそのまま維持**し、
空状態も出しません(notice.js:79-81)。次に開いたときに再試行すればよい。
詳細画面の再取得失敗で前の内容を残すのと同型です。

## 23.5 設定画面: 許可は注入し、解除は確認を挟む

`#/settings` は新しい画面です。hashルーター(第8章・Lab 9)への追記は、
事実上これで全部でした。

```javascript
// router.js:8-13
export const parseHash = (hash) => {
  if (hash === "#/settings") return { name: "settings", id: null };
  const match = LATCH_HASH.exec(hash ?? "");
  if (match) return { name: "latch", id: match[1] };
  return { name: "home", id: null };
};
```

accountPopover(右上のアカウントメニュー)の「設定」ボタンを押すと
`location.hash = "#/settings"` が設定され(`main.js:141-143`)、 screensの
切替は既存の仕組みがそのまま動きます。未知のhashは今までどおりホームです。

画面の中身は2つのセクションです。通知とブロック管理(03 §2)。規定のない
要素(プロフィール編集・ログアウト・テーマ変更)は置きませんでした——
作らないものまで決めて作らない。第7章7.9の「何を導入しないかまで記録する」
作法の画面版です。

### 通知許可: 本当のブラウザ機能を、注入して扱う

通知セクションが扱うのは、D-18(03 §8)の**「許可を拒否しても使える」**という
約束の表示です。プッシュ通知の実送信はM4以降なので、ここで扱うのはブラウザ
の許可状態(granted・default・denied)の表示と取り直しで、サーバとの通信は
発生しません。

ブラウザの許可状態は `Notification.permission` で読める、と直接書きたく
なりますが、ws-8はそうしませんでした。

```javascript
// permission.js:24-26
export const createPermissionControl = ({ notificationApi, mount }) => {
  let permission = notificationApi?.permission; // 初期スナップショット
```

`notificationApi` という引数で**外から渡す**のです。main.jsが
`typeof Notification !== "undefined" ? Notification : undefined` を渡します。
理由は第8章と同じで、試験環境にあります。unit試験のhappy-domには
Notificationがありません。ファイルの先頭で `Notification.permission` を
参照した瞬間、試験はエラーで死にます。APIを引数にしてしまえば、試験は
`{ permission: "default", requestPermission: async () => "granted" }` のような
**偽の部品**を渡せる——第5章のStubLLM、第8章の偽clientと同じ発想です。

状態と文言の対応は、純関数 `permissionText`(permission.js:15-22)が4値の
写像として持ちます。

| permission | 表示 | 操作 |
|---|---|---|
| granted | 通知は許可されています | なし |
| default | 通知は許可されていません | [通知の許可を求める] |
| denied | ブラウザの設定でブロックされています。ブラウザの設定から変更できます | なし |
| API不在 | この環境では通知を利用できません | なし |

deniedに操作がないのは、ブラウザの仕様です。一度拒否(denied)されると
`requestPermission()` はダイアログを出さずにdeniedを返すだけで、変更は
ブラウザの設定画面からしかできません。案内文言だけ出します。どの状態でも
「許可しなくても、アプリ内のお知らせで確認できます。」を添えるのは、D-18の
フォールバック保証——拒否してもお知らせ一覧で通知は読める——の表示です。

### ブロック管理: 取り消しにくい操作に、確認を1つ挟む

ブロック管理セクションは `GET /v1/users/me/blocks` の一覧(表示名+ブロック日)
と、解除ボタンです。解除には**確認モーダルを1つ挟みます**(「{表示名}さんの
ブロックを解除しますか?」)。

挟んだ理由は、回復のコストです。ブロックの登録導線は成立済み詳細にしか
ありません(23.6)。誤って解除してしまえば、やり直すにはそのLATCHの詳細画面
まで行かなければなりません。**取り消しにくい操作ほど、実行のまえに意思確認
を置く**——これは規定のないUIの判断として設計書に記録されました(設計§5-2④)。

解除の送信は、結果ごとに分岐を持ちます。

```javascript
// blocks.js:79-95
const submit = async () => {
  const target = pending;
  if (!target) return;
  try {
    await client.call("DELETE", `/v1/users/${target.blocked_id}/block`);
    items = items.filter((item) => item.blocked_id !== target.blocked_id);
    close();
    render(); // 行単位の除去(カーソル保持)
  } catch (err) {
    if (err?.status === 404) {
      close(); // 既に解除済み — 一覧を取り直して収束
      load().catch(() => {});
      return;
    }
    showError(err?.code === "RATE_LIMITED" ? RATE_LIMIT_TEXT : BLOCK_ERROR_TEXT);
  }
};
```

204なら行を消して終わり。注目は**404の扱い**です。第21章21.5で読んだとおり、
ブロック解除は冪等にしていません。既に消えた行へのDELETEは404 NOT_FOUNDを
返す設計でした(登録の201は冪等・解除の404は冪等でない、と性質で使い分け)。
この404を「通信エラーです」と表示したら、実態は「もう解除済み」なのにユーザー
は失敗と思ってしまいます。そこで通信エラー扱いにせず、**一覧を取り直して
画面を正しい状態へ収束**させます。回答系の409(第17章)を再取得で収束させた
のと同じ型です。

同じ204でも、23.4の既読POSTが「冪等だから気にせず再送できる」だったのと
対照的です。**同じステータスコードでも、窓口の性質次第で扱いが変わる**。
APIの応答の意味は、そのAPIの契約(設計)とセットで読まないと決まらない、
という良い例になっています。

## 23.6 ブロックの登録導線は、成立済み詳細にだけ置く

最後のピースは、これまで**入口が存在しなかった**導線です。ブロックのAPIは
ws-5で実装済みでしたが(第21章・Lab 8)、登録する画面がどれにもありません
でした。ブロックされた側の体験(D-23: 「このチャットは利用できません」)は
実装済みなのに、ブロックする側の操作ができない——ws-7がws-8への引継ぎ事項
として残していた問題です(設計§5-1。採用が承認されて実装されました)。

導線を置いた場所は**成立済み詳細**(matched/completed)だけです。通報
(第21章21.6・Lab 9 §10)と同じ並びに「このユーザーをブロックする」ボタンを
置き、確認モーダルを挟んで `POST /v1/users/{user_id}/block` を送ります。

提案段階(proposed)の詳細に置かなかった理由は、通報との違いにあります。
通報のreportee_idには省略の道がありました——latch_idだけ送ればサーバが
「自分以外の参加者」から相手を解決する(ws-7・第21章21.6)。ところがブロックの
POSTはURLのパスにuser_idを指定する形で、省略解決の契約がありません。提案段階
は参加者が非開示(第17章17.6)なので、画面が「誰を」ブロックするか指定できない
のです。だから導線は、参加者が見えている成立済み詳細にだけ置きます。

1対1なら相手は1人なので固定、グループなら参加者から自分以外を選ぶ
(blockFlow.js:61-71)。送信に成功したら、トースト「ブロックしました」を
出して詳細を再取得するだけです。表示を切り替えるコードは要りません。
D-23のcancelled化・チャットの読取専用化は、登録APIのトランザクションの中で
サーバがすでに適用しているから(第21章21.3)で、**再取得した応答のままに
描画すれば画面は自然に正しい状態になる**。第17章の回答成功後の再取得と同じ
作法です。

## 23.7 この章の再統合

- お知らせと設定の2画面は、**ws-8の時点ではbackendを1行も変えずに**作れた。
  第19章・第21章のAPIを消費する表示のコードだけである。材料(my_response)の
  追加と成立通知も、組み立て側の構造を変えずに届いた
- 行の文言は **type×latch.status の2軸の表**で確定する。通知は不変・
  LATCHは変わるので、表示は「今のstatus」との組合せで決める。終了行は
  my_response(自分の回答)で分岐する——no・deferは操作履歴の文言、
  それ以外は一律の一文(nearbyはタップ先を持たない)
- 不成立の一文は **CLOSED_TEXTの定数1つ**が文言の単一ソース。画面は
  どの一文かを選ぶ `closedText` を共有し、試験は期待値も定数で書く
- 成立通知(latch_matched)の行は、提案の行と**別の行**として並ぶ。
  提案の行が「今どう見えるか」を担い、成立通知の行は「成立したこと+チャット
  導線」を担う。条件サマリは提案の行と詳細画面の担当
- ドットの語義は「開いていない新着がある」。**開いた=見た**の規則と
  冪等な204が、失敗を握って次回に任せる実装を安全にする
- ブラウザの通知許可は**引数で注入**する。happy-domにNotificationが
  ない試験環境でも、偽の部品で4状態を確かめられる
- ブロックの解除は**確認モーダルを挟み**、404は通信エラーにせず再取得で
  収束する。同じ204でも、冪等な既読(気にせず再送)と冪等でない解除
  (404で収束)で扱いが分かれる
- 登録導線は成立済み詳細にだけ置く。提案段階は参加者非開示で相手を指定
  できず、再取得応答のまま描画すればD-23の表示収束は自動

プロトタイプ6画面(03 §2)がこの単位で揃いました。G3の完了条件です。
M3で実装した機能の読み物は、ここで一巡します。次のLab 10では、この章の
マトリクスを本物のAPI応答と本物のブラウザで確かめます——**通知5種の
fixtureをDBに作り、実応答を `notificationLines` に通し、popoverの開閉で
ドットが点いて消えるまで**を、自分の手で歩きます。

## 23.8 用語集(この章で登場した言葉)

| 用語 | 一言でいうと |
|---|---|
| マトリクス | 2軸(今回はtype×status)の交点ごとに値を決めた表。「何を表示するか」の漏れない書き方 |
| 単一ソース | 同じ知識(文言・計算)を1箇所だけに置き、全員がそこを参照する作法 |
| my_response | 応答のlatch要素に乗る「あなた自身の回答」。yes/no/defer・未回答はnull。相手の回答は乗らない |
| closedText | my_responseを見て、操作履歴の文言か統一文言かを1つ返す純関数(view.js)。詳細画面とお知らせ行で共有 |
| CLOSED_TEXT | 不成立を示す一文「この提案は成立しませんでした」の定数(texts.js) |
| 成立通知(latch_matched) | 提案が成立したとき参加者全員へ書かれる通知のtype。行は見出し+チャット導線+バッジ |
| 未読ドット | ベルの横の点。「開いていない新着がある」を意味する |
| preload | アプリ起動時に前もって取っておく1回の取得。お知らせではドット判定に使う |
| Promise.allSettled | 並行処理の個別失敗を握って、全部の完了を待つ書き方 |
| Notification.permission | ブラウザの通知許可状態(granted/default/denied) |
| 確認モーダル | 取り消しにくい操作の実行前に開く意思確認の小窓 |
| 404収束 | エラー表示ではなく再取得で画面を正しい状態へ戻すこと |

## 23.9 確認問題

1. お知らせ行の文言をtypeだけでなくlatch.statusとの2軸で決める理由を、
   「通知は不変・LATCHは変わる」という性質から説明してください
2. お知らせの終了行では、あなたがnoで断った提案は「辞退しました」になり、
   相手が先にnoで断った提案は「この提案は成立しませんでした」になります。
   行に並ぶ材料が my_response(あなた自身の回答)だけであることと、
   03 §7の理由開示禁止を踏まえて、このちがいの理由を説明してください
3. ws-8当時の設計は「終了行は一律の一文」でした。材料がなかったから、という
   理由とあわせて、材料(my_response)が揃ったm3-g3fixでこの判断が03 §7の
   本来の形へ解消した経緯を説明してください
4. `latch-notice.test.js` の期待値が文字列ではなくimportしたCLOSED_TEXTで
   書かれている意味を、「文言を直し忘れた未来」の2通り(片方だけ直す・
   両方直す)で説明してください
5. 成立通知の行と提案の行が、成立済み提案について並ぶとき、それぞれが担う
   役割の分担を、条件サマリとhidden_until_matchの関係から説明してください
6. 既読のPOSTを、行クリックではなくpopoverを開いたときに送る規則の利点と、
   この送り方が失敗を握れるようになった理由(冪等204)を説明してください
7. `permission.js` が `Notification.permission` を直接参照せず引数で受け取る
   理由を、happy-domと偽の部品(StubLLM・偽client)の関係で説明してください
8. ブロック解除の404を通信エラーとして表示しない判断と、同じ「2回目の送信」
   でも既読POST(冪等204)の扱いが違う理由を、それぞれの窓口の契約から
   説明してください
9. ブロックの登録導線を提案詳細(proposed)ではなく成立済み詳細に置いた理由を、
   通報のreportee_id省略との違いで説明してください
