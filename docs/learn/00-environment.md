## 1.2 LATCHというサービス: ユーザーには何が起こるか

LATCH(ラッチ)は、**「やりたいこと」を登録すると、条件の合う人どうしを結びつける**サービスです。
具体例で流れを見てみましょう。

あるユーザーが「今週末、天文館のあたりで飲みに行きたい」という思いをアプリに入力します。
この入力ひとまとまりを、このプロジェクトでは **Intent(インテント=意図)** と呼びます。
サーバーはこの自然文を受け取ると、AI(LLM)を使って「カテゴリ: 飲食」「場所: 天文館周辺」
「日時: 週末」「人数: 2人程度」のような構造化されたデータに変換します。変換結果はデータベースに保存されます。

保存されたIntentは、裏でマッチングの処理にかけられます。同じくらいの期間・場所・条件を持ち、
年齢などの前提を満たす他のユーザーのIntentと組み合わせ、AIの評価を経て、組み合わせの良さが
基準を超えたものだけが「提案(proposal)」として両者に届きます。ユーザーが提案に「参加する」と
答え、相手も参加すれば **LATCH(ラッチ=留め具)** が成立。以降は2人のチャットで詳細を決められます。

この一連の流れを実現するために、このリポジトリには次のようなものが入っています。

- **サーバーのプログラム**(Python言語で書かれた、リクエストを処理するコード)— `backend/`
- **動作の仕様書**(何を作るかの最終決定を記した文書群)— `docs/00〜12`
- **開発の記録**(何をどの順で作り、どんな判断をしたか)— `docs/plans/`
- **フロントエンドの本体**(ユーザーが触る画面。APIに接続する)— `frontend/`
- **フロントエンドの試作**(画面の見本。APIに接続しない・実装基準の参照物)— `prototype/`

## 1.3 土台の3語: クライアント・サーバー・HTTP

この教科書で一番よく出る3つの言葉を、最初に固定しておきます。

**クライアント**は「お願いする側」、**サーバー**は「受けたお願いを処理する側**です。
ブラウザやスマホアプリがクライアント、LATCHのプログラムがサーバーにあたります。
クライアントとサーバーは、**HTTP(エイチティーティーピー)** という世界共通の作法でやり取りします。
HTTPでの一回のやり取りは、「リクエスト(要求)」と「レスポンス(応答)」の対でできています。

実際のやり取りを見てみましょう。Lab 1でも使うこのコマンドは、サーバーに「調子どう?」と聞く
ヘルスチェックです。

```bash
curl http://127.0.0.1:8000/health
```

`curl` は「URLに向かってHTTPのリクエストを送る」コマンドです。この1行で起きていることは次のとおりです。

1. `127.0.0.1` は「自分自身のPC」という意味のアドレス、`8000` はポート番号(マンションの部屋番号のようなもの)です。自分のPCの8000番室で待っているサーバーに向かって…
2. `GET`(ゲット=取得して)という**メソッド**(動詞の指定)で、`/health` という**パス**(場所の指定)を要求します
3. サーバーは処理結果として、**ステータスコード**(結果の要約。200=成功、404=場所がない、401=身分を証明していない、など3桁の数字)と、**本文**(中身のデータ)を返します

成功すると、こんな本文が返ってきます。

```json
{"status":"ok","server_time":"2026-09-27T09:41:23.123456+00:00"}
```

この `{}` で囲まれた書式は **JSON(ジェイソン)** といい、プログラムどうしがデータをやり取りするときの
事実上の共通語です。Pythonの辞書(`dict`)とほぼ同じ形なので、コードを読むうえでは同じものと思って大丈夫です。

「**API(エーピーアイ)**」という言葉もここで定義します。APIとは、サーバーが外部に公開している
窓口の一覧のことです。「`GET /health` で健康状態が聞ける」「`POST /v1/auth/token` で認証トークンを
発行できる」のように、**メソッド+パス+送る内容+返ってくる内容**が決まっている窓口の集合がAPIです。
LATCHの窓口一覧は `docs/05-data-model-api.md` の第5節に全部載っています(いま全部読む必要はありません)。

## 1.4 コードを動かす容器: Docker と docker compose

ここで最初の大きな疑問に出会います。**サーバーは、データベースやRedisといった「お供」つきで動く。
それを開発者の全員のPCで同じように動かすには?**

十年前の開発現場では、新しく入った人が環境を整えるだけで数日かかるのが普通でした。
「私のPCでは動くのにあなたのPCでは動かない」という、いわゆる**「私の環境では動く」問題**です。
原因は様々です。データベースのバージョンが違う、必要な拡張が入っていない、設定ファイルの場所が違う……。

**Docker(ドッカー)** はこの問題への答えです。プログラムと、動かすのに必要な一切のもの
(OSの部品、ライブラリ、設定)をひとまとめにした **イメージ** を作り、そのイメージから
**コンテナ** という隔離された箱を起動します。イメージさえ同じなら、どこで起動しても同じ動きをします。
「冷凍食品を買って電子レンジで温める」と「鍋と材料から作る」の差に例えられます。味(動作)が一定で、
作る人(動かすマシン)の腕に依存しません。

LATCHではコンテナを5つ動かします。複数のコンテナを「どう組み合わせて起動するか」を1つのファイルに
書いたのが `compose.yaml` で、この定義に従って一括起動してくれる道具が **docker compose** です。

| サービス名 | 役割 | 一言でいうと |
|---|---|---|
| `db` | データベース(PostgreSQL+PostGIS) | 全データの長期記憶 |
| `redis` | Redis | 速く読み書きしたい小物の置き場 |
| `pubsub` | メッセージキュー(Pub/Subのエミュレータ) | 保存と裏方をつなぐ知らせの配達係(第9章) |
| `api` | FastAPIのアプリ | HTTPリクエストを受ける窓口 |
| `worker` | 裏方プロセス | 知らせを受けてマッチング処理を進める(第9章) |

## 1.5 言語とその管理: Python と uv

サーバーコードは **Python(パイソン)** という言語で書かれています。読みやすさを重視した設計の
言語で、この教科書で読むコードはすべてPythonです。プロジェクトでは バージョン3.13 を使うと
`backend/.python-version` に固定されています。

Pythonには「**ライブラリ**(他人が書いて公開してくれた、よく使う機能の詰め合わせ)」を導入して
使う文化があります。FastAPIもPostgreSQL接続も、すべてライブラリです。ここで困ることが起きます。
ライブラリは他のライブラリに依存していて、Aの新しい版はBの古い版と相性が悪い、といった
**依存の組み合わせ問題**です。放っておくとプロジェクトごとに違う組み合わせが必要になり、
PCの中がカオスになります(昔は実際にこういう地獄がありました)。

解決策は2段構えです。

1. **仮想環境(かそうかんきょう)**: プロジェクトごとに独立した「ライブラリ置き場」を作り、
   他のプロジェクトと干渉しないようにする仕組み。`backend/.venv/` がそれです
2. **ロックファイル**: 「このプロジェクトはライブラリのどの版のどの組み合わせで動くと確認済みか」を
   1つのファイルに固定する仕組み。`backend/uv.lock` がそれです。このファイルのおかげで、
   誰がいつ `make setup` を実行しても、まったく同じ環境が再現されます

この2つをよしなにやってくれるのが **uv(ユーブイ)** です。Pythonの世界には長年 `pip` と
`venv` という道具が標準でしたが、uvはその代替として近年広く使われるようになった、高速な後継です。
「何を入れるか」の宣言は `backend/pyproject.toml` に書きます。人間はここだけ編集し、
`uv.lock` はuvが自動で計算します(手で編集しません)。

コマンドはすべて `uv run` 経由で実行します。これが「仮想環境の中のPythonで実行する」の意味です。

## 1.6 HTTPとコードの橋渡し: FastAPI と uvicorn

素のPythonには「HTTPのリクエストを受け取る」機能がありません。ソケットを開いて電文を待ち、
HTTPの作法に従って解釈し……という土台の仕事をすべて自分で書くことになります。それは大変なので、
土台を請け負ってくれる **Webフレームワーク** を使うのが普通です。LATCHが使うのは
**FastAPI(ファストピーエーアイ)** です。

FastAPIが請け負ってくれる代表的な仕事は次のとおりです。

- 「`GET /health` が来たら、この関数を呼ぶ」という**結びつけの登録**(第2章で実際のコードを見ます)
- リクエストのJSONをPythonのデータに自動変換し、関数の返り値をJSONに自動変換する
- 関数が例外を投げたら、決められた書式のエラーレスポンスに変換する

FastAPIは「組み立て終わったアプリ」を1つの変数(`app`)として作ります。そして**その変数を
受け取って、実際にネットワークで待ち受ける**役割が **uvicorn(ユービコーン)** です。
ホールと厨房に例えると、FastAPIが厨房の設備とレシピ、uvicornが店構えと入口です。
`compose.yaml` の api サービスに書かれている起動コマンド
`uvicorn latch.main:app` は「`latch/main.py` というファイルの `app` という変数をサーブせよ」
という意味です。

## 1.7 データの置き場: PostgreSQL(PostGIS)と Redis

### PostgreSQL — 長期記憶担当

**PostgreSQL(ポストグレスキューエル、略してポスグレ)** は **データベース** の実装の1つで、
データをファイルではなく、検索・整合性に最適化された形で長期保存する専門のサーバーです。
データは **テーブル**(表)に **行**(レコード)単位で格納され、列ごとに型が決まっています。
Excelのシートに似ていますが、「この列は必須」「この列の値はこの表のあの行を指す」といった
**制約** を入れられる点が本質的に強力です。間違ったデータを入れようとすると、プログラムではなく
データベース自身が拒否してくれます。

LATCHのデータベースには13のテーブルがあります(`users`、`intents`、`latches`、`geofeatures` など)。
どんなテーブルがあるかは `docs/05-data-model-api.md` の第2節が定めの元になっています。

LATCHのPostgreSQLには2つの拡張が入っています。

- **PostGIS(ポストジス)**: 位置(緯度経度)を扱う専門機能を追加する拡張。「この2点は半径1km内か」
  「この点に最も近い地名はどこか」のような地理計算がSQLで書けるようになります
- **pgvector**: 「意味の近さ」を数値のベクトル(長さ768の数字の列)で表し、近い順に検索する機能を
  追加する拡張。マッチングで「内容が似たIntent」を探すのに使います(第10章・第11章)

**Alembic(アレンビック)** という道具もここで紹介します。テーブルの定義を変えたいとき、
本番のデータベースを手作業で変えるのは危険です。「バージョン001→002の変更内容」をコードとして
書いておき、順番に適用・記録してくれるのがAlembicで、この変更コードのことを **マイグレーション**
(移行)と呼びます。実際のファイルは `backend/alembic/versions/` にあります。

### Redis — 速い小物置き担当

**Redis(レディス)** は、データをメモリ上に置いて超高速に読み書きするサーバーです。
PostgreSQLが「金庫」なら、Redisは「手元の付箋」です。保存したデータは電源断で消えることを
前提に、とにかく速さが必要なものに使います。

LATCHでの当面の使い道は3つあります。1つは認証まわりの「**失効リスト**」です。ログアウトされた
アクセストークンを「もう使えない」リストとして記録しておくと、リストに載ったトークンでの
アクセスを即座に拒否できます。次は第7章で読む「**レート制限のカウンタ**」——
「このユーザーは今日何件作ったか」のような、すぐに書き換わる小さな数を数えるのに
Redisの `INCR` コマンドが使えます。3つ目は第21章の「**ブロック一覧のキャッシュ**」で、
DBにあるデータの写し(覚え)を置いて、読み込みのたびにDBを訪れないようにします。どれも
「残り有効期限が切れたら自動で消える」ような、Redisの **TTL**(生存時間)機能と相性の
良い例です(失効リストは第3章以降の認証の章で、カウンタは第7章で、キャッシュは
第21章で詳しく)。

## 1.8 品質の守り: pytest

プログラムの部品が期待どおり動くことを、自動で確かめる仕組みが **テスト** です。
Pythonの世界で最も使われているテスト実行ツールが **pytest(パイテスト)** です。

テストは「入力を与えて、結果がこうなるはず」という Pythonの関数として書かれます。
期待どおりなら **緑(合格)**、違えば **赤(不合格)** です。LATCHのテストの規模と速度はこれです。

- unit テスト(部品単体の試験): backend **1215件を約7〜8秒**(`make test`)。フロントエンドも
  **217件を約1秒**(`frontend/` で `npm test`)。どちらも外部環境を一切使いません
- integration テスト(実DB・実Redis・実Pub/Sub・実サーバーでの組み合わせ試験): 254件を含め計
  **1469件**(2026-10-02のM3 ws-8マージ検証で全件グリーンを確認。ci環境の起動を
  待つ分、実行には数分かかります)

数秒で全部回せる意味は小さくありません。コードを1行変えるたびに確かめられるので、
「壊して試す」学習法(Lab 2)が気軽にできます。この速さ自体が、このプロジェクトの
設計(次章のClock)の成果物です。フロントエンドも同じ構造で、画面の部品から
外部環境(ブラウザ・通信)を切り離して置いてあるため、217件が1秒ほどで
回ります(第8章8.7)。

**TDD(ティーディーディー、テスト駆動開発)** という作り方も、この教科書で何度も出てきます。
先にテスト(期待)を書いて赤を確認し、それから実装を書いて緑にする、という順番です。
LATCHの実装は実際にこの順番で行われました(`docs/plans/` の計画書に「テスト→実装の順」と
繰り返し書かれています)。なぜこの順番にこだわるのかは、第3章でテストと一緒に説明します。

## 1.9 変化の記録: git

**git(ギット)** は、ファイルの変化を時系列で記録する道具です。ある時点の状態に名前
(**コミット**)を付けて保存すると、後からいつでもその時点に戻れたり、変化の内容と経緯を見られたりします。
**GitHub(ギットハブ)** は、その記録をネット上に置いて保管・共有するサービスです。
このプロジェクトの記録は `github.com/hiromu1018ks/latch` にあります。

初心者向けに、このリポジトリ特有の性質をひとつ伝えておきます。**コミット履歴が非常に読みやすい**です。
LATCHは「設計→計画→実装(テスト→実装の順)→検証→マージ」という手順で、小さな単位に分けて作られました。
そのため `git log --oneline` を見ると、何をどの順で足したかが1行ずつ追えます。
さらに `git log -p ファイル名` とすると、そのファイルがどう変わったかの差分つきで読めます。
教科書としての価値が高い資産なので、第2章から積極的に使います。

## 1.11 コマンド集(参照部)

すべてリポジトリのルート(`latch/`)で実行します。

| コマンド | 何が起きるか |
|---|---|
| `make setup` | `backend/.venv/` に依存を導入。初回と、`pyproject.toml` が変わった後に実行 |
| `make up` | `compose.yaml` に従い5サービスを起動。すでに起動していれば何もしない(冪等) |
| `make ps` | 5サービスの状態一覧。`(healthy)` は健康診断合格の印 |
| `make logs` | 5サービスのログを流し見る。Ctrl+Cで停止 |

再実行します。もう1つ、`make g1-gate` は実APIを呼ぶので費用が発生します(全71呼び出しで

## 1.12 このプロジェクトの作られ方: docs/plans に残る記録

LATCHの実装は、人間が仕様を決め、AIエージェントが設計・計画・実装を単位ごとに担い、
人間(とスーパーバイザー)が検証してマージする、という分業で進められました。そのすべてが
`docs/plans/` に記録されています。

- `STATUS.md` — 進行状態の現在位置。何が済んでいて、次は何か
- `M0/・M1/*-design.md` — 設計メモ。**「なぜそう決めたか」**(選択肢と根拠)が書いてある
- `M0/・M1/*-plan.md` — 実装計画。作業をテストつきの小ステップに分解したもの
- `M0/・M1/*-report.md` — 実装報告。何を検証したかの証拠

コードを読んでいて「なぜこんな書き方を?」と思ったら、まず設計メモを探してください。
原則、すべての判断に根拠の节が付いています。この教科書も、コードと設計メモの橋渡しをします。
