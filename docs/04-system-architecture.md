## 1. 本書の目的と位置づけ

MVPの検証対象(01第4節の5仮説)を支えるのに十分で、かつ運用コンポーネント数が最小の構成を目指す。特になすべきは、01第19節の構成図にある2系統の非同期性 — Intent Parserの確認フロー(03第3節)とMatching Workerのイベント駆動処理(01第16節)— を、具体の技術で固定することである。

## 2. 全体アーキテクチャ

01第19節の構成をMVPの現実的な構成へ具体化する。01と同じく上から下が処理の流れである。

```text
        ┌────────────────────┐
        │  Mobile / Web App  │
        └─────────┬──────────┘
                  │ HTTPS + JWT(第4節D-21)
        ┌─────────▼──────────┐
        │     API Layer      │ 認証(IdPトークン検証)/ Intent CRUD /
        └──┬──────┬──────────┘ LATCH回答 / 通知既読
           │      │
┌──────────▼─┐  ┌─▼────────────┐
│ PostgreSQL │  │ Intent Parser │─→ LLM Gateway ─→ LLM API
│ (+pgvector, │  └──────────────┘       │
│  +PostGIS)  │                  送信記録(01第21節)
└──────┬──────┘
       │ Event発行(version入りpayload)
┌──────▼───────────┐
│  Message Queue   │← 障害時はDLQへ隔離(01第16節)
└──────┬───────────┘
       │
┌──────▼───────────┐   ┌───────────────┐
│ Matching Worker  │←─►│ Redis         │
│ (水平スケール)    │   │ キャッシュ /   │
└──────┬───────────┘   │ Jevカウンタ /  │
       │               │ 失効リスト     │
┌──────▼─────────────────────────────┐
│ Hard Filter → Vector Search →       │
│ Cheap Judge → Jev → LATCH Engine    │
└──────┬─────────────────────────────┘
       │
┌──────▼──────┐              ┌──────────┐
│ Notification │              │ Analytics │
│ FCM(APNs含む)│              │ (集計/記録)│
│ +アプリ内通知 │              └──────────┘
└─────────────┘
```

構成の要点は次のとおりである。

- **クライアントはWebから着手する(v0.4)。** 実装基準は`prototype/`(Vite + vanilla JSの静的SPA。デザインシステム・UI文言は03 v0.4第10節に固定)であり、Webクライアント→モバイルアプリの順に拡大する。通知基盤のFCM統一(iOS/Android/Web Push)とD-21のSign in with Apple(iOSのサードパーティログイン要求)はモバイル段階を含めた選定であり、Web段階ではWeb Push経路のみが作動する。この現状は本書の選定(第3節)を変更しない
- **DBを1本化する。** Vector DBをIntent DBと同じPostgreSQL上のpgvectorとし、Geo判定はPostGISで行う。運用対象が減り、01第20節のバックアップ要件(復旧でのVector再構築)も一元化できる
- **LLM呼び出しはGatewayを通す。** Intent Parser・Embedding・Jevの外部送信は単一のLLM Gateway経由に集約し、送信先と送信データ種別の記録(01第21節)と、プロバイダ差し替えの抽象化をここで行う
- **通知は2経路。** プッシュはFCM(APNsはFCM経由で配信)、アプリ内通知はDB保存+ホーム/お知らせ(topbar popover。UI語彙は03 v0.4第10節)表示。この2経路の併用が03 D-18の決定を実現する構成である。プッシュ本文は汎用文に限定する(08 v0.3第2.6節・FR-21の表示規制。条件サマリはsummary_onlyの提案に限り、アプリ内通知と提案画面にのみ表示する。02 v0.3 D-03)
- **計測は最初から3群。** パイプライン(Event Queue lag・Candidate数・Hard Filter通過率・Vector Retrieval件数)、Jev(実行回数・latency・cost)、提案と行動(LATCH Score分布・通知数・YES率)の3群(01第20節)をCloud Monitoringへ集める。02第4節#5の検証とD-16のalertのデータソースである
- **アクセス系基本計測を3群に加える。** DAU・再来訪の素材は、クライアントのセッション開始(アプリ起動・フォアグラウンド復帰)をAPI Layerが受けて計測基盤へ送るセッション開始イベントで集める(09第2.2節の分母)。エンドポイントはPOST /v1/sessions(05 v0.3)。イベントはuser_idと時刻のみを運び、Intentの文言を含まない(08第2.4節)

**ジオコーディングの変換経路(08 D-11の技術選定)。** 正転(地名→座標)はParser通過後・Intent保存前の処理で、location.name(07第2節)を位置参照情報の町字・街区代表点とOSMの名称付きPOI(ランドマーク)へ照合し、geo_centerを定める。逆転(座標→地域名)はLayer 5の提案生成(06)で、geo_centerを約1kmグリッド(投影座標系へ落として丸め)の代表点に最も近い地物の地名(例: 鹿児島市天文館)を地域名としてproposalへ格納する。いずれもPostGIS上の地物テーブルに対するSQLで実装し、位置情報を外部サービスへ送る経路を持たない(01レビューF-18)。地物データはMVP対象エリア(02 D-22)分を初期取り込みし、展開地域の拡大時に追加する

## 4. 未決事項の決定

### D-14 LLMプロバイダ選定基準(技術選定基準)

- 決定内容: 次の6基準で選定する。この順にフィルタとして適用する
  1. 学習利用の禁止 — 入力・出力をモデル学習に利用しないことを契約上明示できること(Zero Data Retention相当)。これを満たさないプロバイダは他の基準に関係なく除外する
  2. データの取り扱い — 送信データの保持期間・データ所在地を制御できること。送信記録(01第21節)と合わせ、どこに何を送ったかを追跡可能であること
  3. 機能 — JSON構造化出力の安定性(Parser・Jev)、温度等の生成制御、日本語の埋め込み品質(Embedding)。Jevはv0.5でSystem Oneモデルを区分に加えた(下記の採用記録)
  4. 性能 — 初期LATCH判定p95 10秒(01第20節)の配分を満たす応答速度と、timeout・retryを含む安定性
  5. コスト — トークン単価とD-16の回数上限から月次コストが予測できること
  6. 可用性 — SLAの明示。複数プロバイダをGateway経由で併存させ、障害時の縮退(D-15、06)に備えられること
- **v0.5追記(採用記録・オーナー裁定C案)**: Layer 4(Jev系統)の第一候補は**System Oneモデル「TypeSafe Jev」(jev-1.13.0)**、フォールバックは**生成LLM(Anthropic Claude API・v0.5時点でSonnet 5→v0.6からHaiku 4.5)**と確定する。v0.6変更の根拠はコスト方針(マネタイズ前の高単価モデル排除・T1 v0.3)とG2日本語評価実測(docs/reviews/g2-threshold-fallback-revision.md)。採用の根拠は次のとおりである。
  - 基準3(機能)の読み替え: Layer 4は入力が正規化テキスト・出力が確率と構造化値であり、テキスト生成能力を要求しない。テキスト生成を行わず確率を返すSystem Oneモデルはこの用途に合致し、Jevの公称スペック(70〜500ms・出力スキーマ保証・入力$0.042/MTok出力無料・較正済み確率)がD-16の回数上限と初期LATCH判定p95 10秒の層別予算(Jev ≤5秒)を余裕をもって満たす。詳細はT1 v0.2(選定資料)が担う
  - 基準1・2(学習禁止・データ取り扱い): TypeSafeは「Jev is not trained on customer requests or responses」を公式に明記し、MCAにも学習データセットへの非包含条項がある。契約面の評価と受容(米国所在・SLAなし)は08 v0.5 D-14に記録する
  - 基準6(可用性): TypeSafeには公開SLAがない。よってフォールバックLLM(Anthropic)を常時併存させ、429・529・timeout時に切替え(07 v0.5第4節)、継続障害はcircuit breakerで吸収する(06 D-15)。可用性はLLMフォールバック構成で担保する構成とする
  - Parser・Embeddingのプロバイダ推奨はT1 v0.2(Anthropic Haiku 4.5・Gemini gemini-embedding-001)であり、08 D-14の契約条件の確認後に確定する
- 根拠: LATCHは「まだ誰にも言っていない意思」を外部送信する(01第21節)。技術特性より先にデータ取り扱いで足切りを行い、残った候補で機能・性能・コストを比較するのが、潜在意思を扱う前提の順序として正しい。契約の締結・告知・同意の設計は08が担当する
- 01への影響: 第21節に選定基準を追記。プロバイダの最終確定は08の契約条件確認後(v0.5でJev系統のみ先に確定)

### D-16 Jev実行コスト(回数)上限の確定値

- 決定内容: 回数ベースで確定する。日次上限 30,000回/日(80%の24,000回でalert)、月次上限 600,000回/月(80%でalert)。上限到達時はJev実行をスキップし、対象候補は「Jev未判定」として記録する。スキップした候補を提案するか保留するかの縮退運転は06がD-15として定める。v0.3追記は次の3点である
  - **月次上限のリセット時点は暦月初のJST 0時**とする(運用開始日起算ではない)。月次到達時の日次カウンタは別管理であり、日次に余裕があっても月次で停止する。月次到達時は運用者への通知をalertと同経路で行い、復帰予定(暦月初)を明示する(FR-50)
  - **実際のAPI呼び出しをすべて「1実行回数」に計上する(v0.5読み替え)。** 旧規定「Jev出力検証失敗の再試行1回(07第4節)の計上」(FR-50)は、07 v0.5で再試行規定が廃止されたことに伴い、**フォールバックLLMへの切替呼び出しも同一の「1実行回数」に計上する**と読み替える。計上しないと、生成LLMの高単価で実際のAPI呼び出しコストが回数上限を超過し得るためである。回数上限そのものは回数ベースで不変であり、プロバイダの変更に影響されない
  - **コスト前提の注記(v0.5)**: 第一候補のTypeSafe Jevは入力$0.042/MTok・出力無料の低単価であり、通常時の月次コストはごく小さい(T1 v0.2の試算)。フォールバックLLMは生成LLMの高単価であるため、切替の長期化は同一回数でのコスト増に直結する。よって80% alertの源流レポートに、第一候補とフォールバックの実行回数の内訳を含める(06 v0.5第5節)
  - **80% alertにはEvent源流上位ユーザーのレポートを添付する。** 内容は、当該期間のIntent別・ユーザー別のJev消費上位リスト(06 v0.5第5節のカウンタ、1Intent日次40回・1ユーザー日次120回の予算と頻度制限30分を適用済みの消費)と、第一候補・フォールバック別の実行回数内訳(v0.5)である。悪用ユーザーが源流でEventを大量発生させた場合に、回数上限の80%到達とともに源流を特定し、運用対応(レート制限の確認・個別対応)に回せるようにするためである(FR-03)
- 根拠: クローズドベータ(02 D-22、DAU数百〜数千)の想定ではMatch Eventが1日数千〜1万、ファネル(01第12節)を経たJev到達数は1イベントあたり平均1〜2回であり、正常時のJev実行は概ね1万回/日以内に収まる。上限はその約3倍の30,000回/日とし、正常運用が上限に触れないマージンを確保したうえで、異常時(Event洪水)にのみブレーキとして作動させる。月次600,000回は日次上限とベータ期間の活動の波(実効20日相当)から導く。回数ベースはK上限(01第11節)と同じ次元であり、プロバイダ単価の変更に影響されない。02レビューの推奨(回数ベース)を採用した。月次リセットを暦月初に固定したのは、日次(JST 0時)と同じく運用者・開発者が共通に読める時点とするためであり、ソースの量産や請求サイクルの基準とも一致する。再試行の計上は、上限が「コストの保証」である以上、実際のAPI呼び出しをすべて数えるのが正しいからである
- 01への影響: 第20節に上限値を追記。縮退運転の内容は06

### D-21 認証方式の確定

- 決定内容: 次のとおり確定する
  - Idプロバイダ: GoogleログインとSign in with Appleの2種。iOSアプリでサードパーティログインを提供する場合のAppleの要求に対応するためである
  - 認証フロー: アプリがIdP認証を行い、得られたIdPトークンをAPIへ提示する。APIはIdPの公開鍵(JWKS)でトークンを検証し、IdP種別+sub識別子でUserと紐付ける。紐付くUserがない場合は新規登録とする
  - セッショントークン: APIが独自のJWT(有効期限1時間)を発行する。リフレッシュトークンは30日・回転式とする
  - セッション管理: JWTはステートレスで検証し、ブロック・退会の即時反映はRedisの失効リストで行う。アカウント連結(複数IdPを同一Userへ束ねる)機能はMVPに含めない
- 根拠: 02の方向性(自前パスワードを持たない)を確定値に落とした。IdPトークンをAPIに渡してバックエンド検証する構成は、クライアント側での検証不完全を排し、なりすまし対策をMVPに含めない(02 D-12)前提での最小の本人性担保になる
- 01への影響: 第22節に認証方式の確定値を追記、第7節のアカウント機能の内容を確定

## 5. コスト保護機構

Jev実行の直前に制御を挟む。経路は次のとおり。

```text
Jev実行要求(Matching Worker)
  → Redisの日次/月次カウンタをINCR
  → 80%到達: alert発報(運用者へ通知。Candidate数・Event数に加え、
     Event源流上位ユーザーのJev消費レポート(第一候補とフォールバック
     LLM別の実行回数内訳を含む、v0.5)を添付、D-16)
  → 上限到達: 実行をスキップ、候補を「Jev未判定」として記録
  → 日次カウンタはJST 0時のリセットジョブで、月次カウンタは暦月初の
     JST 0時の同一ジョブでリセットする(FR-50)
```

**リセットの実装手段(FR-41)。** 日次・月次カウンタのリセットは、スケジューラで起動するリセットジョブ(0時JSTのキック。月次は月初0時も判定)で行う。TTL方式はUTC基準となりJST 0時と9時間ずれるため用いない。ジョブはClockインターフェースのJST日付境界を参照し、テスト環境ではClock操作で0時・月初を再現できる(10 v0.2第1節)。ジョブの失敗時は、最初のJev実行要求でカウンタの日付キーを検査し、前日以前のキーを検知した場合にリセットを実行する(自己修復。ジョブの単一障害点を補う)。

**カウンタはJev Workerではなく実行要求側(Matching Worker)で増やす。** 並行実行でも超過幅を1要求分に抑えられるためだ。alertの宛先とエスカレーションは運用設計に委ねる。**縮退運転の内容** — スキップした候補を保留するか、Cheap Judge以下のスコアで提案するか — は06マッチングパイプライン設計書がD-15として定める。本書は検知と制御の経路のみを確定する。また日次・月次とは別に、ユーザーあたりのIntent作成数・更新頻度の上限(02 D-12で実装を決定)をAPI Layerで強制し、Eventの大量発生自体を源流で抑える。源流を通過した後のJev消費の抑制は、06 v0.3第5節のJev予算(1Intent日次40回・1ユーザー日次120回)と頻度制限(30分)が担い、レート制限・予算・回数上限の三層で保護する。

**Clockインターフェースの適用範囲(FR-41)。** 10 v0.2第1節の時刻方針に合わせ、システム内のすべての時刻参照をClockインターフェース経由とする。適用範囲は次のとおりである — (1)APIの期限判定(response_deadline・expires_atとの比較、06 v0.3第6節。DBのclock_timestamp()は使わない)、(2)Intent期限バッチ・LATCH期限切れバッチ(expiry_sweeper、60秒周期)、(3)30分Bucket再評価のBucket境界、(4)debounceの10秒窓、(5)JST 0時のリセットジョブとRedisカウンタのJST日付キー、(6)作成・更新の時刻検証(過去不可・上限7日、05 v0.3)。テスト環境ではこの範囲のすべてがClock操作で再現できる。

## 6. デプロイ構成とスケーリング方針

- **基盤。** 単一クラウドのマネージドコンテナ基盤にAPI Layer・Matching Worker・Notificationを載せる。PostgreSQL・Redis・Message Queueはすべてマネージドサービスを用い、MVPで自前運用するステートフルコンポーネントをゼロにする
- **可用性。** マルチAZ配置。API Layerは常時2インスタンス以上、ヘルスチェックと自動復旧で01第20節のAPI成功率99.5%(計画停止除く)に対応する
- **スケーリング。** Matching Workerはキュー滞留に応じて0〜Nインスタンスへ水平スケールする(01第20節)。JevはWorker同時実行数に上限を設け、LLM APIのレート制限とD-16の回数上限の双方に合わせる
- **MVP規模の想定。** 02 D-22のクローズドベータ(単一エリア)で、DAU数百〜数千、Active Intent 1万件前後、Match Event 1日数千〜1万を想定する。この規模ではpgvectorとマネージドPostgreSQLで十分であり、専用Vector DBやキューの再選定はIntentプールが10万規模に達した段階で見直す
